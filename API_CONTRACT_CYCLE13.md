> места ред. 1. Правки точечные; разделы про галерею и логотип не менялись.
>
> 1. **§234, §235 — правило подтверждения.** Подтверждение больше **не** требует совпадения присланной
>    строки с написанием карты (сравнивать было бы не с чем: хранить чужую строку стандартная лицензия

> 3. **§232 — `addressPoint`.** Уточнено, что `StoreResults = true` допустим только при расширенной
>    («с сохранением результатов») лицензии Яндекса.
> 4. **§233, §234 — `attribution`.** Это подпись правообладателя **к результатам геокодера**; к
>    ссылкам-переходам (§239) атрибуция не требуется вовсе.
> 5. **§239 — ссылки на карты.** Доступные имена приведены к формулировкам юриста: «Открыть в Яндекс
>    Картах» / «Открыть в 2ГИС»; добавлены пять обязательных условий (без встраивания и скриншотов,
>    `target="_blank" rel="noopener noreferrer"`, без логотипов, без слов «интеграция/работает
>    на/партнёр», в URL только город и адрес; из ответа карты ничего не парсится и не сохраняется).
> 6. **§242 (новый) — `POST /api/companies/address/notice`.** Фиксация подтверждения предупреждения о
>    публичности адреса в `ConsentRecord`. В ред. 1 этого эндпоинта не было.
> 7. **§238 — лимиты.** Политика `address-verify` теперь висит на трёх маршрутах.

**Главное в одной фразе: серверная часть есть только у третьей и четвёртой задач цикла.** Карусель
галереи и порядок наложения логотипа — чистый фронтенд: данные уже приходят в `company.photos`
(`API_CONTRACT_CYCLE10.md` §129), новых запросов, эндпоинтов и полей они не требуют (§241). Ссылки в
Яндекс.Карты и 2ГИС строятся в браузере из `address` + `cityName`, которые уже есть в `CompanyDto`, —
публичная страница компании **не получает ни одного нового запроса**.

**Ломающих изменений в цикле нет.** Всё новое — добавочное; ни одно поле не удалено и не переименовано.

## §230. Конвенции (действуют без изменений, повторены, чтобы не искать)

- `camelCase` в JSON; перечисления — строками; `DateTime` — ISO-8601 UTC.
- Тела ошибок **400/402/409/410/429/503** — **голая строка** (`text/plain`), **401/403** — **пустое**
  тело, **404** — пустое тело там, где существование объекта не подтверждается. `ProblemDetails` не
  используется (кроме автовалидации `[ApiController]`).
- Новые поля в ответах — **добавочные**. Фронт обязан корректно работать при их отсутствии (сервер
  старой версии = «проверка недоступна, адрес не подтверждён»), тем же приёмом, каким `photos: null`
  читается как пустая галерея.
- `null` у вычисляемого поля означает «сервер этого не считал для данного вызывающего», а не «нет
  значения» (конвенция `historyEventCount`/`photos` цикла 10).
- 409 и 503 голой строкой у §242 — не новая конвенция, а буква в букву поведение
  `ClientConsentsController` цикла 5 на тех же ситуациях («текст обновился», «правовые тексты
  недоступны»).

## §232. `CompanyDto` — два добавочных поля

| Поле | Тип | Где заполняется | Смысл |
|---|---|---|---|
| `addressVerification` | `CompanyAddressVerificationDto \| null` | только там, где вызывающий **управляет** компанией | состояние проверки адреса. `null` = «не вычислялось для этого вызывающего» (аноним, клиент) |
| `addressPoint` | `{ latitude, longitude } \| null` | только `GET /api/companies/{slug}` | точка для метки на карте. `null`, если координат нет или их **нельзя хранить по лицензии** |

`CompanyAddressVerificationDto`:

| Поле | Тип | Смысл |
|---|---|---|
| `available` | `boolean` | проверка адреса доступна: рубильник включён **и** вызывающий управляет компанией. `false` → интерфейс **не рисует** кнопку «Проверить адрес» вовсе |
| `status` | `"Verified" \| "Unverified"` | вычисляется сервером: `Verified`, только если текущий текст адреса (после нормализации) совпадает с тем **собственным текстом владельца**, который подтверждали |
| `verifiedAt` | `string \| null` (date-time) | когда подтвердили; `null` при `Unverified` |
| `precision` | `"House" \| "Street" \| "Locality" \| "Other" \| null` | с какой точностью карта нашла адрес в момент подтверждения; `null` при `Unverified` |

**Клиенту статус не показывается** (решение продукта): на анонимной публичной странице
`addressVerification` равно `null`, поэтому показать его невозможно даже по ошибке. `addressPoint` при
этом публичен — точная метка это польза клиенту, а не ярлык «непроверенный салон».

**Где `addressPoint` не `null`:** одновременно должны выполняться три условия — включено хранение
результатов геокодирования (`AddressVerification:StoreResults`, что **допустимо только при
расширенной, «с сохранением результатов», лицензии Яндекса**), адрес подтверждён, точность `House`. В
штатном состоянии прода после этого цикла поле **всегда `null`**, и это нормально: ссылки на карты
тогда ведут на поиск по тексту (§239).

## §233. `POST /api/companies/address/lookup` — НОВЫЙ

Поиск вариантов адреса по картографическому справочнику. **Ничего не сохраняет.** Один эндпоинт
обслуживает и создание компании (её ещё нет), и настройки существующей.

Доступ: `[Authorize]`. Если передан `companyId` — вызывающий обязан управлять этой компанией
(владелец или `SuperAdmin`), иначе **404 с пустым телом** (существование чужой компании не
подтверждается). Лимит запросов — политика **`address-verify`** (30/час на пользователя).

Запрос:

```json
{ "address": "Ленина 5", "cityId": 22, "companyId": "3f7c…" }
```

| Поле | Тип | Обязательно | Правила |
|---|---|---|---|
| `address` | `string` | да | 1…300 символов после обрезки пробелов. Пусто → **400** «Укажите адрес» |
| `cityId` | `int \| null` | нет | подсказка города. Несуществующий или неактивный → **400** «Город не найден». Не передан и передан `companyId` → берётся город компании. Нет ни того, ни другого → поиск без города, предупреждение `CityMismatch` в этом случае не выдаётся |
| `companyId` | `uuid \| null` | нет | для какой компании проверяем (нужно для города и для прав) |

Ответ **200** `AddressLookupResultDto`:

```json
{
  "outcome": "Ok",
  "queriedAddress": "Барнаул, Ленина 5",
  "candidates": [
    {
      "formattedAddress": "Россия, Алтайский край, Барнаул, проспект Ленина, 5",
      "precision": "House",
      "cityName": "Барнаул",
      "point": null,
      "warnings": []
    }
  ],
  "warnings": [],
  "attribution": "© Яндекс"
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `outcome` | `"Ok" \| "Empty" \| "Unavailable"` | что произошло. `Ok` — варианты есть; `Empty` — карта ответила, но ничего не нашла; `Unavailable` — таймаут/ошибка/нечитаемый ответ внешнего сервиса |
| `queriedAddress` | `string` | что именно сервер отправил в карту («город, адрес») — чтобы владелец видел, по чему искали. Это **наш** текст |
| `candidates` | массив, **0…5** | найденные варианты в порядке убывания релевантности, как их вернула карта |
| `candidates[].formattedAddress` | `string` | полное написание, в котором адрес знает карта. **Справочная подсказка на экране**, см. рамку ниже |
| `candidates[].precision` | `"House" \| "Street" \| "Locality" \| "Other"` | точность найденного |
| `candidates[].cityName` | `string \| null` | населённый пункт из ответа карты |
| `candidates[].point` | `{ latitude, longitude } \| null` | координаты. **`null`, если хранить результаты геокодирования не разрешено** (`StoreResults: false`) — это штатное состояние |
| `candidates[].warnings` | массив предупреждений | что не так именно с этим вариантом (точность, другой город) |
| `warnings` | массив предупреждений | что не так с запросом в целом (`NotFound`, `Unavailable`) |
| `attribution` | `string` | подпись правообладателя **к результатам геокодера**; показывается под списком вариантов, пока они на экране, **как прислал сервер**. К ссылкам-переходам (§239) отношения не имеет — там атрибуция не требуется |

> ⚠️ **Что можно и чего нельзя делать с `candidates` (ред. 2, `LEGAL_REVIEW.md` §16.2/§16.5).**
> Под стандартной лицензией Яндекса **результатом** являются и координаты, и **нормализованная строка
> адреса**; хранить результат она не разрешает.
> - **Сервер** не сохраняет из ответа карты **ничего**: ни в `Companies`, ни в любую другую таблицу, ни
>   в файл, ни в лог. Единственное исключение — кеш в памяти процесса с TTL ≤ 30 суток (потолок
>   лицензионный, проверяется на старте).
> - **Клиенту** отдавать варианты можно: это показ результата владельцу в момент проверки.
> - **Подставить выбранный вариант в поле ввода — действие клиента и оно законно**: поле принадлежит
>   человеку, и после подстановки текст в нём — его текст. Именно эту строку он затем отправит в §234,
>   и именно она будет сохранена как **его** адрес.
> - **Чего делать нельзя:** сервер не имеет права сам переписать `Address` строкой из ответа карты, не
>   имеет права «нормализовать» адрес по ответу карты и не имеет права сохранить `formattedAddress` в
>   отдельную колонку «как у нас теперь правильно». Разница между «подставить в поле» и «сохранить как
>   нашу строку» — не стилистическая: второе требует расширенной лицензии.

Коды ответов:

| Код | Когда | Тело |
|---|---|---|
| 200 | всегда, когда запрос корректен и вызывающему это положено — **включая** «не нашли» и «карта недоступна» | `AddressLookupResultDto` |
| 400 | пустой/слишком длинный адрес, неизвестный город | голая строка |
| 401 | нет токена | пусто |
| **404** | **рубильник проверки выключен** (`AddressVerification:Provider = logging`) — функции нет; либо `companyId` чужой/не существует | пусто |
| 429 | лимит `address-verify` | голая строка |

⚠️ **404 при выключенном рубильнике — намеренно.** «Выключено» значит «функции нет», а не «есть и
ничего не делает». Интерфейс не должен доводить до этого ответа вовсе: признак —
`company.addressVerification.available`.

## §234. `PUT /api/companies/{id}/address` — НОВЫЙ

Сохранить адрес компании и, если попросили, подтвердить его по карте. **Единственный эндпоинт,
который пишет поля проверки.** Работает **всегда**, в том числе при выключенном рубильнике: сохранение
адреса не должно зависеть от внешнего сервиса.

Доступ: `[Authorize]` + право управлять компанией (владелец или `SuperAdmin`), иначе 403/404 по
существующему правилу `CanManageCompany`. Лимит — та же политика **`address-verify`**.

Запрос:

```json
{ "address": "Ленина 5", "verify": true }
```

| Поле | Тип | Обязательно | Правила |
|---|---|---|---|
| `address` | `string` | да | 0…300 символов. **Пустая строка = стереть адрес** (`Address` становится `null`, проверка очищается). Это отличается от `PUT /api/companies/{id}`, где `null` значит «не трогать» |
| `verify` | `boolean` | нет, по умолчанию `false` | `true` = «сервер, обратись к карте по этой строке и реши сам» |

**Что записывается всегда:** `Address` — **ровно та строка, которую прислал клиент, байт в байт**.
Сервер её не нормализует, не дополняет городом и не заменяет написанием карты (§233).

**Правило подтверждения (изменено в ред. 2):**

```
Verified  <=> verify: true && outcome == Ok && точность лучшего варианта == House
Иначе        Unverified + предупреждения
```

Совпадение присланной строки с написанием карты **не проверяется и не требуется**: не сохраняя чужую
строку, сравнивать с ней нечего. Подтверждение означает «**по этому тексту карта нашла строение**».
Субъект проверки не изменился: к карте ходит сервер, клиент объявить адрес подтверждённым не может.

Поведение:

| Ситуация | Что записано | `outcome` | Код |
|---|---|---|---|
| `verify: false` | адрес как прислали, проверка очищена → `Unverified`. **Внешних вызовов нет** | `Ok` | 200 |
| `verify: true`, лучший вариант с точностью `House` | адрес как прислали + `verifiedAt` + `precision: House`; координаты — **только если их разрешено хранить** | `Ok` | 200 |
| `verify: true`, варианты есть, но точность ниже дома | адрес как прислали, `Unverified` | `Ok` + `PrecisionStreet`/`PrecisionLocality`/`PrecisionOther` | 200 |
| `verify: true`, карта ничего не нашла | адрес как прислали, `Unverified` | `Empty` | 200 |
| `verify: true`, карта недоступна/таймаут (≤5 с) | адрес как прислали, `Unverified` | `Unavailable` | 200 |
| `verify: true`, рубильник выключен | адрес как прислали, `Unverified`. Внешних вызовов нет | `Disabled` | 200 |
| `address: ""` | `Address = null`, проверка очищена; адрес исчезает с публичной страницы и из поиска по каталогу **немедленно** (кеширования публичного ответа в продукте нет) | `Ok` | 200 |

**Подтверждение ставит только сервер, по результату своего собственного обращения к карте.** Поля
вида «считай этот адрес подтверждённым» в контракте нет и не будет: иначе через прямой вызов API в
базу попал бы «подтверждённый» адрес, которого никто не проверял.

Ответ **200** `CompanyAddressUpdateResultDto`:

```json
{
  "company": { "...": "полный CompanyDto, как у PUT /api/companies/{id}" },
  "verification": {
    "outcome": "Ok",
    "status": "Verified",
    "verifiedAt": "2026-09-24T10:15:00Z",
    "precision": "House",
    "warnings": [],
    "attribution": "© Яндекс"
  }
}
```

Полный `CompanyDto` возвращается затем, чтобы кеш интерфейса обновлялся одним ответом, как это уже
делает `PUT /api/companies/{id}`.

Коды: **200** (все исходы выше), **400** (адрес длиннее 300), **401**, **403** (не управляет
компанией), **404** (компании нет), **415** (тело не `application/json`), **429**.

**Никогда не возвращает 502/504.** Недоступность карты — это `outcome: "Unavailable"` в теле 200:
неудача внешнего сервиса не является неудачей операции «сохранить адрес владельца», и она не имеет
права мешать править свою компанию.

## §235. `PUT /api/companies/{id}` — не меняется, но у `address` появилось следствие

Форма запроса и ответа та же. `address` по-прежнему: `null`/отсутствует — не трогать, строка —
записать.

**Новое следствие:** статус подтверждения вычисляется сервером из сравнения текущего текста адреса с
тем **собственным текстом владельца**, который подтверждали. Поэтому любая правка адреса через этот
эндпоинт (кабинет владельца, суперадмин, прямой вызов API, скрипт) **автоматически** делает адрес
`Unverified`. Геокодер при этом **не вызывается** — ни одного внешнего запроса на сохранении настроек
компании.

То же касается `POST /api/companies`: адрес новой компании всегда `Unverified`, новых полей у создания
компании не появилось. Если владелец пользовался проверкой при создании, интерфейс делает **один**
дополнительный `PUT /api/companies/{id}/address` сразу после успешного создания.

⚠️ **Предупреждение о публичности адреса (§242) этот эндпоинт не проверяет и не блокирует.** Это
осознанное решение (вариант A развилки Q-L11): предупреждение информирует и фиксируется, но не
является условием записи. Прямой вызов API сохранит адрес без строки в журнале — и это известное
ограничение, а не дефект (`ARCHITECTURE_CYCLE13.md` §220.4, R19).

## §236. Предупреждения: коды и кто пишет текст

`warnings[]` — массив объектов `{ code, message }`. **Текст собирает сервер**; интерфейс показывает
`message` и строит логику по `code` (вторая версия формулировок на фронте разошлась бы с серверной —
конвенция проекта).

| `code` | Когда | О чём обязан сказать текст |
|---|---|---|
| `NotFound` | карта не нашла ничего | что адреса может не быть в карте и его можно сохранить как есть. **Без тона «вы ошиблись»** |
| `PrecisionStreet` | найдена только улица | что клиент не найдёт конкретный дом, и что подтверждение не поставлено |
| `PrecisionLocality` | найден только населённый пункт/район | то же, ещё грубее |
| `PrecisionOther` | карта не смогла определить уровень | что проверку нельзя считать состоявшейся |
| `CityMismatch` | населённый пункт найденного адреса ≠ город компании | что от города зависят **часовой пояс** и **город в каталоге**, и что стоит проверить поле «Город» |
| `Unavailable` | внешний сервис недоступен | «Не удалось проверить адрес, попробуйте позже», и что сохранение при этом не заблокировано |

**Город компании автоматически не меняется никогда** — только предупреждение: молчаливая подмена
города сдвинула бы время напоминаний.

Интерфейс обязан связать предупреждение с полем адреса программно (`aria-describedby`), а не только
цветом текста; предупреждение — текст рядом с полем, не модальное окно и не `alert`.

## §237. Что интерфейс обязан читать из ответа (и чего не имеет права выводить сам)

| Вопрос интерфейса | Единственный правильный источник |
|---|---|
| Показывать ли кнопку «Проверить адрес»? | `company.addressVerification?.available === true` |
| Подтверждён ли адрес? | `company.addressVerification?.status` (поля нет → считать `Unverified`) |
| Когда подтвердили? | `company.addressVerification?.verifiedAt` |
| Вести ссылку на точку или на поиск? | `company.addressPoint` (нет → поиск по тексту) |
| Что показать владельцу после проверки? | `verification.outcome` + `verification.warnings[].message` |
| Какая подпись правообладателя у результатов геокодера? | `attribution` из ответа |
| Какой текст предупреждения о публичности адреса и какая у него версия? | `GET /api/legal/texts/PublicAddressNotice` (§242) — **не** зашитая строка во фронте |
| Есть ли у салона фото и какое обложка? | без изменений: `company.photos`, `isCover`/`position === 0` |

Ничего из этого нельзя выводить из роли в JWT, из состава `authStore` или из того, что интерфейс сам
отправил в запросе.

## §238. Лимиты запросов

Новая, **десятая** именованная политика: **`address-verify`** — 30 запросов в час, ключ разбиения —
идентификатор пользователя (все три маршрута требуют авторизации, анонимного случая нет). Висит на
`POST /api/companies/address/lookup`, `PUT /api/companies/{id}/address` **и**
`POST /api/companies/address/notice`: первые два могут дойти до платного геокодера, третий пишет
строки в журнал согласий. Тело 429 — голая строка, как у остальных политик.

Геокодер вызывается **только** по явному действию владельца или суперадмина. Ни один просмотр
публичной страницы, ни один заход в каталог, ни одно сохранение настроек компании геокодер не дёргают.

## §239. Ссылки в карты — контракт фронтенда (сервер в них не участвует)

Серверных полей и эндпоинтов у этой задачи нет. Ссылки собирает единственный модуль
`frontend/src/utils/mapLinks.ts` из уже приходящих `company.address`, `company.cityName` и
необязательного `company.addressPoint`:

| Состояние | Яндекс Карты | 2ГИС |
|---|---|---|
| точка известна (`addressPoint`) | метка на точке, масштаб уровня дома | поиск по тексту + центр карты на точке |
| точки нет (штатно) | поиск по тексту «город, адрес» | поиск по тексту «город, адрес» |

Обязательное: порядок в запросе — **«город, адрес»** (без города «ул. Ленина, 5» открывает другой
регион); координаты в адресах обоих сервисов идут **`долгота,широта`**; всё кодируется
`encodeURIComponent`. Адрес пуст → ни адреса, ни ссылок, пустых кнопок не появляется. Ссылки работают
и для неподтверждённого адреса, и для неавторизованного посетителя.

**Пять условий лицензии (ред. 2, `LEGAL_REVIEW.md` §16.1) — требования к реализации, невыполнение
любого меняет правовой вывод «ключ и лицензия не нужны»:**

1. **Никакого встраивания карты и никаких её изображений** — ни `iframe`, ни JS API, ни статической
   картинки, ни **скриншота** карты: ни в интерфейсе, ни в документации, ни в `CHANGELOG`, ни на
   лендинге.
2. **`target="_blank"` + `rel="noopener noreferrer"`** — обязательны у обеих ссылок; переход
   совершается только по действию человека.
3. **Без логотипов и фирменной графики сервисов** — только текстовые подписи. Доступные имена заданы
   дословно: **«Открыть в Яндекс Картах»** и **«Открыть в 2ГИС»**; зона нажатия ≥44 px.
4. **Без заявлений об интеграции и партнёрстве** — ни «интеграция с Яндекс Картами», ни «работает на
   2ГИС», ни «партнёр» нигде: в интерфейсе, в тарифах, в пользовательском `CHANGELOG`, на лендинге.
   Точное описание — «ссылка на внешнюю карту».
5. **В URL уходит только город и адрес компании** — никаких `utm`, идентификаторов пользователя,
   наших метрик. И ничего из ответа карты **не парсится и не сохраняется**.

## §241. Чего цикл 13 в API НЕ меняет (важно не «починить заодно»)

- **Все четыре эндпоинта фотографий** (`GET/POST /api/companies/{id}/photos`,
  `DELETE …/photos/{photoId}`, `PUT …/photos/order`) — ни параметров, ни форм ответа, ни лимита 10, ни
  дедупа, ни уплотнения позиций. Карусель — **чистый фронтенд**: `company.photos` уже приходит вместе
  с компанией (`API_CONTRACT_CYCLE10.md` §129), и публичная страница не получает ни одного нового
  запроса.
- **`coverPhotoUrl` / `coverThumbnailUrl` / `photos`** — правила заполнения по эндпоинтам прежние
  (§129 цикла 10): `photos` только у `GET /api/companies/{slug}`, `null` = «этот эндпоинт список не
  отдаёт», `[]` = «фотографий нет».
- **`POST /api/companies`** — ни одного нового поля; адрес новой компании всегда `Unverified`.
- **`GET /api/companies/public`** — параметры `cityId`/`search`/`page`/`pageSize` и правила поиска
  (подстрока по названию **или** адресу, в SQL) не меняются. Ред. 2 усилила это: `Address` теперь
  вообще никогда не переписывается ответом геокодера, поэтому строка, по которой ищут, от
  подтверждения не меняется ни на символ.
- **Город и часовой пояс** (`cityId`, `timeZoneId`, `timeZoneIsManual`) — ни формы, ни правил; город по
  адресу автоматически не меняется.
- **Каталог опций, тарифы, суперадминка цен** — новой платной опции цикл не создаёт; ссылки и проверка
  доступны на всех тарифах (и это, по §16.1 п. 5 заключения, ещё и правовое требование, а не только
  продуктовое решение).
- **Виджет `/embed/:slug`** — ни карусели, ни ссылок на карты; поведение записи не меняется.
- **Уведомления** — шаблоны, каналы и доставка не затронуты; ссылок на карты в сообщениях нет.
- **Правовой контур цикла 5/11 по механике** — `GET /api/legal/*`, `POST /api/profile/consents`,
  гейт 451, форма `ConsentRecord`, «Мои согласия» и экспорт данных: ни одного изменения формы. Цикл
  добавляет **седьмой ключ** интерфейсного текста и **новый источник** записей в существующий журнал
  (§242), не трогая ни один существующий эндпоинт.

## §242. `POST /api/companies/address/notice` — НОВЫЙ (ред. 2)

Зафиксировать, что владельцу (или суперадмину) показано предупреждение о том, что адрес компании
станет общедоступным, и он его принял. Основание — `LEGAL_REVIEW.md` §16.4; текст —
`legal-drafts/13-public-address-notice.html`, ключ `PublicAddressNotice`.

**Это не согласие по ст. 10.1 152-ФЗ, а фиксация осознанного действия** (`Act = Acknowledged`).
Работает **независимо от рубильника геокодера**: к проверке адреса эндпоинт отношения не имеет.

Доступ: `[Authorize]`, любой авторизованный пользователь. `companyId` **не требуется**: при создании
компании её ещё нет, а подтверждение — заявление человека, а не свойство компании. Лимит — политика
**`address-verify`** (§238).

Запрос:

```json
{ "textVersion": "2026-09-24-draft", "confirmed": true }
```

| Поле | Тип | Обязательно | Правила |
|---|---|---|---|
| `textVersion` | `string` | да | версия текста, которую пользователь **реально видел** — берётся из `GET /api/legal/texts/PublicAddressNotice`. Сверяется с живым снимком сервера |
| `confirmed` | `boolean` | да | `false` → **400** «Подтверждение обязательно.» |

Ответ **200** `AddressNoticeResultDto`:

```json
{ "version": "2026-09-24-draft", "acknowledgedAt": "2026-09-24T10:15:00Z" }
```

| Поле | Тип | Смысл |
|---|---|---|
| `version` | `string` | версия текста, которая записана в журнал |
| `acknowledgedAt` | `string` (date-time) | когда записано (UTC) |

Коды ответов:

| Код | Когда | Тело |
|---|---|---|
| 200 | записано (или попало в 5-секундное окно идемпотентности журнала и вернулась существующая запись) | `AddressNoticeResultDto` |
| 400 | `confirmed: false` | голая строка «Подтверждение обязательно.» |
| 401 | нет токена | пусто |
| **409** | `textVersion` не совпала с живой версией текста — текст обновился, пока экран был открыт | голая строка «Текст был обновлён ещё раз — перечитайте и подтвердите заново.» |
| 415 | тело не `application/json` | пусто |
| 429 | лимит `address-verify` | голая строка |
| **503** | правовые тексты на сервере не загружены | голая строка «Правовые документы временно недоступны.» |

Что пишется в `ConsentRecord` (таблица цикла 5, **без миграций и без изменений схемы**): субъект —
`ConsentSubject.ForUser(<кто нажал>)`; `DocumentKey = "PublicAddressNotice"`; `DocumentVersion` и
`DocumentHash` — из живого снимка; `Purpose = null`; `Act = Acknowledged`; `Source = AddressForm`
(новый append-only член перечисления, хранится `int`); `IpAddress`/`UserAgent` — как везде, **наружу
не отдаются никогда**. Каждое подтверждение — своя строка (журнал, а не состояние); записи видны в
«Мои согласия» (`GET /api/profile`) и в экспорте данных субъекта без единой правки этих эндпоинтов.

**Что интерфейс обязан сделать вокруг этого эндпоинта:**
- показать **только раздел «Текст для владельца»** из `contentHtml` (остальное в файле — служебные
  приложения; `ARCHITECTURE_CYCLE13.md` §220.2);
- кнопки — «Понятно, сохранить адрес» и «Отмена»; сохранение адреса продолжается только после 200;
- показывать предупреждение при первом заполнении поля «Адрес» и при любом его изменении, **до**
  сохранения, на обоих экранах, где адрес вводится (настройки компании и создание компании);
- при 409 — перечитать текст (`GET /api/legal/texts/PublicAddressNotice`) и попросить подтвердить
  заново; своей формулировки предупреждения интерфейс не придумывает ни при каких ошибках.
