# Запуск тестов и локальная среда

Документ для того, кто работает с репозиторием: как прогнать тесты, что делать, если прогон
красный или не стартует, и как держать на одной машине две рабочие копии, чтобы они не мешали
друг другу.

Это не пользовательская документация продукта — ролевые руководства для клиентов, мастеров и
владельцев компаний лежат рядом, в [`README.md`](README.md) этой папки.

Всё ниже описывает состояние репозитория после цикла 8 («изоляция тестовой и локальной среды»).
Если вы помните, что «для тестов надо поднять Postgres и завести базу `servicebooking_test`», — это
больше не так, начните с раздела «Что изменилось».

---

## Коротко

```bash
dotnet test ServiceBooking.UnitTests     # быстрые, без БД и без Docker
dotnet test ServiceBooking.Tests         # функциональные: нужен запущенный Docker, Postgres не нужен
```

- **Нужен Docker**, а не заранее поднятый PostgreSQL. Прогон сам поднимает контейнер Postgres на
  свободном порту, заводит в нём свои базы и убирает их за собой.
- **Ничего настраивать не надо** — ни переменных окружения, ни строки подключения. Кнопка «Run» в
  Rider работает так же, как `dotnet test`: ключ прогона вычисляется внутри тест-процесса.
- **Два прогона рядом не мешают друг другу** — у каждого свой контейнер, свои базы, свои временные
  каталоги. Это проверено на приёмке двумя одновременными прогонами из двух рабочих копий.
- Тесты идут **параллельно** (4 потока локально, 2 в CI) и в **случайном порядке внутри класса**.
- Если что-то не так со средой — первым делом
  `dotnet run --project ServiceBooking.TestKit -- doctor`.

## Что изменилось (если вы работали с репозиторием до цикла 8)

| Было | Стало |
|---|---|
| Нужен локально запущенный PostgreSQL с базой `servicebooking_test` | Нужен Docker. Postgres прогон поднимает сам |
| Дефолтная строка подключения `Host=localhost;Database=servicebooking_test;…` зашита в тестах | Дефолта нет вовсе. Нет Docker и нет явно заданного сервера — прогон отказывается стартовать с объяснением, ничего не удаляя |
| `SERVICEBOOKING_TEST_CONNECTION` — строка к **базе** | Строка к **серверу**; имя базы прогон выбирает сам. Компонент `Database` из строки всё равно переписывается на `postgres` |
| Прогон пересоздавал общую базу — два прогона на машине конфликтовали | У каждого прогона свой контейнер и свои базы `sbtest_<ключ прогона>_<слот класса>` |
| Тесты выполнялись последовательно, ~178 с | Параллельно, 4 потока; медиана замера приёмки — **46 с** |
| Порядок тестов внутри класса фиксированный | Случайный, с печатаемым и воспроизводимым семенем |

## Что нужно на машине

- **.NET SDK 8.0** (тот же, что в CI).
- **Docker** — Docker Desktop, Docker Engine или colima (для colima есть нюанс, см. «Известные
  ограничения среды»). Отдельный установленный PostgreSQL не нужен и не используется.
- Всё. Никаких переменных окружения, никакого `.env` для тестов — файл окружения нужен только
  dev-стеку (`docker compose up`), и тоже необязателен.

Проверить готовность среды одной командой:

```bash
dotnet run --project ServiceBooking.TestKit -- doctor
```

Команда ничего не меняет и не удаляет. Код возврата `0` — всё в порядке, `2` — какая-то из проверок
не прошла (в выводе будет `FAIL <имя проверки>` и что с этим сделать).

## Как прогнать тесты

### Из командной строки

```bash
dotnet test ServiceBooking.UnitTests   # юнит-тесты: чистая логика, ни Docker, ни базы
dotnet test ServiceBooking.Tests       # функциональные: поднимут свой Postgres в Docker
```

Юнит-набор намеренно не зависит ни от Docker, ни от базы: он должен проходить при остановленном
Docker. Если юнит-тестам вдруг понадобился Docker — это регресс, а не особенность вашей машины.

### Из Rider / IDE

Кнопкой «Run» по тесту, классу или проекту. Настраивать ничего не нужно: и степень параллелизма
(`ServiceBooking.Tests/xunit.runner.json`), и ключ прогона живут внутри тестовой сборки, а не во
внешнем окружении.

Единственное требование к IDE-запуску такое же, как к консольному, — запущенный Docker.

### Что печатает прогон

Первыми строками:

```
[sb-test] run=a3f19c7b  mode=container  server=localhost:54312  user=postgres  databases=sbtest_a3f19c7b_<class-slot>  parallel=4
[sb-test] RandomTestCaseOrderer seed=316598856 (replay this exact order with SERVICEBOOKING_TEST_ORDER_SEED=316598856).
[sb-test] class-db slot=c01 db=sbtest_a3f19c7b_c01
```

- `run=` — ключ прогона, он же средняя часть имён баз и метка на контейнере. По нему прогон
  находится в `docker ps` и в выводе `TestKit status`.
- `mode=container` — прогон поднял свой Postgres; `mode=external` — используется сервер из
  `SERVICEBOOKING_TEST_CONNECTION` (так работает CI). В режиме `external` в этой же строке видно
  `server=` и `user=` — если вы случайно направили прогон не туда, это видно сразу.
- `parallel=` — сколько классов может выполняться одновременно.
- `seed=` — семя случайного порядка тестов внутри класса, см. «Случайный порядок».

Та же информация в машиночитаемом виде — `TestResults/sb-test-run.json` (пишется лучшим усилием;
если записать не удалось, прогон из-за этого не падает).

## Если прогон красный или не стартует

### «Не могу подготовить базу для прогона. Docker недоступен…»

Прогон не нашёл Docker и не увидел заданного сервера — и **осознанно ничего не сделал**, вместо того
чтобы угадать строку подключения и снести чужую базу. Варианты, которые он сам предлагает:

1. запустить Docker и повторить — штатный путь;
2. указать свой сервер PostgreSQL:
   `SERVICEBOOKING_TEST_CONNECTION="Host=localhost;Port=5432;Username=postgres;Password=..."` —
   имя базы в строке игнорируется, прогон заведёт свои.

### «Отказ: прогон попытался удалить базу "…", не являющуюся одноразовой тестовой»

Сработала защита: удалять можно только базы вида `sbtest_<8 hex>_<слот>`, и только их. Ничего не
удалено. Обычная причина — в `SERVICEBOOKING_TEST_CONNECTION` осталось значение из прежней жизни,
где переменная указывала на базу. С цикла 8 эта переменная задаёт **сервер**; имя базы прогон
выбирает сам.

### «Отказ: бюджет соединений не сходится»

Столько параллельных классов при таком пуле соединений не поместится в `max_connections` сервера.
Прогон говорит это **до** первого теста, а не «connection limit exceeded» на трёхсотом. В сообщении
три выхода: снизить параллелизм, поднять потолок сервера или убрать
`SERVICEBOOKING_TEST_CONNECTION` и дать прогону поднять свой контейнер (в нём потолок 300).

Тот же расчёт можно увидеть заранее — проверка `parallel-connection-budget` в
`TestKit doctor` (и поле `parallelism` в `doctor --json`).

### Тест падает то зелёным, то красным

Порядок тестов внутри класса случайный, и классы выполняются параллельно — то есть гонка может
проявиться не на каждом прогоне. Порядок действий:

1. **Повторить упавший порядок.** Возьмите семя из строки `RandomTestCaseOrderer seed=…` того
   прогона, который упал, и повторите:

   ```bash
   SERVICEBOOKING_TEST_ORDER_SEED=316303319 dotnet test ServiceBooking.Tests
   ```

2. **Отличить гонку от настоящей поломки** — прогнать тот же набор в один поток:

   ```bash
   dotnet test ServiceBooking.Tests -- xUnit.MaxParallelThreads=1
   ```

   Зелено в один поток и красно в четыре — это гонка (или зависимость теста от соседа), а не
   сломанная логика.

3. Учтите: часть гонок воспроизводится только под параллельной нагрузкой. На приёмке цикла была
   ровно такая — повтор одного класса с тем же семенем её не показывал, полный прогон с тем же
   семенем показывал.

4. **Крайняя мера на время диагностики** — вернуть весь набор в последовательный режим: в
   `ServiceBooking.Tests/AssemblyInfo.cs` раскомментировать одну строку
   `[assembly: CollectionBehavior(DisableTestParallelization = true)]`. Она там уже есть, с
   инструкцией рядом. Это весь откат — больше править нечего. Изоляция «база на класс» при этом
   сохраняется.

### После прерванного прогона что-то осталось на машине

Штатное завершение убирает всё само; убитый процесс (Ctrl+C, `kill -9`, таймаут) — не вызывает
уборку, но контейнеры примерно через 10 секунд добивает сторож Testcontainers (Ryuk). Остаться
может то, что пережило и это, а на внешнем сервере — базы. Смотреть и убирать:

```bash
dotnet run --project ServiceBooking.TestKit -- status    # что живо
dotnet run --project ServiceBooking.TestKit -- sweep     # что считается мёртвым (ничего не удаляет)
dotnet run --project ServiceBooking.TestKit -- sweep --apply
```

Подробности — в разделе «Инструмент диагностики».

> Отключать Ryuk (`TESTCONTAINERS_RYUK_DISABLED=true`) нельзя — это единственная уборка при
> аварийном завершении. `doctor` отдельно проверяет, что переменная не выставлена.

## Параллелизм

Локально набор идёт в **4 потока**, в CI — в **2**. Единица параллелизма — тест-класс: у каждого
класса своя база, склонированная из шаблона прогона, поэтому классы не делят данные.

Значение по умолчанию лежит в `ServiceBooking.Tests/xunit.runner.json` (`maxParallelThreads`).

**Как изменить на один прогон.** Здесь есть тонкость, которую надо знать, иначе будете долго
удивляться. Реальное число потоков задаёт раннер:

```bash
dotnet test ServiceBooking.Tests -- xUnit.MaxParallelThreads=2
```

А проверку бюджета соединений внутри тест-процесса — отдельная переменная окружения, потому что
прочитать значение раннера изнутри процесса нечем:

```bash
SERVICEBOOKING_TEST_MAX_PARALLEL_THREADS=2 dotnet test ServiceBooking.Tests -- xUnit.MaxParallelThreads=2
```

Если задать только переменную окружения, набор всё равно пойдёт в 4 потока — изменится лишь
арифметика проверки бюджета. Поэтому, меняя параллелизм всерьёз, задавайте **оба** значения
одинаковыми — именно так это сделано в CI (`.github/workflows/ci.yml`). Прогон печатает то число,
которое использовал сам, так что расхождение видно в логе.

Поднимать параллелизм выше 6 смысла нет: время прогона снизу упирается в самый длинный класс
(`CompaniesTests`, 78 тестов), а не в число ядер.

## Случайный порядок тестов

Внутри класса порядок тестов перемешивается на каждом прогоне — это вскрывает скрытые зависимости
вида «тест B проходит только после теста A». Семя перемешивания печатается один раз за прогон:

```
[sb-test] RandomTestCaseOrderer seed=316598856 (replay this exact order with SERVICEBOOKING_TEST_ORDER_SEED=316598856).
```

Задать своё семя (чтобы повторить конкретный прогон — например, красный из CI):

```bash
SERVICEBOOKING_TEST_ORDER_SEED=316598856 dotnet test ServiceBooking.Tests
```

Одинаковое семя даёт одинаковый порядок внутри каждого класса. Порядок **между** классами семенем
не управляется — его определяет раннер и параллелизм.

## Инструмент диагностики: `ServiceBooking.TestKit`

```bash
dotnet run --project ServiceBooking.TestKit -- status [--json]
dotnet run --project ServiceBooking.TestKit -- sweep  [--apply] [--max-age <срок>] [--run-key <ключ>] [--json]
dotnet run --project ServiceBooking.TestKit -- doctor [--json]
```

У всех трёх команд есть `--json`: машиночитаемый вывод идёт в stdout, человекочитаемый — в stderr,
схема — `contracts/cycle8/testkit-status.schema.json`.

### `status` — что сейчас занято

Печатает путь рабочей копии, имя compose-проекта и dev-базы, порты `SB_DB_PORT`/`SB_API_PORT`/
`SB_WEB_PORT`/`SB_GLITCHTIP_PORT` с отметкой «занят/свободен», доступность Docker и список живых
тестовых ресурсов с отметкой «мой/чужой» (мой — заведённый из этого же каталога).

Строка «compose-проект» показывает значение `COMPOSE_PROJECT_NAME` (из окружения или `.env`), а если
та не задана — имя, выведенное из каталога рабочей копии тем же способом, каким его выводит сам
compose (нижний регистр, только `[a-z0-9_-]`, ведущие не-буквенно-цифровые символы отброшены). Это
то же самое имя, что и реальный compose-проект: раньше здесь читалась отдельная переменная
`SB_PROJECT_NAME` с жёстко зашитым дефолтом `servicebooking`, из-за чего во второй рабочей копии с
другим именем каталога `status`/`doctor` показывали чужое имя проекта и `doctor` мог принять
собственные порты этой копии за «занятые соседом» — это исправлено. Явно задавать
`COMPOSE_PROJECT_NAME` по-прежнему можно (штатный механизм compose), но для разведения двух копий
это не требуется: имя, выведенное из каталога, уже их различает.

Первое, что стоит запустить, если `docker compose up` жалуется на занятый порт.

**Команда ничего не меняет** — только читает и пробует занять порт, немедленно отпуская. Безопасна
в любом состоянии машины, включая отсутствующий Docker. Ненулевой код возврата из-за состояния
машины она не возвращает: «всё занято» — это факт, а не ошибка.

Что `status` **не** покажет: тестовые базы в режиме `container`. Они живут внутри контейнера
прогона, и после его завершения наблюдать снаружи уже нечего. Базы перечисляются, только если задан
`SERVICEBOOKING_TEST_CONNECTION` (внешний сервер).

### `sweep` — убрать мусор после прерванных прогонов

По умолчанию — **сухой прогон**: раскладывает найденное по трём категориям и ничего не трогает.

- **Мёртвые** — удаляются только они и только с `--apply`. «Мёртвый» — это конъюнкция, а не
  догадка: наша метка, отсутствие живого процесса-хозяина и возраст больше `--max-age` (по
  умолчанию 2 часа); для базы дополнительно — ни одного подключения к ней.
- **Живые** — не трогаются никогда. Запустить `sweep --apply` во время чужого (или своего) прогона
  безопасно, это проверялось на приёмке.
- **Неопределённые** — не трогаются автоматически. Удалить точечно можно только явным
  `sweep --apply --run-key <ключ>`.

```bash
dotnet run --project ServiceBooking.TestKit -- sweep                      # посмотреть
dotnet run --project ServiceBooking.TestKit -- sweep --apply              # удалить мёртвое
dotnet run --project ServiceBooking.TestKit -- sweep --apply --max-age 30m
```

`--max-age` принимает `30m`, `2h`, `1d`. Значение без единицы, отрицательное или без самого
значения — отказ с понятным сообщением, а не тихое «подмету всё».

Коды возврата: `0` — успех, `1` — некорректные аргументы либо недоступны и Docker, и сервер сразу
(проверить было нечем), `3` — с `--apply` часть ресурсов удалить не удалось (детали в `errors[]`
JSON-вывода).

### `doctor` — готова ли среда

Проверяет: доступен ли Docker (или задан ли внешний сервер), лежит ли в кеше образ Postgres,
доступен ли .NET SDK, свободны ли порты dev-стека, не отключён ли Ryuk, сходится ли бюджет
соединений при текущем параллелизме. Код возврата `0` — всё ок, `2` — есть непройденные проверки,
которые реально мешают тестовому прогону.

Проверка `ports-free` (заняты ли `SB_DB_PORT`/`SB_API_PORT`/`SB_WEB_PORT` — порты dev-стека
`docker compose up`) — **информационная**, её результат никогда не роняет `doctor` в код `2`: сам
тестовый прогон эти порты не использует (`container`-режим поднимает Postgres на отдельном
динамическом порту, `server`-режим — через `SERVICEBOOKING_TEST_CONNECTION`), поэтому их занятость
соседним процессом (например, локально установленным Postgres.app или уже запущенным API) не мешает
тестам. Раньше эта проверка валила весь `doctor` кодом `2` в точности в этой ситуации — исправлено;
`ports-free` теперь только предупреждает в `detail`, если порт занят чужим compose-проектом.
«Занят мной» и «занят соседом» по-прежнему различаются по имени compose-проекта, опубликовавшего
порт, сравнение идёт с тем же выведенным из каталога (или явно заданным `COMPOSE_PROJECT_NAME`)
именем, что и у `status` — см. оговорку выше.

## Две рабочие копии на одной машине

Тесты разводятся сами — ни настройки, ни `.env` для этого не нужно. А вот dev-стек
(`docker compose up`) публикует фиксированные порты, и вот их надо развести руками.

Что уже сделано за вас: имя compose-проекта **выводится из имени каталога**, поэтому у каждой копии
свои контейнеры, своя сеть и свой том. `docker compose down -v` в одной копии не может задеть
данные другой.

Что надо сделать самому, если поднимаете два стека одновременно:

```bash
cp .env.dev.example .env    # и поменять порты во второй копии
```

```env
SB_DB_PORT=5433
SB_API_PORT=5001
SB_WEB_PORT=5174
```

- Файл `.env` не обязателен: свежий клон без него работает на 5432/5000/5173, как раньше.
- `.env` в `.gitignore` и не коммитится; `.env.dev.example` закоммичен и содержит комментарии к
  каждой переменной.
- Имя проекта можно задать явно штатной `COMPOSE_PROJECT_NAME` в том же `.env` — но для самого
  разведения копий это не нужно: значение по умолчанию (из каталога) уже их разводит, и этим же
  выведенным именем (или явным `COMPOSE_PROJECT_NAME`, если задан) `status`/`doctor` отличают «мой
  порт» от «порт соседа» — отдельно задавать что-то ещё для этого не нужно.
- `SB_API_PORT` читает и `frontend/vite.config.ts` — Vite строит из него адрес прокси на API.
- Если занят `SB_WEB_PORT`, Vite сам возьмёт следующий свободный и напечатает итоговый адрес. Если
  занят `SB_API_PORT` или `SB_DB_PORT`, `docker compose up` упадёт с ошибкой публикации порта — это
  намеренно не маскируется, диагностика — `TestKit status`.

Этот `.env` — файл **рабочей копии разработчика**. С `.env` боевой машины (`.env.production.example`,
`DEPLOY.md` §3) он не пересекается: разные машины, разные compose-файлы, непересекающиеся имена
переменных.

## Переменные окружения тестов

Ни одна не обязательна. Без них всё работает.

| Переменная | Зачем | Кто обычно задаёт |
|---|---|---|
| `SERVICEBOOKING_TEST_CONNECTION` | строка подключения к **серверу** (имя базы игнорируется). Задана — прогон идёт в режиме `external` и свой контейнер не поднимает | CI; локально — если хотите гнать против своего сервера |
| `SERVICEBOOKING_TEST_MAX_PARALLEL_THREADS` | число, с которым считается бюджет соединений. Реальный параллелизм задаётся `-- xUnit.MaxParallelThreads=N`, задавайте оба одинаковыми | CI; локально — при диагностике |
| `SERVICEBOOKING_TEST_ORDER_SEED` | семя случайного порядка тестов внутри класса — чтобы повторить упавший порядок | вы, при разборе флака |
| `SERVICEBOOKING_TEST_RUN_KEY` | фиксирует ключ прогона (8 hex) вместо случайного — чтобы имена баз и контейнеров совпадали с идентификатором сборки в логах | CI |
| `SERVICEBOOKING_TEST_NO_TEMPLATE` | аварийный выключатель шаблонной базы: каждая база мигрируется сама | только при проблеме с `CREATE DATABASE … TEMPLATE` на внешнем сервере |
| `SERVICEBOOKING_TEST_SEEDED_TEMPLATE` | предсидированный шаблон; по умолчанию выключено | — |
| `TESTCONTAINERS_RYUK_DISABLED` | **запрещена.** Отключает уборку контейнеров при аварийном завершении | никто |

## Как это устроено в CI

Джоб `backend` в `.github/workflows/ci.yml` идёт по второму пути: Postgres поднимается
service-контейнером GitHub Actions, а не изнутри тест-процесса (Docker-in-Docker не нужен). Поэтому
там задана `SERVICEBOOKING_TEST_CONNECTION` — строка к этому серверу. Базы прогон всё равно заводит
свои и сносит за собой, так что два прогона на одном сервере не конфликтуют.

Параллелизм в CI — 2 (два ядра раннера), заданный в двух местах сразу: `-- xUnit.MaxParallelThreads=2`
у команды и `SERVICEBOOKING_TEST_MAX_PARALLEL_THREADS=2` в окружении джоба.

Ключ прогона в CI выводится из идентификатора сборки и имени джоба — чтобы по логу можно было
понять, чьи это базы, и чтобы два джоба одной сборки не получили одинаковый ключ.

## Известные ограничения среды

### macOS + colima

Testcontainers по умолчанию ищет сокет Docker в `/var/run/docker.sock`, а colima его там не
создаёт — подъём падает на Ryuk с `invalid mount config for type bind: stat …/docker.sock:
operation not supported`. Лечится двумя переменными, **без** отключения Ryuk:

```bash
export DOCKER_HOST=unix://$HOME/.colima/default/docker.sock
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
```

С ними Ryuk поднимается и убирает контейнеры штатно. На обычном Docker Desktop и в CI эти
переменные не нужны и ничего не меняют.

Чтобы не выставлять их в каждой сессии, положите обе строки в свой `~/.zshrc` — тогда и Rider,
запущенный из терминала, их увидит. Rider, запущенный из Dock/Finder, переменные из `~/.zshrc` не
наследует; в этом случае задайте их в конфигурации запуска тестов в самой IDE.

### Прочее

- `dotnet test ServiceBooking.sln` одной командой поднимает **два** процесса (юнит-набор и
  функциональный) и, соответственно, два ключа прогона. Практического эффекта нет — юнит-набор базы
  не касается, — но в логе будут два разных ключа.
- Защита от разрушительных действий работает **по имени базы**, а не по адресу сервера. Если
  подсунуть в `SERVICEBOOKING_TEST_CONNECTION` боевой хост, прогон создаст там свои `sbtest_*` и
  удалит только их — боевая база уцелеет, но мусор и нагрузка на боевом сервере появятся. Поэтому
  прогон и печатает `server=`/`user=` первой строкой.
- Два одновременных параллельных прогона на одной машине замедляют друг друга примерно вдвое (8
  активных потоков на 8 ядрах) — но остаются зелёными: они делят процессор и память, но не
  состояние.
