## §120. Конвенции (действуют без изменений, повторены, чтобы не искать)

- JSON — **camelCase**; перечисления — **строками** (`JsonStringEnumConverter`).
- `DateTime` — ISO-8601 **UTC**; `DateOnly` — `YYYY-MM-DD`; `TimeOnly` — **`HH:mm:ss`**.
  (Фронт по-прежнему дописывает `:00` в `bookingsApi.create` — это не меняется.)
- Тела ошибок **400 / 402 / 409 / 410 / 429** — **голая строка** (`text/plain`), не JSON-объект.
  **401 / 403** — **пустое** тело. `ProblemDetails` не используется, кроме автоматической валидации
  `[ApiController]` (её форма задана глобально `InvalidModelStateResponseFactory`).
- Все тексты ошибок, которые может увидеть пользователь, — **по-русски**. Технические сообщения
  конвейера загрузки остаются как есть и переводятся на фронте `utils/uploadError.ts`.
- Base URL — `/api` (тот же, что у axios-инстанса `frontend/src/api/client.ts`).

## §121. `GET /api/bookings/availability` — ИЗМЕНЁН

Статус каждого дня диапазона одним запросом. Анонимный, лимит `availability` — 60/мин на IP.

### §121.1. Параметры

| Параметр | Тип | Обяз. | Смысл |
|---|---|---|---|
| `companyId` | uuid | да | |
| `masterId` | string | да | |
| `serviceId` | uuid | нет* | одна услуга (прежняя форма) |
| `serviceIds` | uuid[] | нет* | состав визита; повторяется (`serviceIds=a&serviceIds=b`), **не** `serviceIds[]=` |
| `from` | date | да | не раньше `сегодня−1` |
| `to` | date | да | не раньше `from`, диапазон **≤ 31 дня** |
| `manual` | bool | нет | просьба включить режим персонала. По умолчанию `false` |
| `extendedHours` | bool | нет | **НОВЫЙ.** Просьба показать сутки целиком. По умолчанию `false` |

\* нужен `serviceId` **или** `serviceIds`; правила совпадения — как в цикле 6 (`serviceIds[0] == serviceId`).

### §121.2. Главное правило: `manual` и `extendedHours` — это просьба, а не разрешение

Сервер **сам** проверяет членство вызывающего в `companyId` и решает, какой фоллбек применить.
Таблица ровно та же, что у `GET /api/bookings/slots` — специально, чтобы календарь и сетка времени
не могли разойтись:

| `manual` | `extendedHours` | кто вызывает | что происходит |
|---|---|---|---|
| `true` | `true` | персонал этой компании или SuperAdmin | сутки целиком, график и перерывы игнорируются |
| `true` | `false` | персонал этой компании или SuperAdmin | окно по умолчанию 09:00–21:00 на дни без графика |
| любое | любое | **все остальные** | как сегодня: нет графика → день `DayOff` |

`extendedHours=true` **без** `manual=true` не даёт ничего никому.
Запрос от клиента, гостя или сотрудника **чужой** компании с любыми флагами выдачу **не расширяет**.

### §121.3. Ответ

```jsonc
{
  "from": "2026-10-01",
  "to": "2026-10-31",
  "totalDurationMinutes": 60,
  "stepMinutes": 30,
  "horizonDays": 90,
  "horizonLastDate": "2026-12-22",
  "staffMode": true,                 // НОВОЕ
  "days": [
    {
      "date": "2026-10-12",
      "status": "Available",         // Available | FullyBooked | DayOff
      "lastFreeSlotStart": "20:30:00",
      "scheduleState": "DayOff"      // НОВОЕ: Working | DayOff | NoSchedule | null
    }
  ]
}
```

**`staffMode`** — сервер прямо говорит, признал ли он вызывающего персоналом и применил ли режим.
Это **единственный** признак, по которому интерфейс имеет право рисовать режим персонала. Роль в
токене, список компаний и переданный `manual` таким признаком не являются.

**`scheduleState`** — состояние графика мастера на эту дату, **независимо** от того, можно ли туда
записать:

| Значение | Что значит |
|---|---|
| `Working` | на дату есть строка расписания, мастер работает |
| `DayOff` | строка есть, день помечен нерабочим → подпись «выходной» |
| `NoSchedule` | строки расписания нет вовсе → подпись «нет графика» |
| `null` | **поле не заполнено**, потому что `staffMode == false` |

⚠️ **`scheduleState` приходит только при `staffMode: true`.** Для всех остальных он всегда `null` —
различать «выходной» и «график не заполнен» анонимному посетителю незачем, и это осознанное решение
по приватности расписания (`ARCHITECTURE_CYCLE10.md` §103.2).

**Как это читать интерфейсу**

| `staffMode` | `status` | `scheduleState` | День нажимаем? | Подпись |
|---|---|---|---|---|
| `false` | `DayOff` | `null` | **нет** | «выходной» |
| `false` | `FullyBooked` | `null` | нет | «Занято» |
| `false` | `Available` | `null` | да | — |
| `true` | `Available` | `Working` | да | — |
| `true` | `Available` | `DayOff` | **да** | **«выходной»** |
| `true` | `Available` | `NoSchedule` | **да** | **«нет графика»** |
| `true` | `FullyBooked` | любое | нет | «Занято» |

То есть для персонала статус графика — **информация, а не запрет**. Подпись обязана попадать в
доступное имя кнопки дня (`aria-label`), а не только в визуальный текст.

`status` по-прежнему **не содержит** состояния «прошедший день» — браузер знает свою локальную дату
лучше сервера. Прошедшие даты и прошедшее время сегодняшнего дня невыбираемы **во всех режимах**.

### §121.4. Горизонт

- Не-персонал: `to` дальше `horizonLastDate` → **400**, `«Записаться можно не дальше чем на N дней
  вперёд»` (текст не менять — фронт разбирает из него число, `utils/bookingHorizon.ts`).
- Персонал (`staffMode: true`): горизонт **не применяется**, ограничения по `to` нет, кроме правила
  «диапазон ≤ 31 дня». Календарь персонала листается вперёд помесячно; верхняя граница (не менее
  365 дней) — правило интерфейса, сервер её не навязывает.

### §121.5. Ошибки

| Код | Тело | Когда |
|---|---|---|
| 400 | `to must not be before from` | |
| 400 | `Диапазон не может превышать 31 день` | |
| 400 | `from is too far in the past` | `from` раньше `сегодня−1` |
| 400 | `Записаться можно не дальше чем на N дней вперёд` | горизонт, только не-персоналу |
| 400 | `Этот мастер не работает в выбранной компании` | пара company/master не сходится |
| 400 | `Мастер не оказывает услугу: …` | |
| 404 | `Company not found` | |
| 429 | — | политика `availability` |

## §122. `GET /api/bookings/{id}/history` — НОВЫЙ

История изменений одной записи. **Внутренняя информация персонала** (решение П8).

`[Authorize]`. Доступ: **персонал компании этой записи** (`Master`/`CompanyOwner` в ней) **или
SuperAdmin**. Обратите внимание: это шире, чем право менять запись, — любой сотрудник компании видит
историю, не только назначенный мастер и владелец.

### §122.1. Ответ 200

```jsonc
{
  "bookingId": "…",
  "precedesJournal": false,
  "events": [
    {
      "id": "…",
      "kind": "Rescheduled",
      "occurredAt": "2026-09-20T11:04:07Z",
      "title": "Запись перенесена",
      "actor": {
        "kind": "Staff",
        "name": "Иван Петров",
        "role": "Master",
        "label": "Перенёс Иван Петров (мастер)"
      },
      "reschedule": {
        "fromDate": "2026-09-22", "fromStartTime": "10:00:00",
        "toDate":   "2026-09-25", "toStartTime":   "14:30:00"
      },
      "cancellationReason": null
    }
  ]
}
```

`events` — в порядке **возрастания** `occurredAt` (сервер отдаёт хронологию; как её показать —
новое сверху или снизу — решает интерфейс, но **единообразно** во всём продукте).

| Поле | Значение |
|---|---|
| `kind` | `Created` \| `Rescheduled` \| `Cancelled` \| `Completed` \| `NoShow` \| `PaymentMarked` |
| `title` | готовый русский заголовок события, **собирает сервер** |
| `actor.kind` | `Client` \| `Guest` \| `Staff` \| `SuperAdmin` \| `System` |
| `actor.name` | **снимок имени на момент события**; `null` только у `System` |
| `actor.role` | `Master` \| `CompanyOwner` — роль **в этой компании** на момент события; `null` у остальных видов автора |
| `actor.label` | готовая русская строка «кто это сделал», **собирает сервер** |
| `reschedule` | заполнен **только** у `Rescheduled`, иначе `null` |
| `cancellationReason` | заполнен **только** у `Cancelled` и только если причина была указана |

**Тексты собирает сервер** (`title`, `actor.label`) — та же конвенция, что у `NotificationTexts` и
`ChannelPresentation`. Интерфейс форматирует только дату/время и рисует «было → стало» из полей
`reschedule`. Собирать вторую версию формулировок на фронте **нельзя**: они разойдутся.

**Чего в ответе нет и не будет:** телефонов, почты, любых контактов автора. Только идентичность,
имя-снимок и роль.

### §122.2. `precedesJournal` — как отличить «истории нет» от «истории не было никогда»

Журнал ведётся с момента внедрения, backfill'а нет (решение П3). Признак вычисляется сервером: у
записи **нет события `Created`** ⇒ запись создана до внедрения журнала.

| Случай | Ответ | Что делает интерфейс |
|---|---|---|
| Запись создана до внедрения и с тех пор не менялась | `events: []`, `precedesJournal: true` | **блок истории не показывается вовсе** — ни рамки, ни надписи «автор неизвестен» |
| Запись создана до внедрения, но потом перенесена/отменена | `events: [...]`, `precedesJournal: true` | блок показывается + **одна строка пояснения**, что журнал ведётся с определённого момента и более ранние действия в нём не отражены |
| Запись создана после внедрения | `events: [...]`, `precedesJournal: false` | обычный блок |

### §122.3. Ошибки и правило неразглашения

| Код | Тело | Когда |
|---|---|---|
| 401 | пустое | нет токена |
| **404** | пустое | запись не существует **ИЛИ** вызывающий не персонал этой компании |

⚠️ **404, а не 403 — намеренно.** Клиент, запрашивающий историю **собственной** записи, получает
**404**: журнал ему не отдаётся ни в каком виде (П8), и код ответа при этом не должен работать
оракулом «существует ли запись с таким id». Тот же принцип уже соблюдён в `GetSlots` — не сломать.

## §123. `BookingDto` — новое поле `historyEventCount`

Одно добавочное поле, чтобы карточка могла решить, показывать ли блок истории, **не загружая её**.

```jsonc
{ "…": "…", "historyEventCount": 3 }
```

| Эндпоинт | Значение |
|---|---|
| `GET /api/bookings/master` | число событий (одним группирующим запросом на всю страницу, не N+1) |
| `GET /api/bookings/{id}` | число событий — **только если** вызывающий персонал этой компании или SuperAdmin |
| `GET /api/bookings/client` | **всегда `null`** |
| `POST /api/bookings` (ответ) | **всегда `null`** |

`null` означает «сервер не считал», а не «событий нет». Клиентские ответы поля не получают **вообще**
— это не фильтрация на фронте, а незаполненное сервером поле (П8).

**Правило для интерфейса:** кнопка/блок «История» рисуется **только** при `historyEventCount > 0`.
Списки записей историю заранее **не загружают** — только по разворачиванию карточки.

## §124. `GET /api/companies/{id}/masters` — ИЗМЕНЁН

| Параметр | Тип | Смысл |
|---|---|---|
| `serviceId` | uuid | как раньше (пустая строка = «без фильтра», не-uuid = 400) |
| `includeHidden` | bool | **НОВЫЙ.** Включить сотрудников с `providesServices = false` |

`includeHidden=true` **honored только для персонала этой компании и SuperAdmin**. Для всех остальных
он молча игнорируется — фильтр «виден клиентам» остаётся. Публичная выдача не меняется ни на строку.

Ответ — элементы `MasterPublicDto` с новым полем:

```jsonc
{ "userId": "…", "firstName": "Иван", "lastName": "Петров",
  "avatarUrl": null, "bio": null, "providesServices": false }
```

При анонимном/клиентском вызове `providesServices` всегда `true` (иначе элемент не попал бы в
выдачу). Интерфейс персонала использует поле, чтобы подписать, почему этого мастера не видно
клиентам.

## §125. Фото салона: общие правила блока

- **Публичные.** Отдаются анонимно как обычная статика `/uploads/companies/…` (решение П6).
- **До 10 на компанию** (П4). Первое по порядку (`position = 0`) — **обложка**.
- **Файл ≤ 5 МБ**, форматы — те, что продукт принимает сейчас (JPEG/PNG/WEBP), **тип определяется по
  сигнатуре байт**, не по имени и не по `Content-Type`.
- **Метаданные, включая геолокацию, не сохраняются** — изображение ре-энкодится, как везде.
- **Квоту `PhotoQuotaMb` не расходуют** и **не подпадают** под `ClientNotePhotoDays` /
  `photo-retention-cleanup` (П5). Исчерпанная квота клиентских фото на загрузку фото салона
  **не влияет**.
- **Согласия не собираем** (П7): экрана и чекбокса в потоке загрузки нет, `ConsentRecord` не пишется.
- **Права:** только **владелец компании** и **SuperAdmin**. Мастер фото салона не меняет.
- Лимит запросов — политика `uploads`.

Каждая фотография в ответах:

```jsonc
{
  "id": "…",
  "url": "/uploads/companies/9f1c….jpg",       // полноразмерная, до 1600 px
  "thumbnailUrl": "/uploads/companies/3a7b….jpg", // миниатюра, до 480 px
  "width": 1600, "height": 1067,
  "position": 0,
  "isCover": true                               // = (position == 0), для удобства
}
```

Порядок в любом списке — по `position`, при равенстве — по времени создания (детерминирован всегда).

## §127. `POST /api/companies/{id}/photos` — НОВЫЙ

`multipart/form-data`, поле файла — **`file`** (так же, как у логотипа, аватара и картинки услуги).
`[Authorize]`, владелец компании или SuperAdmin, политика `uploads`, `RequestSizeLimit` 5 МБ.

**201 Created** + созданная `CompanyPhotoDto`. Новая фотография добавляется **в конец**
(`position = n`); обложкой она не становится, пока владелец не переставит порядок.

**Повторная загрузка того же файла** (двойной клик, ретрай) возвращает **200** и **уже существующую**
фотографию — дубликат не создаётся и лимит не расходуется (дедупликация по хешу обработанных байт).

### §127.1. Ошибки

| Код | Тело | Когда |
|---|---|---|
| 400 | `В галерее салона может быть не больше 10 фотографий` | попытка загрузить 11-ю |
| 400 | `Нужно выбрать файл для загрузки.` | файл не передан или пуст |
| 400 | `Слишком большой файл — максимум 5 МБ.` | больше 5 МБ |
| 400 | `Можно загрузить JPEG, PNG или WEBP.` | сигнатура не распознана |
| 400 | `Слишком большое изображение — попробуйте файл меньшего размера.` | слишком большие размеры |
| 400 | `Файл повреждён или это не изображение.` | не декодируется |
| 400 | `На сервере закончилось место. Попробуйте позже.` | мало места на диске |
| 401 / 403 | пустое | не авторизован / не владелец |
| 404 | пустое | компании нет |
| 413 | — | превышен `RequestSizeLimit` |
| 429 | — | политика `uploads` |

Тексты конвейера загрузки теперь по-русски **на сервере** (US-125: «сообщение по-русски объясняет
причину») — `ImageUploadService` отдаёт готовые русские формулировки, общие для всех пяти точек
загрузки в продукте. Фронт (`utils/uploadError.ts`) по-прежнему матчит их по подстроке и заменяет на
свои формулировки для конкретных сценариев (например, обе «Слишком больш…»-причины — размер файла и
размер изображения — сведены в одно сообщение); **второй словарь ошибок загрузки не заводим.**
Единственное сообщение, специфичное только для этого эндпоинта, — про лимит 10 фотографий.

## §128. `DELETE /api/companies/{id}/photos/{photoId}` и `PUT /api/companies/{id}/photos/order`

### §128.1. Удаление

`DELETE /api/companies/{id}/photos/{photoId}` → **204 No Content**.
После удаления позиции оставшихся фотографий **компактизируются** в `0..n−1` в той же транзакции:
если удалили обложку, обложкой становится следующая. Файлы с диска удаляются **после** успешного
коммита.

| Код | Когда |
|---|---|
| 204 | удалено |
| 401 / 403 | не авторизован / не владелец |
| 404 | компании нет, или фотографии нет, или фотография принадлежит **другой** компании |

### §128.2. Порядок

`PUT /api/companies/{id}/photos/order`

```jsonc
{ "photoIds": ["id3", "id1", "id2"] }
```

Список — **полная перестановка** текущих фотографий компании: столько же элементов, те же
идентификаторы, без повторов. Первый в списке становится обложкой.

**200 OK** + `CompanyPhotoDto[]` в новом порядке.

| Код | Тело | Когда |
|---|---|---|
| 400 | `Список должен содержать все фотографии салона ровно по одному разу` | не полная перестановка: не тот состав, повтор, чужой id |
| 401 / 403 | пустое | |
| 404 | пустое | компании нет |

Частичная перестановка отвергается намеренно: полный список делает операцию идемпотентной и снимает
вопрос «что произошло с теми, кого не упомянули».

## §129. `CompanyDto` — фотографии приезжают вместе с компанией

Три добавочных поля. Фотографии **не добавляют запросов** к API на публичной странице (требование
производительности).

| Поле | Тип | Смысл |
|---|---|---|
| `coverPhotoUrl` | `string \| null` | полноразмерная обложка |
| `coverThumbnailUrl` | `string \| null` | миниатюра обложки |
| `photos` | `CompanyPhotoDto[] \| null` | весь список в порядке показа |

Что где заполняется:

| Эндпоинт | `cover*` | `photos` |
|---|---|---|
| `GET /api/companies/{slug}` (публичная страница) | да | **да** |
| `GET /api/companies` (каталог) | да | **`null`** |
| `GET /api/companies/my`, `/member` | да | `null` |
| `GET /api/companies/{id}` и прочие | да | `null` |

`photos: null` означает «на этом эндпоинте список не отдаётся», а `[]` — «фотографий нет».
В каталоге список не отдаётся намеренно: сотня салонов × 10 фото — это тысяча строк ради картинок,
которых там не видно. Обложки достаточно.

Обложки на списковых эндпоинтах считаются **одним батчевым запросом** на всю страницу, не по одному
на компанию.

## §130. Чего цикл 10 НЕ меняет (важно не «починить заодно»)

- **`GET /api/bookings/slots`** — ни параметров, ни формы ответа. `manual`/`extendedHours` там уже
  работают правильно; ответ остаётся голым массивом.
- **`POST /api/bookings`** — ни одного нового поля. Свобода персонала на сервере уже есть; цикл её
  только **закрепляет тестами**, а не переписывает.
- **`GET /api/bookings/occupied`**, `/cancel`, `/reschedule`, `/complete`, `/noshow`, `/mark-paid` —
  сигнатуры и коды ответов прежние. Меняется только то, что каждая из них теперь пишет строку в
  журнал в **той же транзакции** (снаружи это не видно).
- **`GET /api/bookings/client`** и карточка записи клиента в `/my-visits` — состав **не меняется**.
  Ни истории, ни автора клиент не получает (П8).
- **Уведомления.** Новые события журнала **не порождают сообщений**.
  `NotificationType.StaffBookingCreated` остаётся неиспользуемым — US-34 не в этом цикле (R8).
- **Виджет `/embed/:slug`** — галереи в нём нет (сознательно отложено); поведение записи для
  посетителя не меняется, хотя код модалки теперь общий.

## §131. Разбор ответов: что обязан проверять фронт

| Вопрос интерфейса | Единственный правильный источник |
|---|---|
| Я в режиме персонала? | `availability.staffMode` |
| Можно ли нажать день? | `status` + (`staffMode` && `scheduleState`) по таблице §121.3 |
| Какая подпись у дня? | `scheduleState` при `staffMode: true`, иначе `status` |
| Показывать ли тумблер «показать остальные часы»? | `availability.staffMode === true` |
| Показывать ли блок истории? | `booking.historyEventCount > 0` |
| Показывать ли пояснение «журнал ведётся с…»? | `precedesJournal === true` && `events.length > 0` |
| Есть ли у салона фото? | `company.photos?.length` (страница компании) или `coverThumbnailUrl` (каталог) |
| Какая фотография обложка? | `position === 0` / `isCover` |

**Ничего из этого нельзя выводить из роли в JWT, из состава `authStore` или из того, какой флаг мы
отправили в запросе.** Режим определяет сервер, и он его прямо сообщает.

## §132. Автосверка контракта (для QA)

Машиночитаемая схема существует затем, чтобы совпадение бэкенда и фронта проверялось инструментом, а
не сверкой отчётов:

```bash
# 1. Форма реализации против контракта (без ручного написания тестов)
schemathesis run contracts/cycle10/openapi.yaml \
  --base-url http://localhost:5000 --checks all

# 2. Мок для фронта, пока бэкенда ещё нет
npx @stoplight/prism mock contracts/cycle10/openapi.yaml --port 4010

# 3. Типы фронта против контракта: перегенерировать, diff обязан быть пустым
cd frontend && npm run types:api:cycle10
git diff --exit-code frontend/src/types/api-cycle10.generated.ts
```

Дополнительно к автосверке формы (она не проверяет смысл) обязательны проверки прав и режима —
матрица не-персонала из `ARCHITECTURE_CYCLE10.md` §113.1 и права ручной записи §113.2.
