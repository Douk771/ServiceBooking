# ARCHITECTURE — цикл 3 ServiceBooking: готовность к продакшену

**Вход:** `SPEC.md` цикла 3 (редакция 3, решения заказчика Р1–Р9 в §0 — окончательные, открытых
вопросов нет), `CURRENT_STATE.md` (актуален на `1c21bca` + цикл 2), `ARCHITECTURE.md`/`API_CONTRACT.md`
цикла 2 (эта ревизия их **заменяет**, сохраняя всё, что не меняется).
**Тип работ:** расширение существующей кодовой базы. Стек не выбирается заново — он **дополняется**
двумя серверными библиотеками (SPEC §7 п. 8) и одним фронтовым тулингом (линтер, US-50).
**Ветка на момент написания:** `sanitation-cycle`, база — `0492092`. Цикл с тех пор завершён и
интегрирован; работа продолжается в `develop`, а состояние цикла сохранено в
`cycle/03-production-readiness` (модель веток — [`DEPLOY.md` §0.0](DEPLOY.md)).
**Baseline, который нельзя ухудшать:** `dotnet build ServiceBooking.sln` → 0 ошибок / 0 предупреждений
(`-warnaserror`); `dotnet test ServiceBooking.Tests` → 344/344; `dotnet test ServiceBooking.UnitTests`
→ 115/115 без PostgreSQL; `npm run test:run` → 35/35; `npx tsc --noEmit` → чисто.

Документ закрывает **все двенадцать вопросов §11 SPEC** и даёт план, по которому backend-,
frontend- и devops-инженер работают параллельно по `API_CONTRACT.md`, не читая код друг друга.

### Чем этот цикл отличается от 1 и 2 — и что из этого следует для архитектуры

Цикл **не продуктовый**. Из семнадцати историй кода приложения касаются семь (US-36…US-39, US-42,
US-43, US-46, US-48, US-49), а шесть — это скрипты, конфиги и раннбуки, которые к `ServiceBooking.API`
не имеют отношения вовсе (US-40 бэкапы, US-41 smoke в CI, US-44 деплой, US-45 инфраструктура трекера,
US-47 nginx, US-51 документация). Поэтому:

1. **Разбивка задач трёхколоночная** (§17): backend / frontend / **devops**. Отдавать бэкенд-разработчику
   `pg_dump` и systemd-таймеры — способ гарантированно получить и плохой бэкап, и невыполненный
   правовой контур.
2. **Новых слоёв не заводим.** Бизнес-логика остаётся в контроллерах (`CURRENT_STATE` §2), сервисного
   слоя не появляется. Все новые чистые помощники кладутся в существующий `Services/` рядом с
   `CompanyMembership.cs` и `PhoneNormalizer.cs` — по образцу цикла 2.
3. **Единственная новая подпапка** — `ServiceBooking.API/Services/Legal/` (провайдер документов,
   опции, фильтр согласия — четыре файла одной темы, ровно как `Services/Scheduling/` в цикле 2).

## 1. Принципы цикла 3

1. **Конвенции не пересматриваются** (SPEC §7 п. 8). Primary constructors, `record`-DTO, ручной
   `MapToDto`, приватные асинхронные предикаты прав внутри контроллеров, 402 для тарифных гейтов,
   plain-text 4xx с маппером на фронте, комментарии «почему» на английском; на фронте — именованные
   экспорты, слой `src/api/<домен>.ts`, react-query, мапперы `src/utils/*Error.ts`.
2. **Новых серверных библиотек ровно две** — `Serilog.AspNetCore` и `Sentry.Serilog` (§11.1).
   Rate limiting, health-checks и `ForwardedHeaders` закрываются встроенными средствами ASP.NET Core 8.
   На фронте новых **рантайм**-зависимостей ноль; добавляется только dev-тулинг ESLint/Prettier (US-50).
3. **Ни один новый эндпоинт не делает лишнего запроса к БД в горячем пути** (SPEC §7 п. 1).
   Это прямо диктует форму проверки согласия: она работает по claim'ам токена и по значению из памяти,
   а не по запросу к таблице согласий на каждом вызове (§6.3).
4. **Персональные данные не покидают контур ни в логах, ни в трекере, ни в выгрузке.**
   Маскирование телефона — не соглашение, а код в конвейере логирования (§11.3); трекер self-hosted;
   выгрузка не раскрывает то, что закрыто моделью доступа (§7.2).
5. **Замена правового текста — эксплуатационная операция, а не релиз** (SPEC §7 п. 7). Из этого следует
   выбор §4: текст живёт файлом в примонтированном каталоге, а не в JS-бандле и не в миграции.
6. **Эксплуатирует один человек** (Р8). Каждое эксплуатационное решение проверяется вопросом «выполнимо
   ли это ночью, с телефона, по скопированной команде». Отсюда: откат без параметров, один канал
   алертов, `curl`-строка для health-check, чек-лист бэкапа на 10 минут.
7. **Ломающие миграции допустимы в последний раз.** Сервис не в продакшене (`MEMORY`), но именно этим
   циклом он к нему готовится. После цикла 3 правило меняется: см. §16.4 — это фиксируется здесь,
   потому что спрашивать будет уже поздно.
8. **Ломающих изменений контракта ровно два** (§18 `API_CONTRACT.md`): пагинация четырёх выборок и
   обязательный флаг согласия при регистрации. Всё остальное аддитивно.

## 2. Стек: что добавляется и почему именно это

| Что | Решение | Обоснование через задачу |
|---|---|---|
| Структурное логирование | **`Serilog.AspNetCore` 8.x** | Де-факто стандарт .NET; одна библиотека даёт JSON в stdout + файл с ротацией + `UseSerilogRequestLogging` с готовым набором полей запроса. Альтернатива «расширить стандартный `ILogger`» требует руками писать и JSON-форматтер, и ротацию, и middleware логирования запроса — это те же два дня, но свой код |
| Трекер ошибок (клиентская часть) | **`Sentry.Serilog` 4.x** | Sink к уже выбранному Serilog вместо второй параллельной пайплайны `Sentry.AspNetCore`; DSN пуст → sink не регистрируется, приложение работает без трекера (SPEC US-45 п. 8) |
| Трекер ошибок (сервер) | **GlitchTip**, self-hosted, docker-compose | Р6 оставил выбор между GlitchTip и self-hosted Sentry. Self-hosted Sentry — это ~20 контейнеров, Kafka, ClickHouse, Redis, официальный минимум 16 ГБ RAM: на VPS с одним экземпляром приложения он потребляет больше, чем сам продукт, и обслуживается сложнее, чем продукт. GlitchTip — Django + PostgreSQL + Redis, ~1 ГБ, и **говорит по протоколу Sentry**, то есть стандартный SDK и DSN работают без изменений. При одном эксплуатанте (Р8) это решающий довод |
| Линтер C# | **`.editorconfig` + `dotnet format`** (в SDK) | Нулевая новая зависимость, шаг в существующий джоб `backend` |
| Линтер фронта | **ESLint 9 (flat config) + Prettier** | Dev-зависимости, в рантайм-бандл не попадают |
| Rate limiting, health-checks, `ForwardedHeaders` | **встроенные в ASP.NET Core 8** | SPEC US-42 п. 1 и US-43 п. 6 запрещают новые библиотеки явно |
| Markdown/HTML-рендер правовых текстов на фронте | **не вводится** | Текст приезжает готовым HTML-фрагментом (§4.2) — новая фронтовая зависимость не нужна |

### 2.1 Что библиотекой намеренно **не** становится

- **Prometheus/Grafana/OpenTelemetry** — вне скоупа (SPEC §8.2). Один экземпляр, десятки салонов,
  один эксплуатант: логи + трекер ошибок закрывают вопрос «что случилось», метрики отвечали бы на
  вопрос «сколько», который сейчас никто не задаёт.
- **Библиотека валидации/санитизации HTML** — правовой текст пишет команда и кладёт оператор на
  сервер; это тот же уровень доверия, что `appsettings.Production.json`. Вместо санитайзера —
  одна проверка провайдера (§4.4), которая отказывается публиковать документ со скриптом.
- **Библиотека архивации для выгрузки данных** — выгрузка синхронная и отдаёт один JSON (§7.2).
- **Hangfire/Quartz для бэкапов** — бэкап снимает дамп СУБД и содержимое docker volume; делать это
  изнутри процесса приложения означает дать приложению доступ к docker-сокету. Бэкап — задача
  **хоста** (§12.1).

## 4. Правовые документы: где живёт текст (ответ на §11 п. 1)

### 4.1 Решение: **файлы в каталоге, примонтированном к контейнеру; метаданные — манифестом рядом**

Рассматривались три варианта из SPEC §11 п. 1:

| Вариант | Замена текста | Цена реализации | Вердикт |
|---|---|---|---|
| Статические файлы рядом с фронтом (в бандле) | требует пересборки фронта и выкладки | ~0 | **Нет** — прямо нарушает US-36 п. 5 |
| Таблица в БД + админский экран публикации | минуты | +1,5 дня: сущность, миграция, CRUD, экран SuperAdmin, права, тесты | **Нет** — экран публикации это продуктовая фича, а тексты меняются два-три раза за жизнь продукта |
| **Файлы в примонтированном каталоге + манифест** | минуты: `scp` файла и (опционально) правка одной строки JSON | ~0,3 дня: провайдер + кэш + контроллер | **Да** |

**Устройство.** Каталог `Legal:Root` (по умолчанию — `<ContentRoot>/App_Data/legal`):

```
App_Data/legal/
├── legal.json      манифест: версии, даты, флаги, имена файлов
├── privacy.html    текст политики (фрагмент HTML: <h2>, <p>, <ul>, <table>)
└── terms.html      текст пользовательского соглашения
```

В репозитории этот каталог **закоммичен** (в отличие от `App_Data/private-uploads`, который в
`.gitignore`) — там лежат черновики US-52. Это даёт три вещи разом: Development и `Testing` работают
из коробки без внешних файлов; тексты живут под контролем версий и проходят ревью как код; сведения
для РКН формируются из того же источника.

На боевом контуре `docker-compose.prod.yml` монтирует хостовый каталог **поверх** запечённого в образ:

```yaml
- ./legal:/app/App_Data/legal:ro   # bind-mount, НЕ named volume: файлы должны быть видны и правимы с хоста
```

Замена текста после юридической вычитки = `scp privacy.html`, правка `legal.json` (новая версия, дата,
`isDraft: false`, `changeKind: "Material"`) и **ничего больше**: провайдер подхватывает изменение сам
(§4.3). Пересборки, передеплоя и рестарта не требуется. Именно это и есть критерий приёмки US-36 п. 5,
сформулированный как результат.

### 4.2 Формат манифеста

```json
{
  "documents": [
    {
      "type": "Privacy",
      "version": "2026-09-15-draft",
      "effectiveFrom": "2026-09-15",
      "isDraft": true,
      "changeKind": "Material",
      "title": "Политика обработки персональных данных",
      "file": "privacy.html"
    },
    { "type": "Terms", "version": "2026-09-15-draft", "...": "..." }
  ]
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `type` | `Privacy` \| `Terms` | Ключ документа. Ровно два, третьего не бывает — enum `LegalDocumentType` |
| `version` | строка ≤ 64 | Единственный идентификатор редакции. Попадает в запись согласия и в `Booking`. Формат — свободный, рекомендуется `YYYY-MM-DD[-draft]` |
| `effectiveFrom` | `YYYY-MM-DD` | Дата вступления в силу, показывается на странице |
| `isDraft` | bool | Взводит плашку и обязывает суффикс `-draft` в версии (§4.4) |
| `changeKind` | `Material` \| `Editorial` | Режим смены версии (US-37 п. 4). **Отсутствует или не распознан → `Material`** — безопасное умолчание |
| `title` | строка | Заголовок страницы |
| `file` | имя файла | Только имя, без путей; провайдер проверяет containment в `Legal:Root` |

**Текст — HTML-фрагмент, а не Markdown.** Markdown потребовал бы рендерера на фронте (новая
рантайм-зависимость) или на бэке (новая NuGet-зависимость) — обе избыточны ради двух документов.
Фрагмент вставляется в стилизованный контейнер через `dangerouslySetInnerHTML`. Граница доверия
явная и записана здесь: **содержимое `Legal:Root` — конфигурация оператора того же уровня, что
`appsettings.Production.json`**; пользователь туда ничего положить не может.

### 4.3 Провайдер: singleton с кэшем и ленивой перезагрузкой

`Services/Legal/LegalDocumentProvider.cs` — singleton. Держит распарсенный манифест и тексты в памяти.
Перед выдачей проверяет `File.GetLastWriteTimeUtc(legal.json)`, но не чаще, чем раз в
`Legal:ReloadSeconds` (умолчание 30). Изменился mtime — перечитывает манифест и все файлы одним
проходом, атомарно подменяя ссылку на неизменяемый снимок (`LegalSnapshot`).

Почему не `FileSystemWatcher`: он ненадёжен на bind-mount'ах в Docker (события inotify не всегда
доходят через границу монтирования) — а тихо не сработавший watcher означает «оператор заменил
текст, а продукт показывает старый», то есть ровно тот отказ, который история должна исключить.
Опрос mtime раз в 30 секунд стоит одного `stat` и не может «не сработать».

Стоимость чтения снимка в горячем пути — разыменование поля. Проверка согласия (§6.3) обращается
именно к нему, поэтому это важно.

### 4.4 Валидация при загрузке и поведение при ошибке

Провайдер отказывается публиковать документ, если: файл отсутствует; `version` пуста или длиннее 64;
`isDraft: true`, а версия не оканчивается на `-draft` (US-36 п. 3 требует, чтобы черновик был виден
по строке версии); в тексте встречается `<script` или `on…=`-атрибут (§4.2 — не санитайзер, а
предохранитель от опечатки оператора).

| Окружение | Манифест невалиден или отсутствует |
|---|---|
| `Production` | **Fail-fast на старте** (§13): без действующих документов сервис не имеет права принимать регистрации. Если каталог сломали уже после старта — предыдущий валидный снимок остаётся в памяти, в лог пишется `Error` (доедет до трекера), новый не применяется |
| `Development` / `Testing` | Стартуем, отдаём 503 на `GET /api/legal/*`, проверка согласия пропускается (иначе тесты, не касающиеся правового контура, начали бы падать) |

Фронт при 503 показывает состояние ошибки со ссылкой «попробовать снова» — пустой страницы быть
не должно (US-36 п. 8).

**Решение заказчика (пост-релиз, code review цикла 3): старт с `isDraft: true` в Production разрешён**
— черновик не является причиной fail-fast сам по себе (это не то же самое, что «манифест невалиден»
выше). Продукт не запирает согласие черновой редакцией молча: суффикс `-draft` сохраняется как есть в
`UserConsent.Version`/`Booking.Consent*Version` (§5.1/5.2 — это ровно `doc.Version`, копия строки из
манифеста), и `isDraft` отдаётся наружу в `GET /api/legal/documents[/{type}]` (`LegalDocumentMetaDto`/
`LegalDocumentDto`), чтобы фронт мог показать плашку «черновик» рядом с текстом.

### 4.5 Индексация и SEO

Страницы отдаются SPA-роутером по `/privacy` и `/terms`, текст приезжает по API. Поисковики,
исполняющие JS, документ увидят; предрендер в цикл не входит. `/privacy` и `/terms` добавляются
в `robots.txt` как разрешённые явно, и в подвал ставится обычная `<a href>` (не `onClick`), чтобы
ссылка была ссылкой для краулера. Этого достаточно: требование US-36 п. 8 — «индексируются», а не
«ранжируются».

## 5. Модель данных цикла (ответ на §11 пп. 2, 4, 12)

Три изменения, ни одно из них не трогает существующие связи.

### 5.1 `UserConsent` — новая сущность

```
UserConsent
  Id            Guid, PK
  UserId        string, FK → AspNetUsers, Cascade
  DocumentType  LegalDocumentType (Privacy | Terms), int в БД
  Version       string(64)
  AcceptedAtUtc DateTime
  уникальный индекс (UserId, DocumentType)
```

**Почему таблица, а не четыре колонки на `AppUser`.** Документов два и их версии независимы; колонки
дали бы `PrivacyVersion`, `PrivacyAcceptedAt`, `TermsVersion`, `TermsAcceptedAt` — четыре поля,
которые при появлении третьего документа превращаются в шесть и требуют миграции `AspNetUsers`.
Таблица с уникальным ключом `(UserId, DocumentType)` описывает то же самое одной строкой на документ
и расширяется без изменения формы. Стоимость — одно `INSERT … ON CONFLICT DO UPDATE` при регистрации
и при принятии; в горячем пути таблица **не читается вовсе** (§6.3).

**Хранится последнее принятое согласие, журнал не ведётся** (SPEC §3.3 п. 2 разрешает). Строка
перезаписывается при принятии новой редакции. Если журнал когда-нибудь понадобится — снимается
уникальный индекс и добавляется выборка «последняя по `AcceptedAtUtc`»; форма таблицы не меняется.

### 5.2 `Booking` — три новых поля

```
ConsentPrivacyVersion  string(64)?   версия политики, действовавшая в момент записи
ConsentTermsVersion    string(64)?   версия соглашения, действовавшая в момент записи
ConsentAcceptedAtUtc   DateTime?     момент
ClientDeleted          bool          = false; клиент удалил аккаунт, строка обезличена
```

- Первые три заполняет **сервер** из снимка провайдера, значения из тела запроса не принимаются
  никогда — иначе «доказательство» подделывается клиентом. Заполняются на **гостевом пути**
  (конклюдентное согласие, US-37 п. 3). На ручной записи персонала остаются `null`: салон собрал
  согласие вне продукта, и записывать сюда версию значило бы утверждать то, чего не было.
- Ретроспективно не переписываются никогда (US-37 п. 6) — в коде нет ни одного пути, который бы их
  обновлял после создания записи.
- `ClientDeleted` нужен, чтобы обезличенный визит выглядел обезличенным, а не битым: без него
  строка с `ClientId = null` и пустым `GuestName` неотличима от повреждения данных, и UI показал бы
  пустое место. Один bool вместо строки-заглушки в `GuestName` — потому что заглушка в имени гостя
  подмешалась бы в группировку клиентской базы (`MastersController.GetClients` группирует по
  `GuestPhone`) и в отчёты.

### 5.3 `AppUser` — одно новое поле

```
DeletedAtUtc  DateTime?   аккаунт удалён пользователем; строка оставлена как надгробие (§7.4)
```

### 5.4 Чего в модели данных **не появляется**

- **Договор поручения обработки** — Р1: бумажный документ, не сущность (SPEC §8.1).
- **Сущность «правовой документ» в БД** — §4.1.
- **Журнал выгрузок данных** — частота ограничивается rate limiter'ом в памяти (§9.4); строка в БД
  на каждую выгрузку не нужна ни для одного сценария этого цикла.
- **`Company.TimeZoneId`** — US-51, осознанно (SPEC §6.5).

## 6. Согласие: как оно записывается и как проверяется (ответ на §11 п. 2)

### 6.1 Регистрация

`RegisterDto` получает поле `bool AcceptedLegal`. Сервер: `false`/отсутствует → **400**
`"Consent to the Terms of Service and the Privacy Policy is required."`. Клиентская валидация
(неактивная кнопка) — удобство, а не защита; тест `LEG-` бьёт прямо в API мимо формы.

При успехе, в той же транзакции, что и создание пользователя, пишутся две строки `UserConsent`
с текущими версиями из снимка провайдера и одним `AcceptedAtUtc`.

### 6.2 Гостевая запись

`POST /api/bookings` по гостевому пути заполняет три поля `Booking` (§5.2) из того же снимка.
Дисклеймер под кнопкой — работа фронта; тела запроса это не касается, новых полей в
`CreateBookingDto` **не появляется**.

### 6.3 Проверка «принята ли действующая редакция» — без запроса к БД

Требование SPEC §11 п. 2: проверка не должна стоить лишнего запроса к БД на каждый вызов API.
Решение — **версии согласия едут claim'ами в JWT и сравниваются со снимком из памяти**.

1. `TokenService.GenerateToken` добавляет два claim'а: `lcp` (принятая версия политики) и `lct`
   (принятая версия соглашения). Значения берутся из `UserConsent` в момент выдачи токена, то есть
   при регистрации, логине и при принятии новой редакции.
2. `Services/Legal/LegalConsentFilter.cs` — глобальный `IAsyncAuthorizationFilter` (регистрируется
   `options.Filters.Add<…>()` в `AddControllers`). На каждом аутентифицированном запросе сравнивает
   claim'ы с `LegalDocumentProvider.Current`. Обе стороны сравнения — в памяти, БД не задействована.
3. Ветвление:

| Состояние | `changeKind` действующей редакции | Ответ |
|---|---|---|
| Версии совпали | — | пропуск |
| Не совпали | `Editorial` | **пропуск**; баннер показывает фронт, узнавая о расхождении из `GET /api/legal/consent-status` |
| Не совпали | `Material` | **451** + plain text; запрос до контроллера не доходит |
| Запрос анонимный | — | пропуск (у гостя согласие фиксируется в самой записи) |
| Маршрут в allow-list | — | пропуск |

4. **Allow-list** (иначе пользователь заперт — SPEC §3.5 п. 9): всё под `/api/legal/*`, `/api/health/*`,
   `POST /api/auth/*`, `GET /api/profile`, `POST /api/profile/delete-account`,
   `GET /api/profile/export`. Выгрузка добавлена сверх буквы SPEC осознанно: право на копию своих
   данных не должно зависеть от согласия с новой редакцией — см. §19.4.
5. **Почему claim, а не запрос к таблице.** Claim может «отстать» только в одном направлении:
   пользователь принял новую редакцию, а токен ещё старый. Этот случай закрыт тем, что
   `POST /api/legal/accept` **выдаёт новый токен** — ровно как логин. Обратный случай (в БД старая
   версия, в токене новая) невозможен: claim пишется только из записанного согласия.
6. **Взаимодействие с `OnTokenValidated`.** Роли и `SecurityStamp` перечитываются из БД на каждом
   запросе (`CURRENT_STATE` §4.1) — это существующий запрос, и мы к нему **ничего не добавляем**.
   Соблазн дочитать там же `UserConsent` отвергнут: это превратило бы один запрос в два на каждый
   аутентифицированный вызов ради данных, которые меняются два раза за год.

### 6.4 Принятие новой редакции

`POST /api/legal/accept` с телом `{ "privacyVersion": "...", "termsVersion": "..." }`. Версии в теле
сверяются с действующими; расхождение → 409 (гонка: пока пользователь читал, текст заменили ещё раз).
Совпали — upsert двух строк `UserConsent` с новым `AcceptedAtUtc` и **выдача нового токена**.

### 6.5 Тарифы, роли и согласие не смешиваются

`LegalConsentFilter` работает до контроллеров и после аутентификации; он не знает ни про роли, ни
про тарифы, и не заменяет собой `[Authorize]`. 451 никогда не выдаётся вместо 401/403: фильтр
пропускает анонимные запросы, за них отвечает пайплайн авторизации.

## 7. Права субъекта: выгрузка и удаление (ответ на §11 пп. 3, 4)

### 7.1 Форма выгрузки: синхронный JSON, без фоновой генерации

`GET /api/profile/export` → `200 application/json` + `Content-Disposition: attachment; filename="servicebooking-export-<дата>.json"`.

Обоснование: очереди в продукте нет (`CURRENT_STATE` §5.1 п. 1), объём данных одного клиента — это
десятки записей и заметок, то есть десятки килобайт. Фоновая генерация потребовала бы задачи,
хранилища артефакта, срока его жизни и эндпоинта скачивания — четыре новые сущности ради ответа,
который собирается за один запрос. Защита от нагрузки — жёсткий rate limit (§9.4), а не асинхронность.

### 7.2 Состав выгрузки

| Раздел | Что входит | Комментарий |
|---|---|---|
| `profile` | имя, телефон (канонический), email, `avatarUrl`, `createdAt` | — |
| `consent` | по каждому документу: версия, момент | US-37 |
| `memberships` | компании, где состоит: имя компании, роль, дата вступления | без внутренних id чужих сущностей |
| `bookings` | дата, время, услуга (имя), компания (имя), мастер (имя), статус, цена, статус оплаты, причина отмены | id брони включается — она своя |
| `reviews` | дата, компания, рейтинг, текст | свой текст |
| `notesAboutMe` | по каждой: компания, дата, **есть ли фото и сколько** | **без текста заметки** (US-38 п. 3) |
| `photosOfMe` | по каждой: компания, дата, размер | **без содержимого** (US-38 п. 2) |
| `notice` | человекочитаемый текст: что в файле нет и к кому обращаться | US-38 п. 5 |

**Ключевые ограничения, зафиксированные архитектурно:**
- Содержимое фото не выдаётся, потому что модель доступа цикла 2 (`GET /api/client-notes/photos/{id}`
  → 404 всем, кроме персонала компании; **SuperAdmin получает 403**) — единственное место в продукте,
  где ограничение доступа сильнее роли. Выгрузка, отдающая эти же байты клиенту, обошла бы её сбоку.
- Текст заметки не выдаётся: это суждение сотрудника салона о клиенте, и отдача его субъекту сделала
  бы заметки бесполезными (мастер перестанет их писать), не добавив субъекту данных о себе.
- Обе трактовки уходят на юридическую вычитку (SPEC §10.2) и меняются **составом ответа**, а не
  архитектурой.
- Никаких `Id` чужих сущностей и никаких хешей (`SecurityStamp`, `PasswordHash`, `ContentHash`
  фотографий) в ответе нет — проверяется тестом `LEG-`.

### 7.3 Форма удаления: `POST /api/profile/delete-account`

POST, а не DELETE: требуется тело с текущим паролем, а `DELETE` с телом плохо поддержан прокси и
клиентами; и это ровно тот же жест, что уже существующий `POST /api/profile/change-phone`
(подтверждение паролем) — конвенция уже есть, изобретать вторую незачем.

Гейты по порядку:
1. Пароль не совпал → **400** `"Неверный текущий пароль"` (дословно как в `change-phone`).
2. За пользователем числится компания (`Companies.Any(c => c.OwnerUserId == me)`) → **409**
   с человеческим текстом (US-39 п. 4).
3. Иначе — удаление.

### 7.4 Что физически происходит: **строка `AppUser` остаётся надгробием**

Это единственное решение цикла, расходящееся с буквой SPEC (US-39 п. 2 говорит «удаляется учётная
запись Identity»). Обоснование — жёсткое, из схемы БД, а не из вкуса:

| FK на `AppUser` | Поведение | Что было бы при физическом `DELETE` |
|---|---|---|
| `Booking.Master` | **Restrict** | Удаление мастера **невозможно** — падает на FK |
| `Review.Master` | **Restrict** | То же |
| `Company.Owner` | **Restrict** | То же (закрыто гейтом 409, но остаётся для бывших владельцев) |
| `MailLog.SentBy` | **Restrict** | Любой, кто хоть раз отправлял рассылку, неудаляем |
| `ClientNote.Master` | **Cascade** | **Удалились бы все заметки, написанные этим мастером о чужих клиентах** — потеря данных салона |
| `WorkingHours.Master`, `WeeklyScheduleTemplate.Master` | Cascade | Расписание исчезает — для мастера это ожидаемо, но неотделимо от строки выше |

То есть «просто удалить строку» либо не работает (Restrict), либо уносит данные салона (Cascade
на `ClientNote`), что прямо запрещено US-39 п. 3 и риском R4.

**Что делает удаление:**

```
транзакция:
  1. UserConsent (мои)                              → DELETE
  2. ClientNote где ClientId = me ИЛИ GuestPhone = мой канонический телефон
       → собрать storage-ключи ClientNotePhoto (каскад заметки), затем DELETE заметок
  3. Booking где ClientId = me      → ClientId = null, GuestName/Phone/Email = null,
                                       ClientDeleted = true, Notes = null
     Booking где GuestPhone = мой   → то же (гостевые записи, сделанные до регистрации)
  4. Review где ClientId = me       → ClientId = null, ReviewerName = "Удалённый пользователь"
                                       (рейтинг и текст остаются: это отзыв о салоне)
  5. CompanyMember где UserId = me  → DELETE, затем IdentityRoleSync (§8) под company-members-локом
  6. AppUser (я):
       FirstName = "Удалённый", LastName = "пользователь", Email = null, PhoneNumber = null,
       UserName = "deleted-" + Id, NormalizedUserName/NormalizedEmail пересчитаны,
       PasswordHash = null, AvatarUrl = null, DeletedAtUtc = now,
       LockoutEnabled = true, LockoutEnd = DateTimeOffset.MaxValue,
       SecurityStamp = новый  ← инвалидирует все выданные токены немедленно
коммит
после коммита: FileStorage.DeletePrivate(ключи фото), FileStorage.DeletePublic(старый avatarUrl)
```

Почему это удовлетворяет требованиям:
- **ПДн не остаётся**: имени, телефона, email, аватара, заметок о нём и его фотографий нет. Строка
  без персональных данных — не персональные данные, а технический якорь для FK.
- **Логин невозможен**: `PasswordHash = null` + вечный lockout + `UserName` больше не телефон.
- **Старый токен не проходит**: смена `SecurityStamp` ломает сверку в `OnTokenValidated` — механизм
  существует с цикла 1, и US-39 п. 7 требует его **проверить**, а не предположить: это отдельный тест.
- **Телефон освобождается**: `UserName` уходит из-под уникального индекса Identity, и по этому номеру
  можно зарегистрироваться заново — новым, чистым аккаунтом.
- **Отчёты салона целы**: визиты на месте со снимками цены и комиссии, заметки мастера о **других**
  клиентах не тронуты.
- **Порядок «БД → файл»** соблюдён (конвенция цикла 2): худший исход — осиротевший файл, который
  подметает `photo-retention-cleanup`.

Формулировка в правовом тексте (US-52) должна описывать именно это: «учётная запись удаляется,
персональные данные стираются; обезличенные сведения о визитах сохраняются у салона».
Расхождение «текст обещает физическое удаление строки, продукт делает обезличивание» было бы
дефектом US-52 (§3.2 п. 5 SPEC).

### 7.5 Что удаление НЕ делает

- Не трогает `Booking`, где пользователь был **мастером** (это данные салона).
- Не трогает заметки, **написанные** им как мастером о других клиентах.
- Не трогает `MailLog`, `SubscriptionChangeLog` — там нет его ПДн, только ссылка-идентификатор.
- Не удаляет компанию (гейт 409).

## 8. Пересчёт Identity-ролей (ответ на §11 п. 5)

### 8.1 Дыра, как она есть сегодня

`CompaniesController.AddMember` (стр. 407–408) и `CreateCompany` (стр. 222–223) роль **добавляют**;
`RemoveMember` (стр. 436–446) её **не убирает**. `AdminController.SetOwner` (стр. 277–278) добавляет
роль новому владельцу и не снимает со старого. Роли перечитываются из БД на каждом запросе, значит
исправление подействует немедленно — но и дыра работает так же надёжно.

### 8.2 Единственная функция

`ServiceBooking.API/Services/IdentityRoleSync.cs` — статический класс рядом с `CompanyMembership.cs`
(та же природа: одна SQL-истина с одним именем, не сервисный слой).

```csharp
public static class IdentityRoleSync
{
    /// Recomputes the Identity roles this user is entitled to purely from their CompanyMember rows.
    /// Never touches Client (base role of every account) or SuperAdmin (owned solely by
    /// PUT /api/admin/users/{id}/roles). Call inside the same transaction as the membership change.
    public static Task SyncAsync(AppDbContext db, UserManager<AppUser> users, string userId);
}
```

Алгоритм:
1. `SELECT DISTINCT Role FROM CompanyMembers WHERE UserId = @userId` — один запрос.
2. Желаемое множество ⊆ `{ "Master", "CompanyOwner" }`.
3. Текущее множество из `userManager.GetRolesAsync`, пересечённое с тем же множеством.
4. Добавить недостающие, снять лишние. `Client` и `SuperAdmin` не входят в область — их значения не
   читаются и не пишутся (US-46 пп. 3, 4).

### 8.3 Все точки вызова, поимённо

| Точка | Файл | Что было | Что станет |
|---|---|---|---|
| Создание компании | `CompaniesController.CreateCompany` | `IsInRoleAsync` + `AddToRoleAsync` инлайном | `SyncAsync` после `db.CompanyMembers.Add` |
| Добавление участника | `CompaniesController.AddMember` | то же | `SyncAsync` |
| Удаление участника | `CompaniesController.RemoveMember` | **ничего** | `SyncAsync` — суть истории |
| Смена владельца компании | `AdminController.SetOwner` | `AddToRoleAsync` новому | `SyncAsync` для **обоих** — старого и нового (US-46 п. 6) |
| Удаление аккаунта | `ProfileController.DeleteAccount` | — | `SyncAsync` после удаления членств (§7.4 шаг 5) |
| `PUT /api/admin/users/{id}/roles` | `AdminController.UpdateRoles` | ручное множество | **не вызывает `SyncAsync`** — §8.5 |

Важно: `SetOwner` меняет `Company.OwnerUserId`, но строку `CompanyMember` с ролью `CompanyOwner`
он сегодня **не переносит**. Задача T-B2 обязана привести их в соответствие в той же транзакции
(снять `CompanyOwner`-членство у старого, завести/повысить у нового), иначе пересчёт по членствам
даст неверный результат — это находка ревью, зафиксированная в §19.3.

### 8.4 Конкурентность

Пересчёт идёт **в той же транзакции**, что и изменение `CompanyMember`, под уже принятым в проекте
`AdvisoryLock.AcquireAsync(db, $"company-members:{companyId}")` (US-46 п. 5). Лок уже используется
в `AddMember` для лимита `MaxEmployees` — `RemoveMember` и `SetOwner` его получают впервые, и это
единственное расширение области блокировки в цикле.

Тонкость: `UserManager` пишет в `AspNetUserRoles` через тот же `AppDbContext`, значит попадает в ту
же транзакцию — отдельного обращения к БД вне транзакции не возникает. Это надо проверить на ревью
явным пунктом: `AddToRoleAsync` вызывает `SaveChangesAsync` внутри себя, поэтому порядок операций
должен быть «изменить членства → `SaveChangesAsync` → `SyncAsync` → commit».

### 8.5 Уже рассинхронизированные данные и `PUT /api/admin/users/{id}/roles`

**Существующая рассинхронизация чинится миграцией данных** `ResyncIdentityRoles` (§16.3): SQL,
удаляющий строки `AspNetUserRoles` для `Master`/`CompanyOwner` там, где нет соответствующего
`CompanyMember`, и добавляющий недостающие. `Client` и `SuperAdmin` не трогаются. Проект не в
продакшене, данных мало, риск нулевой; но написать это надо один раз и в миграции, а не «руками
на сервере», иначе стенд и прод разъедутся.

**`UpdateRoles` намеренно остаётся ручным.** Это инструмент SuperAdmin'а «поставить произвольное
множество ролей»; прогонять его через `SyncAsync` означало бы, что админ не может выдать роль
`Master` человеку без членства — а именно так сейчас чинят частные случаи. Цена: админ может
вручную создать состояние, которое следующее изменение членства перезапишет. Это записано
комментарием в коде и строкой в `API_DOCUMENTATION.md` — предсказуемое поведение, а не сюрприз.

## 9. Rate limiting за прокси (ответ на §11 п. 6)

### 9.1 Реальный IP: `ForwardedHeaders` с доверенными сетями, без умолчаний

Топология: браузер → nginx (хост) → `127.0.0.1:5000` → контейнер `api`. Контейнер видит
не адрес nginx, а адрес шлюза docker-сети, и он **зависит от того, какую подсеть compose выдал**.
Отсюда конфигурация, а не константа:

```csharp
// ForwardedHeaders: KnownNetworks/KnownProxies ship with loopback pre-trusted, which is exactly the
// address every request arrives from inside this container — trusting the default set would mean
// trusting X-Forwarded-For from anyone who can reach the port. Clear both, then add only what the
// operator declared.
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    o.ForwardLimit = 1;                 // exactly one hop: nginx. More hops = spoofable chain.
    o.KnownNetworks.Clear();
    o.KnownProxies.Clear();
    // "ForwardedHeaders:TrustedNetworks": ["172.16.0.0/12"] — the docker bridge, per DEPLOY.md
    foreach (var cidr in config.GetSection("ForwardedHeaders:TrustedNetworks").Get<string[]>() ?? [])
        o.KnownNetworks.Add(IPNetwork.Parse(cidr));
});
app.UseForwardedHeaders();  // FIRST in the pipeline, before UseRateLimiter and before logging
```

Порядок в пайплайне критичен: `UseForwardedHeaders()` идёт **первым**, до `UseSerilogRequestLogging`
и до `UseRateLimiter` — иначе и лимитер, и логи запишут адрес прокси.

В Production пустой `TrustedNetworks` → **fail-fast** (§13): лимитер, считающий всех одним адресом,
это не защита, а отказ в обслуживании (риск R5).

### 9.2 Политики

Все — `FixedWindowLimiter`, `QueueLimit = 0` (по образцу `uploads`), лимиты из конфигурации.

| Политика | Эндпоинт | Ключ партиции | Умолчание |
|---|---|---|---|
| `auth-login` | `POST /api/auth/login` | IP | 10 / 1 мин |
| `auth-register` | `POST /api/auth/register` | IP | 5 / 60 мин |
| `booking-create` | `POST /api/bookings` | **аноним → IP; аутентифицированный → user id** | аноним 10 / 60 мин; аутентифицированный 120 / 60 мин |
| `data-export` | `GET /api/profile/export` | user id | 3 / 1440 мин |
| `uploads` | четыре точки загрузки | user id (существующая) | 10 / 1 мин — **не трогается** |

Секция конфигурации: `RateLimits:{policy}:{PermitLimit|WindowMinutes}`. В `appsettings.Testing.json`
все четыре получают `PermitLimit: 10000` — по образцу того, что цикл 2 уже сделал для `uploads`
(US-42 п. 6): 344 существующих теста не должны начать падать.

**`booking-create` и ручная запись персонала** (US-42 п. 5). Определить «персонал» на уровне лимитера
нельзя: это запрос к `CompanyMembers`, а лимитер обязан работать без БД (SPEC §7 п. 1). Прокси —
факт аутентификации: аутентифицированный вызывающий считается по своему id и с лимитом на порядок
выше. Администратор салона, заводящий десять записей подряд, в гостевой лимит не упирается физически,
потому что считается не по IP. Это записано комментарием в коде.

### 9.3 Health-check вне лимитов

Глобального лимитера в проекте нет — `app.UseRateLimiter()` действует только там, где стоит
`[EnableRateLimiting]`. Значит `/api/health/*` свободны **по умолчанию**, и US-43 п. 5 выполняется
тем, что мы не вешаем на них атрибут. Это отмечено комментарием, чтобы позже никто не «навёл порядок»,
добавив глобальную политику.

### 9.4 Тело 429

Пустого тела быть не должно (иначе фронтовый маппер не отличит 429 от 403) — `OnRejected` уже пишет
строку для `uploads`. Он становится ветвлением по имени политики:

| Политика | Текст |
|---|---|
| `uploads` | `Too many uploads. Try again in a minute.` (**без изменений**, на нём стоит `uploadError.ts`) |
| `auth-login` | `Слишком много попыток входа. Повторите через минуту.` |
| `auth-register` | `Слишком много регистраций с этого адреса. Повторите позже.` |
| `booking-create` | `Слишком много записей с этого адреса. Повторите позже.` |
| `data-export` | `Выгрузка доступна не чаще трёх раз в сутки.` |

Язык русский — эти тексты пользователь видит целиком (`CURRENT_STATE` §6: единой конвенции языка
ошибок нет, есть прецедент русских текстов в `ProfileController`).

## 10. Health-check (ответ на §11 п. 7)

### 10.1 Встроенные `HealthChecks`, два эндпоинта

```
GET /api/health/live   → 200 {"status":"Healthy"}         никогда не трогает БД
GET /api/health/ready  → 200 {"status":"Healthy"} | 503 {"status":"Unhealthy","failed":"database"}
```

Реализация — `builder.Services.AddHealthChecks().AddCheck<DatabaseReadyHealthCheck>("database",
tags: ["ready"])`, два `MapHealthChecks` с предикатами `_ => false` и `c => c.Tags.Contains("ready")`.
`AllowAnonymous`, свой `ResponseWriter` на два поля. Никаких `HealthCheckOptions` по умолчанию:
стандартный JSON публикует имена и **описания исключений** проверок — это ровно то раскрытие
внутренностей, которое запрещает US-43 п. 3. Своя запись из двух полей исключает вопрос.

Подробной диагностики для SuperAdmin **не делаем** — она не нужна ни одному сценарию цикла, а
`GET /api/admin/scheduled-tasks` уже отдаёт то единственное, что интересно смотреть внутри.

### 10.2 Что именно считается «готовностью»

1. `db.Database.CanConnectAsync()` — соединение есть.
2. `GetPendingMigrationsAsync()` пуст — миграции применены.

Тонкость: миграции применяются на старте (`Program.cs`), значит после успешного старта их состояние
измениться не может. `GetPendingMigrationsAsync` при этом заметно дороже `CanConnectAsync`, а
readiness опрашивается docker'ом каждые 30 секунд. Поэтому результат «миграций не осталось»
запоминается в singleton-флаге: первая успешная проверка выставляет его, дальше остаётся только
`CanConnectAsync`. Проверка миграций нужна для **окна старта** (контейнер поднялся, миграции ещё
катятся — деплой не должен переключаться), а не как непрерывный мониторинг.

### 10.3 Связь с docker и деплоем

- `docker-compose.prod.yml`, контейнер `api`: `healthcheck` на `/api/health/live`,
  `interval: 30s, timeout: 3s, retries: 3, start_period: 60s`. `start_period` большой намеренно:
  в него укладывается применение миграций.
- Образ `mcr.microsoft.com/dotnet/aspnet:8.0` не содержит ни `curl`, ни `wget`. Поэтому в runtime-стадию
  `Dockerfile` добавляется `curl` (`apt-get install -y --no-install-recommends curl`, ~1,5 МБ).
  Альтернатива «healthcheck снаружи, из скрипта деплоя» оставляет compose без понятия о здоровье
  контейнера и ломает `depends_on: condition: service_healthy` — а он нужен smoke-тесту (§12.2).
- `deploy/deploy-remote.sh` после рестарта опрашивает `readiness` до таймаута (§12.3).
- `DEPLOY.md` получает строку `curl -s https://ezbook.ru/api/health/ready` и расшифровку трёх
  типовых ответов (US-43 п. 7).

## 11. Логирование и трекинг ошибок (ответ на §11 п. 8)

### 11.1 Serilog: куда пишем

**И в stdout, и в файл.** stdout — потому что это контейнер и `docker logs` должен работать; файл —
потому что `docker logs` теряется при пересоздании контейнера, а разбираться в инциденте нужно
через день. Оба синка — JSON (`CompactJsonFormatter`).

```
Console  → CompactJsonFormatter
File     → /app/logs/app-.json, rollingInterval: Day, retainedFileCountLimit: 14,
           fileSizeLimitBytes: 100 MB, rollOnFileSizeLimit: true
```

Каталог `/app/logs` — отдельный named volume `api_logs` в `docker-compose.prod.yml`. Ретенция
14 файлов × 100 МБ — верхняя граница ~1,4 ГБ, и это записано в `DEPLOY.md` рядом с требованием
следить за диском (US-45 п. 7). Логи **не попадают в бэкап** (US-40): они не данные, а расходник.

`UseSerilogRequestLogging` даёт по каждому запросу: метод, путь, статус, длительность. Обогащение
(`EnrichDiagnosticContext`) добавляет `traceId` и `userId`:

```csharp
// The SAME value the 500 handler puts into problem+json's traceId — Activity.Current?.Id, falling back
// to TraceIdentifier. If these two ever diverge, "найди по traceId" in DEPLOY.md stops working, which
// is the whole point of US-45 p.1.
diag.Set("traceId", Activity.Current?.Id ?? ctx.TraceIdentifier);
diag.Set("userId", ctx.User.FindFirstValue(ClaimTypes.NameIdentifier));
```

### 11.2 Уровни

| Что | Уровень |
|---|---|
| Успешный запрос | `Information` (одна строка на запрос от `UseSerilogRequestLogging`) |
| Ожидаемые 4xx: 400, 402 (упёрлись в тариф), 403, 404, 409 (слот занят), 429, 451 | `Information` — **не** `Warning` и не `Error` (US-45 п. 5) |
| Сбой инфраструктуры без исключения (недоступен трекер, нет места на диске) | `Warning` |
| Необработанное исключение, 500 | `Error` → уходит в трекер |
| Фоновые задачи: старт, итог, длительность | `Information`; ошибка прохода — `Error` (US-45 п. 6) |

Понижение шума: `Microsoft.AspNetCore` и `Microsoft.EntityFrameworkCore` — `Warning`
(иначе EF пишет каждый SQL, и в лог поедут телефоны в параметрах запросов — это не только шум,
но и утечка ПДн).

### 11.3 Как ПДн не попадают в логи — три рубежа, а не договорённость

Требование US-45 п. 2 и риск R8 (история про 152-ФЗ сама создаёт нарушение).

1. **Не логируем то, чего логировать нельзя.** Правило ревью: телефон, имя, email, текст заметки,
   пароль, токен, DSN, ключ капчи не попадают в сообщение лога. Отдельный пункт чек-листа ревью.
2. **Помощник для случая «номер всё-таки нужен»** — `Services/LogMasking.Phone(string?)`:
   `79991234567` → `7999***4567`. Чистая функция, юнит-тесты (проект `UnitTests`, без БД).
3. **Предохранитель на выходе** — `Services/PhoneMaskingEnricher` (`ILogEventEnricher`): проходит по
   строковым свойствам события и маскирует последовательности из 10–15 цифр. Это защита от
   интерполированной строки, которую кто-то напишет через полгода. Стоимость — регулярка по
   свойствам события; чтобы не платить её в горячем пути, обогащение применяется только к событиям
   уровня `Warning` и выше и к событиям с исключением (успешный запрос ПДн не содержит по построению:
   в нём метод, путь, статус, длительность, id и traceId).
4. **EF Core**: `EnableSensitiveDataLogging` **никогда** не включается (сейчас и не включён —
   проверить, что не появится).

Тест `LEG-`: запрос с телефоном в теле → в записанном логе телефона в открытом виде нет.

### 11.4 Трекер: GlitchTip

- Клиент — sink `Sentry.Serilog`, минимальный уровень события `Error`, `SendDefaultPii = false`,
  захват тела запроса выключен, `BeforeSend` прогоняет сообщение и стектрейс через ту же маскировку
  (§11.3 п. 2), `Environment` = имя окружения, `Release` = git sha из переменной сборки.
- **DSN пуст → sink не регистрируется вовсе.** Приложение стартует и работает без трекера
  (US-45 п. 8), по образцу `CaptchaService.IsEnforced`. В `Development` и `Testing` DSN пуст
  по конфигурации, и наружу не уходит ничего (US-45 п. 9). Тест: приложение стартует без секции
  `Sentry`.
- Сервер — `docker-compose.glitchtip.yml` рядом с боевым compose (`web`, `worker`, `postgres`,
  `redis`), на том же VPS, наружу — только через nginx с basic-auth или по отдельному поддомену с
  TLS. Ретенция событий — 30 дней, задаётся явно (`GLITCHTIP_MAX_EVENT_LIFE_DAYS`), потому что
  трекер, тихо съевший диск, отключит продукт (US-45 п. 7).

### 11.5 Алерты: список поводов закрыт

| Повод | Как реализовано |
|---|---|
| Новая, ранее не встречавшаяся ошибка | Штатное уведомление GlitchTip «new issue» |
| Всплеск известной ошибки | Правило GlitchTip: > N событий за M минут |
| **Неуспешный прогон бэкапа** | Скрипт бэкапа при ненулевом коде возврата отправляет событие в GlitchTip тем же DSN (`curl` на envelope-эндпоинт, 6 строк в скрипте) — так алерт приходит одним каналом с остальными |
| Недоступность `readiness` дольше нескольких минут | **Не реализуем внутри GlitchTip.** Внешний аптайм-монитор в скоуп не входит; вместо него — systemd-таймер на хосте, который раз в 5 минут дёргает `/api/health/ready` и при трёх подряд неудачах шлёт событие в GlitchTip тем же способом, что бэкап. Это «дёшево имеющимися средствами» из US-45 п. 4(г) |
| **Ничего из перечисленного ниже** | каждое повторение известной ошибки, любые 4xx, ошибки валидации, срабатывание rate limit — в трекер уровнем `Error` не попадают по построению (§11.2) |

Канал — **один**: e-mail на адрес заказчика, настраивается в GlitchTip, записывается в `DEPLOY.md`.
Дневная сводка — встроенный digest GlitchTip.

## 12. Эксплуатационный контур (ответ на §11 пп. 9, 10)

Весь раздел — зона devops-инженера. Кода приложения он не касается **нигде**, кроме health-check,
который к этому моменту уже сделан бэкендом.

### 12.1 Бэкапы (US-40): скрипт на хосте, запуск systemd-таймером

**Где живёт:** `deploy/backup/backup.sh` + `deploy/backup/servicebooking-backup.service|.timer` —
в репозитории, рядом с остальным деплоем (правило проекта: дополнять существующее).

**Чем запускается: systemd timer, не cron.** Причины прикладные: `journalctl -u servicebooking-backup`
даёт историю прогонов без своего логфайла; `Persistent=true` догоняет пропущенный запуск, если VPS
был выключен; код возврата виден в статусе юнита. Для одного эксплуатанта (Р8) это разница между
«посмотреть одну команду» и «искать, куда cron написал письмо».

**Не контейнер-сайдкар и не `IScheduledTask`:** бэкап должен снимать содержимое docker volume и
работать, когда приложение лежит. Изнутри приложения это потребовало бы примонтировать docker-сокет
в контейнер API — то есть выдать веб-приложению root на хосте. Неприемлемо.

**Что делает прогон:**
1. Проверяет свободное место **до** начала: нужно ≥ (размер прошлой копии × 1,5). Не хватает —
   ошибка в лог, ненулевой код возврата, алерт; наполовину записанного архива не остаётся.
2. `docker compose -f docker-compose.prod.yml exec -T postgres pg_dump -U postgres -Fc servicebooking`
   → `db-YYYYmmddTHHMMSSZ.dump` (кастомный формат, уже сжат).
3. Оба volume — без остановки приложения:
   `docker run --rm -v api_uploads:/src:ro -v $BACKUP_DIR:/dst alpine tar czf /dst/uploads-<ts>.tar.gz -C /src .`
   и то же для `api_private_uploads`. Файлы пишутся один раз и не переписываются (конвейер загрузки
   цикла 2), поэтому «горячая» копия консистентна: худший исход — не попавший в архив файл,
   загруженный в момент снятия.
4. Ротация: 7 ежесуточных + 4 еженедельных (воскресный прогон помечается и живёт дольше). Значения —
   переменные в начале скрипта.
5. Каталог — `/var/backups/servicebooking` на хосте, **вне docker volume**: `docker compose down -v`
   не должен унести копии вместе с данными (US-40 п. 4). Права `0700`, владелец root — это ПДн
   (SPEC §7 п. 3).
6. Итог прогона — строкой в journald; ненулевой код → событие в GlitchTip (§11.5).
7. Место под будущую внешнюю выгрузку (§10.1 SPEC, R13) оставлено функцией-заглушкой
   `upload_offsite() { :; }` с комментарием и ссылкой на R13 — чтобы добавление S3 было одной
   функцией, а не переписыванием скрипта.

**Восстановление** — раздел в существующем `DEPLOY.md`, командами подряд, без размышлений;
обязательный фактический прогон с проверкой, что **приватное фото открывается** через
`GET /api/client-notes/photos/{id}` (US-40 п. 6) — это единственная проверка, доказывающая, что
строки БД и файлы совпали. Дата прогона пишется строкой в тот же раздел.

**Ограничение схемы** — отдельный абзац с заголовком в `DEPLOY.md` и в `README.md`: локальная копия
не защищает от потери сервера (R13). Проверяется приёмкой.

### 12.2 Smoke-тест образа (US-41): расширение джоба `docker-build`

Сегодня джоб только собирает образ. Становится:

```
docker network create ci
docker run -d --name pg --network ci -e POSTGRES_PASSWORD=... postgres:16
docker build -t servicebooking-api:ci .
docker run -d --name api --network ci -p 8080:8080 \
    -e ASPNETCORE_ENVIRONMENT=Production  ← прогон именно как Production
    -e ConnectionStrings__DefaultConnection=... -e Jwt__Key=<32+ случайных> \
    -e SuperAdmin__Password=<не плейсхолдер> -e Storage__PrivateRoot=/app/private-uploads \
    -e ForwardedHeaders__TrustedNetworks__0=172.16.0.0/12 \
    servicebooking-api:ci
deploy/ci/smoke.sh                                  ← сценарий ниже
```

`deploy/ci/smoke.sh` (в репозитории, чтобы его можно было прогнать руками):
1. Ждёт `GET /api/health/live` = 200 (таймаут 90 с) — **не `sleep`** (US-41 п. 2).
2. Ждёт `GET /api/health/ready` = 200 — это и есть подтверждение, что миграции применились.
3. `POST /api/auth/register` (с `acceptedLegal: true`) → токен.
4. `POST /api/profile/avatar` с реальным JPEG → **2xx**. Это единственный путь, который трогает
   SkiaSharp, и он самый короткий: компания не нужна.
5. Проверяет, что возвращённый `avatarUrl` отдаётся по HTTP.
6. Любой шаг упал → `exit 1` → **джоб красный** (US-41 п. 4); в лог выводится `docker logs api`.

**Прогон именно в `Production`** выбран сознательно (US-41 п. 5 оставляет выбор архитектору): так
smoke заодно подтверждает, что fail-fast настроен верно и что список обязательных переменных
окружения в `DEPLOY.md` полный. Обратная сторона — CI придётся править при добавлении новой
обязательной переменной; это желаемое поведение, а не издержка.

Ожидаемое время: сборка образа (уже есть) + ~40–60 с. Цель US-41 п. 7 «единицы минут» выполняется.

**Расхождение с SPEC:** US-41 п. 3 говорит «загрузка изображения возвращает **201**». Фактически
`POST /api/profile/avatar` отдаёт **200** (`API_CONTRACT` цикла 2 §7). Smoke проверяет 200; менять
код эндпоинта ради цифры в SPEC — ломать контракт без причины. Зафиксировано в §19.5.

### 12.3 Деплой с откатом (US-44)

**Сборка фронта уезжает с боевого сервера.** Джоб `frontend` в CI публикует `dist` как артефакт
(`actions/upload-artifact`, retention 30 дней). На сервер приезжает архив.

**Раскладка на сервере:**
```
/var/www/ezbook/
├── releases/
│   ├── 20260915T101500Z/     ← распакованный dist
│   ├── 20260914T190000Z/
│   └── 20260913T120000Z/     ← хранится 3 последних
└── current -> releases/20260915T101500Z    ← симлинк, root в nginx указывает СЮДА
```
Переключение — `ln -sfn <new> current.tmp && mv -Tf current.tmp current`: атомарный `rename(2)`,
промежуточного состояния «часть файлов новая, часть старая» не существует (US-44 п. 4).
После распаковки — `restorecon -R /var/www/ezbook` (SELinux уже есть в текущем скрипте).

**Образ API:** собирается на сервере, как и раньше (полноценный CD не в скоупе, SPEC §8.1), но перед
сборкой текущий образ тегируется `servicebooking-api:previous`. Откат — `docker tag previous latest`
+ `up -d`.

**Процедура деплоя** (`deploy/deploy-remote.sh` переписывается):
1. Тег `previous` на текущий образ; запись текущего симлинка в `/var/www/ezbook/.previous`.
2. Распаковка нового `dist` в `releases/<ts>`, переключение симлинка, `nginx -t && reload`.
3. `docker compose up -d --build api`.
4. **Ожидание `readiness`** с таймаутом 120 с.
5. Не поднялось → печать прямым текстом «ДЕПЛОЙ НЕУСПЕШЕН» и **следующей строкой** готовая команда
   отката (US-44 п. 2).

**Откат — `deploy/rollback.sh` без аргументов**: возвращает симлинк на `.previous`, `nginx reload`,
`docker tag previous → текущий`, `up -d`, ждёт `readiness`. Один аргумент (метка релиза) — опционален,
для отката на две версии назад (US-44 п. 3).

**Миграции не откатываются** — предупреждение в раннбуке отдельным абзацем и короткая инструкция
«что делать, если код надо откатить, а миграция применена» (US-44 п. 5). Поведение «мигрируем на
старте» в цикле не меняется.

### 12.4 Security-заголовки (US-47) и пометки Windows-контура

`deploy/nginx/ezbook.conf`, `location /`: добавляются `Strict-Transport-Security max-age=15552000`
(180 дней, **без `preload`** на первом шаге), `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin`, CSP под фактические источники:

```
default-src 'self';
script-src 'self' https://smartcaptcha.yandexcloud.net;
frame-src https://smartcaptcha.yandexcloud.net;
connect-src 'self' https://smartcaptcha.yandexcloud.net;
img-src 'self' data: blob:;        ← blob: обязателен: приватные фото грузятся блобами (цикл 2 §12.2)
style-src 'self' 'unsafe-inline';  ← Tailwind в JSX даёт инлайновые стили; убирать — отдельная работа

```

`location /embed/` **сохраняет исключение**: ни `frame-ancestors`, ни `X-Frame-Options` — виджет

формы записи **до** выкладки.

Пометки §0.2 SPEC (врезка в `DEPLOY-windows.md`, комментарий в `frontend/public/web.config`, строка
в `README.md`/`DEPLOY.md`) делаются **независимо от судьбы US-47** — это полчаса и они не режутся.

## 13. Fail-fast конфигурации (US-48) — расширение по двум осям

Сегодня: `if (builder.Environment.IsProduction())`. Становится:

```csharp
// Allow-list, not deny-list: an environment we have never heard of (Staging, Preview, Demo) must be
// treated as production-grade. Only the two we KNOW are developer contexts are exempt.
var isDeveloperEnvironment = builder.Environment.IsDevelopment() || builder.Environment.IsEnvironment("Testing");
if (!isDeveloperEnvironment) { … }
```

Состав проверок растёт с трёх до пяти:

| Проверка | Была | Стала |
|---|---|---|
| `Jwt:Key` пуст / < 32 / плейсхолдер | есть | без изменений |
| `SuperAdmin:Password` пуст / плейсхолдер | есть | без изменений |
| `Storage:PrivateRoot` внутри `wwwroot` | есть | без изменений |
| `ForwardedHeaders:TrustedNetworks` пуст | — | **новая** (§9.1): без неё rate limiting превращается в DoS |
| Правовые документы не загрузились | — | **новая** (§4.4): без действующей политики нельзя принимать регистрации |
| `SuperAdmin:Phone` — плейсхолдер | предупреждение | без изменений |

Текст каждой ошибки называет **переменную окружения**, а не ключ конфигурации (US-48 п. 2) —
оператор правит `.env`, а не `appsettings`.

Тесты: приложение с дефолтными секретами и `ASPNETCORE_ENVIRONMENT=Staging` не стартует;
в `Testing` стартует (иначе весь функциональный набор упадёт).

## 14. Формат ошибок — граница, перенесённая без изменений

Правило цикла 1 и 2 сохраняется дословно: **осознанные 4xx — голая строка `text/plain`;
`ProblemDetails` только для необработанного 500**. `AddProblemDetails()` и `UseStatusCodePages*`
по-прежнему запрещены — они переписали бы тела, на которых стоят мапперы `src/utils/*Error.ts`.

Два новых кода цикла:

| Код | Когда | Тело | Кто обрабатывает на фронте |
|---|---|---|---|
| **451** | действующая редакция документов не принята, правка существенная (§6.3) | `text/plain`, строка | интерцептор `client.ts` → блокирующий экран |
| **503** | `readiness` не готов; `GET /api/legal/*` при несобранном манифесте | JSON из двух полей / `text/plain` | страница документов показывает состояние ошибки |

451 обрабатывается в `client.ts` **рядом с существующей веткой 401**, а не в каждом мапперe: это
глобальное состояние приложения, а не ошибка конкретной формы.

## 15. Пагинация (ответ на §11 п. 11)

### 15.1 Единый контракт

Запрос: `?page=1&pageSize=20`. `page` — с единицы; `pageSize` по умолчанию 20, **потолок 100**
(значение больше молча обрезается до 100, а не даёт 400 — US-49 п. 6 требует именно обрезки).

`page` тоже клампится, но и сверху, не только снизу: `page < 1` → 1, а `page` больше
`int.MaxValue / pageSize` (после нормализации `pageSize`) → клампится до этого максимума.
Без верхней границы `(page - 1) * pageSize` в `Pagination.Create`/call-сайтах переполняет
32-битный `int` при достаточно большом `page` (легко достижимо анонимным запросом на публичном
`GET /api/companies/{id}/reviews`), что либо роняет запрос 500-й на уровне БД, либо на in-memory
LINQ молча оборачивается и отдаёт страницу 1 вместо пустой. `Pagination.Normalize` — единственное
место, где применяются обе границы (`DTOs/Common/PagedResult.cs`).

Следствие для контракта: поле `page` в ответе — это **фактически применённая** страница после
обеих границ, а не эхо того, что прислал клиент. Если клиент запросил `page=999999999` при
`pageSize=20`, в ответе будет не `999999999`, а клампированное значение
(`int.MaxValue / 20 ≈ 107374182`), и `items`, скорее всего, будет пустым (страница за пределами
`total`), но `hasNext` при этом гарантированно `false`. Фронту нельзя молча полагаться на то, что
`response.page === requestedPage`.

Ответ — конверт, один и тот же для всех четырёх выборок:

```json
{ "items": [ … ], "page": 1, "pageSize": 20, "total": 137, "hasNext": true }
```

`DTOs/Common/PagedResult.cs`:
```csharp
public record PagedResult<T>(IReadOnlyList<T> Items, int Page, int PageSize, int Total, bool HasNext);
```

`hasNext` вычисляется как `page * pageSize < total` — избавляет фронт от арифметики и от
рассинхронизации, если правило когда-нибудь изменится.

На фронте — ручная копия в `src/types/index.ts` (конвенция проекта, генерации из OpenAPI нет):
```ts
export interface Paged<T> { items: T[]; page: number; pageSize: number; total: number; hasNext: boolean }
```

### 15.2 Четыре выборки

| Эндпоинт | Было | Стало | Сортировка (обязательна: без неё страницы пересекаются) |
|---|---|---|---|
| `GET /api/admin/users` | весь список + **N+1 по ролям** | `PagedResult<AdminUserDto>` | `CreatedAt`, затем `Id` |
| `GET /api/admin/companies` | весь список | `PagedResult<AdminCompanyDto>` | `CreatedAt`, затем `Id` |
| `GET /api/companies/{id}/reviews` | весь список | `PagedResult<ReviewDto>` | `CreatedAt DESC`, затем `Id` |
| `GET /api/masters/clients` | весь список | `PagedResult<MasterClientDto>` | по дате последнего визита DESC, затем ключ клиента |

Тай-брейк по `Id` добавлен архитектором: `OrderBy(CreatedAt)` без него на равных значениях даёт
недетерминированный порядок в PostgreSQL, и «вторая страница не пересекается с первой» (US-49 п. 6)
превращается в флакающий тест.

### 15.3 Что остаётся как было

`GET /api/admin/bookings` — `Take(500)` **остаётся** (US-49 п. 5: пагинация вводится там, где
перечислена; эта выборка в список не входит). 50 заметок на клиента и 5 фото на заметку остаются:
это вложенные ограничения внутри элемента, а не отдельная выборка.

### 15.4 N+1 в `admin/users`

Сейчас — `userManager.GetRolesAsync(u)` в цикле по пользователям: `N` запросов. Заменяется одним
join'ом на страницу:

```csharp
var roleMap = await (from ur in db.UserRoles
                     join r in db.Roles on ur.RoleId equals r.Id
                     where userIds.Contains(ur.UserId)
                     select new { ur.UserId, r.Name })
    .ToListAsync();
```
и группировкой в память. Пагинация без этого только маскировала бы проблему (US-49 п. 3).

## 16. Миграции цикла (ответ на §11 п. 12)

Три, в этом порядке. Каждая создаётся **своим автором в своей задаче** — но не одновременно:
EF Core нумерует миграции по времени, и две ветки, создавшие миграции параллельно, дают конфликт
снапшота. Правило цикла: перед `dotnet ef migrations add` — `git pull` ветки интеграции.

| № | Имя | Содержание | Задача | Зависимости |
|---|---|---|---|---|
| 1 | `AddLegalConsent` | таблица `UserConsents` (+ уникальный индекс `(UserId, DocumentType)`); `Booking`: `ConsentPrivacyVersion`, `ConsentTermsVersion`, `ConsentAcceptedAtUtc`, `ClientDeleted` | T-B5 | нет |
| 2 | `AddUserDeletionTombstone` | `AppUser.DeletedAtUtc` | T-B7 | нет (по схеме независима от № 1) |
| 3 | `ResyncIdentityRoles` | **данные, не схема**: чистка и досоздание строк `AspNetUserRoles` для `Master`/`CompanyOwner` по `CompanyMembers` | T-B2 | нет |

### 16.1 Почему № 3 — миграция, а не команда на сервере

Рассинхронизация уже есть и в dev-базах, и на стенде. Скрипт «прогнать один раз руками» гарантирует,
что где-то его не прогонят. Миграция применяется на старте везде, где применяются остальные.
`Down` для неё — no-op с комментарием: обратной операции у «привели в соответствие» не существует,
и делать вид, что существует, хуже, чем сказать об этом.

### 16.2 Обратимость

`Down` пишется и проверяется для № 1 и № 2 (SPEC §12 п. 5). Разрушительных операций в цикле нет:
ни одна миграция не удаляет данные (в отличие от `NormalizePhoneNumbers` цикла 2).

### 16.3 Порядок применения относительно правового контура

Миграция № 1 добавляет обязательное поле согласия только в `Booking` (nullable) и создаёт пустую
таблицу. Существующие пользователи после её применения **не имеют** записей `UserConsent`, то есть
их claim'ы пусты → при первом входе они увидят блокирующий экран (`changeKind: Material` по
умолчанию). Это и есть желаемое поведение: до цикла 3 согласия не собиралось вовсе, значит его
нужно собрать со всех.

### 16.4 Правило, вступающее в силу **после** этого цикла

Цикл 3 — последний, в котором ломающая миграция допустима без обсуждения. После запуска для реальных
пользователей действует: миграция, теряющая данные, требует (а) отдельного решения заказчика,
(б) свежего прогона бэкапа непосредственно перед применением (US-40 п. 9), (в) описанной процедуры
отката в `DEPLOY.md`. Записано здесь, потому что в следующем цикле спрашивать будет поздно.

## 19. Расхождения со SPEC и решения архитектора

### 19.1 US-41 стартует одновременно с US-43, а не строго первым

SPEC §2.3 ставит smoke-тест первым, US-43 — третьим. Но US-41 п. 2 требует, чтобы smoke ждал
готовности по health-check, которого на первом дне ещё нет. Решение: обе истории стартуют в день
первый разными исполнителями (devops и backend), первые прогоны smoke ждут TCP-порт, финальная
версия — `readiness`. Смысл приоритета сохранён: узнать, работает ли SkiaSharp в контейнере, мы
всё равно успеваем в первый день.

### 19.2 Удаление аккаунта оставляет строку `AppUser` (§7.4)

US-39 п. 2 говорит «удаляется учётная запись Identity». Схема БД делает это либо невозможным
(четыре FK с `Restrict`), либо разрушительным (`ClientNote.Master` — `Cascade`: удалились бы все
заметки, написанные этим мастером о **чужих** клиентах, что прямо запрещено US-39 п. 3 и риском R4).
Решение — надгробие: все персональные данные стираются, логин и токены мертвы, телефон освобождён.
**Требует отражения в тексте US-52**: политика не должна обещать физического удаления строки.

### 19.3 `PUT /api/admin/companies/{id}/owner` сегодня не переносит членство

Найдено при проектировании US-46: эндпоинт меняет `Company.OwnerUserId` и выдаёт роль новому
владельцу, но строку `CompanyMember` с ролью `CompanyOwner` не трогает. Пересчёт ролей по членствам
на таких данных даст неверный результат. T-B2 обязана привести их в соответствие — это расширение
US-46 на ~2 часа, не отдельная история.

### 19.4 Выгрузка данных доступна при непринятой новой редакции

SPEC §3.5 п. 9 явно разрешает при непринятой редакции только чтение документов, выход и удаление
аккаунта. Выгрузка добавлена в allow-list сверх этого: право получить копию своих данных не должно
зависеть от согласия с новой редакцией — иначе оператор косвенно принуждает к согласию. Цена
решения нулевая, обратный вердикт юриста снимается одной строкой в allow-list.

### 19.5 Smoke проверяет 200, а не 201

US-41 п. 3 говорит «загрузка возвращает 201». `POST /api/profile/avatar` фактически отдаёт **200**
(зафиксировано `API_CONTRACT` цикла 2 §7 и тестами `PROF-`). Менять код ответа ради цифры в SPEC —
ломать контракт без пользы. Smoke проверяет фактический код.

### 19.6 Алерт на недоступность `readiness` вынесен на хост

US-45 п. 4(г) допускает «если это дёшево реализовать имеющимися средствами». Внутри GlitchTip
аптайм-мониторинга нет, а внешний сервис — это выход данных наружу. Решение — systemd-таймер на том
же хосте, отправляющий событие в GlitchTip после трёх неудач подряд. Ограничение честное и записано
в `DEPLOY.md`: **если умрёт весь VPS, алерта не будет** — той же природы, что R13.

### 19.7 Чего в цикле нет вопреки соблазну

- Рефакторинга `CompaniesController` (571 строка) — SPEC §8.1 запрещает прямо.
- Перевода `MailingController` на `CompanyMembership` — тот же запрет.
- Сервисного слоя, репозиториев, unit of work — §1 п. 2.
- Кеша ролей в `OnTokenValidated` (P2-11 техдолга) — соблазн велик, потому что мы рядом, но это
  правка горячего пути авторизации в цикле, где и так двенадцать P1-историй. Остаётся в техдолге.

## 20. Риски SPEC → ответ архитектуры

| Риск | Ответ |
|---|---|
| **R1** выпускаемся с текстом не от юриста | Механизм замены готов с первого дня (§4.1); замена черновика обрабатывается как существенная правка и покрыта отдельным тестом (T-B5) |
| **R2** образ не работает | T-D1 идёт первым; smoke бьёт ровно в SkiaSharp через реальный HTTP; падение роняет сборку |
| **R3** бэкап есть, восстановление не работает | T-D2 не считается сделанной без фактического прогона с открытием приватного фото |
| **R13** потеря VPS уничтожает данные вместе с бэкапом | Принят заказчиком. Смягчение: копии вне docker volume, ограничение написано отдельным абзацем в двух местах, `upload_offsite()`-заглушка оставлена под будущую выгрузку |
| **R4** удаление аккаунта ломает данные салона | §7.4: обезличивание вместо каскада, надгробие вместо `DELETE`, тест на неизменность отчёта до/после |
| **R5** rate limiting считает всех одним IP | §9.1: `KnownNetworks.Clear()`, доверенные сети из конфигурации, fail-fast при пустом списке, тест «заголовок от недоверенного адреса игнорируется» |
| **R6** CSP ломает капчу | §12.4: политика написана под фактические источники, включая `blob:` для приватных фото; ручная проверка живой формы до выкладки |
| **R7** цикл не влезает | §17: порядок работ и три параллельных исполнителя; хвост P2/P3 стоит последним и режется по SPEC §2.4 без переделки сделанного |
| **R8** ПДн утекают в логи и трекер | §11.3: три рубежа вместо договорённости, юнит-тест маскирования, `Warning`-уровень для EF, self-hosted трекер |
| **R14** смена версии ломает жизнь пользователям | §6.3: два режима, признак явный, умолчание безопасное; allow-list не запирает пользователя; тесты на оба сценария |
| **R15** алерты никто не читает | §11.5: закрытый список поводов, один канал, дневная сводка |
| **R10** переформатирование хоронит ревью | T-B11/T-F6 идут последними, правила и переформатирование — разные коммиты |
| **R11** уведомление в РКН не подано | Вне контроля команды; сведения передаются T-L1 |
| **R12** новые находки чинятся на ходу | Правило циклов 1 и 2: находки документируются в SPEC следующего цикла. Исключение уже применено один раз — §19.3 (это дыра в правах, эскалирована и включена в US-46) |
