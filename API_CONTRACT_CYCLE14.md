## §160. Конвенции, действующие без изменений

- `camelCase` в JSON; перечисления — **строками** (`JsonStringEnumConverter`, значения — ровно имена
  членов C#, `PascalCase`); `DateTime` — ISO-8601 UTC; `DateOnly` — `YYYY-MM-DD`.
- Тела **осознанных** ошибок 400/402/404(с текстом)/409/429 — **голая строка `text/plain`
  по-русски**. `ProblemDetails` не используется (кроме необработанных 500).
- 401 и 403 — **пустое** тело.
- 451 — «требуется принять новую редакцию документов»; все неанонимные маршруты этого файла по
  умолчанию **закрыты** гейтом `LegalConsentFilter`, в allow-list не вносится ни один.
- **402 в этом цикле не возвращает ни один маршрут.** Подтверждение телефона бесплатно и тарифом не
  гейтится ни в одной точке (Р2/§3 спеки).
- Ни один ответ этого цикла **не содержит** идентификатора MAX-аккаунта (ни в открытом, ни в
  хешированном виде) и **не содержит** payload'а.

**Рубильник цикл не переводит:** в закоммиченной конфигурации `PhoneVerification:Provider = stub`,
то есть `GET /api/phone-verification/config` отвечает `enabled: false`, а вся подсистема ведёт себя
как описано в §171. Это ожидаемое состояние после выката, а не дефект.

## §162. `GET /api/phone-verification/config`

**Анонимный.** Один и тот же ответ обслуживает форму регистрации, профиль и экран смены номера —
второго запроса состояния не заводится (Q5). Образец — `GET /api/push/config`.

**200 OK**
```jsonc
{
  "enabled": true,            // подсистема включена оператором
  "healthy": true,            // вебхук подписан (§146.3 архитектуры). enabled && !healthy = «сейчас не сработает»
  "methods": ["MaxBot"],      // пусто, когда enabled=false
  "sessionTtlSeconds": 600,   // П7
  "pollIntervalSeconds": 2    // рекомендация серверу→клиенту, а не требование
}
```
Выключенное состояние:
```jsonc
{ "enabled": false, "healthy": false, "methods": [], "sessionTtlSeconds": 600, "pollIntervalSeconds": 2 }
```

**Правило фронтенда:** действие «Подтвердить номер через MAX» показывается **только** при
`enabled && healthy`. При `enabled=false` не показывается **ничего** — ни кнопки, ни объяснения, ни
пустого места (US-14-01, US-14-14). При `enabled && !healthy` кнопка тоже не показывается: предлагать
действие, которое сейчас не сработает, — хуже, чем не предлагать.

Кешируется `react-query` со `staleTime` 5 минут.

## §163. `POST /api/phone-verification/sessions` — получить ссылку и QR

**Анонимно или с токеном.** Политика лимитов **`phone-verify-start`** — 10/час (на пользователя,
для анонимных — на IP).

**Запрос**
```jsonc
{ "phone": "+7 (900) 000-00-00" }   // обязателен для анонимного; для авторизованного можно опустить —
                                     // тогда берётся текущий номер аккаунта
```

**201 Created**
```jsonc
{
  "sessionId": "5f1c…",                       // uuid, едет в URL опроса статуса
  "statusToken": "Qm9iLXR…",                   // 32 байта base64url; ВТОРАЯ половина ключа опроса
  "method": "MaxBot",
  "deepLink": "https://max.ru/ezbookbot?start=v1.Zm9vYmFy…",
  "qrPngBase64": "iVBORw0KGgo…",              // может быть null — тогда QR рисует клиент из deepLink
  "phoneMasked": "+7 (900) ***-**-01",
  "expiresAtUtc": "2026-09-24T12:34:56Z",
  "ttlSeconds": 600
}
```
- `statusToken` отдаётся **один раз** и на сервере хранится только его SHA-256. Потеряли — начинайте
  новую сессию.
- `deepLink` — форма из спеки: `https://max.ru/<bot>?start=<payload>`, `payload` ≤ 128 символов (О6).
- `qrPngBase64` — содержимое `data:image/png;base64,…` **без** префикса. Показывается с осмысленным
  `alt`, и **рядом всегда есть `deepLink` текстом**, доступный для копирования и скринридера
  (US-14-02, §5 «Доступность»).
- **Ни одного исходящего вызова к MAX в этом запросе не происходит** — бот узнаёт о сессии, только
  когда пользователь сам его откроет.

**Ошибки**

| Код | Тело (text/plain) | Когда |
|---|---|---|
| 400 | `Введите номер телефона в формате +7 (900) 000-00-00` | номер не проходит `PhoneNormalizer.TryNormalizeRussian` — сверять потом будет не с чем (US-14-01) |
| 409 | `Подтверждение телефона сейчас недоступно.` | подсистема выключена (`enabled:false`) или вебхук не подписан |
| 429 | `Слишком много попыток подтверждения. Попробуйте позже.` | политика `phone-verify-start` **или** превышен `MaxOpenSessionsPerPhone` |
| 401 | — | токен прислан и он невалиден (анонимный вызов без токена — норма) |

## §164. `GET /api/phone-verification/sessions/{sessionId}?statusToken=…` — опрос статуса

Как фронтенд узнаёт о подтверждении без перезагрузки страницы (Q12, П9). Поллинг раз в
`pollIntervalSeconds`, останавливается сам на терминальном статусе или по `expiresAtUtc`.
Отдельной политикой лимитов **намеренно не покрыт** (§150.4 архитектуры).

**200 OK**
```jsonc
{
  "sessionId": "5f1c…",
  "status": "Pending",              // Pending | Linked | Verified | Rejected | Cancelled | Expired
  "failureReason": null,            // код из §165, когда status = Rejected
  "message": null,                  // готовый русский текст причины, собирает СЕРВЕР
  "phoneMasked": "+7 (900) ***-**-01",
  "expiresAtUtc": "2026-09-24T12:34:56Z",
  "verifiedAtUtc": null
}
```
Пример отказа:
```jsonc
{
  "sessionId": "5f1c…",
  "status": "Rejected",
  "failureReason": "PhoneMismatch",
  "message": "Вы поделились номером +7 (900) ***-**-77, а на сайте введён +7 (900) ***-**-01.",
  "phoneMasked": "+7 (900) ***-**-01",
  "expiresAtUtc": "2026-09-24T12:34:56Z",
  "verifiedAtUtc": null
}
```
- `Expired` **вычисляется** (статус `Pending`/`Linked` и `expiresAtUtc < now`), отдельно не хранится.
- `message` — человеческая формулировка, **фронт её не сочиняет и не собирает из кусочков**
  (конвенция цикла 9 №6). `failureReason` — машиночитаемый дубль для аналитики и тестов.
- Номера телефонов в ответе **только маскированные**.

**404** (пустое тело) — неизвестный `sessionId` **или** `statusToken` не подходит. Различать эти два
случая контракт не позволяет намеренно: иначе эндпоинт стал бы оракулом существования сессий.

## §165. Коды причин отказа

`failureReason` — строковое перечисление. Значения append-only.

| Код | Что произошло | Что показывает фронт (текст даёт сервер в `message`) |
|---|---|---|
| `PayloadUnknown` | ссылка не найдена | «Ссылка устарела. Получите новую» |
| `PayloadExpired` | истёк TTL | то же + предложение начать заново (US-14-06) |
| `PayloadAlreadyUsed` | сессия уже использована | то же |
| `PayloadLinkedToAnotherAccount` | по этой ссылке бота открыл другой MAX-аккаунт | «Эта ссылка уже используется в другом аккаунте MAX» |
| `SignatureMismatch` | **подпись `vcf_info` не сошлась** | «Не удалось проверить контакт. Попробуйте ещё раз» |
| `ContactNotOwnedBySender` | **контакт принадлежит не отправителю** (чужой контакт из адресной книги) | «Поделиться можно только собственным контактом» |
| `NoPhoneInContact` | в vCard нет пригодного номера | «В присланном контакте нет номера телефона» |
| `PhoneMismatch` | номера не совпали | «Вы поделились номером X, а на сайте введён Y» |
| `MaxAccountLimitReached` | потолок Р5 (3 номера на MAX-аккаунт) | «С этого аккаунта MAX уже подтверждены три номера» — **без перечисления самих номеров**, это чужие данные |
| `SessionCancelled` | пользователь отменил (или сменил номер в форме) | ничего, экран уже не показывает сессию |
| `SubsystemDisabled` | подсистему выключили посреди сценария | «Подтверждение телефона сейчас недоступно» |

## §166. `DELETE /api/phone-verification/sessions/{sessionId}?statusToken=…` — отмена

**204 No Content — всегда**, и это идемпотентно. Сессия отменяется только при совпадении
`statusToken`; несовпадение и несуществующий id дают тот же 204, чтобы эндпоинт не отвечал на вопрос
«а такая сессия есть?».

Фронтенд обязан звать этот маршрут, когда пользователь **меняет номер в форме** после того, как
запросил подтверждение (US-14-05, R8). Сервер на это не полагается: при регистрации номер сессии
сверяется независимо (§168).

## §167. `POST /api/phone-verification/max/webhook/{token}` — приём апдейтов MAX

**Анонимный.** Аутентификация — секрет **последним сегментом пути**
(`PhoneVerification:Max:WebhookToken`), маскируемый в access-логе nginx и в логах приложения.
Политика лимитов **`phone-verify-webhook`** (600/мин на IP).

Тело — апдейт площадки MAX; контракт описывает минимальную форму, на которую опирается разбор
(`bot_started` с `payload`; `message_created` с вложением `contact`, несущим `vcf_info`,
`max_info`/`tam_info`, `hash`). Неизвестные поля игнорируются.

| Код | Когда | Почему так |
|---|---|---|
| **200** | апдейт разобран и обработан; апдейт **не** распознан; внутри случилось исключение | ⚠️ Площадка **снимает подписку после 8 часов без успешного ответа** (О4). Любой не-2xx на неожиданный апдейт — способ уронить дорожку своими руками. Незнакомое пишется в лог, а не в код ответа |
| **404** | токен не совпал; подсистема выключена | Прецедент цикла 9: нераспознанное на вебхуке → 404, не 400. Существование маршрута не подтверждается |

Тело ответа всегда пустое. Обработчик отвечает быстро; исходящие сообщения боту делаются с таймаутом
5 с и не влияют на код ответа.

## §168. `POST /api/auth/register` — аддитивное изменение

**Контракт обратносовместим.** Всё, что цикл добавляет, — **необязательное** поле запроса и
**аддитивное** поле ответа. Вызов без них ведёт себя ровно как до цикла (US-14-07): те же два
обязательных акцепта, та же необязательная карта целей `PdnConsent`, тот же лимит `auth-register`.

**Запрос (дополнение)**
```jsonc
{
  "firstName": "…", "lastName": "…", "phone": "…", "password": "…", "email": null,
  "legal": { "privacyAcknowledgedVersion": "…", "termsAcceptedVersion": "…" },

  "phoneVerification": {            // ← НОВОЕ, необязательное; можно не присылать вовсе
    "sessionId": "5f1c…",
    "statusToken": "Qm9iLXR…"
  }
}
```

**Ответ 200 (дополнение)** — `AuthResponseDto` получает одно поле:
```jsonc
{ "token": "…", "userId": "…", "phone": "79000000001", "email": null,
  "firstName": "…", "lastName": "…", "roles": ["Client"],
  "phoneVerified": true }          // ← НОВОЕ
```

**Порядок проверок (часть контракта, а не деталь реализации):**
1. `legal` — как сегодня (400/409/503);
2. телефон — как сегодня (400);
3. **новое**, только если `phoneVerification` прислан: сессия существует, `Verified`, не истекло окно
   предъявления, номер совпадает с `phone`, сессия не принадлежит другому пользователю. Не сошлось →
   **409** `Подтверждение номера не подходит к этой регистрации. Подтвердите номер ещё раз.` —
   **аккаунт не создаётся**;
4. создание аккаунта, роль, две записи журнала согласий — как сегодня;
5. **новое:** отметка записывается; если в этот момент у MAX-аккаунта исчерпан потолок Р5,
   **аккаунт всё равно создаётся**, а в ответе `phoneVerified: false`. Регистрация не ломается
   из-за подтверждения (Р1).

⚠️ У `409` на этом маршруте теперь **два** разных смысла (устаревшие версии документов — с цикла 5;
негодное подтверждение — с этого цикла). Различаются текстом; `utils/authError.ts` уже устроен как
подстрочный матчинг.

Подсистема выключена, а поле прислано → **409** `Подтверждение телефона сейчас недоступно.`

## §169. `POST /api/profile/change-phone` — ⚠️ ЛОМАЮЩЕЕ ИЗМЕНЕНИЕ ПОВЕДЕНИЯ

Маршрут получает **новый отказ**, которого раньше не было, и **новую политику лимитов**
`phone-change` (5/час на пользователя; до цикла маршрут не был покрыт никакой политикой).

**Запрос (дополнение)**
```jsonc
{
  "currentPassword": "…",
  "newPhone": "+7 (900) 000-00-02",
  "verification": {                 // ← НОВОЕ, необязательное
    "sessionId": "5f1c…",
    "statusToken": "Qm9iLXR…"
  }
}
```

**Правило (US-14-17, Р3 + Р6)**

| Ситуация | Ответ |
|---|---|
| Номер не меняется | как сегодня — 200 `ProfileDto` |
| На новом номере **нет** гостевых записей | как сегодня — 200. Подтверждение **не требуется** (прямое требование Р1) |
| На новом номере **есть** гостевые записи, годное подтверждение предъявлено | 200 `ProfileDto` с `phoneVerified: true` |
| На новом номере **есть** гостевые записи, подтверждения нет | **409** `На этом номере уже есть записи. Подтвердите его через MAX — тогда номер можно будет сменить.` |
| То же, но подсистема **выключена** | **409** `Сейчас сменить номер на этот нельзя: подтверждение номера на платформе пока не работает.` ⚠️ Честный отказ — часть приёмки, а не краевой случай |
| Неверный пароль / плохой формат / номер занят другим аккаунтом | как сегодня — 400 |
| Превышен лимит | **429** `Слишком много попыток смены номера. Попробуйте позже.` |

**Побочные эффекты успешной смены (US-14-11):** отметка со старого номера снимается в той же
транзакции; `phoneVerified` в ответе истинен только если новый номер подтверждён этим же вызовом.

**Каждая попытка, упёршаяся в гейт, журналируется** (уровень Information, телефон — через
`LogMasking.Phone`, код причины `GuestBookingsExist`). Остаточный оракул перебора устранён не
полностью — это **записанная цена решения Р3** (§0.2 спеки), а не недоделка.

🔴 **Обязательная формулировка при описании результата** — в коммитах, changelog, отчётах и
`CURRENT_STATE.md`:

> закрыт путь через смену номера; путь через регистрацию нового аккаунта на чужой номер остаётся
> открытым осознанно (`SPEC.md` §6.4, блок `V1` в `CURRENT_STATE.md` §9).

## §170. Аддитивные поля в существующих ответах

### §170.1 `ProfileDto` (`GET /api/profile`, `PUT /api/profile`, ответы `change-phone`)

```jsonc
{
  "id": "…", "phone": "79000000001", "email": null, "firstName": "…", "lastName": "…",
  "avatarUrl": null, "roles": ["Client"], "plan": null,
  "phoneVerified": true,                        // ← НОВОЕ
  "phoneVerifiedAtUtc": "2026-09-24T12:31:00Z"  // ← НОВОЕ, null когда не подтверждён
}
```
Отображение (US-14-14): подтверждён → значок **с текстовой подписью** и датой; не подтверждён при
`enabled=true` → нейтральное предложение подтвердить; не подтверждён при `enabled=false` → **в
профиле не меняется ничего** относительно сегодняшнего экрана.

### §170.2 `MasterClientDto` (`GET /api/masters/clients`)

```jsonc
{
  "clientId": "…", "guestPhone": null, "name": "…", "phone": "…", "email": null,
  "lastVisitDate": "2026-09-01", "totalVisits": 3, "notes": [], "bookingSummaries": [],
  "phoneVerified": true        // ← НОВОЕ: true | false | null
}
```

| Значение | Кто | Как рисуется |
|---|---|---|
| `true` | клиент с аккаунтом, номер подтверждён | значок «Телефон подтверждён» с текстовой подписью |
| `false` | клиент с аккаунтом, не подтверждён | **ничего**: ни цвета, ни иконки, ни слов «не подтверждён» |
| `null` | гость без аккаунта | **ничего** — это «неприменимо», а не «не подтверждён» |

🔴 **Запреты, проверяемые на приёмке (R15):** никакой сортировки и фильтрации по признаку; никакого
красного; экран компании, где **у всех** `false`/`null` (а сегодня это любая компания), выглядит
ровно как сегодня. Ни одно действие персонала не начинает зависеть от признака — **это не гейт**.

⚠️ Признака **нет** и не должно появиться в публичных и анонимных ответах: `GET /api/companies`,
`GET /api/companies/public`, карточка компании, виджет, отзывы (Q17).

### §170.3 `GET /api/profile/export`

Добавляется одна секция:
```jsonc
"phoneVerification": {
  "phoneVerified": true,
  "method": "MaxBot",
  "verifiedAtUtc": "2026-09-24T12:31:00Z"
}
```
Идентификатор MAX-аккаунта (в том числе хешированный) и открытые сессии в выгрузку **не входят**
(§151.3 архитектуры). Сопоставление гостевых сущностей по телефону в выгрузке **не меняется** —
решение Р6.
