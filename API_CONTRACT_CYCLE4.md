## 19. Общее для всех эндпоинтов цикла

### 19.1 Соглашения, действующие без изменений

`§0.1` (camelCase, enum строками, `DateOnly`/`TimeOnly`/`DateTime` ISO-8601 UTC) и `§0.2` (формат тел
ошибок: **голая строка** для 400/402/409/429, **пустое тело** для 403 и 401) цикла 3 переносятся
дословно. `AddProblemDetails()` по-прежнему запрещён.

### 19.2 Коды, которыми пользуется этот цикл

| Код | Когда | Тело |
|---|---|---|
| 400 | валидация (неизвестная зона, порог ≥ времени напоминания, неизвестный плейсхолдер, внешняя ссылка в шаблоне) | голая строка |
| **402** | упёрлись в тариф (`AllowNotificationChannel == false`) **или** канал не оплачен / период истёк | голая строка |
| 403 | не владелец, чужая компания, чужой канал, не суперадмин | **пустое** |
| 404 | канала/компании/города нет **или** он не принадлежит вызывающему (чужой канал неотличим от несуществующего) | пусто |
| **409** | состояние не позволяет действие: канал уже подключён, риск не принят, назначение второй компании без подтверждения, цена опции не задана | голая строка |
| **429** | тестовое сообщение чаще порога; вебхук чаще лимита | голая строка |
| 401 | **только вебхук** при неверном токене | пустое |

### 19.3 Права

- **Владелец** — `CompanyMembership.IsOwnerAsync` хотя бы по одной из его компаний; каналы
  фильтруются по `OwnerUserId == userId`. SuperAdmin к владельческим эндпоинтам каналов **не имеет
  доступа** (403): он не должен видеть чужие каналы иначе как в своей сводке.
- **Персонал компании** — `CompanyMembership.IsStaffAsync` (журнал доставки, US-32 п. 5).
- **Настройки и шаблоны компании** — только владелец компании.

### 19.4 Перечисления цикла (значения — точные строки JSON)

```
ChannelState        NotConnected | Connecting | Connected | Disconnected |
                    Blocked | DisabledByOwner | NeedsReconnect | Replaced
ChannelPaymentState NotPaid | Paid | Suspended
NotificationType    BookingConfirmed | Reminder | BookingCancelled | BookingRescheduled |
                    StaffBookingCreated | StaffBookingCancelled
NotificationStatus  Pending | Sent | Delivered | Failed | Expired | Skipped | Cancelled
```

`NeedsReconnect` **обязан** показываться отдельным текстом, а не как `NotConnected` (US-55 п. 2):
владельцу нужно объяснить, *почему* привязка исчезла.

### 19.5 `ChannelDto` — форма, общая для всех ответов о канале

```json
{
  "id": "0d2f…",
  "state": "Connected",
  "stateText": "Канал работает, сообщения уходят с номера +7 999 ***-**-45",
  "phoneMasked": "+7 999 ***-**-45",
  "paymentState": "Paid",
  "paidFrom": "2026-09-18T00:00:00Z",
  "paidUntil": "2026-10-18T00:00:00Z",
  "requestedAt": null,
  "connectedAt": "2026-09-18T10:12:03Z",
  "riskAcceptedAt": "2026-09-18T10:07:41Z",
  "idleSince": null,
  "idleDeadline": null,
  "replacedByChannelId": null,
  "companies": [
    { "companyId": "1a2b…", "companyName": "Салон на Ленина", "isActive": true }
  ],
  "canConnect": false,
  "canReplace": false
}
```

- **`phoneMasked`, а не `phone`.** Полный номер в ответах не возвращается вовсе; владелец видел его
  при сканировании QR. `apiTokenInstance`, `idInstance` и партнёрский токен в DTO **отсутствуют
  физически** — их нет в модели ответа (US-54 п. 3).
- `stateText` формирует **сервер** (тексты US-55 п. 2 в одном месте); фронт его показывает, а не
  сочиняет свой словарь.
- `idleDeadline` — дата, после которой номер будет отключён из-за простоя; `null`, если простоя нет.
  По нему рисуется предупреждение US-62 п. 6. **Плашка в кабинете — единственный способ, которым
  владелец узнаёт и о простое, и о разрыве** (письмо вырезано, `ARCHITECTURE_CYCLE4.md` §31.3),
  поэтому и `state`/`stateText`, и `idleDeadline` обязаны быть отрисованы, а не «сделаны потом».
- **`contactEmail` в DTO нет.** Сбор email владельца при оплате канала убран решением заказчика; поле
  в модели данных остаётся, но не заполняется и наружу не отдаётся (§23.1 архитектуры).
- `canConnect` / `canReplace` — «кнопка активна», посчитанные сервером по тем же правилам, что и
  гейты (конвенция трёхуровневых флагов `CompanyDto`, цикл 3): фронт гасит кнопку заранее, а не
  ловит 402 после клика.

## 20. `GET /api/notification-channels` — US-53 п. 1 · T4-B4 · **НОВЫЙ**

Список каналов владельца.

**Запрос:** без параметров. `[Authorize]`, роль владельца.
**200 OK:** `{ "channels": [ ChannelDto, … ] }` — массив в конверте, не голый массив.
**403** — вызывающий не владелец ни одной компании.

## 21. `GET /api/notification-channels/offer` — US-57 пп. 2, 6 · T4-B11 · **НОВЫЙ**

Что показать владельцу **до** покупки. Отдельный эндпоинт, потому что блок «подключить канал»
рисуется и тогда, когда каналов ещё нет вовсе.

**200 OK**
```json
{
  "available": true,
  "pricePerMonth": 990,
  "currency": "RUB",
  "idleDays": 3,
  "planAllows": true,
  "riskTextVersion": "2026-09-18-draft"
}
```

- `available: false` + `pricePerMonth: null` — **цена суперадмином не задана**; фронт показывает
  «подключение каналов временно недоступно» и **не** показывает ноль (US-57 п. 6).
- `planAllows: false` — тариф не даёт покупать канал; фронт показывает заглушку «доступно на
  тарифе …» (US-31 п. 4).

## 22. `POST /api/notification-channels` — US-57 п. 2 · T4-B4 · **НОВЫЙ**

Заявка владельца на подключение канала. Продукт **не генерирует счёт и не хранит платёжных данных**.

**Запрос:** тела нет. Допускается пустое тело (`{}` либо `Content-Length: 0`) — сервер его
игнорирует и **не** валидирует. Сбор email владельца убран решением заказчика: связь по заявке идёт
вне продукта, а в кабинете владелец видит состояние заявки через `requestedAt` и суперадмин — через
§34.1.

*Фронту (T4-F4):* форма заявки — одна кнопка подтверждения, полей ввода в ней нет.

**201 Created:** `ChannelDto` (состояние `NotConnected`, `paymentState: "NotPaid"`, `requestedAt`
заполнен).
```json
{ "contactEmail": "owner@example.com" }
```
`contactEmail` — необязателен, если у владельца уже есть email; валидируется как email.

**201 Created:** `ChannelDto` (состояние `NotConnected`, `paymentState: "NotPaid"`, `requestedAt`
заполнен).

| Код | Когда | Тело |
|---|---|---|
| 402 | тариф не позволяет купить канал | `"Подключение канала недоступно на вашем тарифе"` |
| 409 | цена опции не задана суперадмином | `"Подключение каналов временно недоступно"` |
| 403 | вызывающий не владелец | пусто |

## 23. `POST /api/notification-channels/{id}/accept-risk` — US-53 п. 7 · T4-B6 · **НОВЫЙ**

Отдельное осознанное действие, **предусловие привязки**.

**Запрос:** `{ "version": "2026-09-18-draft" }` — версия текста, которую владелец видел; сохраняется
вместе с датой (по образцу `UserConsent`).
**204 No Content.**
**400** — версия не совпадает с текущей («текст изменился, прочитайте заново»).

Текст рисков фронт получает в составе `GET /api/notification-channels/offer` (`riskTextVersion`) и
рендерит из своих локализованных строк; **формулировки — «рыба», подлежащая вычитке юристом**.

## 24. Привязка номера и QR — US-53 п. 3 · T4-B6 · **НОВЫЕ**

### 24.1 `POST /api/notification-channels/{id}/connect`

Создаёт инстанс у провайдера и переводит канал в `Connecting`.

**202 Accepted:** `{ "state": "Connecting", "refreshAfterSeconds": 3 }`

| Код | Когда | Тело |
|---|---|---|
| 402 | канал не оплачен или период истёк | `"Канал не оплачен"` |
| 409 | риск не принят | `"Сначала подтвердите условия подключения"` |
| 409 | канал уже подключён / уже идёт привязка | `"Номер уже подключается"` |
| 503 | провайдер недоступен | `"Сервис подключения временно недоступен, попробуйте позже"` |

### 24.2 `GET /api/notification-channels/{id}/qr`

**200 OK**
```json
{
  "state": "Connecting",
  "qrBase64": "iVBORw0KGgo…",
  "refreshAfterSeconds": 3,
  "expiresInSeconds": 20
}
```

- `qrBase64` — **PNG в base64 без префикса**; фронт делает `data:image/png;base64,${qrBase64}`.
- **Фронт обязан опрашивать с интервалом `refreshAfterSeconds`**, а не со своей константой: сервер
  кэширует ответ провайдера на 2 секунды и таким образом защищает провайдера от шторма
  (`ARCHITECTURE_CYCLE4.md` §29.2).
- Когда `state` становится `Connected`, `qrBase64` = `null`; фронт закрывает модалку и инвалидирует
  `GET /api/notification-channels`.
- Опрос прекращается фронтом через **15 минут** — столько же живёт неавторизованный инстанс на
  сервере (US-53 п. 5), после чего канал сам вернётся в `NotConnected`.
- **409** — канал не в состоянии `Connecting`.

### 24.3 `POST /api/notification-channels/{id}/test-message` — US-55 п. 7

Отправка тестового сообщения **только на номер владельца**; другого адресата эндпоинт не принимает
(иначе это инструмент рассылки). Антибан-пауза к нему не применяется.

**200 OK:** `{ "delivered": true, "message": "Сообщение отправлено на ваш номер" }`
**429:** `"Проверять канал можно не чаще одного раза в 5 минут"`
**409:** канал не `Connected`.

## 25. Назначение компаний на канал — US-61 · T4-B4 · **НОВЫЕ**

### 25.1 `POST /api/notification-channels/{id}/companies`

```json
{ "companyId": "1a2b…", "warningAcknowledged": false }
```

| Код | Когда | Тело |
|---|---|---|
| 201 | назначено | `ChannelDto` |
| **409** | это **вторая и последующая** компания на канале, а `warningAcknowledged != true` | `"Требуется подтверждение: несколько салонов на одном номере"` |
| 403 | компания не принадлежит вызывающему | пусто |
| 409 | компания уже назначена на **другой** канал | `"Салон уже привязан к другому номеру"` |

**Текст предупреждения из трёх пунктов (US-61 п. 3) живёт на фронте** и показывается **до** повторной
отправки запроса с `warningAcknowledged: true`. Три пункта обязательны: общий бан, «один номер от
имени разных брендов», делёж скорости (~360 сообщений в час на номер). Повторное назначение той же
компании идемпотентно и возвращает 201 без дубля.

### 25.2 `DELETE /api/notification-channels/{id}/companies/{companyId}` — US-61 п. 5

**204 No Content.** Побочный эффект: невыполненные уведомления **этой компании по этому каналу** →
`Cancelled`; соседняя компания на том же канале не затрагивается; канал и его оплаченный период не
трогаются.

## 26. `DELETE /api/notification-channels/{id}` — US-56 п. 1 · T4-B4 · **НОВЫЙ**

Отвязка канала владельцем.

**204 No Content.** Сервер: завершает сеанс, **удаляет инстанс у провайдера**, стирает секрет,
переводит канал в `DisabledByOwner`, невыполненные уведомления по каналу → `Cancelled`.
**Оплаченный период сохраняется на канале** (US-56 п. 2) — канал остаётся видимым в списке.

## 27. `POST /api/notification-channels/{id}/replace` — US-63 · T4-B12 · **НОВЫЙ**

Замена номера после бана. Повторной оплаты не требует.

**201 Created**
```json
{ "newChannelId": "7c8d…", "paidUntil": "2026-10-18T00:00:00Z", "companiesMoved": 2 }
```

Сервер: создаёт новый канал, **переносит оплаченный период и назначения компаний**, перепривязывает
`Pending`-строки очереди к новому каналу (`Expired` **не воскрешаются**), старый канал → `Replaced`
со ссылкой `replacedByChannelId`. Дальше владелец идёт обычным путём §24.

**409** — канал не в состоянии `Blocked` (кнопка показывается только для него).

## 28. Настройки уведомлений компании — US-31 · T4-B7 · **НОВЫЕ**

### 28.1 `GET /api/companies/{id}/notification-settings`

**200 OK**
```json
{
  "enabledTypes": ["BookingConfirmed", "Reminder", "BookingCancelled", "BookingRescheduled"],
  "reminderLeadMinutes": 1440,
  "minLeadMinutes": 120,
  "planAllowsChannel": true,
  "channel": {
    "assigned": true,
    "channelId": "0d2f…",
    "state": "Connected",
    "stateText": "Канал работает, сообщения уходят с номера +7 999 ***-**-45",
    "paymentState": "Paid",
    "paidUntil": "2026-10-18T00:00:00Z"
  },
  "effectiveEnabled": true,
  "blockedReason": null
}
```

`effectiveEnabled` — то самое **производное** «опция включена» (SPEC §4.0): тариф разрешает **и**
канал назначен **и** оплачен **и** подключён. `blockedReason` — человеческий текст, если нет
(`"Салон не привязан к каналу"`, `"Канал не оплачен"`, `"Канал отвалился"`, `"Недоступно на вашем
тарифе"`). Доступ — владелец компании; **403** для остальных.

> **Правка контракта (найдена фронтендом при интеграции, T4-B7).** `channel.stateText` — источник тот
> же, что у `ChannelDto.stateText` в списке каналов (§19.5, US-55 п. 2): без этого поля вкладка
> «Уведомления» компании была вынуждена сочинять свой текст о разрыве канала, который не совпадал
> дословно с тем, что видно в разделе «Каналы» — для владельца одно и то же событие выглядело как два
> разных сообщения. `null` только когда `channel.assigned == false` (описывать нечего).

### 28.2 `PUT /api/companies/{id}/notification-settings`

```json
{
  "enabledTypes": ["BookingConfirmed", "Reminder"],
  "reminderLeadMinutes": 1440,
  "minLeadMinutes": 120
}
```

| Код | Когда | Тело |
|---|---|---|
| 200 | сохранено | тело как у GET |
| 400 | `reminderLeadMinutes` вне 60…4320 | `"Напоминание можно отправлять за 1–72 часа до визита"` |
| 400 | `minLeadMinutes` вне 0…720 | `"Порог может быть от 0 до 12 часов"` |
| **400** | `minLeadMinutes >= reminderLeadMinutes` | `"Напоминание за 1 час при пороге 2 часа не уйдёт никогда"` |
| 402 | тариф не даёт / канал не оплачен | голая строка |

Изменение порога **немедленно** влияет на стоящие в очереди строки: те, до визита по которым осталось
меньше нового порога, снимаются в `Skipped` ближайшим проходом отправщика.

```json
    { "token": "{КлиентИмя}",     "description": "Имя клиента",        "types": ["*"] },
    { "token": "{Услуга}",        "description": "Название услуги",    "types": ["*"] },
    { "token": "{Мастер}",        "description": "Имя мастера",        "types": ["*"] },
    { "token": "{Дата}",          "description": "Дата визита",        "types": ["*"] },
    { "token": "{Время}",         "description": "Время визита",       "types": ["*"] },
    { "token": "{Салон}",         "description": "Название салона",    "types": ["*"] },
    { "token": "{Адрес}",         "description": "Адрес салона",       "types": ["*"] },
    { "token": "{ТелефонСалона}", "description": "Телефон салона",     "types": ["*"] },
    { "token": "{ПричинаОтмены}", "description": "Причина отмены",     "types": ["BookingCancelled"] },
    { "token": "{НоваяДата}",     "description": "Новая дата",         "types": ["BookingRescheduled"] },
    { "token": "{НовоеВремя}",    "description": "Новое время",        "types": ["BookingRescheduled"] }
  ],
  "unsubscribeLine": "Отказаться от уведомлений: https://ezbook.ru/u/…",
  "templates": [
    {
      "type": "Reminder",
      "body": "Здравствуйте, {КлиентИмя}! Напоминаем о визите {Дата} в {Время}.",
      "isDefault": false,
      "defaultBody": "Здравствуйте, {КлиентИмя}! Напоминаем: {Услуга} {Дата} в {Время}. {Салон}",
      "updatedAt": "2026-09-18T12:00:00Z"
    }
  ]
}
```

- Список плейсхолдеров **приходит с сервера** — фронт рисует кнопки по нему и не держит свою копию.
- `unsubscribeLine` — **нередактируемый хвост**, показывается в редакторе как неактивный текст
  (US-33 п. 4, US-59 п. 3). В `body` его быть не должно и он туда не сохраняется.
- `isDefault: true` = владелец шаблон не менял; кнопка «вернуть текст платформы» = `PUT` с `body: ""`.

### 29.2 `PUT /api/companies/{id}/notification-templates/{type}`

```json
{ "body": "Здравствуйте, {КлиентИмя}! Ждём вас {Дата} в {Время}." }
```

**200 OK** — объект шаблона. **Только владелец** (403), **только при оплаченном назначенном канале**
(402).

| 400, голая строка | Когда |
|---|---|
| `"Неизвестный плейсхолдер {Скидка}. Допустимы: {КлиентИмя}, {Услуга}, …"` | неизвестный токен |
| `"Текст должен быть от 1 до 1000 символов"` | длина |
| `"Внешние ссылки в сообщениях запрещены"` | любой URL, кроме нашего домена |
| `"Текст не может состоять из одних подстановок"` | только плейсхолдеры/пробелы |
| `"В напоминании обязательны {Дата} и {Время}"` | тип `Reminder` |

Правка **не меняет уже поставленные в очередь сообщения** (текст снят на момент постановки).

### 29.3 `POST /api/companies/{id}/notification-templates/{type}/preview` — *(режется пятым)*

`{ "body": "…" }` → **200 OK** `{ "rendered": "…\n\nОтказаться от уведомлений: https://…" }` —
рендер на вымышленных данных вместе со строкой отписки. Валидация та же, что у `PUT`.

## 30. Журнал доставки — US-32 · T4-B10 · **НОВЫЕ**

### 30.1 `GET /api/companies/{id}/notifications`

**Параметры:** `page`, `pageSize` (конвенция `Pagination`, клампится), `status`, `type`, `from`, `to`.
**Доступ:** персонал компании (`IsStaffAsync`), иначе 403.

**200 OK** — конверт `PagedResult<T>` цикла 3:
```json
{
  "items": [
    {
      "id": "aa11…",
      "createdAt": "2026-09-18T09:00:00Z",
      "type": "Reminder",
      "typeText": "Напоминание",
      "recipientName": "Анна",
      "recipientPhoneMasked": "+7 999 ***-**-45",
      "status": "Delivered",
      "statusText": "доставлено",
      "bookingId": "bb22…",
      "visitStart": "2026-09-19T04:00:00Z",
      "sentAt": "2026-09-18T09:00:12Z",
      "channelId": "0d2f…"
    }
  ],
  "page": 1, "pageSize": 20, "total": 137, "hasNext": true
}
```

- **Телефон только маскированный.**
- `statusText` — **русский текст причины, собранный сервером** (US-32 п. 2): «доставлено»,
  «прочитано», «отправлено, доставка не подтверждена», «не доставлено: у клиента нет WhatsApp»,
  «клиент отказался от уведомлений», «визит уже начался — не отправлено», «канал недоступен», «срок
  действия канала истёк», «до визита осталось слишком мало времени», «временный сбой, повторим».
  Причин про лимит и суточный потолок **нет и не будет**.
- Фильтр `status=Expired` **отделён** от `status=Failed` — это требование, а не удобство.

### 30.2 `GET /api/companies/{id}/notifications/summary?days=30`

Отдельный эндпоинт, потому что `PagedResult<T>` — фиксированный конверт без места под сводку.

```json
{
  "days": 30,
  "sent": 412, "delivered": 301, "read": 244,
  "failed": 18, "skipped": 33, "expired": 7,
  "channelPaidUntil": "2026-10-18T00:00:00Z",
  "byCompany": null
}
```

`byCompany` — массив той же формы с `companyId`/`companyName`, **непустой только если на канале
несколько компаний** (US-32 п. 4). `expired` в «не доставлено» **не входит**.

### 30.3 Отметка в карточке записи — US-32 п. 6

`GET /api/bookings/master` и `GET /api/bookings/{id}` получают **аддитивное** поле:
```json
"reminderStatus": { "status": "Delivered", "text": "напоминание доставлено" }
```
`null`, если уведомлений по записи нет.

## 31. Город и часовой пояс компании — US-30 · T4-B2

### 31.1 `GET /api/cities?search=бар&take=20` — **НОВЫЙ**, анонимный

```json
{ "items": [ { "id": 42, "name": "Барнаул", "region": "Алтайский край",
               "timeZoneId": "Asia/Barnaul", "utcOffsetMinutes": 420,
               "label": "Барнаул, Алтайский край" } ] }
```
`take` клампится до 20. Пустой `search` → первые 20 по алфавиту. `label` собирает сервер — фронт не
склеивает название с регионом сам.

### 31.2 `POST /api/companies` — **BREAKING**

Тело получает **обязательное** `cityId` и необязательное `timeZoneId`.

```json
{ "name": "Салон на Ленина", "cityId": 42, "timeZoneId": null, … }
```

| Код | Когда | Тело |
|---|---|---|
| 400 | `cityId` отсутствует | `"Укажите город салона"` |
| 400 | города нет в справочнике | `"Город не найден"` |
| 400 | `timeZoneId` не резолвится | `"Неизвестный часовой пояс"` |

**Влияние на фронт: правка обязательна** — форма создания компании без комбобокса города начнёт
получать 400 (T4-F2).

### 31.3 `PUT /api/companies/{id}`

Принимает `cityId` и `timeZoneId`. Правила (US-30 п. 3):
- передан только `cityId` → зона выводится из города, **если `timeZoneIsManual == false`**;
- передан `timeZoneId`, отличный от городского → `timeZoneIsManual = true`, и последующие смены
  города зону **не перетирают**;
- передан `timeZoneId: null` явно → возврат к городской зоне, `timeZoneIsManual = false`.

### 31.4 `CompanyDto` — пять аддитивных полей (во всех семи точках, отдающих `CompanyDto`)

```json
{
  "cityId": 42,
  "cityName": "Барнаул",
  "cityRegion": "Алтайский край",
  "timeZoneId": "Asia/Barnaul",
  "timeZoneIsManual": false,
  "utcOffsetMinutes": 420
}
```

Фронт показывает выведенную зону **текстом**: «Барнаул → UTC+7, `Asia/Barnaul`» (US-30 п. 3) — угадать
её по интуиции нельзя, и это ровно та ошибка, ради которой поле показывается.

## 32. Отписка — US-33 · T4-B10 · **НОВЫЕ**

### 32.1 Кабинет клиента

`PUT /api/notifications/preferences` `{ "enabled": false }` → **204**.

### 32.2 Публичная страница отказа (ссылка из сообщения)

## 33. `POST /api/notifications/provider-webhook/{token}` — US-32 п. 7 · T4-B13 · **НОВЫЙ** *(режется вторым)*

Анонимный. Тело — **как его присылает провайдер**; разбирает его адаптер, наружу форма провайдера не
документируется намеренно (сменится вместе с провайдером).

| Код | Когда |
|---|---|
| 200 | принято — **в том числе для неизвестного `idMessage`** (иначе провайдер будет ретраить вечно) |
| **401** | токен не совпал; **пустое тело**, ни одна строка не изменена |
| 429 | превышена частота (политика `notifications-webhook`, 600/мин на адрес) |

Ответ всегда пустой: никаких подробностей наружу. Обновление статуса **монотонно**
(`Sent < Delivered < Read`), повторный или опоздавший вебхук ничего не портит.

## 34. Админские эндпоинты — US-57 · T4-B11 · **НОВЫЕ**

Все — под существующим `[Route("api/admin")] [Authorize(Roles = "SuperAdmin")]`; остальным **403**.

### 34.1 `GET /api/admin/notification-channels?state=&paymentState=&page=&pageSize=`

`PagedResult<AdminChannelDto>`: канал, владелец (имя + маскированный телефон), состояние, состояние
оплаты, период, число назначенных компаний, `idleSince`, дата заявки. Заявки — это
`paymentState=NotPaid` с непустым `requestedAt`.

### 34.2 `GET /api/admin/notification-channels/summary`

```json
{ "connected": 12, "connecting": 1, "disconnected": 2, "blocked": 1,
  "needsReconnect": 3, "idle": 4, "expiringIn7Days": 5, "pendingRequests": 2 }
```
Показывается там же, где сегодня `GET /api/admin/scheduled-tasks` — **новых механизмов наблюдаемости
не заводится** (US-55 п. 8).

### 34.3 `POST /api/admin/notification-channels/{id}/payment` — отметка оплаты и продление

```json
{ "paidFrom": "2026-09-18", "paidUntil": "2026-10-18", "amount": 990, "comment": "счёт 114" }
```
**200 OK** → `AdminChannelDto`. Пишет `ChannelPaymentLog` (кто, когда, что изменил).
**400** — `paidUntil <= paidFrom`.
Отметка оплаты **обнуляет простой** (ближайшим проходом фоновой задачи) и не требует повторного QR,
если инстанс ещё жив.

### 34.4 `POST /api/admin/notification-channels/{id}/suspend` · `/resume`

`{ "comment": "неоплата" }` → **204**. Ставит/снимает `IsSuspendedByAdmin`, журналируется там же.

### 34.5 `GET` / `PUT /api/admin/platform-settings`

```json
{ "channelPricePerMonth": 990, "channelIdleDays": 3 }
```
`PUT` принимает оба поля; каждое изменение пишется в `PlatformSettingChangeLog`.
**400** — `channelIdleDays` вне 0…60; `channelPricePerMonth` отрицательная.
`channelPricePerMonth: null` допустим и означает «опция не продаётся».

## 37. Чек-лист согласования BE↔FE перед мёржем цикла

1. Строки `ChannelState` и `NotificationStatus` совпадают с `src/types/index.ts` — **проверяется
   грепом, а не памятью**.
2. Фронт нигде не строит `stateText`/`statusText` сам — он приходит с сервера.
3. Интервал опроса QR берётся из `refreshAfterSeconds`, а не из константы.
4. Диалог назначения второй компании отправляет `warningAcknowledged: true` **только после** показа
   предупреждения из трёх пунктов.
5. Все формы гасят кнопки по `canConnect`/`canReplace`/`planAllows`/`effectiveEnabled`, а не ловят
   402 после отправки.
6. Ни один ответ API не содержит `apiTokenInstance`, `idInstance`, партнёрского токена и полного
   номера клиента — греп по фактическим ответам в функциональных тестах.
7. Форма создания компании отправляет `cityId` (иначе 400) — единственное ломающее изменение цикла.
