# API_CONTRACT — цикл 17 ServiceBooking (§320–§329)

**Назначение.** Точка синхронизации backend- и frontend-разработчика на время цикла 17. Обе стороны
работают по этому файлу и по машиночитаемому `contracts/cycle17/openapi.yaml`, **не читая код друг
друга**. Решения и обоснования — `ARCHITECTURE_CYCLE17.md` (§300–§318).

**Источник истины по ФОРМЕ** — `contracts/cycle17/openapi.yaml`. При расхождении текста ниже и схемы
прав **схема**. Текст объясняет смысл и правила, схема — форму.

**Базовая ревизия:** ветка `cycle/017-c15-techdebt-fixes`, отправная точка `develop` `f45fe56`.
Все «файл:строка» — по ней.

**Что здесь есть.** Только то, что цикл 17 **добавляет или меняет**, плюс фактическое состояние
затронутых ручек. Остальной API — `API_DOCUMENTATION.md` и контракты циклов 3–15; цикл их не меняет.

**Цикл 17 не добавляет ни одного нового эндпоинта.** Всё новое выражено: одним вычисляемым полем
существующего `BookingDto`, одним необязательным полем существующего `SubscriptionRequestDto`, одним
новым кодом ответа у существующей ручки и изменением содержимого одной уже существующей строки.

## §320. Конвенции, действующие без изменений

- `camelCase` в JSON; enum — строками; `DateTime` — ISO-8601 UTC; `DateOnly` — `YYYY-MM-DD`;
  `TimeOnly` — `HH:mm:ss`.
- Тела ошибок `400/402/409/410/429/503` — **голая строка** (`text/plain`), `401/403` — **пустое тело**,
  `404` — пустое тело там, где существование объекта не подтверждается.
- `ProblemDetails` не используется (кроме автовалидации `[ApiController]`); `SuppressMapClientErrors = true`.
- **Все новые поля — добавочные.** Ничего не удаляется и не переименовывается.
- `null` у вычисляемого поля = «сервер не считал это для данного вызывающего», **не** «нет значения»
  и **не** «нельзя».
- Текст, который видит пользователь, **составляет сервер**; фронт печатает как есть (конвенция §41 п. 8
  цикла 7 и §283 цикла 15).

## §322. `PATCH /api/bookings/{id}/cancel` — правило отмены переезжает на сервер

**Форма запроса не меняется:** `[Authorize]`, тело — голая JSON-строка (причина) или `null`.

```http
PATCH /api/bookings/6f3c…/cancel
Authorization: Bearer <jwt>
Content-Type: application/json

"Заболел"
```

### §322.1. Кто и по каким правилам

| Вызывающий | Как определяется сервером | Окно отмены |
|---|---|---|
| **Персонал** | `CanManageBookingAsync`: назначенный мастер, владелец компании, суперадмин | **не применяется** (как сегодня) |
| **Клиент-владелец** | `booking.ClientId == userId` **и** не персонал | **применяется** |
| Все прочие | — | `403`, пустое тело (как сегодня) |

Полномочие вычисляется **из базы**, порядок — сначала персонал. Тело запроса новых полей не получает:
клиент не может попросить послаблений персонала никаким набором параметров.

### §322.2. Правило окна (только клиент-владелец)

```
minHours      = Company.ClientRescheduleMinHours, приведённое к [0..168], иначе 2
visitStartUtc = начало визита в часовом поясе компании, приведённое к UTC
отказ, если   nowUtc > visitStartUtc − minHours часов
```

Это **то же самое поле**, что управляет окном переноса (решение заказчика, SPEC §0-bis). Отдельной
настройки отмены нет. При `minHours = 0` отменять можно вплоть до момента начала визита.

### §322.3. Коды ответов

| Код | Когда | Тело |
|---|---|---|
| `204` | отменено | пусто |
| `400` | причина длиннее 300 символов | голая строка (как сегодня) |
| **`409`** | **клиент-владелец внутри окна, включая уже начавшийся/прошедший визит** | **голая строка, составленная сервером**: `Отменить запись можно не позже чем за {N} ч до визита. Чтобы отменить, свяжитесь с салоном.` (`{N}` — фактическое значение компании) |
| `403` | вызывающий не владелец записи и не персонал | пусто |
| `404` | записи нет | пусто |

**Почему `409`, а не `400`.** `400` у этой ручки уже занят валидацией ввода. Один код на «ты неверно
заполнил» и «ты опоздал» заставил бы фронт **разбирать русский текст подстрокой** — это тот же класс
дефекта, который цикл закрывает в C15-1. `409` = «запрос конфликтует с текущим состоянием ресурса»
и является тем самым машиночитаемым кодом причины, которого требует US-17-06.

⚠️ **Асимметрия с `PATCH /bookings/{id}/reschedule`**, где такое же по смыслу правило отвечает `400`
(§287.2 цикла 15), **осознанная**: менять код ответа уже выпущенной ручки — ломающее изменение,
которого цикл избегает. Зафиксировано как долг `C17-2`.

### §322.4. Что обязан делать фронт

1. Кнопка «Отменить» рисуется по `booking.clientCancelAllowed !== false`, то есть скрывается
   **только** при явном `false`. Локальной арифметики по времени на экране «Мои визиты» не
   остаётся (`canCancelBooking` с константой `> 2` удаляется целиком).
   ⚠️ Прошлая редакция говорила «только по `=== true`», что противоречило п. 2 ниже и требовало бы
   прятать кнопку при отсутствии поля. Реализация следует п. 2; исправлена формулировка, а не код.
2. Если поля в ответе нет (`undefined` — старый кеш, другой эндпоинт) — **кнопка показывается**, и
   решение принимает сервер. Догадываться на фронте запрещено: это вернуло бы правило в вёрстку.
3. `409` показывается **дословно серверной строкой** (`cancelError.ts`, новая ветка), fallback —
   `Отменить запись уже нельзя — свяжитесь с салоном.`
4. После `409` список визитов обязан быть **инвалидирован**: раз сервер отказал по времени, локальные
   флаги устарели.

### §322.4-bis. Объяснение вместо молчания, когда кнопки нет

При `clientCancelAllowed === false` рядом обязана стоять строка с правилом этой компании и с живым
способом отменить («свяжитесь с салоном»), по образцу такой же строки у переноса (§305.2).

Это не косметика. Отказаться от договора об оказании услуг потребитель вправе в любое время
(ст. 32 ЗоЗПП), и закрытая кнопка этого права не отменяет — она ограничивает интерфейс, а не
договор. Но пока интерфейс молчит, ограничение читается как запрет, и тогда оно перестаёт быть
техническим. Вывод `legal-counsel` «верхняя граница окна не обязательна» держится именно на наличии
этой строки; без неё честнее вводить предел в 24 часа.

### §322.5. Видимое изменение поведения (для `API_DOCUMENTATION.md` и `CHANGELOG.md`)

До цикла 17 прямой вызов этой ручки отменял визит **в любой момент**, включая пять минут до начала и
уже прошедшие визиты. После — для клиента-владельца действует окно компании. Персонал не затронут.
Миграции данных нет: правило вычисляется в момент вызова.

## §323. `GET /api/bookings/client` — четвёртое вычисляемое поле `BookingDto`

Форма ответа прежняя (массив `BookingDto`). Цикл добавляет **одно** поле; три поля цикла 15
(`clientRescheduleAllowed`, `clientRescheduleMinHours`, `companyBookingHorizonDays`) остаются без
изменений.

```jsonc
{
  "id": "…", "companyId": "…", "date": "2026-10-02", "startTime": "14:00:00",
  "status": "Confirmed",
  "clientRescheduleAllowed": true,      // цикл 15, не меняется
  "clientRescheduleMinHours": 24,       // цикл 15, не меняется
  "companyBookingHorizonDays": 30,      // цикл 15, не меняется
  "clientCancelAllowed": true           // ← ЦИКЛ 17
}
```

| Поле | Тип | Где считается | Смысл |
|---|---|---|---|
| `clientCancelAllowed` | `boolean \| null` | **только** `GET /api/bookings/client` | Зеркалит правило §322.2 для **этого** визита и **этого** вызывающего: статус `Pending`/`Confirmed` **и** визит дальше окна. `null` — «сервер не считал» (`GET /api/bookings/master`, `GET /api/bookings/{id}`, ответ `POST /api/bookings`). |

**Почему это не то же самое, что `clientRescheduleAllowed`.** Перенос дополнительно требует
`company.allowSelfBooking` и тарифного разрешения онлайн-записи; отмена — **не требует ни того, ни
другого** и цикл этого не меняет. Переиспользовать один флаг для двух кнопок нельзя.

**Подсказка — не разрешение.** Флаг существует, чтобы не показывать кнопку, которая не сработает.
Сервер перепроверяет правило на самом `PATCH` и не доверяет флагу как выданному праву.

**Производительность:** ноль новых запросов. `Company` уже `Include`'ится в этой выборке, `minHours`
и время начала визита в UTC уже вычисляются там же для `clientRescheduleAllowed`.

## §324. `GET /api/bookings/client` + фронт: объяснение вместо пустоты

Контрактных изменений нет — это требование к интерфейсу, проверяемое на приёмке (US-17-02):

- `clientRescheduleAllowed === false` **и** `clientRescheduleMinHours != null` **и** статус
  `Pending`/`Confirmed` → на месте кнопки «Перенести» — текст с **конкретным правилом этой компании**:
  `Перенести можно не позже чем за {N} ч до визита` (при `N = 0` — `Перенести уже нельзя`).
- поля нет → экран ведёт себя ровно как сегодня (ни кнопки, ни текста), **не ломается**.
- Число `N` берётся **только** из `BookingDto.clientRescheduleMinHours`. Константы во фронте
  после цикла быть не должно — это проверяется `grep`'ом на приёмке.

**Окно переноса в сетке (US-17-01).** `RescheduleModal` обязан не предлагать слоты внутри окна:
граница `now + clientRescheduleMinHours` применяется и к списку дней, и к списку слотов. Если слот
всё же отправлен (гонка, устаревшая вкладка), сервер отвечает `400` с готовой русской строкой —
она показывается дословно (поведение `getClientRescheduleErrorMessage` уже такое, меняется только
сетка).

## §325. Биллинг: два уведомления по снятому с продажи тарифу

«Снятый с продажи» тариф = `isActive: true` **и** `isPublic: false`. Новых полей у тарифа нет.

### §325.1. `POST /api/billing/subscription/request` — предупреждение о необратимости

Запрос не меняется (`SubscriptionRequestInputDto`: `planId`, `options[]`, `comment`).
Ответ `200` (`SubscriptionRequestDto`) получает **одно необязательное поле**:

```jsonc
{
  "id": "…", "status": "Pending", "createdAt": "2026-09-25T10:00:00Z",
  "desiredPlanId": "…", "desiredPlanName": "Профи",
  "estimatedMonthlyPrice": 4990, "items": [], "comment": null,
  "irreversibilityNotice": "<текст от legal-counsel>"   // ← ЦИКЛ 17, обычно null
}
```

| Поле | Тип | Когда непусто |
|---|---|---|
| `irreversibilityNotice` | `string \| null` | **все три условия сразу:** у аккаунта есть активная подписка на тариф; этот текущий тариф `isPublic: false`; заявка просит **смену тарифа** (`planId` передан и отличается от текущего). Иначе — `null`. |

**Текст пишет `legal-counsel`** (пп. 6.13.15–6.13.16 `03-terms-owner.html`, П2.8.6
`13-payment-terms.html`). Сервер отдаёт готовую строку простого текста без разметки; фронт печатает
как есть и **не сочиняет** собственную формулировку, даже временную.

Поле приходит и в `GET /api/billing/subscription` внутри `pendingRequest` — чтобы владелец видел
предупреждение не только в момент отправки, но и при следующем открытии экрана заявки.

⚠️ Поле добавляется также в `contracts/cycle7/openapi.yaml` (`SubscriptionRequestDto`), потому что
типы этого экрана фронт берёт из `types/api-cycle7.generated.ts` (`frontend/src/api/billing.ts:2`).
Диф перегенерации обязан быть ровно одним необязательным полем.

**Отметка на будущее (часть приёмки US-17-08).** Самостоятельной смены тарифа в кабинете сегодня нет.
В коде, собирающем это уведомление, обязан стоять комментарий о втором месте показа — экране
самостоятельной смены, когда он появится.

### §325.2. `GET /api/billing/subscription` — напоминание об окончании оплаченного периода

Форма ответа **не меняется**. Меняется **содержимое** уже существующего `warning.text` при
`warning.kind == "Expiring"` (напоминание формируется по `plan.notifyDaysBefore`, поля
`isExpiringSoon`/`expiresInDays` — как сегодня):

| Текущий тариф | `warning.text` при `kind = "Expiring"` |
|---|---|
| `isPublic: true` | **посимвольно как сегодня**: `Подписка истекает через {N} дн. — продлите её, чтобы не потерять возможности тарифа.` |
| `isPublic: false` | та же строка **плюс** предупреждение о необратимости (формулировка — `legal-counsel`) |

`warning.kind = "Expired"` **не меняется** — требование п. 6.8.5 относится к напоминанию **до**
окончания периода.

Фронту делать нечего, кроме регрессии: текст уже печатается как есть.

## §326. `PUT /api/companies/{id}` — контракт не меняется, меняется подпись в интерфейсе

Семантика остаётся ровно такой, как её зафиксировал цикл 15 (§283):

- `clientRescheduleMinHours` **отсутствует в теле** → сохранённое значение **не трогается**;
- значение вне `[0..168]` → `400`, голая строка `Окно переноса — от 0 до 168 часов`;
- `0` — легитимное явное значение, не сброс.

**Что обязан сделать фронт (US-17-03, C15-6.3):** привести подсказку и метку поля в соответствие с
этой семантикой и с тем, что поле теперь управляет **двумя** правилами:

- метка: «за сколько часов клиент может перенести **или отменить** запись»;
- подсказка: `Пусто — оставить текущее значение. 0 — можно перенести и отменить вплоть до начала
  визита. У новой компании по умолчанию 2 часа.`

Поведение «пусто = не отправлять» **не меняется**: менять его значило бы менять контракт выпущенной
ручки. Сегодняшняя подсказка «Пусто — 2 часа по умолчанию» — ложь именно про поведение, и чинится
именно текст.

**Доступность (C15-6.4, НФТ SPEC §3):** у полей `yandexMapsUrl`, `twoGisUrl`,
`clientRescheduleMinHours` при ошибке обязаны быть `aria-invalid` и `aria-describedby`,
указывающий на `id` абзаца с текстом ошибки. Маршрутизация серверной строки к полю уже существует
(`mapLinksFieldError.ts`) и не меняется.

## §327. Правовая подстановка величин — форма ответа API не меняется

`GET /api/legal/texts/{key}` отдаёт тот же HTML, тот же кеш, ту же версию. Меняется **только
клиентская подстановка**: фронт обязан распознавать **любую** форму разметки, которую распознаёт
сборочный сканер (`data-legal-(value|when|unless)\s*=\s*"([^"]*)"`) — произвольные пробелы, переносы
строк, дополнительные атрибуты.

**Контракт между двумя реализациями зафиксирован файлом** `contracts/legal/runtime-value-forms.json`:
для каждой формы разметки он говорит, видит ли её сканер и обязан ли фронт её подставить.
**Инвариант:** `scannerSees === true` ⟹ `frontSubstitutes === true`. Обе стороны читают этот файл в
тестах; расхождение падает, а не проезжает молча.

Сканер `ServiceBooking.LegalKit` **не ослабляется** — он обязан видеть больше подставляльщика, иначе
перестанет ловить опечатки в именах величин.

## §328. Чек-лист интеграции (что фронт обязан проверить до сдачи)

1. Кнопка «Отменить» появляется/исчезает **по `clientCancelAllowed`**, а не по часам браузера;
   `grep -rn "differenceInHours" frontend/src/pages/ClientBookingsPage.tsx` — пусто.
2. `409` на отмене показывает **серверную строку**, список визитов инвалидируется.
3. Отсутствие `clientCancelAllowed` (мок без поля) — кнопка есть, экран не падает.
4. В окне переноса при `clientRescheduleMinHours = 24` нет ни одного дня/слота ближе 24 часов;
   при `0` сетка такая же, как до цикла.
5. `grep -rn "clientRescheduleMinHours" frontend/src` находит чтение минимум в одном **компоненте**,
   а не только в `types/`.
6. Карточка компании: ссылки в карты видны при пустом адресе; при обеих пустых ссылках блок не
   занимает места; в разметке нет `<a href="">`.
7. Подсказка под полем окна и реальное поведение «пусто» совпадают.
8. `pendingRequest.irreversibilityNotice` показывается и сразу после отправки заявки, и при повторном
   открытии экрана.
9. `npm run types:api:cycle17 && git diff --exit-code` — пусто (тот же шаг стоит в CI).

## §329. Чего контракт НЕ меняет (ревью обязано это проверить)

- Форму и семантику `PATCH /api/bookings/{id}/reschedule` — ни одного нового поля, ни одного нового
  кода, `404` вместо `403` (цикл 15) сохраняется.
- Модель тарифов, механику скрытого тарифа, `409` у `PUT /api/admin/plans/{id}`, ручку ручного
  назначения скрытого тарифа (решение заказчика §0-bis по C15-8).
