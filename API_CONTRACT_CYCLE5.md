## 38. Общее для эндпоинтов цикла

### 38.1 Соглашения без изменений

camelCase, `enum` — строкой, `DateOnly` = `"YYYY-MM-DD"`, `DateTime` — ISO-8601 UTC, `decimal` —
число. Тела ошибок: **голая строка** (`text/plain`) для 400/402/409/410/429, **пустое** для 401/403.
`AddProblemDetails()` по-прежнему запрещён.

### 38.2 Коды, которыми пользуется цикл

| Код | Когда | Тело |
|---|---|---|
| 400 | валидация (цена < 0, `quantity < 1`, попытка сменить `code` опции, `unitName` у `Toggle`, отсутствие `unitName` у `Quantity`, ненулевая цена системного бесплатного тарифа, **несуществующий или удалённый пользователь в `newOwnerUserId`**) | голая строка |
| **402** | упёрлись в тариф/лимит: мест нет, лимит компаний исчерпан, **у принимающего аккаунта нет места при переносе компании** | голая строка |
| 403 | не держатель аккаунта / не суперадмин | **пустое** |
| 404 | компании, тарифа, опции, заявки, аккаунта нет **или** объект не принадлежит вызывающему; **публичный прайс при выключенной публикации** | пусто |
| **409** | состояние не позволяет: опция недоступна на тарифе, у опции не задана цена, заявка уже обработана, системный бесплатный тариф, перенос в тот же аккаунт, **перерасход мест без `confirmSeatOverflow`**, **новый ответственный не связан с принимающим аккаунтом** | голая строка |
| **410** | эндпоинт снят с эксплуатации в этом цикле (§54) | голая строка с указанием замены |
| 451 | правовой гейт — **не применяется** к `GET /api/pricing` (добавлен в allow-list) | голая строка |

### 38.3 Права

- **Держатель аккаунта** (`BillingAccount.OwnerUserId == me`) — владельческие billing-эндпоинты.
  SuperAdmin к ним **не имеет доступа** (403) — у него свои админские, конвенция цикла 4.
- **SuperAdmin** — каталог, аккаунты, назначение подписок, очередь заявок, перенос компаний,
  предпросмотр прайса, параметры платформы.
- **Аноним** — только `GET /api/pricing`.
- Права на компанию (`CompanyMembership`) **не меняются ни в одном эндпоинте**: они по-прежнему
  определяются `Company.OwnerUserId` и `CompanyMembers`, а не тем, кто платит.

### 38.4 Словарь интерфейса (Р8, SPEC §3.3 п. 11)

Во **владельческих** ответах нет ни поля, ни текста со словами «биллинг-аккаунт» / `billingAccount`.
Для владельца это «ваша подписка», «ваши компании», «ваш лимит сотрудников». Термин и идентификатор
аккаунта допустимы **только** в ответах под `/api/admin/*`. Это проверяемое требование: см. §56 п. 9.

### 38.5 Перечисления цикла (точные строки JSON)

```
OptionKind                 Toggle | Quantity
OptionAvailability         Unavailable | Included | Extra
SubscriptionStatus         Free | Active | Expired
OptionStatus (только в ответах) Active | PendingPayment | Ending | Unavailable
SubscriptionRequestStatus  Pending | Approved | Rejected | Cancelled
SubscriptionChangeKind     Legacy | Plan | Options | Payment | CompanyTransferred | Migration
ChannelFundingState        Funded | Unfunded | NotPaid
```

`OptionStatus` — **производное** состояние строки на экране владельца, в БД не хранится:
`Active` (оплачена и работает), `PendingPayment` (есть заявка, оплата не подтверждена),
`Ending` (отключена/уменьшена, работает до `endsAt`), `Unavailable` (тариф её больше не допускает).

`ChannelFundingState` — состояние **номера** относительно оплаченного количества
(`ARCHITECTURE_CYCLE5.md` §47.1): `Funded` — входит в оплаченные, `Unfunded` — заведён сверх
оплаченных (не отправляет, но не теряет назначения), `NotPaid` — у аккаунта не оплачено ни одного.

### 38.6 Деньги

Все суммы — `decimal`, валюта одна: `"currency": "RUB"` присутствует в каждом ответе, где есть
деньги (чтобы добавление второй валюты не стало ломающим изменением). Фронт печатает
`toLocaleString('ru-RU')` + `₽/мес`. Суммы целые; дробная часть возможна, но в MVP не используется.

### 38.7 Ломающие изменения цикла — пять

1. `GET|POST|PUT /api/admin/plans` переходят с сырой сущности на DTO (§46).
2. Два эндпоинта отвечают **410 Gone** (§54).
3. `PUT /api/admin/companies/{id}/owner` **перестаёт** снимать компанию с номера и отменять её
   очередь сообщений — осознанная отмена поведения цикла 4 (§53.5).
4. **Семантическое:** `CompanyDto.maxEmployees` и `ProfileDto.plan.maxEmployees` теперь означают
   **суммарный лимит аккаунта**, а не лимит одной компании. Форма не меняется — сломается логика,
   а не сборка (§53.1).
5. **Семантическое:** `ChannelDto.paymentState/paidUntil/paidFrom` считаются из подписки аккаунта,
   а не из полей канала (§53.6).

`ProfileDto.plan` в этой редакции **не ломается** — только дополняется (§53.2).

Публичный прайс. Единственный анонимный эндпоинт цикла; правовой гейт его не трогает.

- `includedCompanies` / `includedEmployees` — базовые лимиты тарифа, **суммарные на подписку**
  (US-71 п. 2: «до N компаний», «до N сотрудников»). `null` = без ограничения.
  Бесплатный тариф публикуется обычной строкой с лимитами 1/1 (П4, подтверждено заказчиком).

- `version` совпадает со значением внутри `ETag` — по нему фронт понимает, что данные те же

  массив вовсе** (никаких «цена по запросу»).
- `notice` — текст про «подключение через администратора» (П3). Юридические формулировки §7 SPEC
  добавляются в **этот же** ответ полем `legalNotice` после вычитки юристом; до тех пор поля нет.

**304 Not Modified** — при совпадении `If-None-Match`, без тела.

**404 Not Found** — публикация выключена (`PlatformSetting pricing.public-enabled`). Фронт в этом
случае **не показывает** ни блок на главной, ни ссылку в навигации; отдельного флага не вводится.

**Правила, на которые фронт обязан опираться, а не пересчитывать:**

1. `totalMonthlyPrice === plan.pricePerMonth + Σ options[].pricePerMonth` — **проверяется тестом с
   обеих сторон** (US-65). Формула печатается на экране дословно.
2. Все тексты (`statusText`, `usage.*Text`, `availabilityText`, `warning.text`, `affected`) собирает
   сервер. Фронт словарей не заводит.
3. `usage.employeesLimit` / `companiesLimit` — `null` означает «без ограничения», а не 0.
4. `usage.numbersPaid` < `usage.numbersRegistered` — нормальное состояние, не ошибка. `numbersText`
   в этом случае **обязан** содержать три вещи: сколько оплачено против скольких заведено, какой
   номер работает (маскированный) и что сделать, чтобы включить остальные
   (`ARCHITECTURE_CYCLE5.md` §47.1). Фронт печатает строку целиком и ничего не дописывает.
5. Опция со `status: "Ending"` имеет непустой `endsAt` и работает до этой даты (SPEC §3.3 п. 9).
6. Опция, которая оплачена, но тариф её больше не допускает, приходит со `status: "Unavailable"` и
   поясняющим `statusText` — молчаливого исчезновения строки не бывает.
7. `availableOptions` содержит только показуемое: `pricePerMonth == null` («цена не задана») в массив
   **не попадает**, кроме случая `availability: "Unavailable"` — он нужен, чтобы написать «доступно
   на тарифе …» (US-70 п. 2).
8. `canRequest: false` → вместо кнопки показывается `availabilityText`.
9. `warning` — `null`, когда предупреждать не о чем. `kind`: `"Expiring"` | `"Expired"`.
10. `companies[]` — первый кандидат на урезание (SPEC §10 п. 1). Если урезан, поле приходит пустым
    массивом; `usage` остаётся всегда.
11. **Ни одно поле и ни один текст этого ответа не содержит слова «аккаунт»** (Р8).

**403** — вызывающий не держатель аккаунта. **404** — у вызывающего нет аккаунта (он не владелец ни
одной компании); фронт в этом случае просто не рисует раздел.

## 42. `POST /api/billing/subscription/request` — US-70 · B5-6 · **НОВЫЙ**

Заявка владельца на изменение тарифа/опций. Ничего не включает — только ставит в очередь.

**Запрос**

```json
{
  "planId": "77aa…",
  "options": [{ "optionId": "2c3d…", "quantity": 1 }],
  "comment": "нужно к ноябрю"
}
```

- `planId` — `null`/опущен = тариф не меняем.
- `options` — **полный желаемый состав**, а не дельта: пустой массив означает «никаких опций».
- `quantity ≥ 1`; для `Toggle` допустима только `1`.

**200 OK** → `SubscriptionRequestDto` (та же форма, что `pendingRequest` в §41) — **и при создании,
и при перезаписи уже существующей ожидающей заявки**. 201 не используется намеренно: у аккаунта не
может быть двух ожидающих заявок (частичный уникальный индекс), повторная отправка — это обновление
(US-70: «повторная заявка не плодит дубликатов»).

Ответ содержит `estimatedMonthlyPrice` — сумму, которую фронт **показал пользователю до
подтверждения** (US-70 п. 1: «итог целиком, а не только дельту»); сервер считает её сам и сохраняет
снимком.

**400** — `quantity < 1`, `quantity > maxQuantity`, неизвестный `optionId`, `Toggle` с `quantity > 1`.
**409** — опция недоступна на выбранном тарифе, у опции не задана цена или она снята с продажи.
**402** — не используется: заявка не упирается в лимиты, она лишь просит.
**403** — не держатель аккаунта. **404** — аккаунта нет.

- **`PUT /{id}`** → 200 + DTO. **`code` менять нельзя** (400) — на него завязаны сид и миграции.
- **`DELETE /{id}`** → мягкое удаление (`isActive = false`), 204. Уже оплаченные строки продолжают
  действовать до конца оплаченного периода (`ARCHITECTURE_CYCLE5.md` §44.3 п. 5) — это **намеренно
  не совпадает** с поведением деактивированного тарифа.
- `capabilityKnown: false` — ключ не из списка известных: опция будет продаваться и считаться в
  сумме, но ничего не включит. Админка обязана показать предупреждение, сохранение **не блокируется**
  (иначе нельзя завести опцию под ещё не выпущенный канал).
- `pricePerMonth: null` допустим и означает «опция не продаётся»: она исчезает из публичного прайса
  и из `availableOptions` владельцев. **Так сегодня выглядит `notifications.whatsapp` — это
  ожидаемое состояние, а не дефект** (US-74).

**400** — цена < 0; неизвестный `kind`; `unitName` у `Toggle`; **отсутствие `unitName` у `Quantity`**
(единица обязана быть названа, US-71 п. 3); `maxQuantity < 1`.
**409** — `code` уже занят.

## 46a. `PUT /api/admin/plans/{id}/system-free` — B5-2 · **НОВЫЙ (cycle-07, ещё не выпущен)**

Выделен из `AdminPlanInput` в цикле 7: у `AdminPlanInput` `additionalProperties: false`, а
`isSystemFree` управляет полем с частичным уникальным индексом (ровно один активный тариф с этим
флагом одновременно) — писать в него обычным `PUT /admin/plans/{id}` небезопасно, нужен отдельный
маршрут с собственными проверками.

**Запрос**

```json
{ "isSystemFree": true }
```

**Ответ 200** — тело как у `AdminPlanDto` (см. §46), с уже применённым/неизменившимся `isSystemFree`.

**Инвариант и почему он не проверяется целиком за один запрос.** §43.4 требует, чтобы системный
бесплатный тариф существовал всегда. Но перенос флага с одного тарифа на другой — это два
последовательных вызова (снять со старого, поставить на новый), а не один атомарный запрос, так
что ни один вызов сам по себе не может гарантировать инвариант «ровно один» — только не сделать
хуже:

- **`isSystemFree: true`** (поставить флаг):
  - **400** — `pricePerMonth` тарифа не равен 0.
  - **409** — флаг уже стоит на другом тарифе. Снимите его с текущего носителя первым запросом,
    затем ставьте на новый вторым.
- **`isSystemFree: false`** (снять флаг):
  - **409** — если снятие флага оставило бы систему без тарифа-кандидата на замену, то есть **нет
    другого активного тарифа с `pricePerMonth = 0`**, готового принять флаг следующим вызовом.
    Флаг **не снимается**, пока не подготовлен (создан или переведён в активные/бесплатные)
    хотя бы один такой тариф-преемник.
- **Идемпотентный no-op** — если `isSystemFree` в запросе совпадает с текущим значением у этого
  тарифа, обе проверки выше не выполняются и ответ всегда **200** без изменений.
- **Гонка** — два одновременных запроса, ставящих флаг на разные тарифы, ловятся частичным
  уникальным индексом БД и возвращаются как **409** с тем же текстом, что и синхронная проверка
  выше (никогда не 500).

**404** — тарифа с таким `id` не существует.

## 48. `PUT /api/admin/billing-accounts/{accountId}/subscription` — US-67 · B5-7 · **НОВЫЙ**

**Назначение тарифа, опций и срока — одним действием** (прямое требование US-67).

**Запрос**

```json
{
  "planId": "77aa…",
  "isActive": true,
  "paidUntil": "2026-11-30",
  "options": [
    { "optionId": "9b3c…", "quantity": 10, "paidUntil": null },
    { "optionId": "7f8a…", "quantity": 1,  "paidUntil": "2026-10-31" }
  ],
  "amount": 5080,
  "comment": "счёт 118",
  "requestId": "55ee…",
  "confirmLimitOverflow": false
}
```

- `options` — **полный желаемый состав**. Опция, которой нет в массиве, **отключается**: ей
  проставляется `endsAt` = конец её оплаченного периода, и она продолжает работать до этой даты
  (SPEC §3.3 п. 9). Немедленного отключения в API нет вовсе — намеренно.
- Уменьшение `quantity` действует по тому же правилу: старое количество работает до `endsAt`.
- `paidUntil` внутри опции: `null` = «следует за подпиской».
- `planId: null` = снять тариф (аккаунт уходит на бесплатный).
- `amount`, `comment` — попадают в журнал; `amount` не участвует в вычислениях.
- `requestId` — если передан, заявка закрывается как `Approved` в **той же** транзакции.
- `confirmLimitOverflow` — требуется, если новые лимиты **меньше уже занятого** (US-67, последний
  критерий).

**200 OK** → `AdminBillingAccountDto`. Возможности всех компаний аккаунта меняются немедленно.

**400** — `paidUntil` в прошлом более чем на 1 день; `quantity < 1`; `quantity > maxQuantity`;
неизвестный `planId`/`optionId`.
**409** — три случая, все с голой строкой и числами:
 (а) опция недоступна на выбранном тарифе (`Unavailable`) — администратор обязан либо сменить тариф,
 либо открыть опцию на нём;
 (б) заявка `requestId` уже обработана;
 (в) новые лимиты меньше занятого, а `confirmLimitOverflow != true` — «Сотрудников занято 12, новый
 лимит 8. Уже заведённые не будут удалены, но добавить новых будет нельзя. Подтвердите.»
**403** — не суперадмин. **404** — аккаунта нет.

Всё изменение пишется в `SubscriptionChangeLog` одной строкой с `changeKind` `Plan`/`Options`/
`Payment` (по фактически изменившемуся), старым и новым составом опций текстом.

Операция выполняется под advisory lock `billing-account:{accountId}`.

## 51. Перенос компании в другой аккаунт — US-77 · B5-10 · **НОВЫЕ**

### 51.0 Одна операция — два сценария

В теле переноса есть **необязательное** поле `newOwnerUserId`:

| Что передали | Что меняется | Сценарий |
|---|---|---|
| `newOwnerUserId` **не задан** | только плательщик (`BillingAccountId`). Ответственный за компанию остаётся прежним | перекладывание точки между **своими** аккаунтами |
| `newOwnerUserId` **задан** | плательщик **и** ответственный — **в одной транзакции** | продажа филиала: и деньги, и управление переходят покупателю за одно действие |

Разбивать это на два вызова нельзя: между ними существует состояние «компания уже оплачивается
покупателем, но управляет ею продавец», и если второй вызов не дойдёт, оно останется незамеченным.

### 51.1 `GET /api/admin/companies/{companyId}/transfer/preview`

`?targetBillingAccountId=…` и **необязательно** `&newOwnerUserId=…`.

Предпросмотр **до** любых записей. Всегда 200, если объекты существуют, — отказ выражается полями,
а не кодом, чтобы админка могла показать причину до нажатия.

```json
{
  "companyId": "1a2b…", "companyName": "Салон на Мира",
  "employeeCount": 4,
  "source": { "billingAccountId": "aa11…", "accountName": "Аккаунт Иванова", "planName": "Базовый" },
  "target": { "billingAccountId": "bb22…", "accountName": "Аккаунт Сидорова", "planName": "Бесплатный" },
  "targetCompaniesUsed": 1, "targetCompaniesLimit": 1,
  "targetSeatsUsed": 1, "targetSeatsLimit": 1,
  "canTransfer": false,
  "blockReason": "На тарифе «Бесплатный» — 1 компания, занято 1. Чтобы принять ещё одну, нужна опция «Дополнительная компания».",
  "seatOverflow": true,
  "seatOverflowText": "После переноса сотрудников станет 6 при лимите 1 (включая нового ответственного). Уже заведённые не будут удалены, но добавить новых будет нельзя.",

- **`newOwner` — `null`**, если параметр не передан; тогда `ownerUnchangedNotice` содержит текст

}
```

**204 No Content** — перенос выполнен. Всё в одной транзакции
(`ARCHITECTURE_CYCLE5.md` §51.3): проверки → снятие с номера и отмена неотправленных сообщений →
смена принадлежности → (если задан `newOwnerUserId`) смена ответственного и ролей → журналы.

Записывается:
- две строки в журналы подписки (`changeKind: "CompanyTransferred"`, по одной в истории каждого
  аккаунта) — **всегда**;
- одна строка в журнал ответственных (§53, `withTransfer: true`) — **только** если ответственный
  сменился.

### 51.3 Коды ответа

| Код | Когда | Тело |
|---|---|---|
| **402** | у принимающего аккаунта нет свободного места в лимите компаний — **перенос отклонён, ничего не изменено** | тот же текст, что `blockReason` |
| **400** | `newOwnerUserId` указывает на несуществующего или удалённого пользователя | голая строка |
| **409** | (а) перенос в тот же аккаунт; (б) `seatOverflow` и `confirmSeatOverflow != true`; (в) **новый ответственный не связан с принимающим аккаунтом** | голая строка с числами / с подсказкой |
| 403 | не суперадмин | пусто |
| 404 | компании или принимающего аккаунта нет | пусто |

Текст 409 (в): «Мария Сидорова не связана с принимающим аккаунтом. Сделайте её держателем этого
аккаунта, добавьте сотрудником в любую его компанию — или выполните перенос без смены
ответственного и смените ответственного отдельно.»

**Правило связи (обоснование — `ARCHITECTURE_CYCLE5.md` §51.1):** новый ответственный обязан быть
либо **держателем** принимающего аккаунта, либо **участником** (`CompanyMembers`) хотя бы одной его
компании. Правило строже, чем у `PUT /api/admin/companies/{id}/owner` (там достаточно любого живого
пользователя), потому что здесь вместе с управлением переезжают деньги: одним действием отдать
оплаченную компанию постороннему нельзя.

Отказ по лимиту компаний — **приёмочный критерий US-77 и проверяется тестом**: после 402 компания
остаётся в исходном аккаунте, ответственный не сменился, назначение на номер цело, очередь сообщений
не тронута.

Владельцу операция недоступна вовсе (Р3) — во владельческом API такого маршрута нет.

## 52. `GET /api/admin/companies/{companyId}/owner-history` — US-64 · B5-9 · **НОВЫЙ**

Журнал смены ответственного — **отдельный от журнала денег** (US-64 п. 4: «в журнале подписки
записи не появляется»).

```json
{ "items": [
  { "id": "…", "changedAt": "2026-09-22T09:14:00Z", "changedByName": "Админ Иванов",
    "oldOwnerName": "Иван Петров", "newOwnerName": "Мария Сидорова",
    "withTransfer": false, "comment": null },
  { "id": "…", "changedAt": "2026-09-20T12:00:00Z", "changedByName": "Админ Иванов",
    "oldOwnerName": "Пётр Сидоров", "newOwnerName": "Иван Петров",
    "withTransfer": true, "comment": "в составе переноса компании в другой аккаунт" }
]}
```

`withTransfer: true` означает, что ответственный сменился **не отдельным решением**, а вместе с
переносом компании (§51): тогда в журнале подписки обоих аккаунтов есть парная строка
`CompanyTransferred` с тем же `companyId` и тем же временем.

### 53.1 `CompanyDto` — **+7 полей** (аддитивно, 7 точек возврата) и одно **семантическое** ломающее

```json
"planName": "Базовый",
"subscriptionStatus": "Active",
"paidUntil": "2026-10-31T00:00:00Z",
"employeeCount": 6,
"accountSeatsUsed": 12,

```

- Три существующих уровня флагов (`allowSelfBooking`/`onlineBookingEnabled`/`planAllowsOnlineBooking`

  управляет этой компанией (анонимный каталог `GET /api/companies`): значения не считались.
  `null` ≠ «безлимит».
- **BREAKING (семантическое): `maxEmployees` теперь = суммарный лимит аккаунта**, а не лимит этой
  компании. Поле помечено **deprecated**. Любая арифметика вида
  `members.length >= maxEmployees` на фронте **обязана быть снята** — она недосчитает сотрудников
  других точек, покажет активную кнопку и поймает 402. Единственный допустимый источник для гашения
  кнопки — `canAddEmployee`.
- `billingAccountId` в этом DTO **отсутствует** (Р8).

### 53.2 `ProfileDto.plan` — **только дополняется** (не ломается)

Все сегодняшние поля остаются и означают то же самое (подписка снова принадлежит аккаунту).
Добавляются:

```json
"totalMonthlyPrice": 5080, "currency": "RUB",
"companiesUsed": 3, "employeesUsed": 12,
"expiresInDays": 9, "isExpiringSoon": true, "optionCount": 2
```

`maxEmployees` — та же смена смысла, что в §53.1, с той же пометкой deprecated (для лимита в UI
используется `/api/billing/subscription`). `plan` остаётся `null` для не-владельцев.
Блок «ваш тариф» дополняется **ссылкой на `/billing`** (US-65).

### 53.3 `POST /api/companies` — причина и текст 402 меняются

Лимит компаний считается **по аккаунту** (было — по `OwnerUserId`, фактически то же множество, но
теперь это явная модель). Текст:
«У вас 1 компания из 1 по тарифу «Бесплатный». Чтобы открыть ещё одну точку, перейдите на платный
тариф или подключите опцию «Дополнительная компания».»
Код прежний — **402**.

### 53.4 `POST /api/companies/{id}/members` — причина и текст 402 меняются

Места считаются **суммарно по всем компаниям аккаунта**. Текст:
«Занято 8 из 8 мест: 5 включено в тариф «Базовый», 3 докуплено. Лимит общий на все ваши точки.
Чтобы добавить сотрудника, подключите опцию «Дополнительные сотрудники».»
Код прежний — **402**. Гейт выполняется под двумя локами (`ARCHITECTURE_CYCLE5.md` §52),
наблюдаемого отличия у клиента нет.

### 53.5 `PUT /api/admin/companies/{id}/owner` — **BREAKING (поведение)**

| Было (цикл 4) | Стало (цикл 5) |
|---|---|
| компания начинала жить по подписке нового владельца (обычно — Free) | **подписка, опции, срок и лимиты не меняются вовсе**: компания остаётся в своём аккаунте |
| компания снималась с номера, её `Pending`-сообщения отменялись | **компания остаётся на номере, очередь не отменяется** (US-64 п. 3) — номер принадлежит аккаунту, а не человеку |
| в журнале подписки ничего | строка в журнале ответственных (`withTransfer: false`), **в журнале подписки по-прежнему ничего** |

Форма запроса и ответа (`204`) не меняется. Это отмена поведения цикла 4, и она требует теста
(US-64).

**Этот эндпоинт остаётся самым простым способом сменить ответственного, когда деньги ни при чём.**
Если нужно сменить и плательщика — это §51, одна операция.

### 53.6 `ChannelDto` (цикл 4) — форма та же, источник значений другой

| Поле | Было | Стало |
|---|---|---|
| `paymentState` | состояние оплаты **канала** (`PaidFromUtc/PaidUntilUtc`) | производное от подписки аккаунта: `Paid`, если номер `Funded`; иначе `NotPaid` |
| `paidUntil` | `NotificationChannel.PaidUntilUtc` | срок опции `notifications.whatsapp` подписки аккаунта |
| `paidFrom` | дата начала оплаты канала | **всегда `null`**, deprecated |
| **`fundingState`** 🆕 | — | `Funded` \| `Unfunded` \| `NotPaid` |
| **`fundingText`** 🆕 | — | готовый текст, объясняющий **причину и что делать** |

`fundingText` собирает сервер (`BillingTexts`), фронт печатает как есть:

| `fundingState` | Текст |
|---|---|
| `Funded` | «Номер оплачен и работает.» (если заведено больше, чем оплачено — «…оплачен 1 номер из 2 заведённых, и он подключён раньше второго») |
| `Unfunded` | «Этот номер не отправляет сообщения: у вас оплачен 1 номер, а заведено 2. Работает тот, что подключён раньше (+7 999 ***-**-45). Чтобы включить и этот, подключите ещё одну «Рассылку в WhatsApp» — или удалите лишний номер.» |
| `NotPaid` | «Рассылки не отправляются: опция «Рассылки в WhatsApp» не оплачена. Чтобы включить, подключите её в разделе «Ваша подписка».» |

Требование приёмки: в тексте `Unfunded` названы **причина (сколько оплачено против скольких
заведено), какой номер работает вместо этого и оба способа это исправить**. Это единственное место
цикла, где платформа сама решает, чей номер замолчит, — пользователь обязан понять почему.

Единственный источник правды об оплате — подписка аккаунта (Р6). Номер сверх оплаченных **не
отправляет**, но сохраняет назначенные компании и состояние подключения.

### 53.7 `GET|PUT /api/admin/platform-settings` — **+1 поле**

```json
{ "channelPricePerMonth": null, "channelIdleDays": 3, "pricingPublicEnabled": false }
```

- `pricingPublicEnabled` — рубильник публичного прайса (§39). **По умолчанию `false`**; включение —
  отдельное осознанное действие суперадмина после вычитки юристом (SPEC §7).
- `channelPricePerMonth` остаётся в ответе для совместимости, но **больше ни на что не влияет**
  (цена опции переехала в каталог) и убирается из админского экрана. Помечено deprecated.
- Поля `freeCompaniesPerAccount` **нет**: US-75 упразднена, лимит бесплатных компаний — обычное поле
  тарифа (Р4).

**молча оставил бы состав опций прежним** — то есть создал бы второй путь записи денег, мимо
единственного `SubscriptionWriter`. Ровно тот класс расхождения, который цикл устраняет.

`GET /api/admin/owners/{ownerUserId}/subscription-history` **остаётся работать** и отдаёт
исторические строки циклов 1–4 — историю не удаляем (US-73).

## 56. Чек-лист согласования BE↔FE перед мёржем цикла

1. `schemathesis run contracts/openapi-cycle5.yaml --base-url <api> --checks all` проходит на всех
   эндпоинтах цикла — машинная проверка «BE и FE сошлись по форме».
2. Фронтовые типы цикла 5 сгенерированы из того же YAML (`npm run types:api`), ручных дублей в
   `types/index.ts` нет — **проверяется грепом**.
3. `totalMonthlyPrice` на экране владельца равен `plan.pricePerMonth + Σ options[].pricePerMonth` —
   тест есть и на бэкенде, и на фронте (US-65).
4. Фронт нигде не строит `statusText`/`usage.*Text`/`availabilityText`/`warning.text`/`unitPriceText`/
   `fundingText` сам.
5. Все кнопки гасятся по `canRequest`/`canDisable`/`canAddEmployee`/`canRequestChanges`, а не ловят
   402/409 после клика. **`maxEmployees` в арифметике фронта не участвует нигде** — греп по
   `maxEmployees` в `frontend/src` даёт только отображение.
6. `GET /api/pricing` при выключенной публикации возвращает 404, и фронт при этом не рисует ни блок
   на главной, ни ссылку — проверяется руками и тестом Vitest.
7. Ни один ответ цикла не содержит `capabilityKey`/`isActive`/`includedQuantity` на **публичных**
   маршрутах.
8. Опция «Рассылки в WhatsApp» отсутствует в `GET /api/pricing` и в `availableOptions` у всех
   тарифов (цена не задана, не публична) — **ожидаемое состояние, а не дефект** (US-74).
9. **Р8:** ни одно поле и ни один текст во владельческих ответах (`/api/billing/*`, `CompanyDto`,
   `ProfileDto`) не содержит слова «аккаунт» в значении «биллинг-аккаунт» и не содержит
   `billingAccountId` — проверяется грепом по ответам в тестах.
10. US-64: после `PUT /api/admin/companies/{id}/owner` — назначение на номер существует,
    `Pending`-сообщения остались `Pending`, все флаги `CompanyDto` и `paidUntil` совпали до и после.
11. US-77, три обязательных прогона:
    (а) перенос **без** `newOwnerUserId` — плательщик сменился, `ownerUserId` компании прежний;
    (б) перенос **с** `newOwnerUserId` — оба поля сменились, в журнале подписки обоих аккаунтов есть
    `CompanyTransferred`, в журнале ответственных — строка с `withTransfer: true`;
    (в) 402 при нехватке лимита у принимающего аккаунта **ничего не меняет** — проверяется
    сравнением состояния до и после неудачной попытки.
12. Предпросмотр переноса с `newOwnerUserId` и без него даёт **разный** `seatOverflow`, когда новый
    ответственный ещё не сотрудник компании (`newOwner.willOccupySeat: true`) — иначе фронт покажет
    предупреждение, не совпадающее с тем, что произойдёт.
