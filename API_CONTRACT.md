# API_CONTRACT — цикл 3 ServiceBooking

**Назначение.** Точка синхронизации backend-, frontend- и devops-инженера на время цикла. Все стороны
работают по этому файлу, а не по коду друг друга (`ARCHITECTURE.md` §17.2, таблица «Точки пересечения
BE↔FE»).

**Что здесь есть.** Все эндпоинты, которые цикл 3 добавляет или меняет, плюс **фактическое состояние**
тех, что затрагиваются косвенно (rate limiting, коды ошибок). Остальной API описан в
`API_DOCUMENTATION.md` и в этом цикле не меняется. Изменения цикла 2 уже применены к коду и здесь
не повторяются.

**Источник истины по решениям.** `SPEC.md` цикла 3 §0 (Р1–Р9) и `ARCHITECTURE.md` (§4 хранение
документов, §5 модель, §6 согласие, §7 права субъекта, §9 rate limiting, §10 health-check,
§14 формат ошибок, §15 пагинация, §18 задачи). Контракт ниже не вводит альтернатив — он фиксирует
принятое в терминах запрос/ответ.

**Базовая ревизия.** Ветка `sanitation-cycle`, коммит `0492092`. Все ссылки «файл:строки» — по ней.

**Ломающих изменений в цикле ровно два**, оба помечены **BREAKING** и сведены в §14:
1. `POST /api/auth/register` требует нового обязательного поля;
2. четыре выборки меняют массив на конверт пагинации.

Всё остальное аддитивно.

## 0. Общие соглашения

### 0.1 Сериализация — без изменений с цикла 2

| Тип C# | JSON | Пример |
|---|---|---|
| Имена свойств | camelCase | `acceptedLegal`, `privacyVersion` |
| `enum` | **строка** (`JsonStringEnumConverter`) | `"Privacy"`, `"Material"`, `"Confirmed"` |
| `DateOnly` | `"YYYY-MM-DD"` | `"2026-09-15"` |
| `TimeOnly` | `"HH:mm:ss"` | `"10:00:00"` |
| `DateTime` | ISO-8601 UTC | `"2026-09-15T11:04:17.9231Z"` |
| `decimal` | число | `800` |

Базовый путь фронта — `/api` (`frontend/src/api/client.ts:5`), токен подставляется интерцептором
(`client.ts:9-13`). Обработка 401 (`client.ts:15-24`) **не меняется**; рядом с ней появляется
обработка 451 (§0.3).

### 0.2 Формат тел ошибок — граница циклов 1 и 2, перенесённая без изменений

| Код | Как формируется | Content-Type | Тело | Цикл 3 |
|---|---|---|---|---|
| 400 | `BadRequest("текст")` | `text/plain; charset=utf-8` | **голая строка** | без изменений; все новые 400 — тоже голые строки |
| 400 | автовалидация `[ApiController]` | `application/problem+json` | `ValidationProblemDetails` | без изменений |
| 401 | пайплайн JWT | — | пустое | без изменений |
| 402 | `StatusCode(402, "текст")` | `text/plain` | голая строка | без изменений |
| 403 | `Forbid()` | — | **пустое** | без изменений |
| 404 | `NotFound()` / `NotFound("текст")` | — / `text/plain` | пусто / строка | без изменений |
| 409 | `Conflict("текст")` | `text/plain` | голая строка | без изменений |
| 413 | `[RequestSizeLimit]` / Kestrel | — | пустое | без изменений |
| 429 | rate limiter, `OnRejected` | `text/plain` | голая строка | **тексты ветвятся по политике** (§9) |
| **451** | `LegalConsentFilter` | **`text/plain`** | **голая строка** | **новый код цикла** |
| **503** | health-check / `LegalController` | `application/json` / `text/plain` | два поля / строка | **новый код цикла** |
| 500 | необработанное исключение | `application/problem+json` | `ProblemDetails` + `traceId` | без изменений |

`AddProblemDetails()` и `UseStatusCodePages*` **запрещены** — они переписали бы тела 4xx, на которых
стоят мапперы `src/utils/*Error.ts`.

### 0.3 451 Unavailable For Legal Reasons — новый код и почему именно он

**Когда.** Аутентифицированный запрос к любому эндпоинту вне allow-list (§0.4), когда версии
согласия в токене не совпадают с действующими, а действующая редакция помечена
`changeKind: "Material"`.

```
HTTP/1.1 451 Unavailable For Legal Reasons
Content-Type: text/plain; charset=utf-8

Примите обновлённые документы, чтобы продолжить.
```

**Почему не 403.** По конвенции проекта `Forbid()` отдаёт **пустое** тело, и фронт не отличил бы
«нет прав» от «не принята редакция» — а реакция на них противоположная (первое показывает ошибку,
второе показывает блокирующий экран на всё приложение). Заводить «403 с телом» означало бы завести
исключение из конвенции. 451 семантически точен, ни один существующий эндпоинт его не отдаёт, и на
фронте он обрабатывается **одной веткой в `client.ts`**, а не в каждом маппере.

**Что делает фронт.** Ветка в `client.ts` рядом с обработкой 401: выставить флаг «требуется согласие»
и отрендерить `ConsentGate`. `logout()` при этом **не вызывается** — пользователь остаётся
авторизованным, он просто ничего не может делать, кроме чтения документов, выхода, просмотра профиля,
выгрузки и удаления аккаунта.

### 0.4 Allow-list: что работает при непринятой редакции

| Маршрут | Почему разрешён |
|---|---|
| `GET /api/legal/**` | нужно прочитать то, что просят принять |
| `POST /api/legal/accept` | иначе принять невозможно |
| `GET /api/legal/consent-status` | фронт узнаёт, что именно требуется |
| `POST /api/auth/**` | вход и регистрация — до всякого согласия |
| `GET /api/health/**` | мониторинг не аутентифицирован вовсе |
| `GET /api/profile` | фронт не может отрисовать даже блокирующий экран без пользователя |
| `POST /api/profile/delete-account` | SPEC US-39 п. 9: несогласный не должен быть заперт |
| `GET /api/profile/export` | решение архитектора, `ARCHITECTURE.md` §19.4 |

Всё остальное под `[Authorize]` — 451.

## 1. `GET /api/legal/documents` — US-36 · задача T-B4 · **НОВЫЙ**

Публичный. Возвращает **метаданные** обоих документов без текстов — этого достаточно для подвала,
для формы регистрации и для сравнения версий на фронте.

**Запрос:** без параметров, без авторизации.

**200 OK**
```json
{
  "documents": [
    {
      "type": "Privacy",
      "title": "Политика обработки персональных данных",
      "version": "2026-09-15-draft",
      "effectiveFrom": "2026-09-15",
      "isDraft": true,
      "changeKind": "Material"
    },
    {
      "type": "Terms",
      "title": "Пользовательское соглашение",
      "version": "2026-09-15-draft",
      "effectiveFrom": "2026-09-15",
      "isDraft": true,
      "changeKind": "Material"
    }
  ]
}
```

| Поле | Тип | Примечание |
|---|---|---|
| `type` | `"Privacy"` \| `"Terms"` | ровно два документа, порядок не гарантирован — искать по `type` |
| `version` | string ≤ 64 | то же значение, что попадает в запись согласия и в `Booking` |
| `effectiveFrom` | `YYYY-MM-DD` | дата вступления в силу |
| `isDraft` | bool | `true` → фронт рисует плашку черновой редакции |
| `changeKind` | `"Material"` \| `"Editorial"` | режим смены версии; фронту нужен только для отладки — решение принимает сервер |

**Коды**

| Код | Тело | Когда |
|---|---|---|
| 200 | JSON выше | норма |
| 503 | `text/plain`: `Правовые документы временно недоступны.` | манифест не загрузился (только вне Production — в Production приложение бы не стартовало) |

## 2. `GET /api/legal/documents/{type}` — US-36 · задача T-B4 · **НОВЫЙ**

Публичный. Метаданные **и текст** одного документа.

**Запрос:** `type` = `privacy` \| `terms` (регистр не важен).

**200 OK**
```json
{
  "type": "Privacy",
  "title": "Политика обработки персональных данных",
  "version": "2026-09-15-draft",
  "effectiveFrom": "2026-09-15",
  "isDraft": true,
  "changeKind": "Material",
  "contentHtml": "<p><strong>Черновая редакция.</strong> Документ подготовлен командой сервиса…</p><h2>1. Общие положения</h2>…"
}
```

`contentHtml` — **фрагмент** HTML (без `<html>`, `<head>`, `<body>`), пригодный для вставки в
контейнер. Допустимые теги: `h2`–`h4`, `p`, `ul`/`ol`/`li`, `strong`, `em`, `a`, `table`/`tr`/`td`/`th`,
`br`. Скриптов и обработчиков событий в нём нет — провайдер отказывается публиковать документ,
содержащий `<script` или `on…=` (`ARCHITECTURE.md` §4.4).

**Пометка о черновике присутствует дважды:** в поле `isDraft` (плашка рисуется фронтом) и **в самом
тексте первым абзацем** (US-36 п. 3) — так она переживает копирование и печать страницы.

**Коды**

| Код | Тело | Когда |
|---|---|---|
| 200 | JSON выше | норма |
| 404 | пусто | `type` не `privacy` и не `terms` |
| 503 | `text/plain`: `Правовые документы временно недоступны.` | документ не загрузился |

**Кэширование.** Ответ отдаётся с `Cache-Control: public, max-age=300` — текст меняется два-три раза
за жизнь продукта, а страница публичная. Пять минут не мешают операционной замене (замена всё равно
подхватывается провайдером за 30 секунд, а посетитель увидит новый текст максимум через пять минут).

## 3. `GET /api/legal/consent-status` — US-37 · задача T-B5 · **НОВЫЙ**

Требует авторизации. **В allow-list** — доступен при непринятой редакции. Ответ считается из
claim'ов токена и снимка документов в памяти: **запросов к БД не делает**.

**200 OK**
```json
{
  "requiresAcceptance": true,
  "showBanner": false,
  "documents": [
    { "type": "Privacy", "version": "2026-10-01", "acceptedVersion": "2026-09-15-draft", "changeKind": "Material" },
    { "type": "Terms",   "version": "2026-09-15-draft", "acceptedVersion": "2026-09-15-draft", "changeKind": "Material" }
  ]
}
```

| Поле | Смысл для фронта |
|---|---|
| `requiresAcceptance` | `true` → показать **блокирующий экран** (`ConsentGate`). Соответствует состоянию «сервер отдаёт 451 на всё остальное» |
| `showBanner` | `true` → показать **ненавязчивый баннер** «документы обновлены» с кнопкой «понятно». Взводится, когда версии разошлись, но `changeKind` всех разошедшихся документов — `Editorial` |
| `acceptedVersion` | версия, принятая пользователем; `null`, если согласие не записывалось (аккаунт из-до цикла 3) |

`requiresAcceptance` и `showBanner` **никогда не бывают `true` одновременно**: существенная правка
перекрывает редакционную.

**Как фронт этим пользуется.** Один `useQuery(['legal-consent-status'])` при входе в приложение и
после каждого логина. Инвалидируется после `POST /api/legal/accept` и после «понятно» на баннере
(баннер гасится локально, в `localStorage` по версии — серверного состояния для баннера нет
намеренно: это уведомление, а не согласие).

**Коды**

| Код | Когда |
|---|---|
| 200 | норма |
| 401 | нет токена |

## 4. `POST /api/legal/accept` — US-37 п. 4 · задача T-B5 · **НОВЫЙ**

Требует авторизации. **В allow-list.** Записывает согласие с действующими редакциями и **выдаёт
новый токен**.

**Запрос**
```json
{ "privacyVersion": "2026-10-01", "termsVersion": "2026-09-15-draft" }
```

Версии в теле обязательны и сверяются с действующими. Это не «клиент сообщает, с чем согласился» —
это защита от гонки: если, пока пользователь читал документ, оператор заменил текст ещё раз,
согласие не должно записаться на редакцию, которой пользователь не видел.

**200 OK**
```json
{
  "token": "eyJhbGciOiJIUzI1NiIs…",
  "acceptedAt": "2026-10-02T08:41:12.4471Z"
}
```

**Токен обязательно кладётся в `authStore`.** Без этого следующий же запрос снова получит 451:
версии согласия едут claim'ами, и старый токен продолжает нести старые значения
(`ARCHITECTURE.md` §6.3).

**Коды**

| Код | Тело (`text/plain`) | Когда |
|---|---|---|
| 200 | JSON выше | норма |
| 400 | `Обе версии документов обязательны.` | пустое поле |
| 401 | пусто | нет токена |
| 409 | `Документы были обновлены ещё раз — перечитайте и примите новую редакцию.` | версия в теле ≠ действующей |
| 503 | `Правовые документы временно недоступны.` | документы не загружены |

## 5. `POST /api/auth/register` — US-37 п. 1 · задача T-B5 — **BREAKING № 1**

Файл: `ServiceBooking.API/Controllers/AuthController.cs:16-44`.

### 5.1 Дельта запроса

```diff
 {
   "firstName": "Иван",
   "lastName": "Петров",
   "phone": "+7 999 123-45-67",
   "password": "SecretPass1",
-  "email": "ivan@example.com"
+  "email": "ivan@example.com",
+  "acceptedLegal": true
 }
```

`acceptedLegal: bool` — **обязателен и должен быть `true`**. Отсутствие поля трактуется как `false`.
Клиентская валидация (неактивная кнопка регистрации) обязательна по US-37 п. 1, но защитой не
считается: тест `LEG-` бьёт прямо в API.

### 5.2 Дельта ответа

Ответ **не меняется** — тот же `AuthResponseDto`. Версии согласия в тело ответа не выносятся:
фронту они не нужны (он их не показывает), а в токене они уже есть.

### 5.3 Что происходит на сервере

В той же транзакции, что и создание пользователя, пишутся две строки `UserConsent` с текущими
версиями обоих документов и одним моментом (UTC). Выданный токен несёт claim'ы `lcp`/`lct`.

### 5.4 Коды

| Код | Тело (`text/plain`) | Когда |
|---|---|---|
| 200 | `AuthResponseDto` | норма |
| 400 | `Consent to the Terms of Service and the Privacy Policy is required.` | `acceptedLegal` не `true` — **новый** |
| 400 | `Phone number must contain 10 to 15 digits.` | без изменений |
| 400 | JSON-массив строк | ошибки Identity, без изменений |
| **429** | `Слишком много регистраций с этого адреса. Повторите позже.` | политика `auth-register` — **новый** |
| 503 | `Правовые документы временно недоступны.` | документы не загружены (вне Production) |

### 5.5 Влияние на фронт: **правки обязательны**

`RegisterPage.tsx` без правки перестанет регистрировать пользователей. Задачи T-B5 и T-F2
**мёржатся вместе** (`ARCHITECTURE.md` §17.1).

## 6. `POST /api/auth/login` — US-42 · задача T-B3

Тела запроса и ответа **не меняются**. Появляется один новый код:

| Код | Тело (`text/plain`) | Когда |
|---|---|---|
| **429** | `Слишком много попыток входа. Повторите через минуту.` | политика `auth-login`: > 10 попыток в минуту с одного адреса |

Фронт: новый маппер `src/utils/authError.ts` (задача T-F0/T-F7), подключается к `LoginPage` и
`RegisterPage`.

## 7. `POST /api/bookings` — US-37 п. 3, US-42 · задачи T-B5, T-B3

### 7.1 Тело запроса не меняется

`CreateBookingDto` **новых полей не получает**. Согласие гостя конклюдентное: строка-дисклеймер под
кнопкой «Записаться» со ссылками на оба документа — это работа фронта, серверу о ней знать не нужно.

### 7.2 Тело ответа получает три поля

`BookingDto` дополняется:

```diff
 {
   "id": "…", "companyId": "…", "date": "2026-09-20", "startTime": "10:00:00",
   "status": "Confirmed", "price": 1500,
+  "consentPrivacyVersion": "2026-09-15-draft",
+  "consentTermsVersion": "2026-09-15-draft",
+  "consentAcceptedAt": "2026-09-15T09:12:44.1200Z",
+  "clientDeleted": false
 }
```

| Поле | Когда заполнено |
|---|---|
| `consent*` | **только на гостевом пути.** На ручной записи персонала и на записи авторизованного клиента — `null` (у клиента согласие хранится в `UserConsent`, у ручной записи собрано салоном вне продукта) |
| `clientDeleted` | `true` — клиент удалил аккаунт, строка обезличена (§10) |

Версии заполняет **сервер** из действующего снимка документов. Значения из тела запроса не
принимаются никогда. Ретроспективно не переписываются (US-37 п. 6).

Аддитивно: существующие потребители `BookingDto` не ломаются, `tsc` не падает (поля опциональны
в TS-типе).

### 7.3 Новый код

| Код | Тело (`text/plain`) | Когда |
|---|---|---|
| **429** | `Слишком много записей с этого адреса. Повторите позже.` | политика `booking-create`: аноним > 10 записей в час с адреса |

**Ручная запись персонала не страдает:** аутентифицированный вызывающий считается по своему
идентификатору с лимитом 120/час, а не по IP (`ARCHITECTURE.md` §9.2). Фронт: ветка 429 в
`src/utils/bookingError.ts`.

```json
    { "company": "Барбершоп «Гвоздь»", "createdAt": "2026-09-20T11:06:12Z", "sizeBytes": 312845 }
  ],
  "notice": "В файл не входят: текст заметок сотрудников салона о вас и содержимое фотографий, загруженных салоном. Эти материалы принадлежат салону как результат его работы; запросить их можно у салона напрямую. По вопросам обработки ваших данных платформой: <адрес из политики>."
}
```

**Уточнение к составу (пост-релизная правка code review, цикл 3).** `bookings` включает не только
брони с `ClientId == текущий пользователь`, но и **гостевые брони, сделанные на тот же канонический
телефон до регистрации** — точно так же, как `notesAboutMe`/`photosOfMe` уже находили их через
`GuestPhone`, и точно так же, как `POST /api/profile/delete-account` уже обезличивает обе ветки
(`ARCHITECTURE.md` §7.4, шаг 3). До этой правки выгрузка показывала только меньшее из двух множеств,
которые удаление считает данными субъекта, — расхождение, недопустимое для правового артефакта.

**Что в выгрузку не входит и почему** (US-38 пп. 2, 3; `ARCHITECTURE.md` §7.2):
- **содержимое фотографий** — приватный класс хранения доступен только персоналу компании;
- **текст заметок** — суждение сотрудника, а не данные субъекта в чистом виде;
- **любые идентификаторы чужих сущностей и любые хеши** (`companyId`, `noteId`, `PasswordHash`,
  `SecurityStamp`, `ContentHash`) — вместо них человекочитаемые имена. Единственные `id` в ответе —
  собственные брони пользователя.

Оба ограничения уходят на юридическую вычитку (SPEC §10.2). При обратном вердикте меняется состав
ответа, а не контракт эндпоинта.

**Коды**

| Код | Тело (`text/plain`) | Когда |
|---|---|---|
| 200 | JSON выше | норма |
| 401 | пусто | нет токена |
| **429** | `Выгрузка доступна не чаще трёх раз в сутки.` | политика `data-export` |

**Фронт (T-F3).** Кнопка «Скачать мои данные» в `ProfilePage`. Рядом обязателен текст: что **входит**
и, отдельной строкой, что **не входит** — иначе выгрузка выглядит неполной по недосмотру (US-38 п. 5).
Скачивание — `blob` через тот же axios (токен нужен), затем `URL.createObjectURL`.

## 9. `POST /api/profile/delete-account` — US-39 · задача T-B7 · **НОВЫЙ**

Требует авторизации. **В allow-list** (SPEC US-39 п. 9: несогласный с новой редакцией не должен быть
заперт). POST, а не DELETE: нужно тело с паролем, и это тот же жест, что у существующего
`POST /api/profile/change-phone`.

**Запрос**
```json
{ "currentPassword": "SecretPass1" }
```

**204 No Content** — тело пустое.

**Коды**

| Код | Тело (`text/plain`) | Когда |
|---|---|---|
| 204 | пусто | удалено |
| 400 | `Неверный текущий пароль` | пароль не совпал (текст дословно как в `change-phone`) |
| 401 | пусто | нет токена |
| 409 | `За вами числится компания. Передайте её другому владельцу или обратитесь в поддержку — тогда аккаунт можно будет удалить.` | `Companies.Any(OwnerUserId == me)` |

**Что происходит** (полностью — `ARCHITECTURE.md` §7.4):

| Данные | Судьба |
|---|---|
| Имя, телефон, email, аватар (файл), пароль | стёрты |
| Согласия `UserConsent` | удалены |
| Заметки **о нём** (по `ClientId` и по `GuestPhone`) и их фотографии + файлы | удалены |
| Заметки, написанные **им** как мастером о других клиентах | **сохранены** — данные салона |
| Визиты как клиента | обезличены: `clientId = null`, гостевые поля очищены, `clientDeleted = true`; дата, услуга, мастер, цена, статус и снимок комиссии **сохранены** |
| Визиты как мастера | **не тронуты** |
| Отзывы | деперсонализированы: имя → `«Удалённый пользователь»`, ссылка на аккаунт снята; рейтинг и текст остаются |
| Членства в компаниях | удалены, Identity-роли пересчитаны (US-46) |
| Токены и сессии | **инвалидированы немедленно** (смена `SecurityStamp`, существующая сверка в `OnTokenValidated`) |
| Телефон | **освобождён** — по нему можно зарегистрироваться заново |

**Важно для фронта (T-F4).** Экран подтверждения обязан перечислять последствия прямым текстом,
включая необратимость и то, что **обезличенные визиты остаются у салона**. Кнопка активна только
при введённом пароле и отмеченном «понимаю, что действие необратимо». После 204 — `logout()` и
редирект на главную.

**Гости без аккаунта самостоятельно удалиться не могут** (US-39 п. 8) — эндпоинта нет и не будет
в этом цикле: гость идентифицируется только номером. Процедура ручная, её шаги (как проверяется
личность заявителя, по каким полям ищется гость — `Booking.GuestPhone`, `ClientNote.GuestPhone`)
описаны в `DEPLOY.md` задачей T-B7.

## 10. `GET /api/health/live` и `GET /api/health/ready` — US-43 · задача T-B1 · **НОВЫЕ**

### 10.1 Живость

```

```
```
200 OK
Content-Type: application/json
{ "status": "Healthy" }
```
К БД **не обращается** никогда. Это то, что опрашивает `healthcheck` контейнера в

### 10.2 Готовность

```
GET /api/health/ready
```

| Код | Тело | Когда |
|---|---|---|
| 200 | `{ "status": "Healthy" }` | соединение с PostgreSQL есть, миграции применены |
| 503 | `{ "status": "Unhealthy", "failed": "database" }` | БД недоступна |
| 503 | `{ "status": "Unhealthy", "failed": "migrations" }` | есть неприменённые миграции (окно старта) |

**Ответ намеренно беден.** Ни строк подключения, ни версий, ни имён исключений, ни стектрейсов
(US-43 п. 3): стандартный `ResponseWriter` ASP.NET публикует описания исключений проверок, поэтому
используется свой, на два поля. Подробной диагностики для SuperAdmin в цикле нет — то, что полезно
смотреть внутри, уже отдаёт `GET /api/admin/scheduled-tasks`.

### 10.3 Для эксплуатации

```bash
curl -s https://ezbook.ru/api/health/ready
```
Расшифровка трёх типовых ответов — в `DEPLOY.md` (задача T-D7). На этот эндпоинт опираются
`healthcheck` контейнера, скрипт деплоя (US-44) и smoke-тест в CI (US-41).

## 11. Пагинация четырёх выборок — US-49 · задача T-B10 — **BREAKING № 2**

### 11.1 Единый контракт

**Запрос:** `?page=1&pageSize=20`

| Параметр | Умолчание | Правило |
|---|---|---|
| `page` | 1 | с единицы; `< 1` → 1; **также клампится сверху** до `int.MaxValue / pageSize` (после нормализации `pageSize`) — без этого `(page-1)*pageSize` переполняет 32-битный `int` на достаточно большом `page` и роняет запрос 500-й. Наблюдаемый отказ зависит от выборки: SQL-выборки (`admin/users`, `admin/companies`, отзывы) отдают 500 на отрицательном `OFFSET`, а `masters/clients` считается в памяти и при отрицательном `Skip` **молча отдаёт первую страницу** вместо запрошенной. Самый чувствительный случай — отзывы компании: единственная из четырёх выборок, доступная анонимно |
| `pageSize` | 20 | потолок **100**; больше — **молча обрезается** до 100, а не 400 (US-49 п. 6) |

Поле `page` в ответе — это **фактически применённая** страница после обеих границ, а не эхо
запрошенного значения: если прислать заведомо огромный `page`, в ответе будет клампированное число,
а не то, что прислал клиент. Фронт не должен полагаться на `response.page === requestedPage`.

**Ответ** — один и тот же конверт для всех четырёх выборок:

```json
{
  "items": [ … ],
  "page": 1,
  "pageSize": 20,
  "total": 137,
  "hasNext": true
}
```

`hasNext = page * pageSize < total` — фронт не считает арифметику сам.

TS-тип (ручная копия в `src/types/index.ts`, конвенция проекта):
```ts
export interface Paged<T> { items: T[]; page: number; pageSize: number; total: number; hasNext: boolean }
```

### 11.2 Что меняется

| Эндпоинт | Было | Стало | Порядок сортировки |
|---|---|---|---|
| `GET /api/admin/users?search=` | `AdminUserDto[]` | `Paged<AdminUserDto>` | `createdAt`, затем `id` |
| `GET /api/admin/companies?search=` | `AdminCompanyDto[]` | `Paged<AdminCompanyDto>` | `createdAt`, затем `id` |
| `GET /api/companies/{companyId}/reviews` | `ReviewDto[]` | `Paged<ReviewDto>` | `createdAt DESC`, затем `id` |
| `GET /api/masters/clients?companyId=&search=` | `MasterClientDto[]` | `Paged<MasterClientDto>` | дата последнего визита DESC, затем ключ клиента |

Параметр `search` и `companyId` сохраняются и применяются **до** пагинации; `total` считается по
отфильтрованному множеству.

**Регрессия QA-цикла 3:** в первой версии этого раздела `search` на `GET /api/masters/clients` был
описан в тексте, но не попал в сигнатуру запроса и не был реализован — фронтенд фильтровал уже
полученную страницу, из-за чего поиск не находил клиентов вне текущей страницы. Исправлено: параметр
`search` (опционален) фильтрует полный список клиентов мастера в этой компании **до** `Skip/Take`,
регистронезависимо по имени клиента (`Name.Contains(search)`) и по телефону — если строка выглядит
как номер (≥5 цифр, без букв), она нормализуется через `PhoneNormalizer` перед сравнением с
канонически хранимым телефоном (та же эвристика, что и в `GET /api/admin/users?search=`), так что
поиск работает независимо от формата ввода номера (`+7 999 ...`, `8(999)...` и т.д.).

Тай-брейк по `id` обязателен: без него PostgreSQL не гарантирует порядок при равных `createdAt`,
и страницы начинают пересекаться.

### 11.3 Что НЕ меняется

- `GET /api/admin/bookings` — `Take(500)` **остаётся** (US-49 п. 5: пагинация вводится только на
  четырёх перечисленных выборках).
- Заметки внутри `MasterClientDto` — по-прежнему ≤ 50 на клиента.
- Фото внутри заметки — по-прежнему ≤ 5.
- `GET /api/companies`, `GET /api/companies/my`, `GET /api/bookings/client` и остальные —
  без пагинации, как было.

### 11.4 Устранение N+1

`GET /api/admin/users` перестаёт вызывать `userManager.GetRolesAsync` в цикле по пользователям
(сегодня — N запросов на страницу). Роли выбираются одним join'ом `AspNetUserRoles × AspNetRoles`.
Контракт ответа этим не меняется — но без этой правки пагинация только маскировала бы проблему
(US-49 п. 3).

### 11.5 Влияние на фронт: **правки обязательны**

`AdminPage.tsx` (две вкладки), `MasterClientsPage.tsx` и блок отзывов на `CompanyPage.tsx` без
правки покажут пустые списки и уронят `tsc`. Задачи T-B10 и T-F5 **мёржатся вместе**.

## 17. Чек-лист согласования BE↔FE перед мёржем цикла

1. `POST /api/auth/register` без `acceptedLegal` даёт 400 — проверено **прямым запросом**, мимо формы.
2. Регистрация с `acceptedLegal: true` пишет две строки согласия; в БД видны версии и момент.
3. Гостевая запись содержит версию, действовавшую в момент записи; после смены версии старая запись
   **не переписана**.
4. Существенная смена версии: старый токен получает **451** на защищённом вызове и **200** на
   `/api/legal/*`, `GET /api/profile`, `GET /api/profile/export`, `POST /api/profile/delete-account`.
5. Редакционная смена версии: 451 не выдаётся нигде, `consent-status` отдаёт `showBanner: true`.
6. `POST /api/legal/accept` вернул новый токен, фронт положил его в `authStore`, следующий запрос
   прошёл без 451.
7. `GET /api/profile/export` отдаёт только свои данные; чужих записей, текста заметок, байт фото и
   хешей в файле нет; четвёртый вызов за сутки → 429.
8. `POST /api/profile/delete-account`: логин не работает, старый токен не проходит, визиты остались
   с `clientDeleted: true`, владелец компании получает 409 с человеческим текстом.
9. Четыре выборки отдают конверт; вторая страница не пересекается с первой; `total` корректен;
   три экрана фронта работают.
10. Перебор логина и спам гостевой записи упираются в 429 с русским текстом; ручная запись персонала
    при этом не страдает.
11. `GET /api/health/ready` отдаёт 503 при остановленной БД и 200 после её подъёма; тело ответа не

### 18.2 `CompanyDto` — агрегат рейтинга компании

Средний рейтинг на публичной странице компании (`GET /api/companies/{slug}`, а также `GET
/api/companies`, `GET /api/companies/my`, `GET /api/companies/member`, `POST /api/companies`,
`PUT /api/companies/{id}`, `POST /api/companies/{id}/logo` — все семь точек, отдающих `CompanyDto`)
до этого прохода считался на фронте из текущей страницы `GET /api/companies/{companyId}/reviews` и
**видимо менялся** при листании отзывов. Добавлены два новых поля, посчитанные в БД (`GROUP BY` /
`AVG`/`COUNT` над ВСЕМИ отзывами компании, не по странице):

```json
{
  ...,
  "averageRating": 4.62,
  "reviewCount": 137
}
```

`averageRating` — `number | null` (`null`, если отзывов ещё нет); `reviewCount` — всегда число,
`0` при отсутствии отзывов. Оба поля есть во всех семи ответах `CompanyDto`; у только что созданной
компании (`POST /api/companies`) они `null`/`0` без обращения к БД — у неё физически не может быть
отзывов. Имена полей выбраны так, чтобы не тесниться с `Rating` внутри `ReviewDto` (§11.2 таблица)
и явно читаться как агрегат, а не как поле одного отзыва.
