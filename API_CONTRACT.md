# API_CONTRACT — цикл санации ServiceBooking (ревизия 2)

**Назначение.** Точка синхронизации backend- и frontend-разработчика на время цикла. Обе стороны
работают по этому файлу, а не по коду друг друга (`ARCHITECTURE.md` §10, таблица «Точки пересечения BE↔FE»).

**Что здесь есть.** Все эндпоинты, которые цикл A реально трогает — их 17 (было 6 в ревизии 1).
Остальной API описан в `API_DOCUMENTATION.md` и в этом цикле не меняется.

**Источник истины по решениям.** `SPEC.md` ревизии 2 §0 (Q1–Q12) и `ARCHITECTURE.md` (§2 общие механизмы,
§3 порядок проверок в записи, §6 границы формата ошибок, §11 задачи T-B*/T-F*). Контракт ниже
не вводит альтернатив — он фиксирует уже принятое в терминах запрос/ответ.

**Базовая ревизия.** Коммит `e6b746c`, ветка `sanitation-cycle`; поведение «как сейчас» совпадает
с `263c661`. Все ссылки «файл:строки» — по ней.

**Что удалено относительно предыдущей редакции этого файла.** Абзац в §1.2 о том, что «мастер,
запрашивающий свой `masterId`, получает 200 при любом `companyId`, в том числе чужом… расширять
предикат в этом цикле не требуется». Это было описание уязвимости A5 как штатного поведения;
починка предиката — первый критерий приёмки US-04. Также удалены строки §8.3 про `GET /api/workinghours`
и про 500 на неизвестном `ownerUserId` — обе позиции теперь в скоупе.

## 1. `GET /api/bookings/slots` — US-13, US-04, US-03 · задача T-B3 (+ T-F2)

Файл: `ServiceBooking.API/Controllers/BookingsController.cs:30-43`, расчёт —
`ServiceBooking.API/Services/SlotService.cs:13-52`.

### 1.1 Текущее поведение

**Доступ:** анонимный (атрибута авторизации нет).

| Query-параметр | Тип | Обяз. | Примечание |
|---|---|---|---|
| `masterId` | `string` | да | |
| `serviceId` | `Guid` | да | |
| `date` | `DateOnly` | да | |
| `manual` | `bool` | нет, по умолчанию `false` | |

`manual=true` honors для **любого аутентифицированного** пользователя (`:40`), и в этом режиме
`SlotService` отдаёт весь день 00:00–24:00 без учёта расписания (`SlotService.cs:22, 31-32`).
Расписание ищется **без `CompanyId`** (`SlotService.cs:18-21`) — мастер, работающий в двух компаниях,
отдаёт на витрине компании B слоты из графика компании A (находка A4).

**200 OK** — массив `TimeSlotResult`, отсортирован по времени:
```json
[{ "start": "10:00:00", "end": "10:45:00" }, { "start": "10:30:00", "end": "11:15:00" }]
```
Прошедшие слоты **входят** в ответ; их отсекает фронт (`BookingModal.tsx:83`, `ManualBookingModal.tsx:100`).

**Коды сейчас:** `200` (в т.ч. пустой массив, если услуги нет или расписания нет),
`400` от автоматической валидации при непарсибельных параметрах.

### 1.2 Целевое поведение

**Появляется обязательный query-параметр `companyId` (`Guid`).** Он нужен дважды: чтобы скоупить
`WorkingHours` по компании (A4) и чтобы проверить членство вызывающего для `manual=true` (A1) —
без компании проверять членство не по чему.

| Query-параметр | Тип | Обяз. | Изменение |
|---|---|---|---|
| **`companyId`** | `Guid` | **да** | **НОВЫЙ** |
| `masterId` | `string` | да | — |
| `serviceId` | `Guid` | да | — |
| `date` | `DateOnly` | да | — |
| `manual` | `bool` | нет | смысл сужается |

Правила:
1. `manual=true` honors **только** если вызывающий — `SuperAdmin` **или** участник компании
   `companyId` с ролью `Master`/`CompanyOwner` (`CompanyMembership.IsStaffAsync`,
   `ARCHITECTURE.md` §2.1). Для всех остальных `manual` игнорируется — расписание соблюдается.
   `403` **не возвращается**: эндпоинт остаётся публичным, просто перестаёт верить флагу на слово.
2. Расписание ищется по `(MasterId, CompanyId, Date, IsWorking)`.
3. Состав и форма ответа, порядок слотов, шаг 30 минут, наличие прошедших слотов в выдаче —
   **не меняются** (US-03 п. 3). Фильтрация прошедшего времени по-прежнему на фронте.
4. Отсутствие `companyId` → `400` `application/problem+json` от автоматической валидации
   `[ApiController]` (поведение фреймворка, §0.2).

### 1.3 Дельта

| Что | Было | Стало |
|---|---|---|
| `companyId` | параметра нет | **обязательный**; без него `400` |
| Расписание мастера-совместителя | берётся любое (без скоупа компании) | только расписание запрошенной компании |
| `manual=true` от постороннего аутентифицированного | весь день 00:00–24:00 | расписание соблюдается, как для гостя |
| `manual=true` от персонала компании | весь день | без изменений |
| Форма `TimeSlotResult`, шаг сетки, прошедшие слоты в выдаче | — | **не меняются** |

### 1.4 Ломающее изменение? **Да, и это главное ломающее изменение цикла**

Потребители:
- слой запросов — `frontend/src/api/bookings.ts:18-20` (`bookingsApi.getSlots`);
- `frontend/src/components/booking/BookingModal.tsx:63, 79` — `company` уже есть в пропсах (`:18`);
- `frontend/src/components/booking/ManualBookingModal.tsx:88, 96` — `selectedCompany!.id` уже
  используется в теле записи (`:105`);
- `RescheduleModal` **не затронут** — он ходит в `GET /api/bookings/occupied`, а не в слоты.

**Что делает фронт (T-F2):**
```ts
getSlots: (companyId: string, masterId: string, serviceId: string, date: string, manual = false) =>
  api.get<TimeSlot[]>('/bookings/slots',
      { params: { companyId, masterId, serviceId, date, manual: manual || undefined } })
     .then((r) => r.data),
```
плюс `companyId` добавляется в `queryKey` обеих модалок (`['slots', companyId, masterId, serviceId, date]`),
иначе кэш смешает слоты разных компаний для мастера-совместителя.

**T-B3 и T-F2 мёржатся одним PR** (`ARCHITECTURE.md` §4.4): обязательный параметр без синхронного
фронта ломает публичную запись — ядро продукта (риск R14). Опциональный параметр с fallback отвергнут:
он оставил бы обход A1 открытым на весь релиз.

## 2. `POST /api/bookings` — US-13, US-05 · задача T-B14

Файл: `ServiceBooking.API/Controllers/BookingsController.cs:45-149`.

### 2.1 Текущее поведение

**Доступ:** атрибута `[Authorize]` нет — принимает и гостя, и залогиненного.

**Тело запроса** — `CreateBookingDto` (`ServiceBooking.API/DTOs/Bookings/BookingDto.cs:30-42`):
```json
{
  "companyId": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "serviceId": "aa11bb22-0000-1111-2222-333344445555",
  "masterId": "6a9c1e2d-3f4b-4a5c-8d6e-7f8091a2b3c4",
  "date": "2026-09-01",
  "startTime": "10:00:00",
  "notes": null,
  "guestName": "Иван",
  "guestPhone": "+79990000000",
  "guestEmail": null,
  "captchaToken": "…"

```
Валидации полей нет вообще: `notes` может быть мегабайтом, `guestName` — любой длины.

**201 Created** — `BookingDto` + заголовок `Location` (`CreatedAtAction`, `:147`).

**Порядок проверок и коды сейчас:**

| # | Условие | Код | Тело (`text/plain`) | Строка |
|---|---|---|---|---|
| 1 | **гость** (`userId is null`) + компании нет | `404` | `Company not found` | `:60-61` |
| 2 | **гость** + `!company.AllowSelfBooking` | `403` | пусто | `:62` |
| 3 | **гость** + капча включена, токена нет | `400` | `Captcha required for guest booking` | `:69-70` |
| 4 | **гость** + капча не прошла | `400` | `Invalid captcha` | `:73-74` |

**Дефекты, которые чинит цикл:**
- «сотрудник» определяется как «аутентифицирован **и** прислал `guestName`» (`:54-55`). Любой клиент,
  добавивший `guestName`, минует шаги 2–5 и шаг 6 (находка A1);
- `companyId`/`serviceId`/`masterId` не связаны между собой (`:89-120`) — можно записаться на услугу
  чужой компании и к мастеру, не работающему в компании (находка A2);
- проверка перед вставкой смотрит **только** на другие записи: ни расписания, ни перерывов, ни даты
  в прошлом, ни сетки 30 минут (находка A3);
- для **залогиненного** несуществующий `companyId` не отсекается нигде → 500 от нарушения FK.

### 2.2 Целевое поведение

Тело запроса, тело успешного ответа (`BookingDto`), код `201` и заголовок `Location` — **без изменений**.
Форма `CreateBookingDto` не меняется, добавляются только ограничения длины.

**Валидация DTO (новое, `[ApiController]` → 400 `application/problem+json`):**
`notes` ≤ 2000, `guestName` ≤ 200, `guestPhone` ≤ 32, `guestEmail` ≤ 256.

**Кто такой «персонал» (US-13 п. 1):**
```
isStaff              = аутентифицирован && (SuperAdmin || участник companyId с ролью Master/CompanyOwner)
isStaffManualBooking = isStaff && guestName не пуст
isGuestPath          = !аутентифицирован || (guestName не пуст && !isStaff)
```
`isGuestPath` — вызывающий, присылающий гостевые данные, но не работающий в компании, проходит
**ровно те же гейты, что и гость**. Для обычного авторизованного клиента (без `guestName`) поведение
**не меняется**.

**Порядок проверок после правки:**

| # | Условие | Код | Тело (`text/plain`) | Новое? |
|---|---|---|---|---|
| 0 | нарушены `[MaxLength]` | `400` | `ValidationProblemDetails` | **новое** |
| 1 | компании нет | `404` | `Company not found` | текст прежний, **применяется и к залогиненному** |
| 2 | `isGuestPath` + `!company.AllowSelfBooking` | `403` | пусто | **применяется шире** |
| 3 | `isGuestPath` + капча включена, токена нет | `400` | `Captcha required for guest booking` | **применяется шире** |
| 4 | `isGuestPath` + капча не прошла | `400` | `Invalid captcha` | **применяется шире** |
| 5 | `isGuestPath` без `guestName`/`guestPhone` | `400` | `Name and phone are required for guest booking` | **применяется шире** |
| 6 | `!AllowOnlineBooking && !isStaffManualBooking` | `402` | `Online booking requires a paid subscription.` | **применяется шире** |
| 7 | услуги нет | `404` | `Service not found` | — |
| 8 | `service.CompanyId != dto.CompanyId` | `400` | `Service does not belong to this company` | **новое** |

| 12 | слот не проходит валидацию (см. ниже) | `409` | `Time slot is no longer available` | **расширено** |
| 13 | успех | `201` | `BookingDto` + `Location` | — |

**Валидация слота (шаг 12), внутри существующей транзакции и `pg_advisory_xact_lock`:**
- **персонал** (`isStaffManualBooking`) — по решению Q7 проверяется **только** пересечение с другими
  записями мастера. Рабочие часы, перерывы и сетка 30 минут к ручной записи персонала **не применяются**;
- **все остальные** — запрошенное `startTime` обязано входить в набор слотов, который выдал бы
  `GET /api/bookings/slots` для этой компании, этого мастера, этой услуги и этой даты. Это тот же код
  (`SlotCalculator`, `ARCHITECTURE.md` §2.2), поэтому расхождения между выдачей и валидацией
  не существует физически. Отклоняются: нерабочий день, время вне окна, попадание в перерыв,
  `startTime` не на сетке, пересечение с другой записью.

**Занятость считается по всем компаниям мастера** — намеренно, поведение сохраняется
(`ARCHITECTURE.md` §2.3): мастер-совместитель физически один.

**Кому принадлежит созданная запись.** Меняется одно поле: `ClientId` заполняется, если вызывающий
не является персоналом, оформляющим ручную запись. Раньше: `ClientId = isManualBooking ? null : userId`
(`:109`) — то есть клиент, приславший `guestName`, создавал «ничью» гостевую запись, к которой затем
кто угодно мог написать отзыв (связка с A6). Стало: `ClientId = isStaffManualBooking ? null : userId`.
Форма `BookingDto` при этом не меняется; меняется значение `clientId` в ответе для сценария
«клиент прислал `guestName`» — сценария, недостижимого через UI.

Тексты всех существующих тел — **дословно прежние**.

### 2.3 Дельта

| Сценарий | Было | Стало |
|---|---|---|
| Клиент (не сотрудник) с `guestName` в компанию с `AllowSelfBooking = false` | `201` | **`403`** |
| Клиент с `guestName` в компанию на Free-тарифе | `201`, бесплатная запись | **`402`** `Online booking requires a paid subscription.` |
| Клиент с `guestName` при включённой капче без токена | `201` | **`400`** `Captcha required for guest booking` |
| Клиент с `guestName` в компанию с предоплатой | `PaymentStatus = NotRequired` | предоплата назначается, как гостю |
| **Гостевая запись в компанию с предоплатой** (`RequirePrepayment` + тариф с `AllowOnlinePayment`) | `PaymentStatus = NotRequired` | **`PaymentStatus = Pending`** |

**Про последнюю строку.** Признаком «ручной записи персонала» раньше служило наличие `guestName` в теле,
а его шлёт каждый настоящий гость — это обязательное поле гостевого пути. Поэтому гостевая запись
молча обходила гейт предоплаты, хотя гостевая запись это такая же онлайн-запись, как и клиентская.
После перехода на проверенное членство (`isStaffManualBooking`) гость получает `Pending` наравне
с зарегистрированным клиентом. Изменение подтверждено заказчиком; **влияние на UI:** в кабинете
мастера у гостевых записей появляется бейдж «ожидает оплаты» (`MyBookingsPage.tsx`), которого раньше

## 19. Что осталось неизменным намеренно

### 19.1 Формат тел ошибок для 400/402/403/404/409 (риск R3)

Самое важное ограничение цикла, и после расширения скоупа оно **усиливается**, а не ослабевает:
новых кодов ответов стало вдвое больше, и каждый обязан подчиняться той же таблице (§0.2).

- `BadRequest("текст")`, `StatusCode(402, "текст")`, `NotFound("текст")`, `Conflict("текст")` продолжают
  отдавать **голую строку** `text/plain`; `Forbid()` — **пустое** тело;
- `BadRequest(createResult.Errors.Select(e => e.Description))` (`CompaniesController.cs:341`) продолжает
  отдавать JSON-массив строк — его разбирает `frontend/src/utils/memberError.ts:23-27`;
- **ни одно существующее сообщение об ошибке не переформулировано.** Тексты `Company not found`,
  `Service not found`, `Time slot is no longer available`, `Online booking requires a paid subscription.`,
  `Captcha required for guest booking`, `Invalid captcha`, `Name and phone are required for guest booking`
  остаются посимвольно прежними — на них завязаны `lower.includes(...)` в `bookingError.ts:18,28,30`;
- **все новые отказы по слоту переиспользуют существующий текст** `Time slot is no longer available`,
  включая «дата в прошлом» и «нерабочее время». Новых текстов 409 в цикле нет вовсе;
- новые тексты 400 не содержат подстрок `captcha`, `name`, `phone` (§0.2);
- `ProblemDetails` — **исключительно** для необработанных исключений (500);
- прямые запреты реализации: **не добавлять** `builder.Services.AddProblemDetails()` и
  **не добавлять** `UseStatusCodePages*`.
