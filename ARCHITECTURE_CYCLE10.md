### §101.2. Что сознательно НЕ берём и почему

- **`react-day-picker` / любой календарь.** Помесячный календарь уже написан и работает у всех
  посетителей; заменить его библиотекой — это переписать публичный экран ради нуля пользы. Прямо
  противоречит §41 `ARCHITECTURE_CYCLE6.md`.
- **`dnd-kit` / `react-beautiful-dnd` для порядка фото.** Цена: +30–50 КБ в бандл публичного
  приложения ради экрана настроек, которым пользуется один человек на салон, плюс drag-and-drop
  недоступен с клавиатуры без дополнительной работы, а доступность — требование НФТ. Порядок
  задаётся кнопками «↑/↓» и «сделать обложкой»: ноль зависимостей, работает с клавиатуры и на
  телефоне, тестируется обычным `userEvent.click`.
- **Библиотека лайтбокса.** См. `useOverlayDismiss` выше.
- **Audit-библиотека / EF interceptors для журнала.** Перехватчик `SaveChanges` пишет «что
  изменилось в строке», а нам нужно «что сделал человек» (перенос ≠ два изменённых поля; отметка
  оплаты ≠ смена колонки). Автоматика дала бы журнал, который никому нельзя показать. Шесть явных
  вызовов в шести местах — честнее и тестируемее.
- **Объектное хранилище (S3/MinIO).** Витрина — это ≤10 файлов на салон. Точка будущей миграции
  одна и уже изолирована — `FileStorage`; трогать её в этом цикле незачем.

### §101.4. Почему выбор оправдан «через призму задачи»

Продукт продаётся как сервис, хостится на одной машине (Ubuntu desktop, не VPS), выкатывается
кнопкой из GitHub Actions. Любая новая зависимость — это новая строка в цепочке поставки, новый
повод упасть на деплое и новая вещь, которую оператор обязан знать. Цикл 10 не приносит ни одной
задачи, которую нельзя решить тем, что уже стоит и уже эксплуатируется. Стоимость хостинга при этом
не меняется: обе новые таблицы малы, фото салона — до 10 файлов по ≤1600 px на компанию
(≈2–4 МБ на салон вместе с миниатюрами).

## §102. Модель данных: две новые сущности, ни одной миграции данных

Обе таблицы **только добавляются**. Backfill'а нет (решение П3). Ни одна существующая колонка не
меняет тип, смысл и обязательность. Это снимает главный риск редакции 1 спеки и соответствует R5.

### §102.1. `BookingEvent` — журнал изменений записи

`ServiceBooking.Core/Entities/BookingEvent.cs`

| Поле | Тип | Смысл |
|---|---|---|
| `Id` | `Guid` | PK |
| `BookingId` | `Guid` | FK → `Booking`, **Cascade** |
| `CompanyId` | `Guid` | **денормализованная копия** `Booking.CompanyId` |
| `Kind` | `BookingEventKind` (int) | что произошло |
| `OccurredAtUtc` | `DateTime` | когда (UTC, как везде в продукте) |
| `ActorKind` | `BookingActorKind` (int) | кто в широком смысле: клиент / гость / сотрудник / суперадмин / система |
| `ActorUserId` | `string?` | FK → `AppUser`, **SetNull** |
| `ActorNameSnapshot` | `string?` (≤200) | **снимок имени на момент события** |
| `ActorRoleSnapshot` | `UserRole?` | роль автора **в этой компании** на момент события |
| `PreviousDate` / `PreviousStartTime` | `DateOnly?` / `TimeOnly?` | заполняются только у `Rescheduled` |
| `NewDate` / `NewStartTime` | `DateOnly?` / `TimeOnly?` | то же |
| `CancellationReason` | `string?` (≤300) | только у `Cancelled`, если причина указана |

**Индексы:** `(BookingId, OccurredAtUtc)` — единственный читающий запрос; `(CompanyId, OccurredAtUtc)`
— скан правила уничтожения. Уникальных индексов нет: это журнал, а не состояние.

**Почему денормализованный `CompanyId`.** Тот же приём, что у `ClientNotePhoto.CompanyId`
(`CURRENT_STATE.md` §3): проверка прав на чтение истории и скан retention делаются **без join'а** с
`Bookings`.

**Почему «было → стало» отдельными колонками, а не JSON-полем.** Событие с полезной нагрузкой ровно
одно (`Rescheduled`), полей у него четыре, они типизированы (`DateOnly`/`TimeOnly`) и их видно в
любом SQL-клиенте при разборе инцидента. JSON потребовал бы парсер, второй контракт внутри контракта
и превратил бы «что было до» в строку, которую нельзя сравнить запросом.

**Почему в журнале нет телефонов и почты.** Требование НФТ спеки. В таблице только идентификатор
автора и снимок имени/фамилии. Это же уменьшает объём ПДн работника, на который ждём срок хранения
(Q2, §116).

**Перечисления** (`ServiceBooking.Core/Enums/`), оба **append-only** — значения едут в БД:

```
BookingEventKind  { Created = 0, Rescheduled = 1, Cancelled = 2, Completed = 3, NoShow = 4, PaymentMarked = 5 }
BookingActorKind  { Client = 0, Guest = 1, Staff = 2, SuperAdmin = 3, System = 4 }
```

`System` не ставится никем в этом цикле — он существует, потому что сущность обязана допускать
системное событие (US-123), и потому что добавлять член перечисления в БД потом дороже, чем сейчас.
R8: **`System` не повод оживлять `NotificationType.StaffBookingCreated`.**

### §102.2. `CompanyPhoto` — фотография салона

`ServiceBooking.Core/Entities/CompanyPhoto.cs`

| Поле | Тип | Смысл |
|---|---|---|
| `Id` | `Guid` | PK |
| `CompanyId` | `Guid` | FK → `Company`, **Cascade** |
| `Url` | `string` (≤300) | публичный URL полноразмерной, `/uploads/companies/<guid>.<ext>` |
| `ThumbnailUrl` | `string` (≤300) | публичный URL миниатюры |
| `ContentType` | `string` (≤100) | |
| `SizeBytes` | `long` | полноразмерная + миниатюра, для эксплуатации |
| `Width` / `Height` | `int` | размеры полноразмерной |
| `ContentHash` | `string` (64) | SHA-256 **обработанных** байт полноразмерной |
| `Position` | `int` | 0-based; **0 = обложка** |
| `UploadedByUserId` | `string?` | FK → `AppUser`, **SetNull** |
| `CreatedAtUtc` | `DateTime` | |

**Индексы:** `(CompanyId, Position)` — **не уникальный**; уникальный `(CompanyId, ContentHash)`.

**⚠️ Почему `(CompanyId, Position)` НЕ уникальный — это осознанное решение, а не забывчивость.**
Перестановка порядка меняет `Position` у нескольких строк сразу. EF Core выпускает отдельный `UPDATE`
на строку, и обычный (не `DEFERRABLE`) уникальный индекс Postgres упадёт на промежуточном состоянии,
где две строки на мгновение делят позицию. Варианты были три: (а) `DEFERRABLE INITIALLY DEFERRED`
через сырой SQL в миграции, (б) двухпроходная запись со сдвигом на +1000, (в) неуникальный индекс.
Выбрано **(в)**: порядок показа — не инвариант безопасности, а оформление витрины, и цена ошибки
здесь нулевая. Целостность даёт сервер: любая мутация перенумеровывает **все** фото компании в
`0..n-1` внутри одной транзакции под advisory-lock `company-photos:{companyId}`. Детерминированный
порядок чтения задан навсегда: **`ORDER BY Position, CreatedAtUtc, Id`** — даже если две строки
каким-то образом сравняются по позиции, выдача останется стабильной, а не «как повезёт».

**Уникальный `(CompanyId, ContentHash)`** — та же защита от дубля при двойном клике, что у
`ClientNotePhoto`, и тот же приём: повторная загрузка того же файла возвращает **уже существующую**
фотографию, а не 11-ю строку и не ошибку.

**П5 в модели:** у `CompanyPhoto` **нет** ни `PhotoRetention`, ни участия в сумме `PhotoQuotaMb`.
Квота считается запросом по `ClientNotePhotos` (`CompaniesController`, `photo-usage`) — новая таблица
туда **не добавляется**, и это надо проверить тестом, а не глазами (§113, QA-2).

**П7 в модели:** `ConsentRecord` по фото салона не пишется. Ни поля, ни вызова `ConsentLedger` на
этом пути нет.

### §102.3. Что НЕ меняется в существующих сущностях

`Booking`, `BookingService`, `Company`, `CompanyMember`, `WorkingHours`, `ClientNotePhoto` — **ни
одного нового поля, ни одного изменённого**. `Company` не получает `CoverPhotoUrl`: обложка — это
`CompanyPhoto` с `Position = 0`, и дублировать её колонкой значило бы завести второй источник правды,
который разойдётся при первом же удалении обложки.

### §102.4. Миграции — две, раздельные, с честным `Down`

1. `AddBookingEventJournal` — таблица + два индекса + FK.
2. `AddCompanyPhotos` — таблица + два индекса + FK.

**Почему две, а не одна.** Блоки B и C независимы и поедут в одном релизе, но откатывать их может
понадобиться поодиночке. Опыт B1 (`AddCoTenancyConstraints` уронила деплой и оказалась необратимой)
прямо говорит: необратимых и «широких» миграций в этом цикле быть не должно.

`Down` у обеих — честный `DropTable`, без no-op. Данных, которые нельзя потерять при откате, в них
нет: журнал ведётся с момента внедрения, фото можно загрузить заново.

⚠️ **R6.** Эти две миграции лягут поверх **одиннадцати невыкаченных миграций цикла 7**. Ни одна из
них не ссылается на колонки цикла 7 (`BillingAccountId` и прочие) — проверено по составу полей выше.
Порядок выката — вопрос к devops **до** мержа, а не после; см. §116 R6.

## §103. Блок A: один экран записи — что меняется на сервере

Причина дефекта подтверждена и она клиентская (§0.2 спеки). Сервер свободу персонала уже даёт.
Серверных изменений в блоке A ровно два, оба — в `GET /api/bookings/availability`.

### §103.1. `extendedHours` у `availability` (закрывает R2)

Параметр добавляется **с той же таблицей доверия**, что у `GET /api/bookings/slots`
(`BookingsController.cs:121-125`), и логика обязана быть буквально одинаковой:

| `manual` | `extendedHours` | вызывающий | `ScheduleFallback` |
|---|---|---|---|
| true | true | персонал этой компании / SuperAdmin | `WholeDay` |
| true | false | персонал этой компании / SuperAdmin | `DefaultWindow` |
| любое | любое | **все остальные** | `None` |

`extendedHours=true` без `manual=true` — это `None`, как и сегодня в `/slots`. Пользователь без
членства не расширяет выдачу **ни при какой комбинации параметров**. Это ключевая регрессия цикла
(НФТ «Безопасность и права»), и она проверяется тестом на каждом из трёх видов не-персонала.

`SlotCalculator` остаётся **единственным** источником правды: `AvailabilityService` уже считает
статус дня той же `Calculate`, что отвечает `/slots`. Разводить их нельзя (R2).

### §103.2. Статус дня перестаёт быть одновременно «подписью» и «запретом» — новое поле `scheduleState`

Это центральное архитектурное решение блока A, и без него требование заказчика невыполнимо.

**Проблема.** Сегодня `DayAvailabilityDto.status` отвечает сразу на два вопроса: «что с графиком» и
«можно ли сюда записать». Для клиента это одно и то же. Для персонала — нет: заказчик требует, чтобы
день без графика **сохранял подпись** «выходной»/«нет графика» и **при этом был нажимаем**. А сервер
при `fallback = DefaultWindow` возвращает такому дню `Available` — то есть подпись исчезает.
Починить это на фронте нечем: в ответе просто нет информации о графике.

**Решение.** `DayAvailabilityDto` получает **дополнительное, необязательное** поле:

```
scheduleState: "Working" | "DayOff" | "NoSchedule" | null
```

- `Working` — на дату есть строка `WorkingHours` с `IsWorking = true`;
- `DayOff` — строка есть, `IsWorking = false` («выходной»);
- `NoSchedule` — строки нет вовсе («нет графика»);
- `null` — **поле не заполнено**, потому что режим персонала не подтверждён.

`status` сохраняет прежний смысл — «можно ли сюда записать при том фоллбеке, который сервер
применил». Для не-персонала форма и значения ответа **не меняются ни в чём**, кроме появления поля
со значением `null`.

**Почему `scheduleState` отдаётся ТОЛЬКО персоналу.** Сегодня анонимный посетитель видит `DayOff` и
не может отличить «у мастера выходной» от «график не заполнен». Различать эти два состояния — новая
информация о расписании чужого сотрудника. Отдавать её анонимно незачем и не требуется ни одной
историей. Правило жёсткое: **`scheduleState` заполняется тогда и только тогда, когда
`staffMode == true`** (§103.3).

### §103.3. `staffMode` в ответе — сервер прямо говорит, что он признал персонал

`AvailabilityDto` получает поле `staffMode: bool` — «сервер проверил членство и применил режим
персонала».

**Зачем.** Требование НФТ: «режим персонала включается по серверной проверке членства, а не по
параметру запроса». Без этого поля фронт вынужден **угадывать**, включён ли режим (по тому, состоит
ли пользователь в компании), и любая ошибка в догадке — это либо потерянная свобода записи, либо
нарисованные персональские элементы управления у постороннего. С полем догадок нет: интерфейс
рисует режим персонала строго по `staffMode`.

Побочная выгода — регрессия становится проверяемой **одной строкой** в тесте: «анонимный / клиент /
сотрудник чужой компании с `manual=true&extendedHours=true` получает `staffMode: false`,
`scheduleState: null` и дни `DayOff` как сегодня». Это и есть главный страховочный тест цикла (R1).

### §103.4. Горизонт и диапазон запроса (R3) — сервер не трогаем

- Ограничение «диапазон ≤ 31 дня» и «`from` не раньше `сегодня−1`» **остаются как есть**. Месячный
  календарь запрашивает ровно один месяц, то есть в них укладывается; листание вперёд — это новый
  запрос на новый месяц, а не расширение диапазона. НФТ «один запрос на месяц» соблюдается.
- Горизонт (`BookingHorizonDays`) для персонала сервер уже игнорирует (`honorManual`). Клиенту
  горизонт по-прежнему применяется и отдаётся в `horizonDays`/`horizonLastDate`.
- Верхняя граница календаря для персонала (не менее 365 дней) — **правило фронта**, а не сервера:
  константа `STAFF_MAX_MONTHS_AHEAD = 12` гасит стрелку «вперёд». Никаких хаков ради обхода
  серверных проверок не требуется — их и не должно появиться (R3 закрыт без изменений сервера).
- Клэмп `from` к сегодняшнему дню в `BookingCalendar` уже сделан в цикле 6 и сохраняется.

### §103.5. Скрытые мастера доступны персоналу (US-122, вопрос Q3)

`GET /api/companies/{id}/masters` сегодня жёстко фильтрует `cm.ProvidesServices`
(`CompaniesController.cs:132`). Для ручной записи это и есть «скрытого мастера не записать».

Изменение: параметр `includeHidden=true`, **honored только для персонала этой компании и
SuperAdmin** (та же проверка `CompanyMembership.IsStaffAsync`, что везде); для всех остальных
игнорируется молча — фильтр остаётся. `MasterPublicDto` получает поле `providesServices: bool`,
чтобы интерфейс мог подписать, почему этого мастера не видно клиентам. Для анонимного вызова поле
всегда `true` (иначе элемент не попал бы в выдачу), то есть утечки нет.

Решение по Q3 принимаю как «виден» — прямо по тексту US-122. Риск низкий и обратим: если заказчик
решит иначе, меняется один флаг в одном запросе.

### §103.6. Чего в блоке A на сервере НЕ делаем

- `POST /api/bookings` не меняется вовсе. Свобода персонала там уже есть (`~стр. 333`, `~стр. 470`),

- `GET /api/bookings/slots` не меняется: `manual`/`extendedHours` там уже есть и работают правильно.

  изменением, а подпись фронт уже знает из ответа календаря.
- `GET /api/bookings/occupied` не трогаем.

## §104. Блок B и блок C: устройство на сервере

### §105. Журнал: единственный писатель, шесть точек вызова, одна транзакция

**`Services/Bookings/BookingEventLog.cs` — единственное место в коде, которое пишет в
`BookingEvents`.** Это прямая калька с `ConsentLedger` (цикл 5): журнал — таблица, доступ к которой
не размазан по контроллерам, ровно затем, чтобы ответ на «что и как попадает в историю» существовал
в одном месте. Никаких `db.BookingEvents.Add(...)` в контроллерах.

Разбиение на классы (следуем линии циклов 4–6 «чистая логика отдельно»):

| Класс | БД | Что делает | Чем покрыт |
|---|---|---|---|
| `BookingEventLog` | да | добавляет строку в текущий `DbContext`, **не вызывая `SaveChanges`** | функциональные тесты |
| `BookingActorResolver` | 1 запрос | по `ClaimsPrincipal` + `Booking` определяет `ActorKind`, `ActorUserId`, снимок имени и роль в компании | функциональные |
| `BookingEventTexts` | нет | русские `title` и `actorLabel` из `Kind`/`ActorKind`/`ActorRoleSnapshot` | **юнит** |

**Почему `BookingEventLog` не вызывает `SaveChanges`.** Требование US-123: «запись события происходит
в той же транзакции, что и само изменение». Способ гарантировать это конструкцией, а не дисциплиной:
писатель только **добавляет** сущность в отслеживаемый граф, а сохраняет её тот же
`SaveChangesAsync`, который сохраняет изменение записи. EF оборачивает один `SaveChangesAsync` в одну
транзакцию — значит «перенос без строки в журнале» и «строка в журнале без переноса» невозможны
физически.

**Шесть точек вызова** (все — `BookingsController`), каждая **до** существующего `SaveChangesAsync`:

| Метод | Событие | Особенности |
|---|---|---|
| `Create` (~стр. 217) | `Created` | внутри уже существующей транзакции с advisory-lock |
| `Reschedule` (~стр. 680) | `Rescheduled` | заполняет `Previous*`/`New*`; внутри существующей транзакции |
| `Cancel` (~стр. 755) | `Cancelled` | пишет `CancellationReason`, если он был передан |
| `Complete` (~стр. 633) | `Completed` | транзакции нет и не нужна — один `SaveChangesAsync` атомарен |
| `NoShow` (~стр. 664) | `NoShow` | то же |
| `MarkPaid` (~стр. 649) | `PaymentMarked` | то же |

⚠️ **Важное отличие от того, как сделаны уведомления.** `NotificationScheduler` вызывается в
`try/catch` и его падение **не роняет** операцию — это правильно для уведомления. Для журнала —
**неправильно и запрещено**: `try/catch` вокруг записи события вернул бы ровно то состояние, которое
US-123 запрещает («перенос есть, строки нет»). Исключение при записи события обязано провалить всю
операцию. Это надо написать в коде комментарием, иначе следующий читатель «причешет» по соседнему
образцу.

**Автор события (R7).** Одна модель на всех:

| Кто вызвал | `ActorKind` | `ActorUserId` | `ActorNameSnapshot` | `ActorRoleSnapshot` |
|---|---|---|---|---|
| Клиент про себя (авторизован) | `Client` | id | «Имя Фамилия» | `null` |
| Гость (без аккаунта) | `Guest` | `null` | введённое им имя | `null` |
| Сотрудник компании | `Staff` | id | «Имя Фамилия» | `Master` / `CompanyOwner` |
| Суперадмин | `SuperAdmin` | id | «Имя Фамилия» | `null` |
| Система (в цикле не возникает) | `System` | `null` | `null` | `null` |

Порядок разрешения строгий и его нельзя менять местами: **SuperAdmin → персонал этой компании →
авторизованный клиент → гость**. Иначе суперадмин, случайно состоящий в компании, подпишется мастером.

Снимок имени переживает удаление сотрудника и удаление аккаунта — тот же принцип, что у
`Booking.Price`, `Booking.CommissionPercent` и `BookingService.NameSnapshot` (US-124).

**Чтение.** `GET /api/bookings/{id}/history` — **один** запрос по индексу `(BookingId,
OccurredAtUtc)`, не N+1, ≤50 событий на типичных данных. Списки записей историю **не тянут**.

**«Есть ли история» без загрузки истории.** `BookingDto` получает поле `historyEventCount: int?`,
заполняемое **только** на персональских эндпоинтах (`GET /api/bookings/master`,
`GET /api/bookings/{id}`) **одним группирующим запросом на всю страницу** — буквально тот же приём,
что `ReminderStatusesForAsync` (`BookingsController.cs:~845`), и по той же причине. На клиентских
эндпоинтах (`GET /api/bookings/client`, ответ `POST /api/bookings`) поле **всегда `null`** — не
«скрыто на фронте», а не заполнено сервером (П8, R7).

Так решается требование «блок истории не показывается вовсе»: карточка знает, что показывать
нечего, **до** разворачивания и без запроса истории.

**Права на историю.** Персонал **этой компании** (`CompanyMembership.IsStaffAsync`) или SuperAdmin.
Это шире, чем `CanManageBookingAsync` (назначенный мастер + владелец), и так задумано: US-123 говорит
«персонал компании». Всем остальным — **404**, включая клиента, которому эта запись принадлежит.
Единый 404 вместо пары 403/404 выбран сознательно: иначе код ответа становится оракулом
«существует ли запись с таким id», а этот принцип уже соблюдён в `GetSlots` и ломать его нельзя.

### §106. Фото салона: тот же конвейер, новый профиль, публичный класс (R9)

**Ничего нового в путях загрузки.** Используется `ImageUploadService.ReadAndProcessAsync(file,
[CompanyPhoto, CompanyPhotoThumb])` — ровно та же схема «одна валидация, два профиля из одних
декодированных байт», что у фото заметок. Значит бесплатно и одинаково получаем: лимит 5 МБ, тип по
сигнатуре байт (не по имени и не по `Content-Type`), проверку свободного места, защиту от
«бомбы» декомпрессии и **удаление метаданных, включая геолокацию** (ре-энкод через `ImageProcessor`).

Два новых профиля в `ImageProcessor.cs` рядом с пятью существующими:

```
CompanyPhoto      = new(1600, SquareCrop: false, PngIfSourceWasPngElseJpeg, JpegQuality: 85)
CompanyPhotoThumb = new(480,  SquareCrop: false, AlwaysJpeg,               JpegQuality: 78)
```

Миниатюра нужна не для красоты, а по НФТ: «отдаются миниатюры, а не оригиналы, полноразмерное — по
клику». 480 px хватает и обложке, и плитке галереи на 2× экране.

**Класс хранения — публичный** (П6, R9): `FileStorage.SavePublicAsync(PublicArea.Companies, …)` →
`/uploads/companies/<guid>.<ext>`, раздаётся анонимно тем же `PhysicalFileProvider`. Третьего пути
хранения не заводим. В Production действует существующий fail-fast на пересечение публичного и
приватного корня — он нас автоматически покрывает.

**Права:** только владелец компании (`CompanyMembership.IsOwnerAsync`) и SuperAdmin. Мастер фото
салона не меняет (US-125) — это **уже** отличается от фото заметок, где достаточно персонала.

**Лимит 10 и порядок.** Проверка «уже 10» и перенумерация — внутри транзакции под advisory-lock
`company-photos:{companyId}`, тот же приём, что у квоты фото заметок. 11-я фотография получает **400
с конкретным русским текстом** про лимит, а не общую ошибку.

**Порядок записи и удаления файлов — как везде в проекте:** сначала коммит строки, **потом** удаление
файла с диска (`storage.DeletePublic`). При загрузке наоборот: файл пишется до `SaveChanges`, и если
`SaveChanges` упал — новый файл удаляется, чтобы не осиротел (образец — `UploadLogo`,
`CompaniesController.cs:466-481`).

**Осиротевшие файлы при удалении компании/аккаунта.** Строки уносит каскад от `Company`, **файлы
каскад не уносит**. Фактическое состояние кодовой базы: **жёсткого удаления компании в продукте нет**
(`db.Companies.Remove` не встречается нигде; компании деактивируются `IsActive = false`). Поэтому
единственные реальные точки, где файлы могут осиротеть, — это будущее удаление компании и путь
удаления аккаунта в `ProfileController`. Задача BE-7 обязана: (1) проверить по коду, уносит ли
удаление аккаунта строки `Company`, (2) если да — добавить удаление файлов фото салона рядом с уже
существующим удалением аватара (`ProfileController.cs:894`), (3) если нет — зафиксировать это
комментарием в `CompanyPhoto.cs`, чтобы тот, кто однажды напишет удаление компании, увидел
требование в момент написания, а не через цикл.

**Витрина не расходует квоту и не самоуничтожается (П5).** Запрос `photo-usage` и правило
`ClientNotePhotoRule` работают **только** по `ClientNotePhotos` и новую таблицу не видят. Это надо
не «не сломать», а **проверить тестом** — иначе через два цикла кто-нибудь добавит витрину в сумму
«для полноты картины».

### §107. Правило уничтожения журнала: таблица есть, срок ждёт юриста (Q2)

Ситуация: у всех тринадцати правил цикла 5 есть обоснованный срок, у журнала его нет и не будет до
ответа `legal-counsel`. Это **не блокирует разработку журнала**, но обязано быть видимым.

Решение: правило `Services/Retention/Rules/BookingEventRule.cs` пишется и **регистрируется сразу**,
а срок берётся из нового ключа `Retention:BookingEventDays`, который добавляется в
`appsettings.json` со значением **`0`**, означающим **«срок не задан»**:

- при `0` правило **ничего не удаляет** и пишет в сводку задачи честную строку
  «`booking-event: срок хранения не настроен, правило пропущено`»;
- когда юрист даст число — это правка **одной строки конфигурации**, без миграции, без
  пересборки, без нового кода.

⚠️ **Fail-fast на старте для этого ключа НЕ добавляем.** Два существующих fail-fast'а
(`TemplateHistoryDays ≥ 365`, `ConsentRecordDays ≥ 1095`) охраняют **юридические минимумы**,
которые уже известны. Здесь минимум неизвестен — уронить старт приложения из-за незаполненного
ключа значило бы заблокировать выкат цикла ответом юриста, чего спека прямо не требует
(«блокирует конфигурацию retention, не саму таблицу»). Вместо падения — видимая строка в сводке
ежедневной задачи.

## §108. Блок A на фронте: слияние двух модалок (самая рискованная часть цикла)

Решение заказчика принято и не обсуждается: один компонент на два входа, выбор даты только
помесячным календарём. Архитектору остаётся внутреннее устройство — оно ниже.

### §108.1. Целевая форма

**Выживает `BookingModal.tsx`** (он обслуживает публичный экран, у него капча, согласия, календарь и
предоплата), **удаляется `ManualBookingModal.tsx`**. Плоский список «сегодня + 14 дней» исчезает из
продукта вместе с ним — это часть работы, а не «потом» (R4).

Пропсы объединённого компонента:

```
company?: Company      // задан — публичная карточка / виджет; не задан — сотрудник выбирает компанию
service?: Service      // задан — клиент пришёл с карточки услуги; не задан — выбор услуг внутри
allowMultipleServices?: boolean = true   // false только для /embed (§43.3 цикла 6 — не менять)
onClose: () => void
```

Три входа:

| Вход | Пропсы | Режим |
|---|---|---|
| `CompanyPage.tsx:250` | `company`, `service` | определяется сервером |
| `EmbedPage.tsx:125` | `company`, `service`, `allowMultipleServices={false}` | определяется сервером |
| «Мои записи → Записать клиента» | ничего | определяется сервером |

Вход «Записать клиента» **сохраняется** — убирается не он, а второй экран за ним.

### §108.2. Как включается режим персонала — и почему не флагом из пропсов

**Правило: `staffMode` приходит из ответа `GET /api/bookings/availability` (§103.3) и больше ниоткуда.**

Никакого пропса `isStaff`, никакого вывода из роли в `authStore`, никакой догадки по «состою ли я в
компании». Если сервер сказал `staffMode: false` — интерфейс ведёт себя ровно как сегодняшний
`BookingModal`, чем бы ни было открыто окно и что бы ни лежало в сторе.

Единственное, что фронт решает сам **до** первого ответа сервера, — показывать ли шаг «выбор
компании» (для него нужен список `companiesApi.getMemberOf()`, а это тоже серверная, проверенная
информация о членстве, а не догадка). Шаг выбора компании показывается, когда `company` не задан.

Следствие: элементы управления персонала (тумблер «показать остальные часы», нажимаемые дни с
подписью «выходной», выбор скрытого мастера) рисуются **только** при `staffMode === true`.

### §108.3. Шаги объединённого компонента

```
company?  →  services  →  master?  →  date  →  slot  →  info  →  done
```

- **company** — только когда `company` не передан. Автовыбор при единственной компании (сохраняем
  поведение `ManualBookingModal`).
- **services** — мультивыбор 1..5. Когда `service` передан, он предвыбран и неудаляем (поведение
  сегодняшнего `BookingModal`); когда не передан — выбор с нуля (поведение `ManualBookingModal`).
  При `allowMultipleServices === false` шаг пропускается целиком.
- **master** — пропускается при ровно одном подходящем мастере (US-64, сохраняем). При
  `staffMode` запрашивается с `includeHidden=true`, и скрытые помечаются подписью «не виден
  клиентам» (§103.5).
- **date** — **только `BookingCalendar`**. Никакого плоского списка ни в каком режиме.
- **slot** — сетка времени; тумблер `extendedHours` и поясняющая строка «мастер в это время не
  работает» — только при `staffMode`.
- **info** — поля контакта. Разветвление ниже.
- **done**.

Поля шага `info` по режимам (это место, где чаще всего теряют способности при слиянии):

| Режим | Поля | Капча | «Записываю другого человека» | Правовая сноска |
|---|---|---|---|---|
| Гость (не авторизован, не персонал) | имя*, телефон*, email | да, если включена | да | да |
| Клиент (авторизован, не персонал) | нет | нет | да | да |
| Персонал (`staffMode`) | имя клиента*, телефон*, email | нет | **нет** | нет |

У персонала чекбокса «записываю другого человека» нет намеренно: `GuardianConfirmation` по решению
цикла 5 относится только к самозаписи клиента/гостя/виджета и **не применяется к ручной записи
персоналом**. Отправлять его с персональского пути нельзя.

### §108.5. `BookingCalendar`: что меняется

Новые пропсы: `manual?: boolean` (просить режим персонала) и колбэк/поле для проброса `staffMode`
наружу (модалка должна знать режим на шаге `slot`).

Правила отрисовки дня:

| Условие | Нажимаем? | Подпись |
|---|---|---|
| прошедший день / прошедшее время сегодня | нет | — |
| `staffMode === false`, `status === 'DayOff'` | **нет** (как сегодня) | «выходной» |
| `staffMode === false`, `status === 'FullyBooked'` | нет | «Занято» (`DAY_FULL_LABEL`) |
| `staffMode === true`, `scheduleState === 'DayOff'` | **да** | «выходной» |
| `staffMode === true`, `scheduleState === 'NoSchedule'` | **да** | «нет графика» |
| `staffMode === true`, `status === 'FullyBooked'` | нет | «Занято» |
| `status === 'Available'` | да | — |
| вне горизонта (только не-персонал) | нет | — |

**Доступность (НФТ, отдельное требование).** Подпись обязана быть в **доступном имени кнопки**, а не
только в визуальном тексте: `aria-label="12 марта, выходной"`. Сегодня `aria-label` уже собирается
из даты и `label` — механизм сохраняем и распространяем на новые подписи. Без этого «выходной, но
нажимаемо» превращается в ловушку для незрячего сотрудника.

Визуальное отличие сохраняется: нажимаемый день-выходной остаётся приглушённым, но получает рамку и
курсор кликабельного — статус остаётся информацией, а не запретом.

Стрелка «вперёд» гасится по `horizonLastDate` **только** при `staffMode === false`; при
`staffMode === true` — по `STAFF_MAX_MONTHS_AHEAD = 12`.

### §108.6. ⚠️ Цена этого рефакторинга — прямо и без смягчений

- **Переписывается код, которым пользуются все анонимные посетители каталога и все встроенные
  виджеты.** Ошибка видна не десяти сотрудникам, а всем. Регрессия здесь дороже самой фичи (R4).
- **Удаляется файл целиком** (`ManualBookingModal.tsx`) вместе с его тестами; тесты не удаляются, а
  **переносятся** на объединённый компонент — иначе вместе с экраном исчезнет и проверка его
  способностей.
- **Три точки открытия** правятся одновременно; частичная миграция запрещена — два разных экрана
  записи после цикла в продукте остаться не должны (US-120).
- **Чем можно сломать работающее:** потерять капчу у гостя (открывает спам-запись), потерять
  правовую сноску (правовой регресс цикла 5), потерять инвалидацию `['master-bookings']`
  («записал, а в списке нет»), потерять `allowMultipleServices={false}` у виджета (виджет и сайт
  разошлись осознанно, C2 — слияние не должно их сводить).
- **Чем страхуемся:** §108.4 поштучно + матрица тестов не-персонала (§113, QA-1) + `staffMode` как
  единственный источник режима (§108.2).

## §112. Что делается параллельно, а что строго последовательно

**Параллельно с первого дня** (и это главная причина, по которой контракт написан до кода):

```
BE-1 ─┐                       ┌─ FE-1 → FE-2 ─┐
BE-2 ─┤                       │               ├─ FE-3 → FE-4 → FE-5
BE-3 ─┼─ независимы друг от   │               ├─ FE-6
BE-7 ─┘  друга и от фронта    └───────────────┼─ FE-7
                                              └─ FE-8
```

- **Весь бэкенд и весь фронтенд идут параллельно.** Точка синхронизации одна —
  `contracts/cycle10/openapi.yaml`. Фронт разрабатывает против мока (`prism mock`), не дожидаясь
  ни одного эндпоинта.
- **BE-1, BE-2, BE-3, BE-7 параллельны между собой** — разные файлы, разные таблицы, общих правок
  нет. Их можно раздать хоть четверым.
- **FE-2, FE-6, FE-7, FE-8 параллельны между собой** — разные компоненты.

**Строго последовательно** (и не пытаться «сэкономить»):

- `BE-3 → BE-4 → BE-5`: нельзя писать события, пока нет писателя, и писателя — пока нет таблицы.
- `BE-7 → BE-8 → BE-9`: то же для фото.
- `FE-3 → FE-4 → FE-5`: удалять `ManualBookingModal` можно **только** после того, как объединённый
  компонент умеет всё из §108.4. Удалить раньше — гарантированно потерять способность.
- `FE-2` желательно **до** `FE-3`: календарь — единственный путь выбора даты, и модалка строится
  вокруг него.

**Два общих файла — риск конфликта, развести по времени:**

- `BookingsController.cs` правят BE-1, BE-5, BE-6 → делать в таком порядке одному человеку, либо
  мержить BE-1 первым.
- `CompaniesController.cs` правят BE-2 и BE-9 → BE-2 первым (он маленький).

**Порядок вливания в ветку цикла:** BE-1 → (BE-2, BE-3, BE-7) → остальное. BE-1 первым потому, что
от `staffMode` зависит вся фронтовая логика режима, и чем раньше он окажется в ветке, тем раньше
фронт слезет с мока.

## §113. Как проверяется, что мы ничего не сломали

### §113.1. Матрица не-персонала — обязательная, поштучная (QA-1, R1, R4)

Три вида не-персонала × четыре проверки. Ни одну клетку не пропускать.

| Проверка \ Кто | Анонимный гость | Авторизованный клиент | Сотрудник **чужой** компании |
|---|---|---|---|
| `availability` с `manual=true&extendedHours=true` → `staffMode: false` | ✔ | ✔ | ✔ |
| `scheduleState` во всех днях `null` | ✔ | ✔ | ✔ |
| День без расписания приходит `DayOff` и в интерфейсе не нажимается | ✔ | ✔ | ✔ |
| Горизонт записи применяется (400 за `horizonLastDate`) | ✔ | ✔ | ✔ |
| `slots` с `extendedHours=true` не расширяет выдачу | ✔ | ✔ | ✔ |
| Капча и правовые согласия гостя на месте | ✔ | — | — |

Дополнительно: `GET /api/bookings/{id}/history` клиенту **своей собственной** записи → **404**.

### §113.2. Права на ручную запись (П2, QA-3)

Закрепить тестами текущее поведение, ничего не сужая: мастер записывает **себе**, мастер записывает
**другому мастеру своей компании**, владелец записывает **любому**; сотрудник компании A на мастера
компании B → отказ.

### §113.3. Автосверка контракта (QA-2)

Машиночитаемая схема существует ровно для того, чтобы это не проверялось глазами и не подтверждалось
«на словах в отчётах»:

```bash
# форма реализации против контракта
schemathesis run contracts/cycle10/openapi.yaml --base-url http://localhost:5000 --checks all

# типы фронта против контракта: перегенерировать и убедиться, что diff пуст
cd frontend && npm run types:api:cycle10 && git diff --exit-code src/types/api-cycle10.generated.ts
```

Вторая команда — дешёвая защита от R10: если бэкенд поменял форму, а контракт нет (или наоборот),
diff перестанет быть пустым.

### §113.4. Юнит-тесты (чистые классы, без БД и HTTP)

`BookingEventTexts` (все шесть событий × пять видов автора), `CompanyPhotoOrdering` (перестановка,
компактизация после удаления, отказ на неполную перестановку). Это продолжение линии циклов 4–6.

## §114. Безопасность и права — сводка решений

| Вопрос | Решение |
|---|---|
| Авторизация | Ничего нового. JWT Bearer + Identity как есть. Новых схем, новых claim'ов, новых гейтов нет |
| Режим персонала | Только серверная проверка `CompanyMembership.IsStaffAsync`; `manual`/`extendedHours` из запроса — **просьба**, а не разрешение. Ответ честно сообщает результат полем `staffMode` |
| Утечка расписания | `scheduleState` отдаётся только при `staffMode: true` (§103.2) |
| Чтение истории | Персонал компании + SuperAdmin. Всем остальным **404**, включая владельца записи-клиента. Код ответа не работает оракулом существования |
| Автор в клиентских ответах | Не «спрятан на фронте», а **не заполняется сервером**: `historyEventCount` = `null`, эндпоинт истории недоступен (П8) |
| Загрузка фото салона | Только владелец компании и SuperAdmin; политика лимита `uploads`; тип по сигнатуре; ≤5 МБ; проверка свободного места; метаданные (включая геолокацию) срезаются ре-энкодом |
| Публичность фото | Осознанная: витрина, публичный класс хранения, отдаётся анонимно (П6). Приватный класс **не задействован** |
| Хранение секретов | Новых секретов цикл не вводит. `.env`, мастер-ключ, отпечаток ключа — не трогаем |
| Журнал | Только на добавление. Ни одного маршрута на правку/удаление события. Телефонов и почты в нём нет |
| Масштабирование | Журнал — append-only с одним рабочим индексом; удаление по сроку — существующей ежедневной задачей. Фото — ≤10 файлов на салон; точка миграции в объектное хранилище изолирована в `FileStorage` и в этом цикле не трогается |

## §115. Совместимость: что обязано остаться прежним

- Форма ответов всех существующих эндпоинтов **не ломается**. Все новые поля **добавочные**:
  `staffMode`, `scheduleState`, `historyEventCount`, `photos`, `coverPhotoUrl`,
  `coverThumbnailUrl`, `providesServices`. Старый потребитель, не знающий о них, продолжает работать.
- `BookingDto` — новое поле добавляется **в конец** записи со значением по умолчанию, чтобы
  существующие позиционные вызовы конструктора (их много, в том числе в тестах) продолжили
  компилироваться. Тот же приём, что у `BookedForOther`/`GuardianConfirmation` в цикле 5.
- Клиентский и гостевой сценарий записи, виджет `/embed` для посетителя, публичная выдача слотов —
  **не меняются по поведению**, хотя код под ними теперь общий. Свобода расписания остаётся
  свойством пути персонала (решение Q7 цикла 6 в силе).
- Состав карточки записи клиента в `/my-visits` не меняется ни на одно поле (П8).
- `GET /api/bookings/slots` не меняет форму ответа.
- Единственное **удаление** во всём цикле — компонент `ManualBookingModal.tsx` и строка
  «Фото: компания». Ни одного удалённого эндпоинта, ни одной удалённой колонки.

## §116. Риски и что с ними делаем

| **R3** | Горизонт и диапазон запроса календаря | Сервер не меняем: диапазон ≤31 дня и клэмп `from` уже совместимы с помесячным листанием. Ограничение «365+ дней для персонала» — константа на фронте. Хаков ради обхода серверных проверок быть не должно |
| **R4** | Слияние модалок — исполнительский риск высокой цены | Инвентаризация §108.4 **до** рефакторинга; `ManualBookingModal` удаляется последним (FE-5), после того как объединённый компонент умеет всё; тесты переносятся, а не удаляются |
| **R5** | Миграции | Две раздельные, только добавляющие, честный `Down`, backfill'а нет |
| **R6** | Миграции поедут поверх 11 невыкаченных миграций цикла 7 | Ни одна миграция цикла 10 не зависит от колонок цикла 7 — проверено по составу полей. Порядок выката — вопрос к devops **до мержа**. Архитектурно мы этот риск не снимаем, только не усугубляем |
| **R7** | Кто автор для клиентских событий | Единая модель автора (§105): пять `ActorKind`, `ActorUserId` опционален, снимок имени обязателен. Разделение «персонал / клиент» заложено в DTO, а не в фильтр на фронте |
| **R8** | Журнал не должен порождать уведомлений | Ни одного вызова `NotificationScheduler` из `BookingEventLog`. `NotificationType.StaffBookingCreated` остаётся мёртвым — US-34 не в этом цикле. Проверить на ревью |
| **R9** | Два класса хранения, fail-fast на пересечение | Фото салона — публичный класс, существующий `ImageUploadService`/`ImageProcessor` + новый профиль. Третьего пути загрузки не появляется |
| **R10** | Ручное копирование типов на фронт | Новые типы — из генерации (§101.3), сверка diff'ом в QA-2 |
| **Q2** | Срок хранения журнала (юрист) | Правило пишется и регистрируется; ключ `Retention:BookingEventDays: 0` = «не задан», правило ничего не удаляет и говорит об этом в сводке. Ответ юриста → правка одной строки конфига (§107). Разработку не блокирует |
| **Q3** | Виден ли скрытый мастер персоналу | Решено «виден» (§103.5). Обратимо одним флагом |
| — | ⚠️ Нагрузка на `availability` выросла в значимости | После слияния этот эндпоинт — единственный путь выбора даты **и** он открывается с публичной страницы. Его время ответа теперь влияет на всех посетителей. Существующий лимит `availability` (60/мин на IP) и «один запрос на месяц» сохраняются; превращать его в запрос на день **запрещено** |
