# Деплой ServiceBooking на VPS (reg.ru), домен ezbook.ru

Схема: Postgres + ASP.NET API в Docker (только на 127.0.0.1:5000, наружу не торчат),
фронтенд собирается статикой и отдаётся хостовым nginx, nginx же терминирует HTTPS
(Let's Encrypt) и проксирует `/api` и `/uploads` на контейнер API.

Все команды ниже выполняются по SSH на самом VPS, если не указано иное.

---

## 0.0. Модель веток

Что откуда и куда едет. Ветками распоряжается devops-роль, остальные работают внутри уже
подготовленной ветки и сами их не создают и не мёрджат.

| Ветка | Что это | Как туда попадает код |
|---|---|---|
| `master` | прод | только мердж из `release-candidate`, с тегом версии |
| `release-candidate` | предрелизная стадия | мердж `develop`, когда решено резать релиз — после одного цикла или пачки |
| `develop` | интеграционный ствол | только завершённые циклы, прошедшие ревью и приёмку QA; можно continuous-деплоить в dev/staging |
| `cycle/<slug>` | один цикл (задача, гипотеза) | ответвляется от актуального `develop` |

Порядок на релизе: `develop` → `release-candidate` → регрессия QA на самой `release-candidate`
(на стыке нескольких циклов всплывает то, чего не было у каждого по отдельности) → закрытие
CHANGELOG и публикация пользовательских гайдов → мердж в `master`, тег, деплой в прод.

**Текущее состояние.** `develop` содержит циклы A, B и C. `master` стоит на `263c661` и намеренно
не двигался: релиза не было — на VPS ничего не выкатывалось, GlitchTip не поднимался, CSP на
скачивании выгрузки живьём не проверялся (см. §9 CURRENT_STATE.md, блок P0). Пока это не сделано,
двигать `master` значило бы пометить как прод то, что ни разу не запускалось.
`release-candidate` ещё не заводилась — она создаётся в момент решения о релизе.
Ветка `sanitation-cycle` — это цикл C до перехода на новую схему именования; оставлена как есть,
новые циклы именуются `cycle/<slug>`. Ветки `feature/*` — остатки июльской работы, полностью
влиты в `master`, сохранены намеренно.

CI собирает `master`, `release-candidate`, `develop` и всё, что по маске `cycle/**`.

## 0. Перед началом

- В DNS домена `ezbook.ru` (в панели reg.ru → раздел "Домены" → управление DNS) должны
  стоять A-записи `ezbook.ru` и `www.ezbook.ru`, указывающие на IP вашего VPS.
  Проверить с любого компьютера:

  ```bash
  dig +short ezbook.ru
  dig +short www.ezbook.ru
  ```

  Оба должны вернуть IP сервера. Если ещё не настроено — до этого TLS-сертификат не выдастся.

- Узнайте IP и способ входа по SSH (обычно `ssh root@ВАШ_IP`, реже отдельный пользователь —
  reg.ru присылает это на почту при заказе VPS).

## 1. Первичная настройка сервера

Сервер на **AlmaLinux 8** — пакеты через `dnf`, файрвол через `firewalld`,
SELinux по умолчанию в режиме `enforcing` (это не мешает, но нужно явно
разрешить nginx проксировать запросы на backend — см. ниже).

```bash
ssh root@ВАШ_IP

dnf update -y

# Docker (официальный репозиторий для RHEL-семейства — подходит и для AlmaLinux)
dnf install -y dnf-plugins-core
dnf config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
dnf install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
systemctl enable --now docker

# nginx
dnf install -y nginx
systemctl enable --now nginx

# certbot (из EPEL)
dnf install -y epel-release
dnf install -y certbot python3-certbot-nginx

# прочее
dnf install -y git nano

# Firewall — открываем только SSH, HTTP, HTTPS
systemctl enable --now firewalld
firewall-cmd --permanent --add-service=ssh
firewall-cmd --permanent --add-service=http
firewall-cmd --permanent --add-service=https
firewall-cmd --reload

# SELinux: разрешить nginx проксировать запросы на localhost:5000 (backend в Docker)
setsebool -P httpd_can_network_connect 1
```

Проверка: `docker --version`, `nginx -v` — обе команды должны отработать без ошибок.
`getenforce` должен вывести `Enforcing` — это нормально, всё уже разрешено выше.

## 2.1. Правовые документы (файлы вне git)

С цикла C (US-36) `docker-compose.prod.yml` монтирует `./legal` (каталог рядом с `docker-compose.prod.yml`
на хосте) поверх черновика, запечённого в образ. При первом деплое создайте его из черновика в репозитории:

```bash
mkdir -p /opt/ezbook/app/legal
cp /opt/ezbook/app/ServiceBooking.API/App_Data/legal/*.* /opt/ezbook/app/legal/
```

Замена текста после юридической вычитки (US-36 п. 5) — **это эксплуатационная операция, не релиз**:

```bash
scp privacy.html root@ВАШ_IP:/opt/ezbook/app/legal/privacy.html
# отредактируйте /opt/ezbook/app/legal/legal.json на сервере: новая version (без "-draft", если это
# финальный текст), effectiveFrom, isDraft:false, changeKind: "Material" или "Editorial"
```

Пересборка и рестарт контейнера **не требуются** — провайдер сам перечитывает `legal.json` в течение
`Legal:ReloadSeconds` (30 c по умолчанию). `changeKind: "Material"` разлогинивает всех, кто ещё не принял
новую редакцию (451 на защищённых вызовах, ARCHITECTURE.md §6.3); `"Editorial"` — нет.

## 3. Секреты (.env)

```bash
cp .env.production.example .env
nano .env
```

Заполните:
- `POSTGRES_PASSWORD` — сгенерируйте: `openssl rand -base64 24`
- `JWT_KEY` — сгенерируйте: `openssl rand -base64 48` (**обязательно**: минимум 32 символа и не равно
  плейсхолдеру из `appsettings.json` — иначе контейнер откажется стартовать, см. ниже)
- `SUPERADMIN_PHONE` — ваш номер в формате `+7XXXXXXXXXX`, станет суперадмином при первом запуске
- `SUPERADMIN_PASSWORD` — пароль для аккаунта суперадмина (**обязательно**: не равно плейсхолдеру
  `Admin12345` — иначе контейнер откажется стартовать)
- `SMARTCAPTCHA_SECRET_KEY` / `SMARTCAPTCHA_SITE_KEY` — из кабинета Yandex Cloud SmartCaptcha
- `FORWARDEDHEADERS__TRUSTEDNETWORKS__0` — подсеть docker-моста этого стека (по умолчанию
  `172.16.0.0/12`, см. §9.1 `ARCHITECTURE.md`); rate limiting считает реальный IP клиента только через
  доверенную сеть. **Обязательно**: пустое значение — контейнер откажется стартовать.
- `SENTRY_DSN` — из GlitchTip (см. раздел «Трекер ошибок и алерты» ниже). Необязательно: пустое —
  приложение работает без трекера.
- `GIT_SHA` — заполняется автоматически `deploy/deploy-remote.sh`, руками не трогайте.

Сохраните (Ctrl+O, Enter, Ctrl+X в nano). Файл `.env` не попадёт в git — он в `.gitignore`.

**Перед запуском проверьте подстановку переменных** (не поднимает контейнеры, только печатает
итоговый конфиг):

```bash
docker compose -f docker-compose.prod.yml --env-file .env config
```

Убедитесь, что `Jwt__Key`/`SuperAdmin__Password` в выводе — реальные значения, а не пустые строки.
С этого цикла API **фейлится при старте** (fail-fast, не поднимается вовсе), если `Jwt:Key` или
`SuperAdmin:Password` отсутствуют либо остались плейсхолдером — так безопаснее, чем боевой контейнер,
который тихо стартовал бы со значением `Admin12345`/недлинным ключом из `appsettings.json`.

## 4. Backend + Postgres в Docker

```bash
cd /opt/ezbook/app
docker compose -f docker-compose.prod.yml --env-file .env up -d --build
```

Проверка, что всё поднялось:

```bash
docker compose -f docker-compose.prod.yml ps
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5000/api/companies   # ожидаем 200
```

Swagger в Production **не поднимается вовсе** (доступен только при локальной разработке,
`ASPNETCORE_ENVIRONMENT=Development`) — `curl .../swagger/index.html` теперь корректно вернёт `404`,
это не признак проблемы.

Если `curl` не вернул 200 — посмотрите логи и пришлите мне вывод:

```bash
docker compose -f docker-compose.prod.yml logs api --tail=100
```

### Два класса хранения файлов

С этого цикла у API два независимых docker volume под загруженные изображения:

| Volume | Что лежит | Как раздаётся |
|---|---|---|
| `api_uploads` | логотипы компаний, аватары, картинки услуг (публичные) | напрямую через `/uploads/...`, `nginx`/`UseStaticFiles` |
| `api_private_uploads` | фото к заметкам о клиентах (персональные данные) | только через `GET /api/client-notes/photos/{id}`, с проверкой прав |

Бэкапьте **оба**, но с разным приоритетом: `api_uploads` можно потерять и пережить (просто временно
пропадут картинки), `api_private_uploads` — персональные данные клиентов салонов, требует того же
уровня защиты бэкапа, что и сама база Postgres.

```bash
# Быстрый бэкап обоих volume разом (пример; адаптируйте под вашу схему бэкапов)
docker run --rm -v ezbook_api_uploads:/from -v ezbook_api_private_uploads:/from-private \
  -v /opt/ezbook/backups:/to alpine \
  tar czf /to/uploads-$(date +%F).tar.gz -C / from from-private
```

Приватный каталог задаётся переменной `Storage__PrivateRoot` (уже прописана в
`docker-compose.prod.yml`, менять не нужно) — если она случайно окажется внутри `wwwroot`, API
откажется стартовать (fail-fast), а не тихо начнёт раздавать чужие фото публично.

## 5. Сборка фронтенда

**С цикла C (T-D3, US-44) фронтенд больше не собирается на самом боевом сервере** — сборку делает CI
на каждый push (`.github/workflows/ci.yml`, джоб `frontend`, шаг `Upload frontend dist`), и именно этот
артефакт уезжает на VPS. Причина — боевой сервер не должен тратить CPU/память на `npm run build` и не
должен зависеть от того, что на нём стоит подходящая версия Node.

Раскладка на диске — релизы плюс симлинк, который переключается атомарно (ARCHITECTURE.md §12.3):

```
/var/www/ezbook/
├── releases/
│   ├── 20260915T101500Z/     ← распакованный dist конкретного релиза
│   └── 20260914T190000Z/     ← хранятся 3 последних, старые чистит deploy-remote.sh сам
└── current -> releases/20260915T101500Z    ← симлинк, nginx `root` указывает СЮДА (см. §6)
```

**Первичная настройка (один раз):** создайте каталог и, если он ещё пуст, начальный релиз вручную —
дальше `deploy/deploy.sh` (см. §9) делает это сам при каждом деплое:

```bash
mkdir -p /var/www/ezbook/releases
```

Первый деплой после первичной настройки сервера делается той же командой `./deploy/deploy.sh` с вашей
машины (§9) — она скачивает готовый `dist` из CI и раскладывает его сама; ключ капчи
(`VITE_SMARTCAPTCHA_SITEKEY`, это публичный site-key, не секретный) должен быть задан один раз как
**переменная репозитория в CI** (GitHub → Settings → Secrets and variables → Actions → **Variables** →
`VITE_SMARTCAPTCHA_SITEKEY`), а не на сервере — Vite подставляет его во время `npm run build`, который
теперь и происходит в CI (`.github/workflows/ci.yml`, джоб `frontend`).

Проверка после первого деплоя: `ls -la /var/www/ezbook/current/index.html` — файл должен существовать
через симлинк.

## 6. nginx + HTTPS

На AlmaLinux (в отличие от Ubuntu) конфиги сайтов кладутся прямо в `/etc/nginx/conf.d/` —
папка уже подключена через `include` в `/etc/nginx/nginx.conf`, отдельно её включать не нужно.

```bash
cp /opt/ezbook/app/deploy/nginx/ezbook.conf /etc/nginx/conf.d/ezbook.conf

nginx -t        # проверка синтаксиса — должно быть "syntax is ok" / "test is successful"
systemctl reload nginx

# Выпуск и установка сертификата (certbot сам допишет server-блок на 443 и настроит редирект с 80)
certbot --nginx -d ezbook.ru -d www.ezbook.ru
```

### Security-заголовки (US-47)

`deploy/nginx/ezbook.conf` ставит:

| Заголовок | Значение | Зачем |
|---|---|---|
| `Strict-Transport-Security` | `max-age=15552000` (180 дней, **без `preload`** на первом шаге) | браузер запоминает HTTPS-only на этот сайт |
| `X-Content-Type-Options` | `nosniff` | браузер не переопределяет тип контента сам |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | не течёт полный URL в заголовке Referer на чужие домены |
| `Content-Security-Policy` | см. файл конфига | ограничивает источники скриптов/стилей/картинок |

Эти три — HSTS, `nosniff`, `Referrer-Policy` — стоят на **всём** сайте, включая `/embed/*`: они не
про фрейминг, виджет от них не ломается.

**CSP обязательно включает `img-src ... blob:`** — приватные фото к заметкам о клиентах (цикл B)
грузятся на фронте как `blob:` через `useAuthedImage` (заголовок `Authorization` браузер не приложит к
обычному `<img src>`, только эти два способа — blob или proxy — вообще работают). Без `blob:` в CSP
эти фото просто не отобразятся, при этом никакой ошибки в консоли, кроме глухого CSP-варнинга, не будет
— если меняете CSP, **проверьте живую карточку клиента с фото** до выкладки, а не только форму записи.

`style-src 'self' 'unsafe-inline'` — Tailwind в JSX даёт инлайновые стили; убрать `unsafe-inline» —
отдельная работа (nonce/hash на каждый стиль), не в этом цикле.

**CSP обязательно включает `style-src ... https://fonts.googleapis.com` и `font-src 'self'
https://fonts.gstatic.com`** — `frontend/index.html` грузит шрифты Newsreader/Inter с Google Fonts
(таблица стилей с `fonts.googleapis.com`, сами файлы `.woff2` — с `fonts.gstatic.com`). Без этих двух
источников браузер отказывается загружать таблицу стилей (`default-src 'self'` откатом блокирует и её,
и шрифты), приложение тихо остаётся на системном шрифте, а в консоли — пачка `Refused to load the
stylesheet`. Проверено живьём (прод-сборка фронта за локальным nginx с этим CSP, headless-браузер):
без этих директив — CSP-ошибка и `Refused to load`; с ними — стили и `.woff2` грузятся 200 OK, ошибок
нет.

**Yandex SmartCaptcha не требует в CSP ничего, кроме `smartcaptcha.yandexcloud.net`** — проверено
живьём рендером реального виджета: `mc.yandex.ru` (Метрика) и `yastatic.net` (шрифты/скрипты), которые
виджет действительно подгружает, запрашиваются ИЗНУТРИ его собственного iframe
(`checkbox.*.html` на `smartcaptcha.yandexcloud.net`, уже разрешённого через `frame-src`) под CSP-
политикой самого Яндекса, а не как запросы верхнего документа — так что добавлять их в `script-src`/
`connect-src` этого сайта не нужно. Если Яндекс когда-нибудь изменит виджет так, что он начнёт делать
top-level запросы на новый хост напрямую (а не из iframe), это всплывёт как `Refused to connect`/
`Refused to load` в консоли при следующей живой проверке — тогда и добавлять.

**Против встраивания в чужой iframe** — отдельная пара заголовков, `X-Frame-Options: DENY` +
`Content-Security-Policy: frame-ancestors 'none'`, стоит только в `location /` — кроме одного маршрута,
`/embed/*` (виджет записи, US-03), для которого встраивание — единственный смысл существования
страницы, и эти два заголовка туда намеренно не добавляются. Если добавляете новый `location` в
конфиг — не забудьте, что он унаследует поведение того блока, в который попадёт (`/embed/` без
ограничения, `/` — с ним).

**Проверка после выкладки (обязательна, US-47):**

```bash
curl -I https://ezbook.ru/                | grep -Ei 'strict-transport|x-content-type|referrer-policy|content-security|x-frame'
curl -I https://ezbook.ru/embed/anything  | grep -Ei 'x-frame|frame-ancestors'   # должно быть ПУСТО
```

И вручную, глазами, в браузере **до** выкладки на прод: форма записи с капчей открывается и
отправляется (риск R6 — CSP может тихо заблокировать SmartCaptcha), карточка клиента с загруженным
фото открывает миниатюру и полноразмер (риск CSP + `blob:`).

Certbot спросит email (для уведомлений об истечении сертификата) и согласие с условиями —
ответьте на вопросы в терминале. Автопродление сертификата на AlmaLinux настраивается
отдельно (пакет certbot из EPEL не ставит systemd-таймер сам) — добавьте его вручную:

```bash
echo "0 3 * * * root certbot renew --quiet --deploy-hook 'systemctl reload nginx'" \
  > /etc/cron.d/certbot-renew
```

Проверить, что обновление сработает, можно командой `certbot renew --dry-run`.

## 7. Проверка

Откройте `https://ezbook.ru` в браузере — должна открыться главная страница.
Зарегистрируйте тестовый аккаунт, проверьте вход под номером из `SUPERADMIN_PHONE` —
у него должна появиться ссылка «Админ» в шапке.

**Правовые документы — осознанное решение, не сюрприз.** Проверьте, какая редакция сейчас опубликована:

```bash
cat /opt/ezbook/app/legal/legal.json | grep -E 'version|isDraft'
```

Если `isDraft: true` (версия вида `2026-09-08-draft`) — это ЗАВОДСКОЕ состояние репозитория и
**разрешено запускаться в Production с ним** (решение заказчика, fail-fast на черновик намеренно не
добавлен). Каждый регистрирующийся пользователь получит запись согласия именно с этой версией — просто
проверьте, что вы делаете это осознанно, а не потому что забыли про §2.1. Если правовая вычитка уже
прошла — обновите текст и `legal.json` по инструкции в §2.1 ДО первых регистраций, иначе более ранние
пользователи будут числиться согласившимися с черновиком, а не с финальным текстом.

## 8. Обновление после будущих изменений в коде (деплой с проверкой и откатом, T-D3/US-44)

**С цикла C деплой запускается только с локальной машины** (`deploy/deploy.sh`, §9) — оно и скачивает
готовый фронтенд из CI, и запускает `deploy-remote.sh` на сервере. Голый `git pull && deploy-remote.sh`
на сервере больше не самодостаточен: `deploy-remote.sh` теперь требует аргументом номер релиза,
каталог которого должен уже существовать под `/var/www/ezbook/releases/` — это `deploy.sh` готовит
заранее, скачивая `dist` из артефакта CI.

Что делает прогон (`deploy/deploy-remote.sh <release-timestamp>`):

1. Тегирует текущий образ API `servicebooking-api:previous` и запоминает текущий релиз-симлинк
   в `/var/www/ezbook/.previous` — это и есть всё, что нужно для отката.
2. Атомарно переключает `/var/www/ezbook/current` на новый релиз (`ln -sfn ... && mv -Tf ...` —
   `rename(2)`, промежуточного «наполовину новый сайт» состояния не бывает), `nginx -t && reload`.
3. `docker compose up -d --build` — пересобирает и перезапускает контейнер API.
4. **Ждёт `/api/health/ready`** (таймаут 120 с) — не просто «контейнер запустился», а именно готовность
   (БД доступна и миграции применены). Если не дождался — печатает **`ДЕПЛОЙ НЕУСПЕШЕН.`** и
   **следующей строкой** готовую команду отката, чтобы можно было её скопировать не думая.
5. Подчищает старые релизы (оставляет 3 последних).

Проверить вручную (без нового деплоя, если что-то показалось не так):

```bash
curl -s https://ezbook.ru/api/health/ready
```

### Откат — одна команда, без аргументов

```bash
cd /opt/ezbook/app
bash deploy/rollback.sh
```

Откатывает и фронтенд (симлинк `current` → предыдущий релиз), и backend (образ `:previous` →
`:latest`, **без пересборки** — именно поэтому откат быстрый) одной командой, ждёт `readiness`,
печатает статус контейнеров. Необязательный один аргумент — метка более старого релиза
(`bash deploy/rollback.sh 20260913T120000Z`) для отката на две и более версии назад по фронтенду;
backend-образ при этом всё равно откатывается на единственный сохранённый `:previous` (истории
образов глубже одного шага скрипт не хранит).

**Прогон «выкатили → проверили → откатили → проверили» выполнен на локальном стенде 2026-09-09**
(два последовательных релиза с разным содержимым `index.html` и разным образом API; `rollback.sh` без
аргументов вернул систему к первому релизу за секунды, без пересборки образа, `readiness` подтверждён
после отката). На боевом VPS с реальным nginx/systemd этот же прогон нужно повторить один раз перед
тем, как полагаться на процедуру в первый раз в бою, и дописать дату сюда.

### Откат кода после применённой миграции — что делать

Миграции применяются автоматически при старте API (`Program.cs → MigrateAsync()`) и **`rollback.sh` их
не откатывает** — это не входит в его задачу, а «откатить миграцию» в общем случае не всегда вообще
возможно без потери данных (например, `NormalizePhoneNumbers` цикла B необратима).

Если после деплоя выяснилось, что новый **код** сломан, но миграция из этого же релиза уже накатилась:

1. Сначала спросите: старый код вообще совместим со **схемой после миграции**? Если миграция чисто
   аддитивна (новая колонка/таблица, старый код её просто не знает) — да, `rollback.sh` полностью
   безопасен, накатывать ничего обратно не нужно.
2. Если миграция удалила колонку/таблицу, которую старый код читает — `rollback.sh` вернёт код,
   который тут же упадёт на первом же обращении к отсутствующему полю. В этом случае откат кода
   **без плана по данным делать нельзя** — сначала пишется и применяется вручную обратная миграция
   (`dotnet ef migrations add`, `Down()` — ARCHITECTURE.md §16.2 требует писать `Down` для всех
   несокрушительных миграций цикла C именно ради этого случая), и только потом `rollback.sh`.
3. Если обратной миграции нет и данные уже частично в новой форме — это инцидент, не рутинная
   операция: сначала свежий бэкап (§10 ниже, если ещё не снят сегодня), потом решение вручную, не по
   шаблону.

Но проще — деплоить одной кнопкой с локальной машины, см. следующий раздел.

### Фоновая задача уборки фото и рестарт контейнера при деплое

`docker compose up -d --build` на живом стеке шлёт запущенному API-контейнеру `SIGTERM` и через
таймаут (по умолчанию 10 с) — `SIGKILL`, если тот не остановился сам. С цикла B в API есть первый
фоновый процесс (`ScheduledTaskRunner`, ARCHITECTURE.md §8) — уборка просроченных фото по
расписанию. Специально ничего настраивать под graceful shutdown не нужно: задача и так работает
короткими порциями (по 200 строк, транзакция — единицы миллисекунд, ARCHITECTURE.md §9.1) и держит
`pg_advisory_xact_lock` только на время своей короткой транзакции, а не на весь проход. Если
контейнер убьют посреди порции, транзакция не закоммитится и откатится сама (Postgres), в БД не
останется наполовину обработанной пачки — в худшем случае на диске останется файл-сирота без
строки, а его подберёт тот же процесс уборки при следующем запуске (порядок «сначала БД, потом
диск», ARCHITECTURE.md §1.4). Отдельного `docker compose stop --timeout` тюнинга под это не требуется.

## 9. Деплой по кнопке (из Rider)

Идея: локальный скрипт `deploy/deploy.sh` скачивает готовый фронтенд из последнего успешного прогона
CI для текущего коммита, отправляет его на VPS по SCP, затем по SSH запускает там
`deploy/deploy-remote.sh <новый-релиз>`. Чтобы Rider мог просто нажать ▶ без ввода пароля на каждый
клик, нужен вход по SSH-ключу — и, отдельно, GitHub CLI.

### 9.0. GitHub CLI (один раз, на вашей локальной машине)

```bash
brew install gh   # или см. https://cli.github.com для другой ОС
gh auth login
```

`deploy.sh` использует `gh run list`/`gh run download`, чтобы найти CI-прогон для коммита, который вы
деплоите, и скачать его артефакт `frontend/dist` — без входа `gh` не сможет прочитать приватный
репозиторий. На самом VPS `gh` не нужен — только на машине, откуда запускается деплой.

### 9.1. Настройка SSH-ключа (один раз, на вашей локальной машине)

```bash
# Если ключа ещё нет
ssh-keygen -t ed25519 -C "deploy-ezbook"

# Скопировать публичный ключ на сервер
ssh-copy-id root@31.31.197.39
```

Проверка — эта команда должна отработать **без запроса пароля**:

```bash
ssh root@31.31.197.39 "echo ok"
```

Если просит пароль — ключ не скопировался или на сервере отключён вход по ключу
(`PubkeyAuthentication` в `/etc/ssh/sshd_config`), разберём по выводу `ssh -v`.

### 9.2. Локальный конфиг деплоя

```bash
cp .deploy.env.example .deploy.env
```

В `.deploy.env` уже стоит `SSH_HOST=root@31.31.197.39` — поменяйте, если IP/пользователь
другие. Файл в `.gitignore`, в репозиторий не попадёт.

Проверка вручную (без Rider):

```bash
./deploy/deploy.sh
```

Если отработало без ошибок — на сервере обновился и backend, и frontend.

### 9.3. Кнопка в Rider

1. **Run → Edit Configurations… → + → Shell Script**
2. Заполните:
   - **Name**: `Deploy to VPS`
   - **Script path**: `deploy/deploy.sh` (или полный путь до него)
   - **Working directory**: корень проекта (`ServiceBooking`)
3. **OK** — сохранить.
4. Конфигурация появится в выпадающем списке рядом с зелёной кнопкой ▶ в тулбаре
   Rider. Выберите её и нажмите ▶ (или Shift+F10) — это и есть «кнопка деплоя»:
   скрипт найдёт готовый фронтенд-билд текущего коммита в CI, отправит его на сервер новым релизом,
   переключит на него симлинк, пересоберёт backend-контейнер и дождётся готовности (или напечатает
   команду отката, если что-то не взлетело — см. §8).

Вывод скрипта будет в панели **Run** внизу Rider — так же, как у обычного запуска
приложения, только выполняется он на сервере.

## 10. Бэкап и восстановление (T-D2, US-40)

### 10.1. Что и как бэкапится

Бэкап делает `deploy/backup/backup.sh` **на самом хосте** (не сайдкар-контейнер, не фоновая задача
внутри API — см. обоснование в ARCHITECTURE.md §12.1), запускается **systemd-таймером**, не cron'ом:

```bash
mkdir -p /opt/ezbook/app  # если ещё не создан (см. §2)
cp /opt/ezbook/app/deploy/backup/servicebooking-backup.service /etc/systemd/system/
cp /opt/ezbook/app/deploy/backup/servicebooking-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now servicebooking-backup.timer

# Проверка
systemctl list-timers servicebooking-backup.timer
systemctl status servicebooking-backup.timer
```

Каждый прогон:
1. Проверяет свободное место (нужно ≥ 1,5× размера прошлой копии) — не хватает, ничего не пишет,
   код возврата ненулевой.
2. `pg_dump -Fc` базы (уже сжатый формат).
3. `tar czf` обоих docker volume, **без остановки приложения**: `api_uploads` (публичные картинки) и
   `api_private_uploads` (фото к заметкам — персональные данные, см. §4 «Два класса хранения»).
4. Ротация: 7 ежесуточных + 4 еженедельных (воскресенье).
5. Всё пишется в `/var/backups/servicebooking` — **вне** любого docker volume, права `0700`: команда
   `docker compose down -v` не может унести копии вместе с оригиналами (US-40 п. 4).
6. Итог — в `journalctl -u servicebooking-backup`; неуспех дополнительно шлёт событие в GlitchTip
   (§11), если `SENTRY_DSN` задан в `.env`.

Посмотреть историю прогонов:

```bash
journalctl -u servicebooking-backup --no-pager -n 50
ls -la /var/backups/servicebooking
```

### 10.2. Восстановление — по шагам, без раздумий

```bash
cd /opt/ezbook/app

# 1. Остановить API (Postgres можно оставить)
docker compose -f docker-compose.prod.yml --env-file .env stop api

# 2. Восстановить базу из последнего дампа
LATEST_DB=$(ls -t /var/backups/servicebooking/db-*.dump | head -1)
docker compose -f docker-compose.prod.yml --env-file .env exec -T postgres \
  pg_restore -U postgres -d servicebooking --clean --if-exists < "$LATEST_DB"

# 3. Восстановить оба volume (ВНИМАНИЕ: перезаписывает их текущее содержимое)
LATEST_UPLOADS=$(ls -t /var/backups/servicebooking/uploads-*.tar.gz | head -1)
LATEST_PRIVATE=$(ls -t /var/backups/servicebooking/private-uploads-*.tar.gz | head -1)
docker run --rm -v ezbook_api_uploads:/dst -v /var/backups/servicebooking:/src alpine \
  sh -c "rm -rf /dst/* && cd /dst && tar xzf /src/$(basename "$LATEST_UPLOADS")"
docker run --rm -v ezbook_api_private_uploads:/dst -v /var/backups/servicebooking:/src alpine \
  sh -c "rm -rf /dst/* && cd /dst && tar xzf /src/$(basename "$LATEST_PRIVATE")"

# 4. Запустить API и дождаться готовности
docker compose -f docker-compose.prod.yml --env-file .env up -d api
curl -s https://ezbook.ru/api/health/ready

# 5. ОБЯЗАТЕЛЬНАЯ проверка (US-40 п. 6): приватное фото открывается через API, а не просто "файл на
#    диске есть" — это единственная проверка, доказывающая, что строки БД и файлы совпали.
#    Войдите под учётной записью персонала компании, откройте карточку клиента с фото и убедитесь,
#    что миниатюра и полный размер загружаются (либо curl'ом с Bearer-токеном на
#    GET /api/client-notes/photos/{id}, если фото/id уже известны).
```

Занимает 10–15 минут при разумном размере базы — это оценка, на которую и рассчитан чек-лист выше
(SPEC Р8, «выполнимо ли это ночью, по скопированной команде»).

**Фактический прогон выполнен на локальном тестовом стенде 2026-09-09**: создана компания, заметка
клиента с загруженным фото; фото подтверждённо открывалось через `GET /api/client-notes/photos/{id}`
(200, `image/jpeg`); снят `pg_dump` + `tar` обоих volume теми же командами, что в `backup.sh`; стенд
полностью уничтожен (`docker compose down -v`, все volume удалены); база и оба volume восстановлены
из бэкапа с нуля; то же самое фото **снова открылось** через тот же эндпоинт с тем же содержимым —
подтверждение, что строки БД (заметка, фото, компания, учётная запись) и файл на диске совпали
один в один после полного цикла уничтожения и восстановления. На боевом VPS этот прогон стоит
повторить один раз вручную (с реальными `systemd`/`pg_dump` в проде) и дописать дату сюда — локальный
стенд подтверждает механику команд, но не заменяет проверку на целевой ОС (AlmaLinux) с реальным
объёмом данных.

### 10.3. Ограничение схемы бэкапа — прочитать обязательно

**Бэкап хранится ЛОКАЛЬНО, на том же VPS, что и оригинальные данные.** Внешней копии нет — решение
заказчика (SPEC R13, §10.1): готового и бесплатного места для offsite-копии на момент цикла C не
нашлось, а откладывать бэкап целиком до появления такого места хуже, чем сделать локальный сейчас.

Это защищает:
- от порчи данных (кривая миграция, ошибка в коде, случайный `DELETE`);
- от ошибки оператора (кто-то удалил не то через админку).

Это **не защищает**:
- от потери или недоступности самого VPS (сгорел дата-центр, провайдер заблокировал аккаунт, диск
  физически умер) — копия пропадёт вместе с оригиналом.

Когда появится место под внешнюю копию — заполнить `upload_offsite()` в `deploy/backup/backup.sh`
(сейчас это осознанная заглушка-стаб, оставленная именно под эту доработку) одной функцией, без
переписывания остального скрипта.

## 11. Трекер ошибок и алерты (T-D4, US-45, GlitchTip)

### 11.1. Поднять GlitchTip

```bash
cd /opt/ezbook/app
docker compose -f docker-compose.glitchtip.yml --env-file .env up -d
```

Первый вход — по адресу, указанному при настройке nginx (см. `docker-compose.glitchtip.yml` и
комментарий в нём про поддомен/basic-auth — GlitchTip **не** публикуется на голом порту без защиты
входа). Создайте организацию и проект, тип — **Node/Other** подойдёт (нас интересует только DSN,
не готовые интеграции). Скопируйте DSN проекта — `Settings → Client Keys (DSN)`.

### 11.2. Подключить приложение

```bash
# в .env на VPS
SENTRY_DSN=https://<key>@<ваш-домен-glitchtip>/1
```

```bash
docker compose -f docker-compose.prod.yml --env-file .env up -d api   # применить новую переменную
```

Пусто — приложение работает без трекера (US-45 п. 8), это нормальное состояние до тех пор, пока
GlitchTip не поднят. `deploy/backup/backup.sh` использует **тот же** `SENTRY_DSN` для алерта о
неуспешном бэкапе — заполнили один раз, получили оба канала алертов сразу.

### 11.3. Проверка

Спровоцируйте тестовую ошибку (например, временно сломайте что-то безобидное или дождитесь
органической 500) — в GlitchTip должно появиться **ровно одно** новое issue. Ретенция событий задана
явно (`GLITCHTIP_MAX_EVENT_LIFE_DAYS=30` в `docker-compose.glitchtip.yml`) — трекер, тихо съевший весь
диск, отключит продукт, поэтому она не бесконечна.

### 11.4. Куда смотреть, когда что-то сломалось

Один канал — e-mail, настраивается в GlitchTip (`Settings → Notifications`), на адрес заказчика.
Список того, что вызывает алерт (и **только** это — остальное намеренно тихое, US-45 п. 5, чтобы
единственный эксплуатант не тонул в шуме):

| Повод | Откуда |
|---|---|
| Новая, ранее не встречавшаяся ошибка | GlitchTip «new issue», автоматически |
| Всплеск известной ошибки | Правило в GlitchTip: > N событий за M минут — настройте под свою нагрузку в `Settings → Alerts` |
| Неуспешный прогон бэкапа | `backup.sh` шлёт событие сам при ненулевом коде возврата (§10.1 п. 6) |
| `/api/health/ready` не отвечает 3 проверки подряд | `deploy/monitor/health-alert.sh` (systemd-таймер, раз в 5 минут — см. ниже) |

Дневая сводка — встроенный digest GlitchTip (`Settings → Notifications → Daily digest`).

**Ограничение (то же по духу, что и у бэкапа, §10.3):** если весь VPS недоступен, GlitchTip
недоступен вместе с ним — алерта не будет. Мониторинг снаружи VPS в этот цикл не входит.

### 11.5. Монитор доступности (алерт на долгий 503)

```bash
cp /opt/ezbook/app/deploy/monitor/health-alert.sh /opt/ezbook/app/deploy/monitor/
chmod +x /opt/ezbook/app/deploy/monitor/health-alert.sh
cp /opt/ezbook/app/deploy/monitor/health-alert.service /etc/systemd/system/
cp /opt/ezbook/app/deploy/monitor/health-alert.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now health-alert.timer
```

Опрашивает `/api/health/ready` раз в 5 минут; при трёх подряд неудачах шлёт событие в GlitchTip тем же
DSN. Тоже на хосте, тоже systemd — работает даже если сам API-контейнер лежит.

## 12. Health-check — что означают ответы (T-D7, US-43)

```bash
curl -s https://ezbook.ru/api/health/ready
```

| Ответ | Значит |
|---|---|
| `{"status":"Healthy"}` | можно деплоить, можно давать нагрузку |
| `{"status":"Unhealthy","failed":"database"}` | БД недоступна ИЛИ остались непринятые миграции — смотрите `docker compose logs api` |
| нет ответа / connection refused / таймаут | процесс не поднялся вовсе, либо nginx не может до него достучаться — сначала `docker compose ps`, потом `docker compose logs api` |

`GET /api/health/live` (без обращения к БД) используется docker'ом внутри `healthcheck:` контейнера
`api` (`docker-compose.prod.yml`) — если он не подтверждает "Healthy" 3 раза подряд, `docker compose ps`
покажет контейнер как `unhealthy`. `start_period: 60s` в healthcheck рассчитан на то, что миграции при
старте могут занять время — не паникуйте, если первые секунды после `up -d --build` контейнер отвечает
не сразу.

## 13. Часовые пояса (T-D6, US-51)

Все контейнеры (Postgres, API) должны работать в **UTC** — это не настраивается отдельно, `postgres:16-alpine`
и `mcr.microsoft.com/dotnet/aspnet:8.0` уже используют UTC по умолчанию, если хост-таймзону явно не
пробрасывать (`TZ=...` не задаётся ни в одном compose-файле этого проекта — так и должно оставаться).

Все временные метки в БД (`CreatedAt`, `AcceptedAtUtc`, `DeletedAtUtc` и т.д.) — `DateTime`/`timestamp`
в UTC. Смотрите также `README.md` — там отдельно записано, что **у продукта нет понятия часового пояса
компании**: время визита (`Booking.Date`/`StartTime`) — это **местное время салона**, введённое
персоналом буквально, без какой-либо конвертации между часовыми поясами. Компания в Москве и компания
во Владивостоке видят и вводят время одинаково буквально, «как на часах в салоне» — конвертации в UTC
или обратно для времени визита **нет** ни на бэкенде, ни на фронте (`Company.TimeZoneId` в модели
данных отсутствует осознанно, ARCHITECTURE.md §5.4). Это ограничение продукта, а не баг: если сеть
компаний в разных часовых поясах когда-нибудь понадобится — это отдельный цикл работ, не текущий.

## Если что-то пошло не так

Пришлите мне вывод одной из этих команд — разберём по выводу:

```bash
docker compose -f docker-compose.prod.yml logs api --tail=100
nginx -t
journalctl -u nginx --no-pager --tail=50
certbot certificates

# Если nginx отдаёт 502/403 без явной причины в логах — часто виноват SELinux, проверьте:
ausearch -m avc -ts recent
```
