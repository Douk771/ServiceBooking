## §360. Конвенции, действующие без изменений

* `camelCase` в JSON; `enum` — строками (имена членов C#, PascalCase); `DateTime` — ISO-8601 UTC.
* Тела осознанных ошибок **400/402/409/429** — **голая строка** `text/plain` по-русски;
  **401/403** — пустое тело; **404** — пустое тело там, где существование объекта не подтверждается
  (`Program.cs`, `SuppressMapClientErrors = true`). `ProblemDetails` не используется.
* **451** — «требуется принять новую редакцию документов» (глобальный `LegalConsentFilter`); новые
  маршруты по умолчанию **закрыты** гейтом. Единственное исключение — §360.2.
* Все новые поля **добавочные**. Цикл не удаляет и не переименовывает ничего у существующих
  маршрутов (§372).
* Текст, который видит человек, собирает **сервер**; фронт печатает его дословно и ветвится по
  машиночитаемому коду (§41 п. 8). Тексты цикла 18 живут в
  `ServiceBooking.API/Services/Billing/TrialLegalNotices.cs` (**Д20** — отдельный файл, не регион
  в `LegalNotices.cs`).
* `null` у вычисляемого поля = «сервер не считал это для данного вызывающего», а не «нельзя».

### §360.1 Единственное намеренное исключение из «4xx — строка»

**Отказ в активации триала — это JSON**, а не голая строка:

```json
{ "code": "TrialPhoneAlreadyUsed", "message": "На этот номер телефона пробный период уже предоставлялся, поэтому предоставить его снова мы не можем: …" }
```

Причина: US-18-06 требует **одновременно** машиночитаемый код (фронт ветвится) и готовый русский
текст (фронт печатает). Разбирать русскую строку подстрокой — ровно тот дефект, который цикл 17
чинил в другом месте. Precedent в проекте уже есть: `PricingPublicationBlockedDto` — 409 с JSON-телом
на `PUT /api/admin/platform-settings` (цикл 11, §114.2). Статус — **409 Conflict** (состояние
аккаунта/платформы не позволяет), кроме `400` на невалидном вводе (пустая причина у перевыдачи).

### §360.2 Одно исключение из «новые маршруты закрыты гейтом 451»

`GET /api/profile/delete-account/preview` (§377) добавляется **в allow-list** `LegalConsentFilter`,
потому что там уже находится `POST /api/profile/delete-account` (`API_CONTRACT.md` §0.4): экран
удаления аккаунта обязан работать у человека, который **не принял** новую редакцию документов —
иначе отказ от сервиса становится заблокирован требованием принять условия сервиса. Предупреждение о
реестре пробных периодов (**О8**) живёт на этом экране, значит и его источник обязан быть доступен в
том же режиме. Остальные маршруты цикла 18 в allow-list **не** добавляются.

## §362. `GET /api/billing/trial` — владелец, «можно ли и что сейчас»

`[Authorize]`. Ответ **200** `TrialStateDto`; **404** (пустое тело) — у пользователя нет
биллинг-аккаунта и он не владелец; **401** — нет токена.

```json
{
  "state": "Available",
  "planId": "8f4c…",
  "planName": "Пробный период",
  "durationDays": 14,
  "mailingWindowDays": 7,
  "warningThresholdsDays": [7, 3, 1],
  "endsAtPreview": "2026-10-09T11:20:00Z",
  "refusalCode": null,
  "message": "Пробный период даёт возможности тарифа «Пробный период» на 14 дней — до 09.10.2026 включительно. …",
  "activationTerms": {
    "version": "2026-09-26",
    "sha256": "3f1a…",
    "text": "Пробный период даёт возможности тарифа «Пробный период» на 14 дней — до 09.10.2026 включительно. …",
    "acknowledgementRequired": false,
    "shownAt": null,
    "acknowledgedAt": null
  },
  "planChangeNotice": null,
  "startedAt": null,
  "endsAt": null,
  "daysLeft": null,
  "grantSource": null,
  "mailingWindow": {
    "state": "NotStarted",
    "startedAt": null,
    "endsAt": null,
    "daysLeft": null,
    "text": "Рассылки клиентам входят в пробный период, но их срок ещё не начался: 7 дней отсчитываются с того момента, когда вы впервые привяжете номер для рассылок. …"
  },
  "warning": null,
  "includes": ["Онлайн-запись", "Рассылки клиентам", "Аналитика", "Публичная страница компании", "Онлайн-оплата"],
  "limits": { "companies": 5, "employees": 25, "photoQuotaMb": 1000 }
}
```

**`state`** — закрытое множество из четырёх значений:

| `state` | Смысл | `refusalCode` |
|---|---|---|
| `Available` | можно активировать прямо сейчас | `null` |
| `Unavailable` | нельзя, и сервер говорит почему | один из §364 |
| `Active` | триал идёт | `null` |
| `Expired` | триал был и закончился | `TrialAlreadyUsed` |

🔴 **Фронт не вычисляет доступность сам** (US-18-12): ни «использован ли триал», ни «остались ли
дни», ни «идёт ли окно рассылок». Всё это — поля ответа. Кнопка рисуется по `state == "Available"`,
причина — по `message`.

🔴 **`trial` не становится `null`, если триал у аккаунта когда-либо был.** При `state == "Expired"`
объект обязан приходить целиком (с `endsAt` и с `warning`), иначе сообщение о состоявшемся переходе
исчезнет с экрана и Т3 будет нарушено.

### §362.1 `activationTerms` — фиксация показа условий (Т1, Т5)

| Поле | Смысл |
|---|---|
| `version` | версия редакции текста активации (`TrialLegalNotices.ActivationTermsCurrentVersion`, формат `yyyy-MM-dd`) |
| `sha256` | хеш **точных байтов** текста этой версии после подстановки параметров-заглушек редакции; нужен, чтобы «показали версию X» проверялось, а не утверждалось |
| `text` | готовый русский текст **дословно**; для `state == "Available"` он же лежит в `message` — это один и тот же серверный текст, а не два (разойтись им нечем) |
| `acknowledgementRequired` | `true`, только если триал уже выдан **суперадмином**, а владелец условия ещё не подтверждал (§368). Пока `true`, фронт обязан показывать текст блоком, который нельзя закрыть |
| `shownAt` / `acknowledgedAt` | момент показа и момент подтверждения по журналу выдачи; `null` до активации |

**Правовая нагрузка (не стилистика).** Правомерность всей схемы уведомления «только кабинет, без
почты и SMS» держится на том, что владелец при активации был проинформирован о дате окончания и
последствиях (Д18/Т1, `LEGAL_REVIEW_CYCLE18.md` §5.2 п. 1). Поэтому:

* `POST /api/billing/trial` **обязан** прислать `termsVersion`, и сервер записывает версию и хеш в
  журнал выдачи — без этого утверждение «владелец знал» нечем доказать;
* текст версии **никогда не удаляется** из кода: архивные редакции доступны по §376;
* фронт **не имеет права** сократить, переформатировать или склеить этот текст из кусочков
  (`LEGAL_REVIEW_CYCLE18.md` §4, правило 1). Он печатает `text` целиком.

`endsAtPreview` — до какой даты триал действовал бы, если активировать **сейчас** (нужен, чтобы
кнопка обещала конкретную дату; тот же параметр подставлен в `activationTerms.text`). У
`state == "Active"` он равен `endsAt`.

`warningThresholdsDays` — какие пороги предупреждений обещаны **этому** владельцу: у `Available` —
текущая настройка платформы, у `Active`/`Expired` — **снапшот, взятый в момент выдачи** (Д19).
Изменение порогов в админке уже выданный триал не трогает.

`planChangeNotice` — текст `TrialRemainderForfeitedOnPlanChange` (О9): непустой, пока
`state == "Active"`, и `null` во всех остальных состояниях. Показывается **до** подтверждения заявки
на платный тариф (§365).

`mailingWindow.state`: `NotStarted` | `Running` | `EndingSoon` | `Ended` | `NotApplicable`
(последнее — когда рассылки не входят в состав триала на текущей матрице опций).

### §362.2 `warning` — и почему у него появились два новых поля

Форма расширяет существующий `SubscriptionWarningDto` (цикл 17):

```json
{ "code": "TrialExpired", "text": "Пробный период закончился 09.10.2026, и подписка переведена на бесплатный тариф. …",
  "affected": ["Онлайн-запись", "Рассылки клиентам"], "dismissible": false, "visibleUntilUtc": "2026-11-08T09:00:00Z" }
```

Коды: `TrialExpiring` (порог 7/3/1), `TrialExpired`, `TrialMailingEndingSoon`, `TrialMailingEnded`,
`TrialOverLimit`. `affected` собирается **из реальных флагов тарифа** (N24), не общим списком, и
рендерится **непосредственно под** текстом: тексты юриста ссылаются на него словами «перечисленные
ниже», и вынос списка в другое место делает ссылку ложной.

| Поле | Правило |
|---|---|
| `dismissible` | **решает сервер, а не фронт.** `false` у `TrialExpired` — всегда. У остальных `true` |
| `visibleUntilUtc` | до какого момента сервер обязуется отдавать это предупреждение. У `TrialExpired` — **не раньше, чем через 30 календарных дней после состоявшегося перехода** (Т3, пункт 6.16.11 Соглашения). У остальных `null` |

🔴 **Т3 — требование с правовой нагрузкой.** `TrialExpired` — единственное сообщение, которое доходит
до владельца, не заходившего в кабинет во время триала. Оно обязано жить ≥30 дней и **не исчезать
после первого просмотра**: фронт не рисует у него кнопку «закрыть» и не пишет признак «прочитано» ни
в `localStorage`, ни куда-либо ещё. Порог 30 дней — константа кода, а не настройка админки.

## §363. `POST /api/billing/trial` — активация владельцем

`[Authorize]`, `[EnableRateLimiting("trial-activate")]`.

```json
{ "termsVersion": "2026-09-26" }
```

**Тело появилось ровно для одного — подтвердить, какую редакцию условий клиент показал человеку.**
Попросить другой срок, другой состав или другие лимиты им нельзя: других полей нет, а единственное
допустимое значение `termsVersion` — текущая версия с сервера (§362.1). Любое другое (устаревшая
редакция, неизвестная строка, пустое поле) → **409 `TrialTermsVersionMismatch`**: клиент показал не
тот текст, значит зафиксировать «владелец был проинформирован» невозможно, и выдавать триал нельзя.
Это fail-closed того же рода, что `TrialUniquenessCheckUnavailable`.

| Код | Тело | Когда |
|---|---|---|
| **200** | `OwnerSubscriptionDto` (целиком, с уже заполненным `trial`) | активировано |
| **400** | строка | тело отсутствует или `termsVersion` пустой |
| **409** | `TrialRefusalDto` (JSON, §360.1) | любая причина отказа §364, включая `TrialTermsVersionMismatch` |
| **404** | пустое | нет биллинг-аккаунта и он не создаётся (пользователь не владелец) |
| **429** | строка | больше 5 попыток в сутки |
| **401 / 451** | пустое | нет токена / нужно принять новую редакцию документов |

Почему 200 отдаёт **весь** `OwnerSubscriptionDto`, а не `TrialStateDto`: после активации меняется
весь экран «Ваша подписка» (статус, состав, лимиты, использование, опции). Отдать частичный ответ —
значит заставить фронт делать второй запрос и на мгновение показать несогласованный экран.

**Что сервер записывает при успехе** (детали — `ARCHITECTURE_CYCLE18.md` §335.3–§335.4): версию
текста, **хеш текста, взятый на сервере** (а не присланный клиентом — иначе подделка), момент показа,
момент подтверждения, снапшоты длительности, окна рассылок и порогов предупреждений.

**Идемпотентность:** повторный `POST` — это **409 `TrialAlreadyActive`** или
**409 `TrialAlreadyUsed`**, никогда не «молча ок». Двойной клик получает ровно один триал, вторая
подписка и вторая строка журнала не появляются (US-18-04, гарантия — индекс + advisory-lock).

### §363.1 `POST /api/billing/trial/terms-acknowledgement`

`[Authorize]`. Тело — `{ "termsVersion": "2026-09-26" }`. Нужен ровно для одного случая: триал выдал
**суперадмин** (§368), владелец при этом ничего не нажимал и условий не видел. Пока подтверждения
нет, `activationTerms.acknowledgementRequired == true`, и кабинет показывает условия блоком, который
нельзя закрыть.

| Код | Тело | Когда |
|---|---|---|
| **200** | `TrialStateDto` | подтверждение записано либо уже было записано раньше (идемпотентно) |
| **400** | строка | `termsVersion` пустой |
| **409** | `TrialRefusalDto` с `TrialTermsVersionMismatch` | присланная версия не текущая |
| **404** | пустое | у аккаунта нет ни одной выдачи триала — подтверждать нечего |
| **401 / 451** | пустое | нет токена / нужно принять новую редакцию документов |

🔴 **Отметка подтверждения ставится один раз и никогда не перезаписывается** (set-once): повторный
вызов отвечает 200 и **не** двигает `acknowledgedAt`. Иначе журнал переставал бы отвечать на вопрос
«когда человек впервые узнал», ради которого он и ведётся.

## §364. Коды отказа: закрытая таблица

Порядок проверок фиксирован (часть контракта): сначала форма запроса, потом состояние платформы,
потом своё прошлое, потом чужое. Тексты — финальные формулировки `legal-counsel` из
`Services/Billing/TrialLegalNotices.cs`; ниже приведён **смысл**, а не разрешение их переписать.

| № | `code` | Смысл | Ключ текста (`TrialLegalNotices`) | Обходится `regrant`? |
|---|---|---|---|---|
| 0 | `TrialTermsVersionMismatch` | клиент показал не текущую редакцию условий → фиксация показа невозможна | `TrialTermsVersionMismatchNotice` ⚠️ | нет |
| 1 | `TrialNotOffered` | тарифа-триала нет, он неактивен, снят с витрины или его настройки испорчены | `TrialRefusedPlanUnavailable` | нет |
| 2 | `TrialAlreadyActive` | триал уже идёт | `TrialAlreadyActiveNotice` ⚠️ | нет |
| 3 | `AlreadyOnPaidPlan` | есть действующая платная подписка (Д9) | `TrialRefusedActivePaidSubscription` | нет |
| 4 | `TrialAlreadyUsed` | триал уже использован; текст называет **дату** (это своё прошлое) | `TrialRefusedAlreadyUsedByAccount` | да |
| 5 | `PhoneVerificationUnavailable` | номер владельца не подтверждён, И подсистема подтверждения номера выключена (R7) — если номер уже подтверждён, состояние подсистемы не проверяется вовсе | `TrialRefusedPhoneVerificationUnavailable` | да |
| 6 | `PhoneNotVerified` | номер владельца не подтверждён; текст ведёт на подтверждение | `TrialRefusedPhoneNotVerified` | да |
| 7 | `TrialUniquenessCheckUnavailable` | проверка однократности недоступна (нет ключа) — fail-closed | `TrialRefusedUniquenessCheckUnavailable` | **нет** |
| 8 | `TrialPhoneAlreadyUsed` | номер есть в реестре; текст **без даты, имени и признака существования другого аккаунта** | `TrialRefusedPhoneAlreadyUsed` | да |

⚠️ **Две формулировки, которых в `LEGAL_REVIEW_CYCLE18.md` §4 нет** (`TrialTermsVersionMismatchNotice`,
`TrialAlreadyActiveNotice`): правовой обязанности они не исполняют — это сообщения о состоянии
интерфейса («условия обновились, перечитайте», «пробный период уже идёт»). Они живут в том же файле,
но помечены в коде как **не правовые**, и задача L1 обязана их назвать, чтобы юрист не считал, что
файл целиком его. Все остальные тексты переносятся **дословно**.

### §364.1 Переименование по Д17 — это часть контракта, а не косметика

`TrialAntifraudUnavailable` больше **не существует**. Действующий код —
`TrialUniquenessCheckUnavailable`. Причина: **Д17** запрещает слова «акция», «антифрод» и
«злоупотребление» в пользовательских текстах, названиях целей обработки, **кодах ошибок** и
**журналах**. Правило срабатывает и на добросовестном человеке, который просто зарегистрировался
заново, а слово «акция» тянет квалификацию стимулирующего мероприятия
(`LEGAL_REVIEW_CYCLE18.md` §2.1, §3.4).

Следствия, обязательные к соблюдению обеими дорожками:

* в JSON, в TypeScript-типах, в `utils/trialError.ts`, в логах и в сообщениях GlitchTip — только
  `UniquenessCheck`; журнальное событие — `trial.uniqueness-check.applied`, уровень `Information`,
  **без номера телефона в любом виде, включая маскированный, и без счётчиков попыток**
  (`LEGAL_REVIEW_CYCLE18.md` §6.2 Р3);
* короткая формулировка цели для интерфейса и журналов — **«проверка однократности пробного
  периода»**; полная формулировка (для Политики и уведомления РКН) — дословно из **Д17**;
* в подписях экранов вместо «настройки акции» — **«настройки пробного периода»**.

🔴 **Правило «ответ — не оракул»** (§4.27 🔒, §5.0-septies): по ответу `TrialPhoneAlreadyUsed`
нельзя установить, существует ли на этом номере чужой аккаунт, когда он получал триал и кто это.
Текст — без параметров. Это проверяется тестом, а не доверием.

## §365. `GET /api/billing/subscription` — добавочные поля

Форма прежняя (`OwnerSubscriptionDto`), добавлено:

```jsonc
{
  "trial": { /* TrialStateDto, §362; null — ТОЛЬКО если триала у аккаунта никогда не было и он недоступен */ },
  "usage": {
    "companiesUsed": 5, "companiesLimit": 1,
    "overLimitCompanies": 4,          // НОВОЕ, 0 когда в пределах лимита
    "overLimitEmployees": 24,         // НОВОЕ
    "overLimitText": "Бесплатный тариф допускает компаний: 1, сотрудников: 1. Сейчас у вас компаний: 5, сотрудников: 25 — это больше лимита. Ничего из созданного не удалено и не отключено: …"  // НОВОЕ, null когда в пределах
  }
}
```

`overLimitText` — это и есть «деградация = заморозка» на языке владельца (Д3), ключ
`TrialOverFreeLimitsNotice`. Текст обязан оставаться утверждением «ничего не удалено и не
отключено», потому что именно это утверждение делает правомерным отсутствие второго канала
уведомлений (**Т4**): как только на переходе появится хоть одно необратимое последствие, плашки в
кабинете станет недостаточно.

Ни одно другое поле экрана смысла не меняет; аккаунт **не на триале** получает ответ, побайтово
совпадающий с тем, что отдавался до цикла (кроме `trial: null` и трёх полей со значениями
`0/0/null`).

**Заявка на платный тариф при действующем триале.** Экран заявки (`POST /api/billing/subscription/request`)
обязан **до** подтверждения показать `trial.planChangeNotice`
(`TrialRemainderForfeitedOnPlanChange`, О9, исполнение пункта 6.16.10 Соглашения). Отдельного
маршрута под этот текст нет намеренно: он приходит тем же ответом, который уже рисует экран, и
поэтому не может «отстать» от состояния триала.

## §366. Админка: флаг тарифа

### `PUT /api/admin/plans/{id}/system-trial`

`[Authorize(Roles = "SuperAdmin")]`. Запрос: `{ "isSystemTrial": true }`. Ответ **200** —
`AdminPlanDto`.

| Код | Тело | Когда |
|---|---|---|
| **400** | строка | у тарифа `pricePerMonth != 0` — триал не оплачивается |
| **409** | строка | триалом уже помечен другой тариф / этот тариф — системный бесплатный / гонка (нарушение частичного уникального индекса) |
| **404** | пустое | тарифа нет |

Повторный вызов с тем же значением — **200** без изменений (та же идемпотентность, что у
`system-free`). Поля `isSystemTrial` в `AdminPlanInput` **нет** — флаг меняется только этим
маршрутом, чтобы обычная правка полей не переставила его случайно.

### `AdminPlanDto` — два добавочных поля

```jsonc
{
  "isSystemTrial": false,
  "optionCoverage": { "configured": 3, "total": 5, "text": "В тариф включено 3 из 5 опций каталога" }
}
```

`optionCoverage` существует потому, что **отсутствие строки `PlanOptionRule` = `Unavailable`**
(fail-closed): «максимальный тариф» требует явно проставленных правил на каждую опцию, а опция,
добавленная в каталог позже, в триал сама не попадёт. Это поведение, а не дефект — но суперадмин
обязан видеть его на экране (US-18-03).

### `DELETE /api/admin/plans/{id}`

Новый повод для существующего **409** (строка): «Тариф пробного периода нельзя удалить».
`PUT /api/admin/plans/{id}` — **409** при деактивации тарифа-триала с живыми подписчиками (текст
существующий: «перенесите подписчиков»); снятие с витрины (`isPublic: false`) — **разрешено** и
означает «новые триалы не выдаются, действующие доживают» (пункт 6.16.12 Соглашения: прекращение
предложения не затрагивает уже предоставленные пробные периоды).

## §367. Админка: настройки пробного периода

`GET /api/admin/platform-settings` → существующий DTO + три поля:

```jsonc
{
  "channelPricePerMonth": 1200, "channelIdleDays": 3, "pricingPublicEnabled": false,
  "trialDurationDays": 14,
  "trialMailingWindowDays": 7,
  "trialWarningThresholdsDays": [7, 3, 1]
}
```

`PUT` — те же поля, **все три nullable**: `null`/отсутствие = «не менять» (та же семантика, что
`isPublic`/`sortOrder` в `AdminPlanInput`). Это не косметика: без неё существующий фронт, не знающий
о новых полях, сбрасывал бы длительность при каждом сохранении цены канала.

| Код | Тело | Когда |
|---|---|---|
| **400** | строка | `trialDurationDays` вне `1..365`; `trialMailingWindowDays` вне `1..365` или **больше** длительности; `trialWarningThresholdsDays` — не 1..5 различных положительных значений или порог больше длительности; **пороги не совпадают с теми, что обещает текущая редакция текста активации** (§367.1) |
| **409** | `PricingPublicationBlockedDto` | существующая причина (включение публичных цен при черновой оферте) — не меняется |

Изменения журналируются `PlatformSettingChangeLogs` (как цена канала), кеш соответствующего ключа
инвалидируется **после** коммита.

### §367.1 Д19: правка настроек действует ТОЛЬКО на новые триалы

Уже выданные триалы правкой настройки **не меняются** — обещанные длительность, окно рассылок и
пороги предупреждений лежат снапшотом на биллинг-аккаунте и в строке журнала выдачи (US-18-07,
**Д19**). В ответах это видно прямо: `trial.durationDays`, `trial.mailingWindowDays` и
`trial.warningThresholdsDays` у `state == "Active"` — **снапшот**, а не текущая настройка. Проверка
приёмки формулируется как контрактная: сменили настройку → у действующего триала все три поля и
`endsAt` **не изменились**.

Почему у порогов есть вторая, более жёсткая проверка (400 в таблице выше). Текст `TrialActivationTerms`
называет числа «7, 3 и 1» **буквально**, подстановки под них в редакции нет. Значит порог,
выставленный в админке вразрез с текстом, делает **уже показанный** текст недостоверным для новых
выдач — и правкой числа это не лечится. Поэтому каждая редакция текста активации объявляет, какие
пороги она обещает (`TrialLegalNotices.ActivationTermsPromisedThresholds[version]`), а `PUT`
отвергает несовпадение с объяснением: «текущая редакция текста активации обещает пороги 7, 3, 1;
другие значения возможны только с новой редакцией текста от legal-counsel». Это не запрет менять
пороги — это требование менять их **вместе с текстом**, который их обещает.

🔴 `NotifyDaysBefore` на тарифе для порогов триала **не используется** — это напоминание об окончании
**оплаченного** периода, отдельная сущность (§5.1). Подменять им пороги запрещено (US-18-03).

## §368. Админка: выдача триала аккаунту

### `POST /api/admin/billing-accounts/{accountId}/trial`

`[Authorize(Roles = "SuperAdmin")]`, тело отсутствует. **200** — карточка аккаунта
(`AdminBillingAccountDto`, та же форма, что у `GET …/{accountId}`, с заполненным `trial`).
**409** — `TrialRefusalDto` (те же коды §364, те же тексты, кроме `TrialTermsVersionMismatch` — его
здесь быть не может). **404** — аккаунта нет.

Проверки **те же самые**, что у владельца: одна проверка одноразовости, один ключ проверки
однократности, одна запись в журнал. Разные проверки на двух путях — это и есть дыра, через которую
триал берут второй раз (Д1).

🔴 **Т1 на админском пути закрывается иначе, и это названо честно.** Суперадмин нажимает кнопку
вместо владельца — владелец условий в этот момент не видел. Поэтому строка журнала получает
`termsVersion` (текущая редакция), но `termsShownAt = null` и `termsAcknowledgedAt = null`, а
`GET /api/billing/trial` у владельца возвращает `activationTerms.acknowledgementRequired = true`:
условия показываются блоком, который нельзя закрыть, до вызова §363.1. Момент, когда владелец
фактически узнал условия, оказывается в журнале **отдельным полем**, а не смешивается с моментом
выдачи. Это слабее, чем показ до активации, и остаточный характер этой разницы зафиксирован в
`ARCHITECTURE_CYCLE18.md` §356 — она не замазывается одинаковой отметкой.

### `POST /api/admin/billing-accounts/{accountId}/trial/regrant`

**Отдельный маршрут, а не флаг у предыдущего** — намеренно (Д1-бис): аварийный выход не должен быть
достижим случайным полем в теле обычного запроса.

```json
{ "reason": "Пробный период не сработал из-за сбоя 12.09, исправляем свою ошибку" }
```

| Код | Тело | Когда |
|---|---|---|
| **200** | `AdminBillingAccountDto` | выдано повторно; отметка обойдена **явно** |
| **400** | строка | `reason` пустой, только пробелы или длиннее 500 символов |
| **409** | `TrialRefusalDto` | `TrialNotOffered`, `TrialAlreadyActive`, `AlreadyOnPaidPlan`, `TrialUniquenessCheckUnavailable` — эти четыре **не обходятся** |
| **404** | пустое | аккаунта нет |

Что попадает в журнал: автор, адресат, время, причина, `grantSource: "SuperAdminOverride"`, версия
текста условий — и это видно в истории аккаунта (US-18-04). Обычная активация — ни владельцем, ни
суперадмином — отметку не обходит **никогда**.

⚠️ **Правовая рамка причины (пункт 6.16.6.1 Соглашения, `LEGAL_REVIEW_CYCLE18.md` §2.4):** повторная
выдача допустима **только как исправление собственной ошибки платформы** (сбой, ошибочная выдача,
необоснованный отказ), а не как индивидуальная уступка — иначе это предпочтение одному абоненту
перед другими (пункт 6.13.11.1, пункт 2 статьи 426 ГК РФ). Код обеспечивает обязательность причины и
её попадание в журнал; содержательная рамка — операционное правило, и оно должно стоять подсказкой
рядом с полем ввода причины в админке.

текста условий — история аккаунта читается без обращения к БД.

## §370. Витрина: `+isTrial`

`PublicPlanDto` получает `isTrial: boolean` рядом с существующим `isFree`. Оба маршрута —
`GET /api/pricing` (анонимный, ETag, `max-age=60`) и `GET /api/admin/pricing/preview`
(SuperAdmin, `no-store`) — форму меняют **только** этим полем.

Поведение, которое цикл **не** меняет и которое надо понимать правильно:

* `GET /api/pricing` отвечает **404 с пустым телом**, пока выключен рубильник `pricing.public-enabled`
  или оферта `isDraft: true`. Триала публично не видно — **это ожидаемое состояние, а не дефект**
  (§4.19, §9 B8). Цикл гейт не обходит.
* `GET /api/admin/pricing/preview` показывает Триал **всегда** — единственный способ проверить
  карточку до публикации.
* Место карточки задаёт `sortOrder`, текст — `highlights`; оба правятся в админке. Чтобы Триал не
  читался как «второй бесплатный тариф», работает текст карточки, а не код.
* ⚠️ **Операционное правило витрины** (`LEGAL_REVIEW_CYCLE18.md` §2.3, часть 7 статьи 5 ФЗ «О
  рекламе»): в `highlights` карточки триала обязаны стоять четыре сведения — продолжительность,
  однократность, отдельный короткий срок рассылок, переход на бесплатный тариф без удаления данных.
  Код смысл текста проверить не может, поэтому требование живёт **подсказкой на экране правки
  тарифа** (задача F4), а не валидацией.

## §371. Что обязан проверить фронт (и чего не должен делать)

**Обязан:**
1. Печатать `message`, `activationTerms.text`, `warning.text`, `mailingWindow.text`,
   `planChangeNotice`, `overLimitText`, `trialRegistryNotice`, `statusText` **дословно**; не
   склеивать из кусочков, не сокращать, не «поправлять стиль» (тексты исполняют обязанности из
   пункта 6.16 Соглашения — `LEGAL_REVIEW_CYCLE18.md` §4, правило 1).
2. Ветвиться по `state`/`code`, а не по подстроке русского текста.
3. Показать кнопку активации только при `trial.state == "Available"`; при `Unavailable` — причину.
   Кнопка отправляет `termsVersion` из того же ответа, текст которого был показан.
4. После `POST /api/billing/trial` использовать **ответ** как новое состояние экрана (не перезапрашивать).
5. Обработать **429** и **409 `TrialTermsVersionMismatch`** отдельными текстами (маппер
   `utils/trialError.ts`, 14-й по счёту); у второго — перечитать `GET /api/billing/trial` и показать
   обновившиеся условия заново, а не повторять запрос со старой версией.

## §374. Чего в контракте намеренно нет

* **Ни одного поля, которым клиент просит другой срок, другой состав или другие лимиты.** Срок и
  состав задаёт платформа. Единственное поле в теле `POST /billing/trial` — `termsVersion`, и оно не
  просит, а **подтверждает** показанную редакцию условий; любое значение, кроме текущего, отвергается
  (§363). Попросить послаблений формой запроса физически нельзя — принцип сохранён.
* **Ни одного маршрута, отдающего номер или его хеш из реестра предоставленных пробных периодов.**
* **Ни одного маршрута оплаты, продления или возврата** — цикл не заводит платежей (это не удобство,
  а условие правомерности Д2/Т4: на переходе нет списаний).
* **Ни одного способа узнать со стороны, существует ли чужой аккаунт на номере.**
* **Ни одного маршрута доставки уведомлений** (почта/SMS/мессенджер владельцу) — Д2. По триалу почта
  **не обещана** ни в контракте, ни в текстах (Д21: чужой долг комплекта цикл не расширяет).
* **Ни одного поля согласия на обработку реестра** — основание пункт 7 части 1 статьи 6 152-ФЗ, а не
  согласие (**Д15**).
* **Ни одной настройки, которой можно изменить срок или пороги уже выданного триала** (**Д19**): в
  теле `PUT /api/admin/platform-settings` нет ни `accountId`, ни «применить к действующим».

## §376. `GET /api/admin/trial-terms/{version}` — чем доказывается Т1

`[Authorize(Roles = "SuperAdmin")]`. Отдаёт **архивную** редакцию текста активации по её версии.

```json
{
  "version": "2026-09-26",
  "sha256": "3f1a…",
  "isCurrent": true,
  "promisedWarningThresholdsDays": [7, 3, 1],
  "template": "Пробный период даёт возможности тарифа «{0}» на {1} дней — до {2} включительно. …"
}
```

| Код | Тело | Когда |
|---|---|---|
| **200** | `TrialTermsDto` | версия есть в реестре редакций |
| **404** | пустое | такой версии не существует |
| **401 / 403** | пустое | нет токена / не SuperAdmin |

Зачем маршрут нужен и почему он не «аудит на всякий случай». Через полгода после спора платформе
придётся не утверждать, а **показывать**: вот строка выдачи с версией и хешем, вот текст этой
версии, хеш совпадает — значит человеку было сообщено именно это, включая дату окончания, судьбу
данных и отсутствие второго канала уведомлений. Поэтому:

* `template` — это редакция **с подстановками `{0}`–`{3}`**, а не готовая строка: подставленные
  значения (название тарифа, число дней, дата) лежат в той же строке журнала выдачи и в снапшотах на
  аккаунте, так что показанный текст восстанавливается однозначно;
* `sha256` считается **от шаблона** — иначе хеш зависел бы от даты и перестал отвечать на вопрос «эта
  ли редакция»;
* **редакции не удаляются никогда.** Выпущенная версия остаётся в коде даже после замены на новую,
  иначе хеш в журнале выдачи не с чем сверить. Это инвариант, закреплённый юнит-тестом
  (`ARCHITECTURE_CYCLE18.md` §338.4).

## §377. `GET /api/profile/delete-account/preview` — предупреждение до необратимого действия

`[Authorize]`, **в allow-list гейта 451** (§360.2).

```json
{ "trialRegistryNotice": "Отметка о том, что на ваш подтверждённый номер телефона предоставлялся пробный период, удалением учётной записи не стирается. …" }
```

| Код | Тело | Когда |
|---|---|---|
| **200** | `AccountDeletionPreviewDto` | всегда для авторизованного пользователя |
| **401** | пустое | нет токена |

`trialRegistryNotice` — текст `TrialRegistryNoticeOnAccountDeletion`; **непустой только у владельца,
которому пробный период предоставлялся**, иначе `null`. Это не «дополнительная информация», а
исполнение пункта 5.6.7.7 Политики и условия правомерности хранения реестра дольше жизни аккаунта
(`LEGAL_REVIEW_CYCLE18.md` §3.6 П2): субъект узнаёт правило **до** необратимого действия, тем же
приёмом, которым цикл 16 сделал правомерным «немой» 204.

Про оракула здесь думать не нужно: ответ говорит о **своём** прошлом вызывающего, чужих данных в нём
нет. Номера и хеша в ответе нет (§374).

Форма ответа — объект, а не строка, **намеренно**: на этом экране в следующих циклах появятся другие
предупреждения того же жанра, и добавление поля в объект не будет ломающим изменением.
