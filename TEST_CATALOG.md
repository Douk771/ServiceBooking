# Каталог функциональных тест-кейсов

Этот документ — человеко-читаемое описание всех функциональных (интеграционных) тестов проекта, расположенных в `ServiceBooking.Tests/Tests/`. Тесты гоняются против настоящего HTTP-конвейера приложения и реальной изолированной базы `servicebooking_test` (см. `ServiceBooking.Tests/Infrastructure/`), а не моков.

## Как устроены ссылки на тесты

Каждый тестовый метод помечен атрибутом `TestCase("PREFIX-NNN")`, например:

```csharp
[Fact, TestCase("BK-003")]
public async Task GuestBooking_OnFreePlanCompany_ReturnsPaymentRequired() { ... }
```

Id **не привязан к номеру строки в файле** — он не меняется, если тест переместить, переименовать соседние методы или отрефакторить класс. Поэтому в этом документе нет ссылок вида `файл.cs:123`: они бы протухали при любой правке теста. Вместо этого, чтобы найти тест по id, используйте поиск по строке — она встречается в коде ровно один раз:

```bash
grep -rn "BK-003" ServiceBooking.Tests/
```

Для `[Theory]`-тестов (параметризованных через `[InlineData]`) один id покрывает все наборы данных сразу — атрибут стоит один раз на методе, а не на каждом случае.

Сам класс атрибута — `ServiceBooking.Tests/Infrastructure/TestCaseAttribute.cs`. Он не влияет на выполнение тестов (xUnit его не использует), это чисто документационная метка.

## Auth

### POST /api/auth/register

Регистрация и вход теперь **по номеру телефона** (телефон — идентификатор аккаунта, `UserName == phone`); email необязателен.

**Цикл 2 (US-26) — BREAKING № 4.** Всё, что возвращается в `AuthResponseDto.Phone`, теперь **канон**
(только цифры), а не строка «как ввели». `AUTH-001` и `AUTH-004` переписаны: сравнение с исходным
`phone` заменено на сравнение с `PhoneNormalizer.Normalize(phone)`. Функциональные сценарии «один и тот
же номер в разных форматах — один аккаунт» покрыты `CO-`-тестом на автосоздание мастера (тот же
`PhoneNormalizer`, тот же результат) и юнитами `PhoneNormalizerTests`; отдельного `AUTH-`-теста на
«регистрация 8999… + вход +7999… — один аккаунт» не заводилось отдельно от `PhoneNormalizerTests`,
поскольку правило одно и то же и уже покрыто на уровне чистой функции — предложение для qa-engineer:
добавить сквозной `AUTH-0xy`-сценарий именно на двух РАЗНЫХ форматах при регистрации/входе одного и
того же пользователя, если нужна дополнительная end-to-end гарантия поверх юнитов.

#### AUTH-001 — Регистрация с валидными данными возвращает токен и роль Client

Анонимный запрос регистрирует нового пользователя с именем, телефоном и паролем (без email). Ожидается 200 OK, непустой токен, `phone` в ответе — канонический вид отправленного номера (US-26), `email` — `null`, а единственная присвоенная роль — «Client».

#### AUTH-002 — Повторная регистрация с уже занятым телефоном возвращает 400

Пользователь уже зарегистрирован с определённым телефоном. Повторная попытка регистрации с тем же телефоном (другой пароль) должна вернуть 400 Bad Request — телефон является уникальным идентификатором аккаунта.

#### AUTH-003 — Регистрация с некорректными данными возвращает 400 (параметризованный тест)

Проверяются два случая: пустой телефон и слишком короткий пароль («short»). В обоих случаях регистрация должна быть отклонена с 400 Bad Request.

### POST /api/auth/login

#### AUTH-004 — Вход с верными учётными данными возвращает токен

Пользователь регистрируется, затем логинится тем же телефоном и паролем. Ожидается 200 OK и `phone` в ответе, совпадающий с переданным.

#### AUTH-005 — Вход с неверным паролем возвращает 401

Зарегистрированный пользователь пытается войти с заведомо неправильным паролем. Ожидается 401 Unauthorized.

#### AUTH-006 — Вход с несуществующим телефоном возвращает 401

Попытка входа с телефоном, который никогда не регистрировался, возвращает 401 Unauthorized (без утечки информации о том, существует аккаунт или нет).

#### AUTH-007 — После пяти неудачных попыток входа аккаунт временно блокируется

Пользователь регистрируется, затем пять раз подряд вводит неверный пароль. После этого даже ПРАВИЛЬНЫЙ пароль отклоняется с 401 Unauthorized — сработала блокировка ASP.NET Identity по количеству неудачных попыток (действует в течение окна блокировки).

### Защищённые эндпоинты (на примере GET /api/profile)

#### AUTH-008 — Запрос к защищённому эндпоинту без токена возвращает 401

Анонимный запрос к `GET /api/profile` (требует `[Authorize]`) без заголовка Authorization возвращает 401 Unauthorized.

#### AUTH-009 — Запрос к защищённому эндпоинту с испорченным токеном возвращает 401

В заголовок Authorization подставляется заведомо невалидная строка (не настоящий JWT). Запрос к `GET /api/profile` должен вернуть 401 Unauthorized — токен не проходит валидацию подписи/формата.

#### AUTH-010 — Запрос к защищённому эндпоинту с валидным токеном проходит успешно

Свежезарегистрированный пользователь обращается к `GET /api/profile` со своим настоящим токеном. Ожидается 200 OK — базовая проверка, что весь конвейер аутентификации (выпуск токена → валидация на защищённом эндпоинте) работает целиком, а не только по отдельности.

#### AUTH-011 — Токен, выданный до смены пароля, отзывается после `POST /api/profile/change-password`

`ChangePasswordAsync` ротирует `AppUser.SecurityStamp`; тот же, ни разу не перевыпущенный токен перестаёт проходить (401) на `GET /api/profile`, потому что `sstamp`-клейм внутри него больше не совпадает с текущим штампом (US-17).

#### AUTH-012 — Токен, выданный после смены пароля, работает

Новый логин после смены пароля даёт токен с актуальным `sstamp` — `GET /api/profile` отвечает 200.

#### AUTH-013 — Токен, выданный до смены телефона, отзывается после `POST /api/profile/change-phone`

`SetUserNameAsync` (используется при смене телефона) тоже ротирует `SecurityStamp` — тот же эффект отзыва, что и при смене пароля.

## Bookings

Этот файл — «дымовой» тест сквозного сценария бронирования: компания → мастер → услуга → рабочее время → запись. Он же служит первой проверкой общего тестового каркаса (`ApiTestBase`), на который опираются остальные ~175 тестов.

### POST /api/bookings — базовый сценарий

#### BK-001 — Авторизованный клиент успешно бронирует свободный слот

Готовится полная цепочка: владелец → компания → мастер → услуга (60 минут, 1500) → рабочий день. Зарегистрированный клиент создаёт бронирование на 10:00. Ожидается 201 Created, статус брони — Confirmed, ClientId совпадает с клиентом, а конец слота (11:00) корректно вычислен из длительности услуги.

#### BK-002 — Повторное бронирование того же слота возвращает конфликт

Один клиент успешно бронирует слот 14:00 у мастера (201 Created). Второй клиент пытается забронировать тот же слот у того же мастера в ту же дату — ожидается 409 Conflict.

### Гейтинг тарифа Free для онлайн-бронирования

#### BK-003 — Гостевое бронирование на бесплатном тарифе отклоняется с 402

Компания создаётся с `allowSelfBooking: true`, но остаётся на бесплатном тарифе (`onlineBooking: false`). Неавторизованный гость пытается создать бронирование, указывая имя и телефон — ожидается 402 Payment Required.

#### BK-004 — Самостоятельное бронирование авторизованным клиентом на бесплатном тарифе тоже отклоняется с 402

Та же бесплатная компания. На этот раз бронирует зарегистрированный и авторизованный клиент сам за себя (без `guestName`) — и всё равно получает 402 Payment Required. Это ключевое отличие от прежнего поведения: бесплатный тариф блокирует онлайн-самозапись независимо от того, гость это или авторизованный клиент — гейт не ограничивается только гостями.

#### BK-005 — Ручная запись сотрудником на бесплатном тарифе проходит успешно

Та же бесплатная компания. Мастер (авторизован) сам вносит запись для стороннего клиента, указывая его имя и телефон («Walk-in Client») — это ручная запись «с ресепшена», а не онлайн-самозапись. Ожидается 201 Created, ClientId в ответе — null, а имя клиента в ответе совпадает с переданным именем гостя. Единственное исключение из гейта тарифа Free — именно такая ручная запись сотрудником.

#### BK-006 — Гостевое бронирование на платном тарифе проходит успешно

Компании назначается подписка на тариф с включённым `AllowOnlineBooking`. Неавторизованный гость успешно создаёт бронирование (201 Created), ClientId — null, имя клиента в ответе совпадает с переданным именем гостя.

#### BK-007 — Гостевое бронирование при выключенном allowSelfBooking запрещено

У компании выключен флаг `allowSelfBooking`, хотя подписка платная (Pro). Гостевая попытка бронирования возвращает 403 Forbidden — платный тариф не отменяет запрет самостоятельной записи, если владелец явно его выключил.

### Жизненный цикл записи (мастер)

#### BK-008 — Мастер завершает запись, но не может перенести уже завершённую

Клиент бронирует слот, мастер отмечает бронирование выполненным (`complete`, 204 No Content). Попытка перенести (`reschedule`) уже завершённую запись должна вернуть 400 Bad Request — перенос допустим только для активных записей.

#### BK-009 — Посторонний мастер не может завершить чужую запись

В компании два мастера. Клиент бронирует запись к первому мастеру. Второй мастер той же компании пытается вызвать `complete` для этой чужой записи — ожидается 403 Forbidden.

#### BK-014 — Владелец компании может отменить запись, в которой он лично не мастер

Регрессионный тест: `cancel` раньше проверял только ClientId/MasterId/SuperAdmin, упуская ветку CompanyOwner, которая уже была у complete/noshow/mark-paid/reschedule — владелец, не будучи назначенным мастером записи, не мог отменить запись в собственной компании. Клиент бронирует запись к мастеру, владелец (не мастер записи) вызывает `cancel` — ожидается 204 No Content. Проверка владения для всех штатных операций теперь идёт через общий helper `CanManageBookingAsync`.

### Отмена, занятость слота и права доступа

#### BK-015 — Клиент отменяет свою запись, и слот снова доступен для бронирования

Отмена должна реально освобождать слот: проверка конфликта исключает записи со статусом Cancelled. Первый клиент бронирует слот 10:00 и отменяет его; второй клиент бронирует ровно тот же слот — ожидается 201 Created. Закрепляет ключевой инвариант, что отменённая запись не блокирует время.

#### BK-016 — Посторонний клиент не может отменить чужую запись

Клиент создаёт запись; другой зарегистрированный пользователь (ни клиент записи, ни мастер, ни владелец) пытается вызвать `cancel` — ожидается 403 Forbidden.

#### BK-017 — GET /api/bookings/occupied включает активную запись и исключает отменённую

**T-B16 (US-20, находка E3, решение Q9): эндпоинт больше не публичный.** `masterId` не секрет
(`GET /api/companies/{id}/masters` отдаёт id всех мастеров публично), поэтому анонимный доступ позволял
кому угодно вытянуть занятость любого мастера по всем его компаниям. Теперь требуется `[Authorize]` +
явное право: `SuperAdmin`, сам мастер, либо персонал хотя бы одной компании, где этот мастер тоже
состоит. Занятость по-прежнему считается по всем компаниям мастера (без `companyId`, намеренно —
решение Q9, совместитель физически один человек), поэтому мастер, обращающийся о себе (как в этом
тесте), продолжает получать `200`. Создаются две записи (9:00 и 12:00), вторая отменяется. Ответ содержит интервал активной записи (9:00) и не содержит отменённый интервал 12:00 — фильтр `Status != Cancelled` работает.

#### BK-018 — Перенос на занятый слот даёт конфликт, затем на свободный — успех

У мастера две записи (9:00–10:00 и 12:00–13:00). Попытка перенести вторую на 9:30 (пересекается с первой) даёт 409 Conflict; перенос на свободные 15:00 проходит (204 No Content), при этом EndTime пересчитывается из длительности услуги (16:00).

#### BK-044 — Анонимный вызов GET /api/bookings/occupied возвращает 401

Регрессия для находки E3: без токена — `401`, а не занятость мастера.

#### BK-045 — Посторонний авторизованный пользователь получает 403

Пользователь, не связанный ни с мастером, ни с его компанией. Ожидается `403`, тело пустое.

#### BK-046 — Мастер-совместитель видит интервалы из обеих своих компаний в одном ответе

Мастер состоит в компаниях A и B, в каждой у него есть запись на выбранную дату. Запрос от имени
самого мастера возвращает оба интервала в одном ответе — подтверждает, что кросс-компанийность выдачи
сохранена намеренно (решение Q9), несмотря на добавленную авторизацию.

#### BK-047 — Владелец компании, где состоит мастер, тоже получает 200

Пример роли за пределами «сам мастер» — персонал (`CompanyOwner`) той же компании, где мастер работает.

### Предоплата (опция владельца × тариф AllowOnlinePayment)

#### BK-019 — Самозапись при включённой предоплате и оплачиваемом тарифе создаётся Pending, mark-paid переводит в Paid

Полный жизненный цикл статуса оплаты: `RequirePrepayment` + тариф с `AllowOnlinePayment` → самостоятельная запись клиента создаётся со статусом `Pending`; мастер вручную подтверждает оплату через `mark-paid`, статус становится `Paid`.

#### BK-020 — Самозапись при включённой предоплате, но тарифе без онлайн-оплаты остаётся NotRequired

Владелец включил `RequirePrepayment`, но у тарифа нет `AllowOnlinePayment` — двойной гейт НЕ переводит запись в `Pending` (зеркалит `CompanyDto.PrepaymentEnabled`). Запись создаётся со статусом `NotRequired`.

#### BK-021 — Ручная запись сотрудника игнорирует предоплату даже при полностью включённой опции

Предоплата касается только онлайн-самозаписи: запись, внесённая сотрудником «с ресепшена» (`GuestName`), имеет статус `NotRequired`, даже когда включены и флаг компании, и флаг тарифа.

#### BK-022 — GET /api/bookings/{id}: владелец компании видит запись, посторонний клиент — нет

Владелец компании (не мастер записи и не клиент) успешно получает запись (200 OK) — доступ по управлению компанией; посторонний зарегистрированный пользователь получает 403 Forbidden.

### GET /api/bookings/slots

Регрессионное покрытие для бага в UI: экран сотрудника «Записать клиента» (ManualBookingModal.tsx) строил собственную фиксированную временную сетку и отфильтровывал только уже занятые бронированиями интервалы, ни разу не проверяя рабочие часы или перерывы мастера — из-за этого только что созданный перерыв всё равно показывался как доступный для записи. Исправление свело этот экран к тому же эндпоинту `/api/bookings/slots`, которым уже пользовался клиентский флоу онлайн-записи (BookingModal.tsx), унаследовав фильтрацию по перерывам и рабочим часам "бесплатно". Тесты ниже закрепляют, что сам этот общий эндпоинт генерации слотов действительно исключает перерывы, дни без рабочих часов и уже занятые бронированиями интервалы — раньше это не проверялось напрямую ни одним тестом.

**T-B3 (US-03/US-04/A4/A1).** Параметр `companyId` (`Guid`) стал **обязательным**: без него `400`
`application/problem+json` от автоматической валидации. Он используется дважды — скоупит `WorkingHours`
по компании (мастер-совместитель отдаёт расписание только запрошенной компании, находка A4) и решает,
кому верить флагу `manual=true` (только `SuperAdmin` или участник этой компании с ролью
`Master`/`CompanyOwner`, находка A1). Все существующие тесты этого раздела обновлены — они передают
`companyId` в query, поведение сеток слотов не изменилось.

#### BK-010 — Слоты, пересекающиеся с перерывом, исключаются, а слоты до и после него остаются

Мастеру выставляется рабочий день 09:00–18:00 с перерывом 13:00–14:00. Для 60-минутной услуги запрос слотов должен содержать слот с началом в 12:00 (заканчивается ровно к началу перерыва) и в 14:00 (начинается ровно по окончании перерыва), но не должен содержать слоты с началом в 12:30, 13:00 или 13:30 — каждый из них так или иначе пересекается с перерывом.

#### BK-011 — Слоты, пересекающиеся с уже существующим бронированием, исключаются

Клиент бронирует 60-минутную услугу на 11:00. Последующий запрос слотов на эту же дату не должен содержать слот с началом в 11:00, но должен содержать слоты в 10:00 и 12:00 — соседние часы, не пересекающиеся с занятым интервалом.

#### BK-012 — Список слотов пуст, если у мастера нет рабочих часов на эту дату

Для мастера намеренно не выставлялись рабочие часы на выбранную дату (в отличие от большинства других тестов, где `SetWorkingDayAsync` вызывается явно). Запрос слотов возвращает 200 OK с пустым списком, а не ошибку — SlotService.GetAvailableSlotsAsync явно проверяет случай отсутствия рабочего дня и возвращает `[]`.

#### BK-023 — Слот, выходящий за конец рабочего дня, не предлагается

Рабочий день 09:00–12:00, услуга 60 минут. Последний допустимый старт — 11:00 (заканчивается ровно в 12:00); старт в 11:30 закончился бы в 12:30, за пределами рабочего дня, поэтому он не должен быть в списке. Проверяется, что 11:00 присутствует, а 11:30 и любой слот с окончанием позже 12:00 — нет.

### GET /api/bookings/slots?manual=true

Регрессионное покрытие для бага, из-за которого сотрудник не мог вручную забронировать клиента на дату, для которой мастер ещё не выставил рабочие часы: ManualBookingModal.tsx пользовался тем же эндпоинтом `/api/bookings/slots`, что и гостевая онлайн-запись, а `SlotService.GetAvailableSlotsAsync` без явно выставленных рабочих часов всегда возвращал пустой список — вне зависимости от того, кто спрашивает. Флаг `manual` открывает для авторизованного вызывающего диапазон на весь день, если рабочих часов на дату нет; гостевая самостоятельная запись этот флаг никогда не отправляет, и её поведение не изменилось.

#### BK-024 — С флагом `manual=true` при отсутствии рабочих часов возвращается диапазон на весь день

Рабочие часы на дату намеренно не выставлены. Авторизованный запрос с `manual=true` для 60-минутной услуги должен содержать слот с началом в 00:00 и последний вмещающийся до полуночи слот с началом в 22:30 (заканчивается в 23:30) — слот с началом в 23:00 закончился бы ровно в 24:00, что `TimeOnly` представить не может, поэтому корректно исключается защитой от переполнения, а не падает с ошибкой.

#### BK-025 — С флагом `manual=true` уже занятые интервалы всё равно исключаются

Рабочие часы выставлены, клиент бронирует 60-минутную услугу на 11:00. Запрос слотов с `manual=true` не должен содержать слот с началом в 11:00, но должен содержать соседний слот в 9:00 — флаг открывает доступ к нерабочим часам, но не отменяет проверку конфликтов с существующими бронированиями.

#### BK-026 — Анонимный вызывающий не может обойти проверку рабочих часов через `manual=true`

`manual` — параметр, приходящий от клиента, поэтому учитывается только для действительно авторизованного вызывающего. Анонимный запрос с `&manual=true` на дату без рабочих часов всё равно возвращает пустой список, как и без этого параметра.

#### BK-042 — `manual=true` от аутентифицированного, но не состоящего в компании пользователя не открывает расписание

Закрывает A1: раньше `manual=true` от ЛЮБОГО авторизованного пользователя открывало полный день без учёта расписания. Теперь это работает только для персонала запрошенной компании — посторонний авторизованный пользователь получает тот же (пустой, при отсутствии рабочих часов) результат, что и гость.

#### BK-043 — Расписание мастера-совместителя не утекает между его компаниями

Закрывает A4: мастер состоит в двух компаниях, рабочие часы выставлены только в компании A. Запрос слотов с `companyId` компании A отдаёт непустую сетку, с `companyId` компании B — пустой список, хотя `masterId` один и тот же.

### Гонка при одновременном бронировании одного слота

#### BK-013 — Из пяти одновременных запросов на один и тот же слот успевает ровно один

Регрессионный тест на TOCTOU-гонку: проверка "слот свободен" и вставка записи раньше выполнялись без транзакции и без блокировки, поэтому два параллельных запроса могли оба пройти проверку и оба создать запись на один и тот же слот одного мастера. В отличие от BK-002 (последовательные запросы), здесь пять клиентов отправляют запрос на бронирование одного и того же слота одновременно через `Task.WhenAll`. Ожидается ровно один `201 Created` и четыре `409 Conflict` — `POST /api/bookings` теперь оборачивает проверку конфликта и вставку в транзакцию с Postgres advisory lock по ключу (мастер, дата), которая сериализует конкурентные запросы.

### POST /api/bookings — целостность создания (T-B14, US-13, US-05, находки A1/A2/A3)

Самая крупная задача цикла. Порядок проверок в `Create` теперь: компания существует (404, теперь и для
авторизованного) → определение `isStaff`/`isGuestPath` → гейты гостя (403 самозапись выключена, 400
капча, 400 имя/телефон) применяются к КАЖДОМУ, кто не является персоналом этой компании, даже если он
авторизован и прислал `guestName` (закрывает A1) → 402 тариф → услуга существует (404) → услуга
принадлежит этой компании (400, новое) → услуга активна (400, новое) → мастер — участник этой компании
(400, новое, закрывает A2) → дата/время не в прошлом и не переполняет сутки (409, новое, закрывает A3) →
внутри лока: для персонала (`isStaffManualBooking`) — только конфликт с другими записями (решение Q7);
для всех остальных — `SlotCalculator.IsSlotAllowed`, тот же код, что отдаёт `GET /api/bookings/slots`.
Тексты существующих 400/402/403/404/409 не изменились (риск R3); новые 400 не содержат подстрок
`captcha`/`name`/`phone`, чтобы не провалиться в чужую ветку фронтового маппера.

Заодно: `Program.cs` получил глобальный обработчик необработанных исключений — `500` теперь всегда
`application/problem+json` с `traceId` (см. SVC-016), но НЕ переписывает тела уже существующих
400/402/403/404/409.

#### BK-027 — Авторизованный вызывающий с несуществующим companyId получает 404

Раньше проверка компании выполнялась только в гостевой ветке — авторизованный вызывающий с плохим
`companyId` доходил до `SaveChangesAsync` и падал на нарушении FK (`500`). Теперь `404` для всех.

#### BK-028 — То же для владельца без подписки: 404, а не 402

Проверка существования компании должна идти РАНЬШЕ тарифного гейта — иначе вызывающий, который
случайно оказался владельцем без подписки, увидел бы вводящий в заблуждение `402` на опечатку в
`companyId`.

#### BK-032 — Клиент с guestName в компанию с выключенной самозаписью получает 403

Закрывает A1: раньше `guestName` в одиночку превращал любого авторизованного клиента в «персонал» и
пропускал все гостевые гейты. Клиент, не состоящий в компании, но приславший `guestName`, теперь
проходит ровно те же проверки, что и гость — включая `Company.AllowSelfBooking`.

#### BK-033 — То же на бесплатном тарифе — 402

Тот же клиент на компании с `onlineBooking: false` получает `402`, как и обычный гость/клиент без
`guestName` — тарифный гейт больше не обходится одним лишь присутствием `guestName`.

#### BK-050 — Авторизованный клиент не может записаться при выключенной самозаписи

`AllowSelfBooking = false`, записывается залогиненный клиент сам на себя (без `guestName`).
Ожидается `403`. До правки переключатель проверялся только в гостевой ветке, поэтому авторизованный
клиент обходил его прямым вызовом API — тот же класс обхода, что закрывала находка A1.

#### BK-051 — Ручная запись персонала не блокируется выключенной самозаписью

`AllowSelfBooking = false`, запись создаёт мастер компании с `guestName`. Ожидается `201`:
переключатель управляет публичной витриной, а не рабочим инструментом персонала.

#### BK-049 — Гостевая запись в компанию с предоплатой получает Pending

#### BK-040 — Время не на 30-минутной сетке (10:07) даёт 409

#### BK-041 — Перенос (`Reschedule`) в прошедшую дату даёт 409

только для персонала (`CanManageBookingAsync`: мастер, `CompanyOwner` компании или `SuperAdmin` — клиент
переносить свою запись не может вообще), поэтому по решению Q7 к нему применяется правило персонала
(не в прошлом + нет пересечения), а не полная валидация против расписания. Полная валидация сломала бы
`RescheduleModal`, чья сетка 08:00–21:00 не знает о рабочих часах мастера.

### GET /api/bookings/client?status= (T-B15, US-07)

Фильтр переписан на общую чистую функцию `BookingFilters.TryParseClientStatus`/`BookingFilters.Upcoming`
(юниты — `BookingFiltersTests.cs`). Раньше `Enum.TryParse<BookingStatus>(status, out var s)` без
`ignoreCase` молча игнорировал `upcoming` (единственное значение, которое реально шлёт фронт), а также
статусы в нижнем регистре; любой неизвестный текст тоже проглатывался без ошибки. Теперь: `upcoming` в
любом регистре фильтрует на `Confirmed`/`Pending` с датой в будущем (строго позже `now`); имя статуса в
любом регистре и числовое значение enum продолжают фильтровать, как раньше; всё остальное — `400`
`"Unknown status filter. Expected: upcoming, Pending, Confirmed, Cancelled, Completed, NoShow."`.

#### BK-029 — status=upcoming возвращает только будущие Confirmed/Pending записи

Клиент имеет одну прошедшую (заведённую напрямую через scope — публичный `Create` больше не принимает
прошедшую дату, см. T-B14) и одну будущую запись. `?status=upcoming` возвращает только будущую.

#### BK-030 — status=Completed и status=Cancelled фильтруют как раньше (регрессия)

Одна запись переведена в `Completed`, другая отменена. Каждый фильтр возвращает ровно свою запись —
поведение для явных статусов не изменилось.

#### BK-031 — Неизвестный статус возвращает 400

`?status=garbage` — `400` с точным текстом из контракта, вместо тихого игнорирования фильтра.

### Флаг onlineBookingEnabled

#### CO-007 — Бесплатный тариф: онлайн-бронирование выключено, даже если allowSelfBooking включён

Компания создаётся с `allowSelfBooking: true`, но на бесплатном тарифе (`onlineBooking: false`). При запросе компании по slug `AllowSelfBooking` должен быть `true`, а `OnlineBookingEnabled` — `false`, так как флаг должен отражать реальную возможность бронирования (иначе клиентский UI позволит начать бронирование, которое завершится ошибкой 402).

#### CO-008 — Платный тариф с включённым self-booking: онлайн-бронирование доступно

Компании с `allowSelfBooking: true` назначается подписка на тариф с `AllowOnlineBooking = true`. Запрос компании по slug должен вернуть `OnlineBookingEnabled: true`.

#### CO-009 — Платный тариф, но self-booking выключен: онлайн-бронирование всё равно недоступно

Компании с `allowSelfBooking: false` назначается подписка на тариф с `AllowOnlineBooking = true`. `OnlineBookingEnabled` должен остаться `false` — одного платного тарифа недостаточно, обязательно нужен ещё и включённый `allowSelfBooking`.

#### CO-010 — Истёкшая платная подписка отключает онлайн-бронирование

Компании назначается тариф с `AllowOnlineBooking = true`, но с датой окончания оплаты (`paidUntil`) в прошлом (вчера). `OnlineBookingEnabled` должен быть `false` — проверка совпадает с той же логикой истечения срока, которую применяет эндпоинт бронирования перед созданием гостевого бронирования.

#### CO-011 — Список компаний корректно отражает флаг для каждой компании отдельно

Создаются две компании: одна на бесплатном тарифе (без привязанного тарифа) с `allowSelfBooking: true`, другая — с тарифом, у которого `AllowOnlineBooking = true`. Запрос `GET /api/companies` должен вернуть список, где у бесплатной компании `OnlineBookingEnabled = false`, а у платной — `true`.

#### CO-052 — Список «моих компаний» отражает флаг AllowAnalytics для каждой компании

Владелец без подписки (бесплатный тариф) и владелец с активной подпиской на полнофункциональный тестовый тариф запрашивают `GET /api/companies/my`. У бесплатной компании `AllowAnalytics` должен быть `false`, у платной — `true`. Это поле нужно фронтенду, чтобы скрывать вкладку «Отчёты» вместо показа страницы, которая тихо получает 402.

### Отображение в общем списке (опция владельца × гейт тарифа)

#### CO-053 — Компания скрывается из общего списка при отказе владельца от размещения

Владелец на полнофункциональном платном тарифе выключает `showInPublicListing` через `PUT /api/companies/{id}`. Публичный `GET /api/companies` больше не содержит эту компанию — собственный отказ владельца работает независимо от тарифа и не может быть «перекрыт» им.

#### CO-054 — Компания скрывается из общего списка, если тариф не разрешает размещение

Владелец хочет быть в списке (`showInPublicListing` по умолчанию true), но аккаунту назначен тариф с `AllowPublicListing = false`. Публичный список не содержит компанию — для попадания в общий список нужны оба условия сразу.

#### CO-055 — Прямая ссылка по slug работает даже для скрытой из списка компании

Компания скрыта из общего списка (`showInPublicListing = false`), но `GET /api/companies/{slug}` по-прежнему возвращает 200 OK — гейт закрывает только каталог (`GET /api/companies`), а не собственную страницу компании.

#### CO-056 — «Мои компании» продолжают показывать скрытую из списка компанию

Владелец скрывает компанию из общего списка, но `GET /api/companies/my` по-прежнему её содержит, при этом `ShowInPublicListing = false` и вычисляемый `PublicListingEnabled = false` — кабинет владельца не каталог, скрытые компании из него не пропадают.

### Онлайн-оплата (опция владельца × гейт тарифа)

Владелец без подписки включает `requirePrepayment` — в ответе `RequirePrepayment = true`, но вычисляемый `PrepaymentEnabled = false` (Free не разрешает онлайн-оплату). После назначения тарифа с `AllowOnlinePayment = true` тот же флаг в `GET /api/companies/my` становится `true`. ### POST /api/companies/{id}/logo

#### CO-058 — Загрузка корректного изображения устанавливает LogoUrl под /uploads/

Владелец отправляет multipart-файл с Content-Type `image/jpeg`. Ответ 200 OK, `LogoUrl` в DTO непустой, начинается с `/uploads/companies/` и заканчивается `.jpg` — файл сохранён на диск сервера и раздаётся статикой.

Владелец загружает логотип дважды. Первый файл доступен по статике (`GET` возвращает 200). После второй загрузки URL меняется, новый файл отдаётся (200), а старый удалён и теперь возвращает 404 — прежний файл на диске подчищается при замене.

и CO-061 используют реально декодируемые изображения (`TestImages`, SkiaSharp) вместо байтов-заглушек
`0xFF 0xD8 0xFF 0xD9`, которых до этого цикла было достаточно (проверялся только `Content-Type`).

#### CO-074 — Content-Type врёт про формат, реальное содержимое — не изображение → `400`

Регрессия на новый загрузчик: раньше такой файл принимался (проверялся только заголовок).

#### CO-075 — Сигнатура настоящая (JPEG magic bytes), но файл не декодируется → `400`

Два независимых шага пайплайна (ARCHITECTURE.md §4.1, шаги 5 и 8): сигнатура отсекает подмену формата,

### GET /api/companies/{id}/masters

### PUT /api/companies/{id}/members/{memberId}/services

**T-B11 (US-16, находка B2).** Перед любыми изменениями (до `RemoveRange`) проверяется, что каждый
присланный `serviceId` существует и принадлежит компании `{id}`. Раньше владелец компании A мог
привязать своего мастера к услугам компании B, а несуществующий `Guid` давал `500` от нарушения FK
— теперь оба случая дают `400` `"One or more services do not belong to this company."`, и правка
атомарна (ни одна связка не создаётся/не удаляется при отказе).

#### CO-019 — Владелец обновляет список услуг мастера, изменения видны в /members

Владелец назначает мастеру одну услугу через `PUT .../services`. Ожидается `NoContent`, а последующий запрос списка участников должен показать, что у мастера теперь ровно одна услуга — назначенная.

#### CO-020 — Обновление услуг мастера посторонним пользователем запрещено

Случайный пользователь пытается вызвать `PUT .../services` для чужого мастера. Ожидается `Forbidden`.

#### CO-069 — Услуга чужой компании в списке отклоняется, существующие привязки не трогаются

Мастеру уже назначена одна «своя» услуга. Владелец пытается заменить список услугой, которая

### GET /api/companies/{id}/stats

**T-B12 (US-18, решение Q11, находка B5).** Фильтр переведён с `b.CreatedAt` на `b.Date` — дата
**визита**, а не дата создания строки — совпадает с `GET /api/reports/masters`, который уже фильтровал
по `Date`. Раньше запись, созданная 30 июня на визит 5 июля, попадала в отчёт «за июнь» и рисовалась
столбиком на 5 июля — вне выбранного диапазона; два отчёта в одном UI могли показывать разные цифры за
один период. `newClientsCount` тоже переведён на `Min(b.Date)` (ARCHITECTURE.md §14.3) — иначе внутри
одного ответа остались бы две разные семантики даты. `from`/`to` стали `DateTime?`: отсутствие любого —
`400` `"Both 'from' and 'to' are required."`; `to < from` — `400`
`"Invalid date range: 'to' must not be earlier than 'from'."`.

#### CO-043 — Статистика агрегирует выручку и количество бронирований для владельца

**Переформулирован в T-B12**: диапазон `from`/`to` теперь покрывает дату **визита** (`NextWeekday()`),
а не момент вызова. Создаются мастер, услуга (цена 2500) и рабочий день; клиент создаёт бронирование,
которое мастер завершает (`complete`). Владелец запрашивает статистику за период, покрывающий дату
визита. Ожидается 200 OK, `TotalRevenue = 2500`, `BookingsCount = 1`, `CompletedCount = 1`.

#### CO-044 — Запрос статистики посторонним пользователем запрещён

Пользователь, не связанный с компанией, запрашивает `GET /api/companies/{id}/stats`. Ожидается `Forbidden`.

#### CO-071 — Фильтр по дате визита совпадает с GET /api/reports/masters за тот же период

Запись создаётся «сейчас» (`CreatedAt`), но визит — через несколько дней (`Booking.Date`). Запрос
статистики за период, покрывающий именно дату визита, находит запись и даёт ту же сумму выручки, что
`GET /api/reports/masters` за тот же диапазон, — оба эндпоинта теперь согласованно читают `Date`.

#### CO-072 — Вызов без `from`/`to` возвращает 400

`GET /api/companies/{id}/stats` без query-параметров. Ожидается `400` `"Both 'from' and 'to' are required."`.

#### CO-073 — `to < from` возвращает 400

Явно некорректный диапазон. Ожидается `400` `"Invalid date range: 'to' must not be earlier than 'from'."`.

### POST /api/companies/{id}/members — лимит сотрудников по тарифу

Тариф — это подписка **аккаунта владельца**, а не отдельной компании (см. `AccountSubscription`); лимит сотрудников (`MaxEmployees`) резолвится через владельца компании и считает ВСЕХ участников (владелец уже занимает одно место). Без подписки действует ограничительный baseline Free: `MaxEmployees = 1`.

#### CO-045 — Добавление сотрудника при достигнутом лимите тарифа возвращает 402

Владелец компании уже сам является одним `CompanyMember` (создаётся автоматически вместе с компанией). Аккаунту назначается тестовый тариф с `MaxEmployees = 1` — лимит уже исчерпан одним владельцем. Попытка добавить ещё одного сотрудника (`POST /api/companies/{id}/members`) должна вернуть 402 Payment Required, а не создать сотрудника сверх лимита.

#### CO-046 — Добавление сотрудника в пределах лимита тарифа проходит успешно

Та же ситуация, но тарифу назначен `MaxEmployees = 2` — под лимитом с учётом владельца. Добавление сотрудника проходит успешно (200 OK).

#### CO-047 — Без подписки нельзя добавить даже первого мастера (Free = 1 сотрудник)

Аккаунт владельца вообще без подписки (`attachPlan: false`) → ограничительный baseline Free с `MaxEmployees = 1`. Владелец уже занимает единственное место, поэтому добавление даже первого мастера возвращает 402 Payment Required — до апгрейда тарифа компания состоит только из владельца.

### POST /api/companies — лимит компаний-филиалов по тарифу

Ограничение `MaxCompanies` — свойство аккаунта: при создании компании считается число компаний владельца против лимита его плана. Без подписки baseline Free = 1 компания (это и защищает от спама бесплатными компаниями). Блокируется только создание новых, существующие сверх лимита не трогаются.

#### CO-048 — Вторая компания на аккаунте без подписки возвращает 402

Владелец уже создал одну компанию (первая всегда проходит: 0 < 1). Аккаунт без подписки → Free с `MaxCompanies = 1`. Попытка создать вторую компанию (`POST /api/companies`) возвращает 402 Payment Required.

#### CO-049 — Создание компаний в пределах лимита тарифа, затем блок сверх него

У владельца уже 1 компания; аккаунту назначается тариф с `MaxCompanies = 2`. Создание второй компании проходит (201 Created), а третьей — отклоняется с 402 Payment Required.

### Гонка при одновременных запросах к лимиту тарифа

#### CO-050 — Из пяти одновременных запросов на добавление сотрудника лимит заполняется ровно нужным числом мест

Регрессионный тест на TOCTOU-гонку: подсчёт текущих участников и сравнение с `MaxEmployees` раньше выполнялись без блокировки, поэтому параллельные запросы могли все прочитать одно и то же (ещё не увеличенное) число участников, все пройти проверку и все создать запись — компания оказывалась сверх лимита мест. Владелец уже занимает одно место; тариф с `MaxEmployees = 2` оставляет ровно одно свободное. Пять кандидатов одновременно (`Task.WhenAll`) пытаются стать мастерами компании — ожидается ровно один `200 OK` и четыре `402 Payment Required`.

#### CO-051 — Из пяти одновременных запросов на создание компании лимит филиалов пропускает ровно одну

Та же TOCTOU-гонка, но для лимита `MaxCompanies` на аккаунт владельца. У владельца уже есть 1 компания; тариф с `MaxCompanies = 2` оставляет ровно одно свободное место. Пять параллельных запросов на создание новой компании — ожидается ровно один `201 Created` и четыре `402 Payment Required`.

### Сырые флаги возможностей тарифа (PlanAllows*, MaxEmployees)

В отличие от `OnlineBookingEnabled`/`PrepaymentEnabled`/`PublicListingEnabled` (которые уже совмещают собственный переключатель владельца с тарифом), эти поля должны отражать только тариф — форма настроек компании гасит (`disabled`) чекбокс, который тариф не поддерживает вовсе, а для этого нужно знать это независимо от текущего сохранённого значения переключателя владельца.

#### CO-063 — На бесплатном тарифе без подписки отдаются ограничительные флаги возможностей

У владельца вообще нет подписки → бесплатный базовый набор. `GET /api/companies/my` должен вернуть `PlanAllowsOnlineBooking = false`, `PlanAllowsOnlinePayment = false`, `PlanAllowsPublicListing = true`, `MaxEmployees = 1`.

#### CO-064 — С полнофункциональным тарифом отдаются разрешающие флаги возможностей

Компании назначается полнофункциональная подписка. `GET /api/companies/my` должен вернуть `PlanAllowsOnlineBooking = true`, `PlanAllowsOnlinePayment = true`, `PlanAllowsPublicListing = true`, `MaxEmployees = null` (без ограничения).

#### CO-065 — `PlanAllowsOnlinePayment` остаётся `true`, даже когда собственный переключатель владельца выключен

Ключевое отличие поля от совмещённого состояния: при полнофункциональном тарифе, но выключенном `RequirePrepayment`, `PrepaymentEnabled` (совмещённое) корректно равно `false`, а `PlanAllowsOnlinePayment` (сырая возможность тарифа) остаётся `true` — оно описывает, что разрешает тариф, а не то, что сейчас реально применяется.

### GET /api/services?companyId=

#### SVC-001 — Публичный список услуг компании не включает удалённые (soft-delete)

### POST /api/services

**T-B7 (US-09, решение Q1).** Каталог услуг теперь редактирует только `CompanyOwner` (и `SuperAdmin`) —
из `CanManageCompany` убрана ветка `Master`. Чтение (`GET /api/services`) не изменилось: мастер по-прежнему
видит услуги компании для сценария `ManualBookingModal` (см. SVC-014). Также добавлена валидация
`CreateServiceDto`: `[MaxLength(200)]` на `Name`, `[MaxLength(2000)]` на `Description`, `[Range(1,1440)]`
на `DurationMinutes`, `[Range(0,1_000_000)]` на `Price` — нарушение даёт `400 application/problem+json`.
Атрибуты стоят **прямо на параметрах** позиционного `record`, не как `[property: ...]` — на этом рантайме
(net8.0, `Microsoft.AspNetCore.App` 8.0.3) `[property: ...]` роняет модель-байндинг исключением
`InvalidOperationException` («validation metadata must be associated with the constructor parameter»).

#### SVC-014 — Мастер по-прежнему читает услуги компании (US-09, регрессия ManualBookingModal)

`GET /api/services?companyId=` не защищён и не менялся — мастер видит услуги компании точно так же, как
и до цикла. Это критерий готовности T-B7: сценарий «мастер выбирает услугу при ручной записи» не должен
сломаться сужением прав на запись.

#### SVC-015 — Услуга с `durationMinutes = 0` отклоняется валидацией (гипотеза E1 аудита)

Воспроизводит находку E1: при нулевой длительности интервал конфликт-проверки
(`b.StartTime < slotEnd && b.EndTime > startTime`) вырождается и не срабатывает никогда, позволяя сколько
угодно записей на одно и то же время. `[Range(1, 1440)]` на `CreateServiceDto.DurationMinutes` закрывает
это на уровне валидации: `POST /api/services` с `durationMinutes = 0` возвращает `400`.

#### SVC-016 — SuperAdmin создаёт услугу в несуществующей компании → 500 application/problem+json (T-B14, §6)

Вне скоупа US-09 (та история только про роль Master), но остаётся стабильной точкой проверки нового
глобального обработчика исключений: `SuperAdmin` проходит `CanManageCompany` безусловно, а
`ServicesController.Create` не проверяет существование компании, поэтому запрос доходит до
`SaveChangesAsync` и падает на FK `Services.CompanyId → Companies`. Раньше это была пустая `500`/
страница разработчика; теперь — `500` с `Content-Type: application/problem+json` и непустым `traceId`.

### POST /api/services/{id}/image (US-25, цикл 2)

#### SVC-017 — Владелец компании загружает картинку услуги, `imageUrl` обновляется

Публичный класс хранения, `wwwroot/uploads/services/` — та же карта прав, что у редактирования услуги.

#### SVC-018 — Мастер (не владелец) → `403`

Тот же предикат, что уже действует для создания/редактирования/удаления услуги (US-09, решение Q1).

#### SVC-019 — Неизвестная услуга → `404`

Существование проверяется до прав — как и в остальных методах `ServicesController`.

**Round 3 (code review BLOCKER).** `CreateServiceDto.ImageUrl` убран из `POST`/`PUT /api/services`
целиком — раньше клиент мог указать произвольный `ImageUrl` (например,
`/uploads/../../appsettings.Production.json`), а затем вызвать `POST /api/services/{id}/image`, чтобы
`FileStorage.DeletePublic(oldUrl)` удалил произвольный файл на диске. Теперь `imageUrl` устанавливается
и меняется ИСКЛЮЧИТЕЛЬНО через `POST /api/services/{id}/image` (то же самое уже верно для аватара и
логотипа компании), а `FileStorage.DeletePublic` сам по себе получил ту же проверку принадлежности
результата корню (`ResolveContained`), что раньше была только у `ResolvePrivatePath` — двойная защита:
даже если бы источник произвольного URL снова появился, `DeletePublic` больше не удалит файл вне
`wwwroot/uploads`. Покрыто юнитами `FileStorageTests` (4 кейса, path traversal через `../` и глубоко
вложенный путь) — все существующие вызовы `new CreateServiceDto(...)` в `ServicesTests.cs`/
`ReportsTests.cs`/`ApiTestBase.cs` обновлены под новую (пятипараметровую) сигнатуру.

## WorkingHours

**T-B1/T-B4 (US-04, находки A5/B3).** Предикат `CanManage` был дырявым: `requesterId == masterId`
пропускал вызывающего с ЛЮБЫМ `companyId`, если он указывал свой собственный `masterId`, независимо от
того, состоит ли он в этой компании вообще. Починка (общий запрос `CompanyMembership.IsStaffAsync`/
`IsOwnerAsync`) добавляет проверку членства и в эту ветку. `GET /api/workinghours` получил тот же
предикат (раньше не проверялся вовсе — WH-011/WH-012). `PUT` обёрнут в транзакцию + advisory lock
(ключ `working-hours:{masterId}:{companyId}:{date}`) — WH-017. В БД появился уникальный индекс
`(MasterId, CompanyId, Date)`.

### GET /api/workinghours

#### WH-001 — Пустой список, если записей рабочего времени ещё нет

Для мастера без единой записи рабочих часов запрашивается диапазон в 7 дней от ближайшего буднего дня. Ожидается 200 OK с пустым списком.

#### WH-002 — Записи в пределах диапазона возвращаются корректно

Для мастера задаётся один рабочий день (`SetWorkingDayAsync`). Запрос диапазона, включающего эту дату, должен вернуть ровно одну запись с этой датой и флагом `IsWorking = true`.

#### WH-011 — Посторонний аутентифицированный пользователь не может читать чужое расписание

`GET /api/workinghours` теперь защищён тем же предикатом, что и `PUT`/`DELETE` — раньше проверки не было вовсе, и любой залогиненный читал расписание любого мастера в любой компании. Ожидается `Forbidden`.

#### WH-012 — Мастер компании не может читать расписание другого мастера той же компании

Мастер, состоящий в компании с ролью `Master` (не `CompanyOwner`), пытается прочитать расписание коллеги. Ожидается `Forbidden` — членство в компании само по себе не даёт видеть чужие расписания, только своё (см. WH-013) или все, если ты `CompanyOwner`.

#### WH-013 — Мастер читает своё собственное расписание в своей компании

Мастер запрашивает `GET /api/workinghours` про себя же в компании, где состоит. Ожидается `200 OK`.

#### WH-014 — Владелец читает расписание своего мастера

`CompanyOwner` запрашивает расписание мастера своей компании. Ожидается `200 OK`.

#### WH-015 — Мастер не может выставить себе рабочие часы в компании, где не состоит (находка A5)

Ключевая регрессия для дыры A5: мастер компании A вызывает `PUT /api/workinghours` с `masterId` = свой
собственный, но `companyId` компании B, в которой он не состоит. Раньше это давало `200` и создавало
строку — теперь `Forbidden`, и последующий `GET` от имени владельца компании B подтверждает, что строка
не создана (пустой список).

#### WH-016 — Уволенный участник теряет доступ к своему расписанию

Мастер сохраняет расписание, затем владелец удаляет его из компании (`DELETE /api/companies/{id}/members/{memberId}`). Повторная попытка мастера сохранить своё расписание в этой компании возвращает `Forbidden` — предикат проверяет членство на КАЖДЫЙ запрос, а не разово.

#### WH-017 — Пять параллельных `PUT` на одну дату дают ровно одну строку (находка B3)

Регрессия на TOCTOU-гонку: раньше `Upsert` был check-then-act без транзакции и без блокировки. Пять
одновременных запросов (`Task.WhenAll`) на один и тот же `masterId`+`companyId`+`date` теперь все
получают `200 OK`, но прямой запрос к БД через scope подтверждает, что строка ровно одна — транзакция
+ `pg_advisory_xact_lock` (ключ `working-hours:{masterId}:{companyId}:{date}`) сериализует запросы, и
уникальный индекс `(MasterId, CompanyId, Date)` не даёт дублю появиться даже теоретически.

### PUT /api/workinghours

#### WH-003 — Мастер устанавливает свои рабочие часы с перерывом

Мастер сам вызывает `PUT /api/workinghours`, задавая рабочий день 9:00–18:00 с перерывом 13:00–14:00. Ожидается 200 OK, `MasterId` в ответе совпадает с мастером, а список перерывов содержит ровно один перерыв с заданными временами.

#### WH-004 — Владелец устанавливает рабочие часы мастера

Владелец (не сам мастер) задаёт рабочие часы мастера 10:00–16:00. Ожидается 200 OK с соответствующими `StartTime`/`EndTime` в ответе — то есть владелец компании тоже вправе управлять расписанием мастера.

#### WH-005 — Установка рабочих часов посторонним аутентифицированным пользователем запрещена

Случайный пользователь, не связанный с компанией, пытается задать рабочие часы мастера. Ожидается `Forbidden`.

#### WH-006 — Повторный вызов на ту же дату обновляет существующую запись и полностью заменяет перерывы

Мастер сначала сохраняет рабочий день 9:00–17:00 с перерывом 12:00–13:00, затем повторно сохраняет ту же дату с часами 10:00–19:00 и без перерывов. Ожидается, что `Id` записи не изменился (это обновление, а не дубликат), новые часы применены, список перерывов пуст, а при запросе списка за эту дату возвращается ровно одна запись (не две).

### DELETE /api/workinghours/{id}

#### WH-007 — Владелец успешно удаляет запись рабочих часов

Владелец удаляет запись рабочего дня мастера через `DELETE /api/workinghours/{id}`. Ожидается `NoContent`.

#### WH-008 — Сам мастер тоже может удалить свою запись рабочих часов

Мастер удаляет собственную запись рабочего дня. Ожидается `NoContent` — право удаления не ограничено только владельцем.

#### WH-009 — Удаление записи посторонним пользователем запрещено

Пользователь, не связанный с компанией, пытается удалить запись рабочих часов мастера. Ожидается `Forbidden`.

#### WH-010 — Удаление несуществующей записи возвращает 404

Запрос `DELETE /api/workinghours/{id}` со случайным `Guid` возвращает `NotFound`.

## ScheduleTemplate

**T-B1/T-B4 (US-04, находки A5/B3/B4).** Тот же дырявый предикат `CanManage`, что в `WorkingHoursController`
(буквальная копия), чинится тем же способом. `PUT` и `apply` обёрнуты в транзакцию + advisory lock
(`schedule-template:{masterId}:{companyId}` и `working-hours:{masterId}:{companyId}` соответственно).
`apply` получает потолок диапазона: `to < from` → `400`, диапазон свыше 366 дней → `400` (ST-014/ST-015).

### GET /api/schedule-template

#### ST-001 — Пустой список, если шаблон ещё не сохранён

Для нового мастера без сохранённого шаблона расписания запрашивается `GET /api/schedule-template`. Ожидается 200 OK с пустым списком.

### PUT /api/schedule-template

#### ST-002 — Сохранение шаблона на все 7 дней недели, GET возвращает ровно сохранённое

Владелец сохраняет шаблон на все 7 дней недели: будни (1–5) рабочие с 9:00 до 18:00, выходные (6–7) нерабочие. Ожидается 200 OK при сохранении, а последующий `GET` должен вернуть все 7 записей с правильными временами, номерами дней недели и корректным флагом `IsWorking` (true для будних, false для выходных дней).

#### ST-003 — Повторное сохранение с другим набором дней полностью заменяет старый шаблон

Сначала сохраняются два дня (понедельник и вторник, 9:00–18:00), затем шаблон перезаписывается одним днём (среда, 10:00–16:00). После второго сохранения `GET` должен вернуть ровно одну запись — за среду с новыми часами, старые дни должны полностью исчезнуть.

#### ST-004 — Сохранение шаблона посторонним аутентифицированным пользователем запрещено

Случайный пользователь, не связанный ни с компанией, ни с мастером, пытается сохранить шаблон расписания мастера. Ожидается `Forbidden`, так как `CanManage` разрешает это только SuperAdmin, самому мастеру или владельцу компании.

#### ST-005 — Получение шаблона посторонним аутентифицированным пользователем запрещено

Аналогично сохранению — посторонний пользователь пытается вызвать `GET /api/schedule-template` для чужого мастера. Ожидается `Forbidden`.

#### ST-006 — Применение шаблона посторонним аутентифицированным пользователем запрещено

Посторонний пользователь пытается вызвать `POST /api/schedule-template/apply` для чужого мастера и компании. Ожидается `Forbidden`.

#### ST-007 — Сам мастер может сохранить свой шаблон, даже не будучи владельцем компании

Мастер (не владелец) сохраняет собственный шаблон расписания. Ожидается 200 OK — правило `CanManage` явно допускает случай `requesterId == masterId`, то есть мастер управляет своим шаблоном сам.

#### ST-008 — SuperAdmin может сохранить шаблон для любого мастера и компании

SuperAdmin сохраняет шаблон расписания для мастера чужой компании. Ожидается 200 OK.

### POST /api/schedule-template/apply

#### ST-009 — Применение при отсутствии сохранённого шаблона возвращает 400

Владелец пытается применить шаблон (`apply`) для мастера, у которого шаблон ещё не сохранён. Ожидается `BadRequest`.

#### ST-010 — Применение к чистому диапазону дат создаёт рабочие часы, совпадающие с шаблоном

Сохраняется шаблон на все 7 дней (8:00–16:00, рабочие), затем применяется к диапазону из 7 дней начиная с ближайшего буднего дня. Ожидается 200 OK, а запрос рабочих часов на первую дату диапазона должен вернуть запись с `IsWorking = true` и часами 8:00–16:00, соответствующими шаблону.

#### ST-011 — Применение шаблона перезаписывает существующую запись рабочих часов, а не дублирует её

Для даты `from` заранее создаётся запись рабочих часов с часами 7:00–11:00, отличными от шаблона. Затем сохраняется шаблон для дня недели этой даты с часами 9:00–20:00 и выполняется `apply`. Ожидается, что после применения для этой даты существует ровно одна запись (не две) с обновлёнными часами 9:00–20:00 — то есть шаблон перезаписывает существующую запись, а не создаёт дубликат.

#### ST-012 — Получение шаблона посторонним по "себе как masterId" в чужой компании запрещено (находка A5)

Мастер компании A вызывает `GET /api/schedule-template` с `masterId` = свой собственный, но `companyId` компании B, где он не состоит. Раньше `requesterId == masterId` в одиночку давало доступ; теперь `Forbidden`.

#### ST-013 — Уволенный участник теряет доступ к `apply` своего шаблона

Мастер сохраняет шаблон, затем владелец удаляет его из компании. Повторный вызов `POST /api/schedule-template/apply` от имени мастера для той же компании возвращает `Forbidden`.

#### ST-014 — Диапазон `apply` свыше 366 дней отклоняется (находка B4)

Диапазон `to - from` больше 366 дней (≈1000 дней) без потолка приводил к ~350 тыс. итераций и такому же
числу отслеживаемых сущностей — риск падения процесса по памяти, причём (в связке с A5) от постороннего
пользователя. Теперь такой вызов сразу отклоняется `400 Bad Request` до входа в цикл применения.

#### ST-015 — `apply` с `to < from` отклоняется

Явно некорректный диапазон (конец раньше начала) возвращает `400 Bad Request` вместо тихого прохода с нулевым результатом.

## Reviews

**T-B5 (US-14, находка A6).** `booking.ClientId != null && booking.ClientId != userId` пропускал проверку
целиком для гостевых бронирований (`ClientId == null` для всего оффлайн-потока и ручных записей
персонала) — любой залогиненный пользователь, узнавший `bookingId` завершённой гостевой записи (она
возвращается гостю самим `POST /api/bookings`), мог опубликовать отзыв от своего имени в чужую компанию.
Условие исправлено на `booking.ClientId != userId` — гостевая запись отзыв теперь не принимает ни от
кого (RV-013). Отдельный механизм отзывов для гостей не добавляется (решение Q8).

### POST /api/reviews

#### RV-001 — Успешное создание отзыва владельцем завершённого бронирования

Готовится полный сценарий: владелец компании, мастер, услуга, рабочий день, клиент бронирует и мастер отмечает бронирование как Completed. Клиент, которому принадлежит бронирование, отправляет отзыв с оценкой 5 и комментарием. Ожидается 200 OK и непустой Id созданного отзыва.

#### RV-002 — Отзыв на ещё не завершённое бронирование отклоняется

Клиент создаёт бронирование, но оно остаётся в статусе Confirmed (мастер его не завершал). Попытка оставить отзыв на такое бронирование должна вернуть 400 Bad Request, так как отзыв разрешён только после завершения услуги.

#### RV-003 — Отзыв на несуществующее бронирование возвращает 404

Клиент отправляет запрос на создание отзыва, указывая случайный Guid бронирования, которого нет в системе. Ожидается 404 Not Found.

#### RV-004 — Повторный отзыв на то же бронирование возвращает конфликт

После успешного создания первого отзыва на завершённое бронирование, повторная попытка того же клиента оставить второй отзыв на то же бронирование должна вернуть 409 Conflict — один отзыв на бронирование.

#### RV-005 — Отзыв от чужого клиента на не своё бронирование запрещён

Бронирование принадлежит одному клиенту (ClientId проставлен, это не гостевая запись). Другой зарегистрированный пользователь пытается оставить отзыв на это чужое завершённое бронирование — ожидается 403 Forbidden.

#### RV-006 — Оценка вне диапазона 1-5 отклоняется

Параметризованный тест проверяет оценки 0, -1, 6 и 100 — все они вне допустимого диапазона 1-5. Для каждого значения запрос на создание отзыва к завершённому бронированию должен вернуть 400 Bad Request.

#### RV-007 — Граничные значения оценки 1 и 5 принимаются

Параметризованный тест проверяет, что крайние допустимые значения рейтинга — 1 и 5 — успешно принимаются сервером (200 OK), в отличие от значений, выходящих за границы диапазона.

### GET /api/reviews/can-review

#### RV-008 — У нового пользователя список бронирований, доступных для отзыва, пуст

Только что зарегистрированный пользователь без единого бронирования запрашивает список бронирований, которые он может оценить. Ожидается 200 OK и пустой список.

#### RV-009 — После завершения бронирования оно появляется в списке can-review, а после отзыва — исчезает

После завершения бронирования его Id появляется в списке "можно оставить отзыв" у клиента. После того как клиент оставляет отзыв, тот же бронинг должен пропасть из этого списка — то есть эндпоинт отражает актуальное состояние (уже отзыв оставлен или ещё нет), а не просто список завершённых бронирований.

### GET /api/companies/{companyId}/reviews

#### RV-010 — У компании без отзывов публичный список отзывов пуст

Для только что созданной компании без единого отзыва анонимный запрос списка отзывов компании возвращает 200 OK с пустым массивом.

#### RV-011 — Публичный список отзывов компании доступен без авторизации и отсортирован от новых к старым

Создаются два завершённых бронирования у одной компании с одним мастером и услугой, на каждое клиент оставляет отзыв (с задержкой между ними, чтобы CreatedAt точно отличались). Запрос делается без токена авторизации (эндпоинт должен быть публичным) и должен вернуть оба отзыва, при этом второй (более поздний) отзыв идёт первым в списке; также проверяется, что в записи присутствуют корректные имя мастера и название услуги.

#### RV-012 — Публичный список отзывов возвращает отзывы только своей компании

Отзыв, оставленный в одной компании, не должен попадать в публичный список отзывов другой компании. Создаются два завершённых бронирования в разных компаниях, на каждое оставлен отзыв. Запрос списка отзывов компании B содержит ровно один отзыв (для B) и не содержит отзыв компании A.

#### RV-013 — Отзыв на завершённую гостевую запись запрещён кому угодно (находка A6)

Гостевое бронирование (`ClientId == null`) доводится до статуса Completed. Любой залогиненный
пользователь (не только посторонний — вообще любой, включая того, кто узнал `bookingId` из ответа
`POST /api/bookings`) пытается оставить на него отзыв. Ожидается `403 Forbidden`, отзыв не создан.

## Masters

### GET /api/masters/clients

**T-B13 (US-22, решение Q10).** Правило «контакты клиента видны мастеру только 24 часа после визита»
снято целиком, без замены: `cutoff`, обе проверки `showContact` и все тернарные подстановки удалены —
`phone`/`email` отдаются мастеру всегда. Никакой существующий тест это правило не закреплял как
обязательное (см. прежний текст MC-002 ниже), поэтому регрессий нет; MC-012 — новый тест, закрепляющий
снятое ограничение.

#### MC-001 — Пользователь, не состоящий в компании, не может получить список её клиентов

Посторонний пользователь запрашивает список клиентов компании, к которой не имеет отношения — ожидается 403 Forbidden.

#### MC-002 — Мастер-участник компании получает сгруппированный список зарегистрированного клиента с числом визитов и контактами

Зарегистрированный клиент делает два бронирования у одного мастера. Список клиентов, запрошенный мастером, содержит одну запись на этого клиента с TotalVisits = 2, корректным именем и без GuestPhone. Телефон и email клиента показываются всегда (US-22, правило «видно только 24ч после визита» снято — см. MC-012). Также проверяется, что в ответе присутствует и корректно заполнено поле BookingSummaries (по 2 записи, статус Confirmed, верная услуга и дата) — это регрессионный тест: раньше поле полностью отсутствовало в ответе, хотя фронтенд (MasterClientsPage.tsx) безусловно вызывал на нём `.length`/`.map` при раскрытии истории визитов клиента, из-за чего страница падала при клике на любого клиента.

#### MC-003 — Гостевое бронирование группируется по телефону гостя

Гостевое бронирование (без учётной записи, с GuestName и телефоном) создаётся владельцем компании. В списке клиентов мастера находится запись, сгруппированная по GuestPhone: ClientId = null, имя равно имени гостя, TotalVisits = 1, телефон и email соответствуют указанным при бронировании.

#### MC-007 — BookingSummaries отражают текущий статус записей, включая переходы Confirmed → Completed/Cancelled, наряду с активными записями

У одного зарегистрированного клиента три бронирования у мастера. Первое мастер переводит в Completed, второе — в Cancelled, третье остаётся Confirmed (активная запись). Список клиентов мастера показывает TotalVisits = 3 и три записи в BookingSummaries с соответствующими статусами (Completed, Cancelled, Confirmed). Это напрямую покрывает новую панель истории клиента на экране «Мои записи» (MyBookingsPage.tsx), которая показывает полную историю визитов — включая ещё не завершённые записи — с бейджем статуса на каждой.

#### MC-008 — Заметка, добавленная при активной записи, остаётся видимой после того, как запись переходит в NoShow

Клиент бронирует запись к мастеру. Мастер добавляет заметку о клиенте, пока запись ещё активна (Confirmed) — заметка сразу видна в списке клиентов, а BookingSummaries содержит единственную запись со статусом Confirmed. Затем мастер отмечает эту запись как NoShow. При повторном запросе списка клиентов заметка по-прежнему присутствует, а BookingSummaries отражает новый статус (NoShow). Тест проверяет ключевое свойство новой функции «отзыв о клиенте»/истории на экране «Мои записи»: заметка не привязана к конкретному бронированию и не пропадает и не дублируется при смене статуса записи, через которую её открывали.

### POST /api/masters/clients/notes

#### MC-004 — Добавленная мастером заметка о клиенте появляется в его собственном списке клиентов

Клиент делает бронирование у мастера. Мастер добавляет текстовую заметку об этом клиенте через AddNoteRequest (с `companyId`). При последующем запросе списка клиентов этого мастера заметка присутствует в поле Notes соответствующей записи.

**Заметки о клиентах общие в рамках одной компании.** Заметка теперь привязана к компании (`ClientNote.CompanyId`), а не только к автору: любой мастер компании видит заметки коллег по тому же клиенту (например, при первом визите клиента к новому мастеру — чтобы видеть предыдущий контекст, а не начинать «вслепую»). Удалять заметку по-прежнему может только её автор. Заметки не пересекаются между разными компаниями.

#### MC-009 — Заметки о клиенте видны всем мастерам одной компании

Один и тот же клиент бронирует к двум мастерам компании. Мастер A пишет заметку о клиенте; мастер B, у которого тот же клиент есть в списке, видит эту заметку — общая история клиента в рамках компании.

#### MC-010 — Заметки не пересекаются между разными компаниями

Один клиент бронирует в двух разных компаниях (значит, присутствует в списках обеих). Заметка, оставленная в компании A, не должна появляться, когда клиент отображается в компании B — у разных бизнесов раздельные истории клиентов.

#### MC-011 — Добавление заметки не-участником компании запрещено

Только участник компании может внести заметку в её общую историю клиентов. Посторонний пользователь получает 403 Forbidden.

### DELETE /api/masters/clients/notes/{id}

#### MC-005 — Мастер может удалить собственную заметку

Мастер добавляет заметку (о госте по телефону) и затем удаляет её по Id — ожидается 204 No Content.

#### MC-006 — Другой мастер не может удалить чужую заметку, эндпоинт возвращает 404, а не 403

Мастер A добавляет заметку. Мастер B (другой мастер той же компании) пытается удалить эту заметку. Поскольку MastersController.DeleteNote ищет запись с условием `MasterId == userId`, чужая заметка просто не находится под чужим Id — в результате возвращается 404 Not Found, а не 403 Forbidden, хотя по смыслу это похоже на запрет доступа.

#### MC-012 — Визит более 24 часов назад всё равно показывает контакт (US-22, снятие правила)

Регрессия на снятое ограничение: бронирование задним числом (дата на 10 дней в прошлом, проставляется
напрямую через scope — публичный флоу никогда не создаёт запись в прошлом) больше не прячет `phone`/
`email` клиента от мастера. Раньше это ветвление физически не тестировалось (в старом варианте теста
было явное примечание, почему), потому что для этого требовался прямой доступ к БД — теперь, когда
правила больше нет, тест просто проверяет обратное: контакт виден всегда.

### Цикл 2 (US-07): заметка — объект, а не строка — **BREAKING № 1**

`notes: string[]` → `notes: ClientNoteDto[]`. `POST /api/masters/clients/notes` теперь возвращает `201`
с полным объектом заметки (было `200 { id }`); проверка прав ужесточена до `CompanyMembership.IsStaffAsync`
(было «любое членство», включая роль `Client`); право удаления расширено до «автор ИЛИ владелец компании»
(решение Q16), а изоляция между компаниями теперь даёт `403` персоналу той же компании и `404` персоналу
другой (ARCHITECTURE.md §21.4) — было единое `MasterId == userId → иначе 404` для обоих случаев.

#### MC-013 — Заметка, созданная из панели под записью, получает `bookingId`/`bookingDate`/`bookingServiceName`

`AddNoteRequest.BookingId` заполняется реальным `Guid` визита — ответ `201` содержит дату визита и
название услуги, подгруженные через `Booking.Service` без второго запроса с фронта.

#### MC-014 — `bookingId` из чужой компании — `400`

Визит из компании A передаётся при создании заметки в компании B — `Booking does not belong to this
company.`

#### MC-015 — Пустой текст заметки — `400`

`Note text is required.` — проверка руками в контроллере (не автовалидация `[ApiController]`), чтобы
тело осталось голой строкой, а не `ValidationProblemDetails` (API_CONTRACT.md §2.1).

#### MC-018 — Заметка без `clientId` и без `guestPhone` — `400` (round-3 code review finding, qa-engineer)

До этого исправления `AddNoteRequest` принимал заметку без единого идентификатора клиента (ни
`ClientId`, ни `GuestPhone`) — она успешно писалась в БД, но `GET /api/masters/clients` группирует
заметки только через `COALESCE(ClientId, GuestPhone)`, так что такая заметка становилась навсегда
невидимой («заметка-сирота»). Мастер шлёт `AddNoteRequest` с обоими полями `null` — ожидается `400
"Either clientId or guestPhone is required."`. Подтверждено откатом исправления в
`MastersController.cs` (тест падает с `201` вместо `400`) и живым прогоном приложения.

#### MC-019 — `clientId` постороннего пользователя без брони в этой компании — `400` (round-3 code review finding, qa-engineer)

Тот же раунд ревью: `ClientId` не проверялся вообще — любой сотрудник компании мог приложить заметку к
произвольному `AppUser.Id`, который никогда не бронировал в этой компании. Мастер шлёт `AddNoteRequest`
с `ClientId` только что зарегистрированного постороннего пользователя, у которого нет ни одной брони ни
в одной компании — ожидается `400 "Client is not associated with this company."` (то же правило «кто
считается клиентом компании», что уже используется в `GetClients`). Тест также проверяет, что заметка
не была молча записана и не всплывает потом в `GET /api/masters/clients` под чужим `clientId`.
Подтверждено откатом исправления (тест падает) и живым прогоном приложения.

#### MC-005/MC-016/MC-006/MC-017 — Права удаления по решению Q16

`MC-005` — автор удаляет свою заметку → `204`. `MC-016` — владелец компании удаляет чужую заметку → `204`
(новое право, было недостижимо). `MC-006` — коллега по той же компании, не автор и не владелец → `403`
(было `404` из-за старого условия `MasterId == userId` в самом `WHERE`). `MC-017` — персонал другой
компании → `404` (существование чужой заметки не подтверждается).

состояние из БД. Единственное исключение — SCH-007, которому нужен настоящий раннер: он точечно включает
планировщик через `WebApplicationFactory.WithWebHostBuilder` (по образцу `CaptchaService.IsEnforced`),
как и предполагает ARCHITECTURE.md §8.5 для тестов самого планировщика. Чистая арифметика «пора ли /
просрочена ли» покрыта юнитами `ScheduledTaskScheduleTests`.

- **SCH-001** — фото, у которого `CreatedAt` продвинут за пределы cutoff тарифа (`SixMonths`), удаляется
  задачей `photo-retention-cleanup`: строка пропадает из `ClientNotePhotos`, оба файла (полный и
  миниатюра) больше не открываются через `FileStorage.OpenPrivate`.
- **SCH-002** — тариф `Forever`: фото пятилетней давности после прохода задачи остаётся нетронутым.
- **SCH-003** — `AdvisoryLock.TryAcquireAsync` с одним и тем же ключом из двух независимых
  транзакций/подключений: первая получает лок, вторая немедленно получает `false` (не ждёт) —
  неблокирующее поведение, на которое опирается пропуск параллельного запуска (ARCHITECTURE.md §8.4).
- **SCH-004** — `GET /api/admin/scheduled-tasks` не-администратору → `403`.
- **SCH-005** — при заполненной строке `ScheduledTaskStates` эндпоинт отдаёт `lastSucceeded`,
  `lastSummary` и `isOverdue = false` для недавнего успешного прохода.
- **SCH-006** — задача, для которой строки в `ScheduledTaskStates` вовсе нет (никогда не запускалась):
  `lastStartedAt = null`, `isOverdue = true`.
- **SCH-007** (code review finding, SPEC US-21 п.3/п.14, «падающая задача не роняет соседей») —
  запускает настоящий `ScheduledTaskRunner` на отдельном хосте с укороченным тиком (1 с) и вторым,
  тестовым `IScheduledTask`, который безусловно бросает исключение, зарегистрированным рядом с боевым
  `photo-retention-cleanup`. Ожидание: у бросающей задачи `LastSucceeded = false` и заполненный
  `LastError`; у `photo-retention-cleanup` в том же цикле тика `LastSucceeded = true` (сосед отработал,
  несмотря на падение первой); сам хост остаётся живым и отвечает на обычный HTTP-запрос после этого.
  **Round 3 (code review finding, изоляция):** `Storage:PrivateRoot` для этого отдельного хоста
  переопределён на одноразовый временный каталог (`WithWebHostBuilder` + `UseSetting`), а не указывает на
  общий корень — до этого исправления настоящий `photo-retention-cleanup`, работавший до 20 с внутри
  этого теста, мог удалить файлы, от которых зависят другие тесты этого набора (или тесты, выполняющиеся
  параллельно/после), из общего `App_Data/private-uploads`. Каталог удаляется в `finally` после теста.
- **SCH-008** (QA-блокер после ревью round 3, SPEC US-20 п.6/US-21 пп.8-9, «уборка файлов-сирот»)
  — файл записывается напрямую через `FileStorage.SavePrivateAsync` (в обход эндпоинта загрузки, поэтому
  строки `ClientNotePhotos` для него никогда не существовало — ровно документированный «худший случай»:
  сбой между записью файла и коммитом строки, либо удаление, снёсшее строку, но не один из двух файлов),
  затем его `mtime` искусственно отодвигается на 25 часов назад (за `OrphanMinAge` = 24ч). До фикса:
  `DeleteOrphanFilesAsync` падал `InvalidOperationException` на КАЖДОМ прогоне, как только на диске
  существовал хотя бы один файл-сирота — `db.ClientNotePhotos... .SelectMany(p => new[] { p.StoragePath,
  p.ThumbnailPath })` внутри LINQ-to-SQL запроса не транслируется EF Core/Npgsql. Фикс: `Select` в
  анонимный тип материализует пары путей через `ToListAsync`, `SelectMany` разворачивает их в плоский
  список уже в памяти. Тест проверяет: `ExecuteAsync` не бросает и возвращает `Affected >= 1`; файл
  физически удалён с диска.
- **SCH-009** (соседний тест на risk R3, чтобы фикс SCH-008 не превратился в «удалять вообще все файлы
  без строки») — файл-сирота с mtime «только что» (моложе `OrphanMinAge`) остаётся нетронутым: неотличим
  от файла, который прямо сейчас пишет ещё не закоммиченная загрузка.

**Найдено QA (финальный прогон цикла 2, БЛОКЕР) — уборка файлов-сирот падает всегда, тестов на неё нет
вообще.** Ни один из тестов выше не создаёт файл-сироту (файл на диске без строки в БД,
`PhotoRetentionCleanupTask.DeleteOrphanFilesAsync`) — вся эта ветка ни разу не выполнялась ни
автотестами, ни ручным ревью. Живой прогон (`ASPNETCORE_ENVIRONMENT=Testing`, реальная БД, файл положен
вручную под `Storage:PrivateRoot` с `mtime` старше 24 часов, задача запущена с укороченным периодом)
показал, что `DeleteOrphanFilesAsync` **падает при первом же файле-кандидате**:
`db.ClientNotePhotos.Where(...).SelectMany(p => new[] { p.StoragePath, p.ThumbnailPath })` —
LINQ-выражение `SelectMany(p => new string[] { ... })` не транслируется Npgsql/EF Core в SQL и бросает
`System.InvalidOperationException` в рантайме (`PhotoRetentionCleanupTask.cs:155-158`). Следствия: весь
проход задачи помечается `lastSucceeded = false` в `GET /api/admin/scheduled-tasks` с полным
стектрейсом в `lastError`, файл-сирота не удаляется и остаётся до следующего прохода — который упадёт
точно так же, бесконечно. Приложение не падает (изоляция задач работает, это отдельная гарантия, её
подтверждает SCH-007), но сама уборка сирот не работает НИКОГДА, пока на диске есть хотя бы один такой
файл — а SPEC (US-20 п.6, US-21 п.9) прямо рассчитывает на неё как на страховочную сеть для ровно этого
сценария. Не мой участок — чинит backend-developer (вероятный фикс: материализовать пары путей через
`.Select(p => new { p.StoragePath, p.ThumbnailPath }).ToListAsync()`, затем разворачивать в `List<string>`
уже в памяти, а не через `SelectMany` внутри LINQ-to-SQL). После фикса нужен новый функциональный тест
на этот путь — сейчас его нет.

### Статистика

#### ADM-008 — Статистика отражает новую компанию и новое бронирование

Супер-админ снимает срез статистики (`before`), затем создаётся новая компания с владельцем, мастером и услугой, назначается рабочий день мастеру, и клиент создаёт бронирование (ожидается 201 Created). ### Пользователи

#### ADM-009 — Поиск пользователей по подстроке email возвращает только совпадение

Регистрируется пользователь с уникальным тегом в email. Супер-админ делает GET `/api/admin/users?search={tag}`. Проверяется 200 OK, что среди результатов ровно один пользователь с нужным Id, и что все возвращённые записи содержат тег в email (никаких посторонних совпадений).

#### ADM-010 — Поиск пользователей по имени находит нужного пользователя

Регистрируется пользователь с уникальным именем (firstName). Супер-админ ищет по этому имени через GET `/api/admin/users?search={firstName}`. Проверяется, что искомый пользователь присутствует в результатах.

#### ADM-044 — Поиск из одних не-ASCII цифр не возвращает всех пользователей (round-3 code review finding, qa-engineer)

Регрессионный тест на находку прошлого раунда ревью: `GetUsers` считает строку «похожей на телефон»
по `char.IsDigit` (юникодный), но нормализует её через `PhoneNormalizer.Normalize`, который держит
только ASCII `0-9`. Строка из одних арабо-индийских цифр (`٠١٢٣٤`, 5 символов, ни одной буквы) проходит
проверку «похоже на телефон», но нормализуется в `""` — без явной проверки `phoneSearch.Length > 0`
условие `PhoneNumber.Contains("")` истинно для каждой строки, и поиск молча возвращает всех
пользователей (утечка данных). Тест регистрирует контрольного пользователя с уникальным именем, шлёт
`GET /api/admin/users?search=٠١٢٣٤` и проверяет, что контрольный пользователь **не** попал в выдачу —
если бы фильтр деградировал в «вернуть всех», он бы там оказался, хотя ни имя, ни email, ни телефон
контрольного пользователя арабских цифр не содержат. Подтверждено вручную (откат исправления в
`AdminController.cs` → тест падает; исправление возвращено → тест проходит) и живым прогоном приложения.

#### ADM-011 — Смена ролей супер-админом полностью заменяет старые роли новыми

Новый пользователь стартует с ролью "Client". Супер-админ вызывает PUT `/api/admin/users/{id}/roles` со списком `["Master"]` — ожидается 204 No Content. Пользователь логинится заново, и проверяется, что теперь у него единственная роль "Master", а "Client" отсутствует — то есть роли не добавляются, а замещаются.

### Роли применяются немедленно, без повторного входа

#### ADM-025 — Выданная роль работает сразу же на уже существующем токене, без повторного логина

Регрессионный тест: раньше роли "запекались" в JWT только на момент его выпуска, поэтому смена роли требовала повторного входа, чтобы получить новый токен. Пользователь регистрируется (роль только "Client") и токен из регистрации сохраняется. Запрос к эндпоинту, требующему роль "Master" (`GET /api/bookings/master`), с этим токеном сначала возвращает 403 Forbidden. Супер-админ назначает пользователю роль "Master" через `PUT /api/admin/users/{id}/roles`. Тот же самый (ни разу не перевыпущенный) токен теперь проходит проверку и получает 200 OK — потому что роли на каждом запросе перечитываются из базы (`OnTokenValidated` в `Program.cs`), а не берутся только из claim'ов токена.

#### ADM-026 — Отозванная роль немедленно теряет доступ на уже существующем токене, без повторного логина

Пользователю назначается роль "Master", и его токен успешно проходит `GET /api/bookings/master` (200 OK). Затем супер-админ отзывает роль, заменяя список ролей обратно на `["Client"]`. Тем же самым токеном повторный запрос к `GET /api/bookings/master` возвращает 403 Forbidden — закрывает потенциальную брешь безопасности, при которой пользователь с отозванной (например, понижением с SuperAdmin) ролью сохранял повышенный доступ вплоть до истечения токена (до 7 дней).

#### ADM-012 — Смена ролей для несуществующего пользователя возвращает 404

Супер-админ вызывает PUT `/api/admin/users/{случайный Guid}/roles`. Ожидается 404 Not Found.

#### ADM-013 — Неизвестное имя роли даёт корректный 400, а не необработанное исключение

Пользователю с единственной ролью "Client" пытаются назначить несуществующую роль "TotallyBogusRoleXYZ". Раньше `UserStore.AddToRoleAsync` бросал `InvalidOperationException` на непонятной роли, что оборачивалось в 500; теперь контроллер заранее проверяет существование всех ролей через `RoleManager.RoleExistsAsync`, поэтому ожидается чистый ответ 400 Bad Request.

#### ADM-014 — Неизвестная роль в запросе не портит существующие роли пользователя

Тот же сценарий с "TotallyBogusRoleXYZ" (ответ 400 подтверждён), но дополнительно проверяется побочный эффект: раньше старые роли снимались ДО того, как вызов `AddToRolesAsync` падал на неизвестной роли, из-за чего пользователь мог остаться совсем без ролей после неудачного запроса. После перелогина проверяется, что роль "Client" по-прежнему на месте.

#### ADM-015 — Смесь валидной и невалидной роли отклоняет запрос целиком

В списке ролей передаются одновременно валидная "Master" и несуществующая "TotallyBogusRoleXYZ". Ожидается 400 Bad Request, и после перелогина у пользователя должна остаться исходная роль "Client" — то есть частичное применение (назначение только валидной роли) не допускается, запрос атомарен.

### Компании

#### ADM-016 — Поиск компаний заполняет счётчики участников, бронирований и план подписки

Создаётся компания с уникальным именем (для точечного поиска), ей проставляется распознаваемое имя через PUT `/api/admin/companies/{id}`, добавляется мастер, услуга и одно бронирование клиента, а также назначается общий тестовый тариф «QA Full Access». GET `/api/admin/companies?search={tag}` должен вернуть эту компанию единственной в выдаче с `MemberCount = 2` (владелец + мастер), `BookingCount = 1` и `PlanName = "QA Full Access"` — то есть агрегированные поля считаются верно.

#### ADM-017 — Повторное обновление подписки обновляет существующую запись, а не дублирует её

Для аккаунта владельца дважды вызывается PUT `/api/admin/owners/{ownerUserId}/subscription` с разными тарифными конфигами и датами (сначала один тестовый тариф, затем другой). Оба вызова возвращают 204 No Content. При последующем запросе `/api/admin/companies` компания владельца должна отражать `PlanConfigId` именно от второго вызова (`SubscriptionActive = false`), подтверждая, что обновление прошло по существующей записи аккаунт-подписки (upsert по владельцу), а не создало дубликат.

#### ADM-018 — Деактивация компании скрывает её из публичного списка

До изменения компания присутствует в публичном GET `/api/companies`. Админ деактивирует её через PUT `/api/admin/companies/{id}` с флагом `isActive = false` (204 No Content). После этого повторный запрос публичного списка компаний уже не должен содержать эту компанию.

### PUT /api/admin/companies/{id}/owner — смена основного владельца

#### ADM-027 — Супер-админ переназначает владельца, и новый владелец сразу может управлять компанией

Супер-админ назначает нового владельца (обычного зарегистрированного пользователя, не участника компании) через `PUT /api/admin/companies/{id}/owner`. В `GET /api/admin/companies` компания отражает новый `OwnerUserId`. Дополнительно проверяется, что смена `OwnerUserId` сама по себе не дала бы прав управления (их даёт членство в `CompanyMembers`) — эндпоинт также создаёт/повышает членство нового владельца до CompanyOwner, поэтому после перелогина новый владелец успешно редактирует компанию через `PUT /api/companies/{id}`.

#### ADM-028 — Смена владельца недоступна не-супер-админу

Обычный владелец компании пытается вызвать эндпоинт смены владельца — ожидается 403 Forbidden.

#### ADM-029 — Несуществующий пользователь в качестве нового владельца даёт 400

Супер-админ передаёт случайный Guid вместо ID существующего пользователя — ожидается 400 Bad Request («User not found»).

#### ADM-030 — Смена владельца несуществующей компании даёт 404

Запрос со случайным Guid компании возвращает 404 Not Found.

#### ADM-039 — Смена владельца на удалённый (надгробный) аккаунт даёт 400 *(финальная приёмка, найдено code-review)*

`UpdateCompanyOwner` целенаправленно принимает `userId` уже удалённого аккаунта (сам аккаунт сначала
проходит `POST /api/profile/delete-account`, получает `DeletedAtUtc`, теряет пароль и возможность
когда-либо снова войти) — до правки эндпоинт принял бы такой id как обычный, отдав компанию владельцу,
который физически не может ей управлять. Тест регистрирует пользователя, удаляет его аккаунт, затем
пытается назначить его владельцем существующей компании — ожидает 400.

#### ADM-031 — Смена владельца переносит биллинг на план нового владельца

Тариф резолвится через `Company.OwnerUserId`, поэтому передача владения должна перевести компанию на тариф нового владельца — в этом весь смысл поля. Компания создаётся у владельца без подписки (Free); готовится второй владелец с активным платным планом на своём аккаунте. После смены владельца в `GET /api/admin/companies` компания ссылается на нового владельца и отражает его план (`PlanName = "QA Full Access"`, `SubscriptionActive = true`).

### Бронирования

#### ADM-019 — Фильтрация бронирований по компании, диапазону дат и статусу

Создаются два бронирования на разные даты у одной компании; второе завершается (`complete`), приобретая статус, отличный от первого (Confirmed). Далее проверяется несколько комбинаций фильтров GET `/api/admin/bookings`: только по `companyId` (должны вернуться оба бронирования), `companyId + status=Completed` (только второе), `companyId + диапазон дат`, покрывающий только первую дату (только первое), и комбинация всех трёх фильтров сразу (только второе). #### ADM-020 — Полный цикл CRUD для тарифного плана: создание, обновление, мягкое удаление, 404 на несуществующем id

### DELETE /api/admin/plans/{id} и PUT .../subscription — валидация (US-08, находка B1/R2/D2)

#### ADM-032 — Удаление плана с активным подписчиком возвращает 409, план остаётся активным

Плановый конфиг деактивируется напрямую в БД. Попытка назначить его владельцу через `PUT /api/admin/owners/{id}/subscription` возвращает `400 Bad Request` вместо тихого назначения.

#### ADM-034 — Владелец на деактивированном плане получает Free

### PUT /api/admin/owners/{ownerUserId}/subscription — подписка аккаунта, история изменений

#### ADM-021 — Обновление подписки с «голой» датой (без времени/зоны) в PaidUntil больше не падает 500

Регрессионный тест на баг из реального использования: обычный `<input type="date">` на странице админки отправляет `paidUntil` как строку `"2026-08-01"` без времени и часового пояса. System.Text.Json десериализует такую строку в `DateTime` с `Kind=Unspecified`, а Npgsql требует `Kind=Utc` для колонки `timestamp with time zone` — раньше это приводило к необработанному исключению и 500. Тест отправляет именно такой «голый» JSON напрямую (минуя типизированный DTO, чтобы точно воспроизвести формат, который в реальности шлёт браузер) и ожидает 204 No Content — `AdminController.UpdateSubscription` теперь нормализует значение в UTC перед сохранением.

#### ADM-022 — История изменений подписки возвращает записи от новых к старым с корректными старыми/новыми значениями

Для аккаунта владельца дважды меняется подписка: сначала назначается тестовый тариф с комментарием "activated", затем подписка сбрасывается на Free (`planConfigId: null`) с `isActive: false` и комментарием "cancelled". Запрос `GET /api/admin/owners/{ownerUserId}/subscription-history` возвращает ровно 2 записи, при этом более позднее изменение ("cancelled", `NewIsActive = false`, `NewPlanName = "Free"`) идёт первым, а более раннее ("activated", `NewIsActive = true`) — вторым — подтверждая, что каждое обновление подписки пишет новую запись в лог, а не перезаписывает одно поле заметки, как раньше.

#### ADM-023 — Подписка аккаунта покрывает все компании одного владельца

Тариф — свойство аккаунта, а не отдельной компании. Владельцу без подписки назначается тариф с `MaxCompanies = 3` (через первую компанию), после чего он создаёт вторую компанию. В `GET /api/admin/companies` обе компании владельца ссылаются на один и тот же `OwnerUserId` и отражают один и тот же `PlanConfigId` — подтверждая, что план применяется ко всем филиалам владельца, а не только к той компании, через которую он был выставлен.

#### ADM-024 — GetUsers отдаёт тариф аккаунта и число компаний владельца

Управление тарифом в админке живёт на вкладке «Пользователи», поэтому `GET /api/admin/users` должен отдавать для каждого владельца его резолвнутый план и число компаний, которыми он владеет. Владельцу без подписки назначается тестовый тариф; в выдаче по email этого владельца запись содержит `OwnedCompanyCount = 1`, верный `PlanConfigId` и `SubscriptionActive = true`.

**Round 3 (code review finding) — утечка данных в `GET /api/admin/users?search=`, тестов ещё нет.**
`looksLikePhone` считался через Unicode-совместимый `char.IsDigit`, а фактическая нормализация
(`PhoneNormalizer.Normalize`) держит только ASCII `0-9` (US-26, специально держится в синхроне с SQL —
см. `PhoneNormalizerTests`, раздел юнит-тестов выше). Строка, состоящая ТОЛЬКО из не-ASCII цифр (например,
арабо-индийских), проходила проверку «похоже на телефон», после нормализации превращалась в `""`, и
`PhoneNumber.Contains("")` возвращал ИСТИНА для каждой строки — суперадмин, ищущий конкретного
пользователя такой строкой, получал полный список всех пользователей. Исправлено защитой
`phoneSearch.Length > 0 &&` перед веткой поиска по телефону; отдельная (некритичная, по решению
координатора не требующая фикса) особенность старого формата частичного поиска не тронута. **Предложение
для qa-engineer**: `ADM-0xy` — `GET /api/admin/users?search=` со строкой из одних не-ASCII цифр не должен
возвращать весь список пользователей.

## Uploads: раздача `/uploads` (sanitation cycle, найдено QA)

Файл `UploadsStaticFilesTests.cs`, отдельный `UploadsStaticFilesTestFactory` (не общая коллекция `Api`) —
каждый тест поднимает собственный хост с переопределённым `Storage:PublicRoot` и/или content root.
Закрывает пробел, описанный в PROF-016: PROF-016/PROF-017 охраняют правку `Program.cs` (раздача
`/uploads` с `FileStorage.PublicRootFullPath`, каталог создаётся `Directory.CreateDirectory` ДО
построения `PhysicalFileProvider`) только косвенно, через случайность незакоммиченного `wwwroot`. Оба
теста ниже независимы от git: проверено вручную откатом на голый `app.UseStaticFiles()` — оба красные
(`404`) на откате, оба зелёные на текущей версии `Program.cs`.

- **UPL-001** — `Storage:PublicRoot` указывает на временный каталог ВНЕ content root. После старта хоста
  файл записывается туда штатной загрузкой (`POST /api/profile/avatar`), а `GET` возвращённого
  `/uploads/...` возвращает `200`. Голый `app.UseStaticFiles()` тут отдал бы `404` всегда — он раздаёт
  `wwwroot`, а файл лежит не там.
- **UPL-002** — content root — заведомо новый временный каталог, в котором `wwwroot` не существует.
  Санитарная проверка (`Directory.Exists(.../wwwroot)` → `false`) выполняется ДО старта хоста, а не
  после — сам факт появления `wwwroot` сразу при старте хоста (до первого запроса) уже часть проверяемой
  правки. После старта файл, записанный через `POST /api/profile/avatar`, всё равно отдаётся (`200`) —
  пин на то, что каталог публичного корня создаётся до конструирования `PhysicalFileProvider`.

Обе фабрики регистрируют пользователя через `/api/auth/register`, которому для прохождения
`LegalConsentFilter` нужен реальный `legal.json` — `UploadsStaticFilesTestFactory` при переопределении
content root дополнительно выставляет `Legal:Root` на настоящий `ServiceBooking.API/App_Data/legal`
(иначе регистрация упала бы по несвязанной причине).

Создаются два завершённых бронирования у одного мастера — одно в пределах диапазона, другое на 30 дней позже (вне диапазона). Запрос отчёта с диапазоном, покрывающим только первую дату, должен вернуть для мастера `BookingsCount = 1` и `TotalAmount = 500` — второе, более позднее бронирование не учитывается.

#### RPT-003 — Незавершённые бронирования (Confirmed, Cancelled) не попадают в отчёт

Для одного мастера создаются два бронирования: одно остаётся в статусе Confirmed (никогда не завершается), второе клиент отменяет (Cancelled, подтверждено 204 No Content на отмену). Запрос отчёта за диапазон, покрывающий обе даты, не должен вообще содержать запись для этого мастера — ни Confirmed, ни Cancelled не считаются завершёнными (Completed), поэтому у мастера ноль засчитываемых бронирований.

#### RPT-004 — Владелец компании не может получить отчёт по чужой компании

Есть два владельца с разными компаниями. Владелец B запрашивает отчёт по мастерам компании A (`companyId=companyA.Id`) под своим токеном. Ожидается 403 Forbidden.

#### RPT-005 — Обычный клиент не может получить отчёт по мастерам

Пользователь с ролью только "Client" запрашивает GET `/api/reports/masters` для существующей компании. Ожидается 403 Forbidden.

#### RPT-006 — Мастер не может получить отчёт по мастерам

Пользователь с ролью "Master" (не CompanyOwner и не SuperAdmin) запрашивает тот же отчёт по своей компании. Ожидается 403 Forbidden — эндпоинт предназначен только для владельца компании и супер-админа.

#### RPT-007 — Отчёт по мастерам недоступен анонимному пользователю

GET `/api/reports/masters` без токена авторизации возвращает 401 Unauthorized.

#### RPT-008 — Супер-админ может получить отчёт по любой компании, даже не своей

Мастеру с комиссией 25% создаётся и завершается бронирование на услугу стоимостью 400. Супер-админ (не владелец этой компании) запрашивает отчёт по мастерам за нужный диапазон. Ожидается 200 OK и наличие в отчёте записи по этому мастеру с `BookingsCount = 1` — доступ супер-админа не ограничен владением компанией.

### GET /api/reports/masters — гейтинг по тарифу

#### RPT-009 — Отчёт по мастерам без тарифа с AllowAnalytics возвращает 402

Компания остаётся без привязанного тарифа (Free по умолчанию, `AllowAnalytics = false`). Запрос владельцем отчёта по мастерам возвращает 402 Payment Required — эта проверка выполняется уже после проверки роли/владения компанией.

#### RPT-010 — Отчёт по мастерам с тарифом, включающим AllowAnalytics, проходит успешно

Компании назначается тестовый тариф с `AllowAnalytics = true`. Запрос отчёта владельцем возвращает 200 OK.

### Снимок цены на момент бронирования

#### RPT-011 — Отчёт отражает цену на момент бронирования, а не текущую цену услуги

Регрессионный тест: раньше выручка и комиссия считались через join на текущую `Service.Price`, поэтому изменение цены услуги задним числом меняло суммы по уже завершённым и оплаченным записям. Мастеру с комиссией 10% создаётся и завершается бронирование на услугу стоимостью 1000. После этого владелец поднимает цену той же услуги до 5000 через `PUT /api/services/{id}`. Отчёт по мастерам за период, включающий дату записи, должен по-прежнему показывать `TotalAmount = 1000` и `MasterEarnings = 100` — по цене на момент создания записи (`Booking.Price`), а не по новой цене услуги.

#### RPT-013 — Комиссия в отчёте не меняется после увольнения мастера

> **Смена ставки комиссии внутри отчётного периода не покрыта — известный пробел.** Суммы при этом
> считаются верно: `MasterEarnings`/`CompanyEarnings` складываются построчно из снимков
> `Booking.Price` и `Booking.CommissionPercent` каждой записи, так что деньги не портятся. Но поле
> `commissionPercent` в ответе `GET /api/reports/masters` — это ставка последней по дате записи
> в группе, то есть при двух разных ставках в периоде показанный процент не будет соответствовать
> части сумм. Теста на сценарий «две записи одного мастера в одном периоде с разными ставками» нет.
> Если владельцы начнут менять ставки в середине месяца, отображаемый процент стоит переделать
> в диапазон или средневзвешенное — тогда же и покрыть тестом.

Мастер с комиссией 40% выполняет визит на 1000, затем его удаляют из компании; отчёт за тот же период
запрашивается повторно. Ожидается `MasterEarnings = 400` и `CompanyEarnings = 600`, а не 0/1000.
Регрессия того же класса, что RPT-011: комиссия читалась из текущего членства, поэтому увольнение
переписывало закрытые периоды. `Booking.CommissionPercent` — снимок на момент создания записи.

#### RPT-012 — Отчёт мастера-совместителя использует комиссию именно этой компании (US-15)

Мастер состоит в компаниях A и B с разными комиссиями (50% в A, 15% в B — устанавливается владельцем каждой компании отдельно). Завершённое бронирование создаётся в компании B на услугу за 1000. Отчёт `GET /api/reports/masters?companyId={B}` показывает `CommissionPercent = 15` и `MasterEarnings = 150` — комиссию, установленную владельцем B, а не ту, что установил владелец A.

## Security / Rate limiting (US-42, US-46, цикл 3, найдено QA)

Файлы `RateLimitingTests.cs` (`SEC-040`…`SEC-044` + `SEC-042b`) и `IdentityRoleSyncTests.cs`

- **SEC-040** — превышение `auth-login` (лимит занижен до 3) → 429 с непустым телом.
- **SEC-041** — два разных доверенных `X-Forwarded-For` партиционируются независимо: исчерпание квоты
  одним адресом не блокирует другой.
- **SEC-042 / SEC-042b — исправлено в этом прогоне QA (продукт не виноват, был виноват тест).**
  Изначальная реализация обоих тестов гоняла запросы через голый `RateLimitTestFactory.CreateClient()`,
  под которым `HttpContext.Connection.RemoteIpAddress` у `TestServer` всегда `null` — а встроенный
  `ForwardedHeadersMiddleware` включает проверку `ForwardedHeaders:TrustedNetworks` только когда
  `RemoteIpAddress` **не** `null`; при `null` он применяет `X-Forwarded-For` безусловно, независимо от
  конфигурации. Из-за этого оба теста «доказывали» дыру, которой в продукте нет. Подтверждено
  изолированным пробником на голом `TestServer` (см. итоговый отчёт QA) и добавлением в
  `RateLimitTestFactory` `IStartupFilter`, подставляющего фиксированный «настоящий» TCP-адрес
  (`127.0.0.1` по умолчанию) до `UseForwardedHeaders()` — с реальным (не `null`) адресом лимитер ведёт
  себя ровно так, как требует SPEC §5.2 п.2/п.7: заголовок от пира вне `TrustedNetworks` игнорируется.
  **`SEC-042` дополнительно переименован и переписан**: с *пустым* `TrustedNetworks` (умолчание
  `appsettings.json`) `ForwardedHeadersMiddleware` в реальности не «игнорирует» заголовок, а **доверяет
  ему безусловно от любого пира** (`KnownNetworks.Count == 0 && KnownProxies.Count == 0` полностью
  отключает проверку, а не проваливает её) — это подтверждено тем же пробником и хуже, чем
  формулировка в ARCHITECTURE.md §9.1/комментарии `Program.cs` («лимитер посчитает всех одним адресом
  nginx»). В Production это невозможно ровно благодаря отдельному fail-fast (`Program.cs`, US-42 п.2) —
  но этот fail-fast (пустой `TrustedNetworks` вне `Development`/`Testing`) сам не покрыт ни одним тестом
  (пробел US-48, зафиксирован в итоговом отчёте). `SEC-042b` (список настроен, но не включает реальный
  адрес — реалистичный сценарий для Production) теперь зелёный и подтверждает правильное поведение.
- **SEC-043** — превышение `auth-register` (лимит занижен до 2) → 429.
- **SEC-044** — `GET /api/health/live` не ограничен лимитом `auth-login`, даже когда его лимит равен 1
  и уже исчерпан на другом эндпоинте того же хоста.
- **SEC-050** — мастер, удалённый из единственной компании, немедленно (без перевыпуска токена) теряет
  доступ к `[Authorize(Roles="Master,CompanyOwner")]`-эндпоинту → 403.
- **SEC-051** — мастер, состоящий в двух компаниях, удалённый из одной, сохраняет доступ через членство

- **SEC-052** — `PUT /api/admin/companies/{id}/owner`: новый владелец получает доступ, старый —

- **SEC-053** — роль `Client` не снимается никогда, даже после ухода из всех компаний.

(ARCHITECTURE_CYCLE4.md §27.1's invariant).** Ни один тест ЭТОГО набора, кроме файлов, реально тикающих
`ScheduledTaskRunner` (`NotificationDispatchTests.cs`, `NotificationDispatchExtraTests.cs`), не должен
оставлять после себя канал в состоянии `Connected` с непустой очередью `Pending`-строк — иначе реальный
фоновый раннер, запущенный ПОЗЖЕ в той же базе другим тестовым классом, молча подберёт и отправит чужую
строку, ломая точность assert'ов на количество вызовов транспорта. `NotificationChannelsTests.cs` и
`NotificationQueueingTests.cs` явно документируют и соблюдают это в комментариях к своим seed-хелперам.

### NotificationChannelsTests.cs (`NTF-C001`…`NTF-C018`) — свой `NotificationTestFactory` на тест

Новый `ServiceBooking.Tests/Infrastructure/NotificationTestFactory.cs` (аналог `RateLimitTestFactory`):

- **NTF-C004** — `POST /api/notification-channels` при тарифе без `AllowNotificationChannel` → 402.
- **NTF-C005** — та же заявка при незаданной цене (тариф ОК) → 409.
- **NTF-C006** — заявка разрешена → 201, `NotConnected`/`NotPaid`, `requestedAt` заполнен.
- **NTF-C007** — `.../connect` на неоплаченном канале → 402.
- **NTF-C008** — `.../connect` без принятого риска → 409 с текстом про «условия».
- **NTF-C009** — `.../accept-risk` с устаревшей версией текста → 400.
- **NTF-C010** — **приоритетный сценарий двойного клика**: два параллельных `.../connect` — ровно один

- **NTF-C013** — назначение чужой (не своей) компании на канал → 403.
- **NTF-C014** — отвязка одной компании от канала с двумя компаниями: её `Pending`-строки → `Cancelled`,

- **NTF-C016** — `.../replace` на неблокированном канале → 409.
- **NTF-C017** — **приоритетный сценарий смены владельца компании**: назначение снято, `Pending`-строка

- **NTF-C018** — `DELETE` (отвязка владельцем): оплаченный период сохраняется, `Pending`-строки канала →

### NotificationQueueingTests.cs (`NTF-Q001`…`NTF-Q004`) — общая коллекция `"Api"`

Что реально ставится в очередь `OutboundNotifications` при создании/отмене/переносе записи — не
доставка (доставка — файлы ниже). Каналы сеются напрямую в БД в состоянии `Disconnected` (не
`Connected`) — намеренно, см. примечание об изоляции выше; `NotificationGate.Evaluate` не смотрит на
`ChannelState` вовсе, так что для целей этого файла это ничего не меняет.

- **NTF-Q001** — создание записи ставит `BookingConfirmed` и `Reminder`, обе `Pending`.
- **NTF-Q002** — отписавшийся клиент: строки всё равно СОЗДАЮТСЯ (не пропускаются молча), но со статусом
  `Skipped` и `Reason=RecipientOptedOut`; сама запись создаётся успешно независимо от этого.
- **NTF-Q003** — **приоритетный сценарий**: отмена записи за 90 минут до визита при пороге напоминания в
  600 минут всё равно ставит `BookingCancelled` в очередь `Pending` — порог «осталось меньше N» относится
  только к напоминаниям, не к отмене (регрессия, которую чинили: салон отменял за 90 минут, клиент не
  получал ничего).
- **NTF-Q004** — перенос записи в то же окно: уведомление о переносе ставится в очередь так же
  безусловно, а вот НОВОЕ поколение напоминания для этого же визита корректно блокируется тем же порогом
  (`Skipped`/`BelowMinimumLeadTime`) — асимметрия документирована как ожидаемая.

### NotificationDispatchExtraTests.cs (`NTF-D03`…`NTF-D05`) — та же коллекция `"NotificationDispatch"`

Дополняет `NotificationDispatchTests.cs` (`NTF-D01`/`NTF-D02`, написаны backend-разработчиком, T4-B14).
`NotificationDispatchTestFactory` получил один новый необязательный параметр,
`budgetSecondsOverride` (аддитивно, оба существующих вызова без параметра не изменились) — без него
`Notifications:Dispatch:BudgetSeconds` (int, целые секунды) нельзя ужать настолько, чтобы бюджет
реально прервал проход в разумное время реального теста.

- **NTF-D03** — **приоритетный сценарий приоритета по времени визита**: визит через 3 часа и визит через
  60 дней поставлены в очередь в ОБРАТНОМ порядке (дальний первый) — отправлены в ПРАВИЛЬНОМ порядке
  (ближний первый), несмотря на порядок постановки.
- **NTF-D04** — **приоритетный сценарий бюджета без дублей**: `BudgetSeconds=1`, подменный транспорт с
  реальной задержкой 550 мс/сообщение (без искусственной задержки RecordingTransport проход завершается
  мгновенно вне зависимости от бюджета, реального прерывания не получить). Три строки на одном канале:
  первый проход отправляет ровно 2 (проверка бюджета — перед каждой строкой, а не во время отправки уже
  начатой — §26.1), третья остаётся `Pending`; второй проход (свежий бюджет) досылает третью БЕЗ
  повторной отправки первых двух (уникальность номеров получателей по всем вызовам транспорта).
- **NTF-D05** — **приоритетный сценарий простоя канала**: `FakeClock` продвигается на 2 из 3 дней порога
  — предупреждение (`IdleWarningSentAtUtc`) выставлено, инстанс ЕЩЁ жив; ещё 2 дня (итого мимо порога) —
  инстанс удалён, `state=NeedsReconnect`, оплаченный период и назначение компании на месте, а
  `Pending`-строка канала (с намеренно далёким `DueAtUtc`, чтобы её не подобрал обычный
  `notification-dispatch`, который тот же хост тоже реально тикает) остаётся `Pending`.

### Не покрыто функциональными тестами этого прогона (зафиксировано, не блокер)

- **Бэкфилл существующих компаний на Барнаул/`Asia/Barnaul` при миграции** (SPEC §13 п.5) технически не
  воспроизводим через `WebApplicationFactory`-тест: фикстура каждый раз накатывает миграции (включая
  бэкфилл) на ЧИСТУЮ базу без единой существующей компании с `CityId IS NULL` до миграции — сам
  бэкфилл проверен чтением SQL миграции (`20260918051815_AddNotificationChannels.cs`), не тестом.
- **`getInstances` партнёрского аккаунта не содержит лишних инстансов** (SPEC §13 п.6, последний пункт) —
  по определению требует реального партнёрского аккаунта GREEN-API, недостижимо на `Provider=logging`;
  ручная проверка на инстансе приёмки, не функциональный тест.
- Шаблоны сообщений (US-59, `GET`/`PUT .../notification-templates`, предпросмотр), настройки уведомлений
  компании за пределами порога/типа (US-31), журнал доставки (US-32, `GET .../notifications`,
  `.../summary`) и админские `GET .../notification-channels`, `/summary`, `/payment`, `/suspend`,
  `/resume` (US-57) не получили отдельных функциональных тестов в этом прогоне — см. «Вердикт» в
  итоговом отчёте QA: частичное покрытие, не блокер интеграции при этом объёме риска, но зафиксировано
  как пробел на следующий цикл.
