## §300. Что цикл делает, в трёх абзацах

Цикл не добавляет продукту ни одной функции. Он делает правдой то, что продукт уже обещает: кнопка,
которую видно, работает; правило «поздно отменять» проверяется там, где его нельзя обойти; правовой
текст не может молча остаться неподставленным; сборка перестаёт расходиться сама с собой.

Технически это **четыре независимые дорожки**: (A) пять фронтовых починок карточки и кабинета клиента,
(B) одна серверная проверка в `PATCH /api/bookings/{id}/cancel`, (C) правовой контур — регэксп
подстановки и два уведомления по снятому с продажи тарифу, (D) инфраструктура — снапшот миграции,
зависимости, генерация типов, внешняя документация, флейк.

**Ни одной миграции. Ни одной новой сущности. Ни одной новой зависимости в `package.json` и `*.csproj`**
(кроме возможного апгрейда версий существующих — §309). Всё, что цикл добавляет к API, — **аддитивно**:
одно вычисляемое поле в `BookingDto`, одно необязательное поле в `SubscriptionRequestDto`, один новый
код ответа `409` у уже существующей ручки отмены.

## §301. Стек: ни одной новой зависимости, и почему это правильный выбор именно здесь

Стек **не выбирается**, он уже есть и работает в проде: ASP.NET Core 8 (`net8.0`) + EF Core 8.0.11 +
PostgreSQL 16 на сервере; React 18 + TypeScript + Vite + TanStack Query + Tailwind + Vitest на фронте;
CI — GitHub Actions (`.github/workflows/ci.yml`), деплой — Docker + VPS.

Обоснование «через призму задачи», а не привычки:

1. **Цикл техдолговый.** Каждая новая зависимость здесь — это риск, который цикл должен был бы
   погасить, а не создать. Все пять пунктов блока A и весь блок B выражаются существующими
   средствами (чистая функция в `Services/Bookings/`, поле в существующем DTO, проп в существующем
   компоненте).
2. **Эксплуатация.** Продукт разворачивается одной командой на одном VPS; managed-сервисов нет.
   Любой новый рантайм-компонент (очередь, кеш, отдельный сервис) увеличил бы стоимость владения
   ради починки регэкспа — несоразмерно.
3. **Масштабирование/продажа как сервиса.** Единственное место, где цикл мог бы повлиять на стоимость
   хостинга, — §303 «ни одного нового запроса к БД на горячих экранах». Это соблюдено: `clientCancelAllowed`
   считается из уже загруженных `Company`/`Booking` в той же выборке (`GET /api/bookings/client`),
   без второго round-trip и без N+1.
4. **Единственное допустимое изменение зависимостей** — подъём версий уже присутствующих пакетов
   фронта ради `npm audit high = 0` (§309), причём **без новых пакетов** и без правок прикладного кода.

**Инструменты, уже лежащие в репозитории и используемые этим циклом (не новые):**
`openapi-typescript` (генерация типов), `@stoplight/prism` (мок для фронта), `schemathesis` (сверка
формы реализации с контрактом — запускается QA, в зависимости не добавляется),
`.config/dotnet-tools.json` → `dotnet-ef 8.0.11` (единственный допустимый способ генерировать миграции,
§308).

## §303. Модель данных: не меняется ни на одну колонку

**Ни одной миграции в цикле.** Это следствие §0-bis: окно клиентской отмены берёт существующее
`Company.ClientRescheduleMinHours` (`ServiceBooking.Core/Entities/Company.cs`,
миграция `20260924185511_AddCompanyMapLinksAndRescheduleWindow`), отдельного поля не заводим.

Следствия, которые разработчики обязаны принять как ограничение, а не как недосмотр:

1. **Одно значение управляет двумя правилами.** Владелец, поставивший 24 ч «для переноса», получает
   24 ч и для отмены. Это решение заказчика; текст подсказки в кабинете обязан это сказать (§305.3).
2. `ClientRescheduleWindow.Min = 0`, `Max = 168`, `Default = 2` — границы уже валидируются в
   `CompaniesController.Update`; цикл их не меняет.
3. **Единственное изменение схемы в цикле** — правка `…Designer.cs` **уже применённой** миграции
   (§308). Состояние БД при этом не меняется ни на байт; `Up()`/`Down()` не трогаются вовсе.

## §304. Блок B: правило отмены переезжает на сервер (US-17-06, C15-5)

Самая ответственная часть цикла — единственное изменение, видимое снаружи как **новый отказ**.

### §304.1. Правило, целиком

Отмену запрашивает **клиент-владелец записи** (`booking.ClientId == userId` и при этом он не персонал
этой компании) → применяется окно. Отменяет **персонал** (`CanManageBookingAsync`: назначенный мастер,
владелец компании, суперадмин) → **окно не применяется вообще**. Порядок вычисления полномочия —
дословно как в `Reschedule` (§257.1 цикла 15): **сначала персонал**, потом клиент-владелец. Мастер,
который зачем-то является клиентом собственной записи, получает послабления персонала.

```
authority = CanManageBookingAsync(booking, userId) ? Staff
          : booking.ClientId == userId            ? ClientOwner
          : None
```

- `None` → как сегодня: `403` (`Forbid()`). **Не меняем на 404.** Цикл 15 сменил `403→404` у
  `reschedule` намеренно (оракул по id); у `cancel` такого решения не принималось, а менять код
  ответа «заодно» — это ломающее изменение, которого SPEC §3 прямо запрещает (аддитивность).
- `Staff` → поведение байт в байт как сегодня.
- `ClientOwner` → проверка окна (ниже), затем всё как сегодня.

**Проверка окна (клиент):**

```
minHours            = ClientRescheduleWindow.Normalize(company.ClientRescheduleMinHours)
visitStartUtc       = NotificationTiming.ComputeVisitStartUtc(booking.Date, booking.StartTime, company.TimeZoneId)
разрешено, если     DateTime.UtcNow <= visitStartUtc - TimeSpan.FromHours(minHours)
```

Один конец, а не два (у переноса их два — текущий визит и новый; у отмены нового визита нет).
Функция кладётся **рядом с существующей, в тот же файл**
`ServiceBooking.API/Services/Bookings/ClientRescheduleWindow.cs`:

```csharp
/// <summary>§304.1 — клиентская ОТМЕНА: один конец окна. Тот же Company.ClientRescheduleMinHours,
/// что и перенос (решение заказчика, SPEC §0-bis) — отдельного поля намеренно нет.</summary>
public static bool CanClientCancel(DateTime nowUtc, DateTime visitStartUtc, int minHours)
    => nowUtc <= visitStartUtc - TimeSpan.FromHours(minHours);
```

Новый файл/класс `ClientCancelWindow` **не заводить**: два класса с одной константой разъедутся
ровно так же, как разъехались фронт и сервер, — это и есть болезнь, которую цикл лечит. Имя класса
остаётся `ClientRescheduleWindow`, его doc-comment дополняется словом «и отмена» (переименование
тронуло бы пять файлов ради эстетики — цена не оправдана).

### §304.2. Код ответа: `409`, а не `400` (ответ на Р-2 SPEC)

| Ситуация | Код | Тело |
|---|---|---|
| причина длиннее 300 символов | `400` | голая строка (как сегодня) |
| **поздно отменять** | **`409 Conflict`** | голая строка, составленная сервером: `Отменить запись можно не позже чем за {N} ч до визита. Чтобы отменить, свяжитесь с салоном.` |
| чужая запись | `403` | пусто (как сегодня) |
| записи нет | `404` | пусто (как сегодня) |

**Почему 409, хотя у переноса то же правило отвечает 400.** `400` у отмены уже занят валидацией
ввода («причина > 300»). Отдать обоим один код — значит заставить фронт **разбирать русский текст
подстрокой**, чтобы понять, что произошло. Это ровно тот класс дефекта (две стороны по-разному
читают одну строку), который цикл закрывает в C15-1; воспроизводить его в блоке B было бы
самоотрицанием. `409 Conflict` = «запрос конфликтует с текущим состоянием ресурса» — визит уже
слишком близко; это и есть машиночитаемый код причины, которого требует US-17-06. У `reschedule`
код **не меняется** (это было бы ломающим изменением ради симметрии). Асимметрия осознанная и
документируется в `API_CONTRACT_CYCLE17.md` §322 и в `API_DOCUMENTATION.md`.

### §304.3. Что видит фронт: `BookingDto.clientCancelAllowed`

Новое **вычисляемое, необязательное** поле, по конвенции проекта (§286 цикла 15): считается **только**
в `GET /api/bookings/client`, везде остальное `null` = «сервер этого для данного вызывающего не считал».

```
clientCancelAllowed = (status == Pending || status == Confirmed)
                   && nowUtc <= visitStartUtc - minHours
```

Плановая проверка (`AllowSelfBooking`, `plan.AllowOnlineBooking`) **сюда не входит**: отмена сегодня
не зависит ни от подписки салона, ни от того, включена ли онлайн-запись, и цикл это не меняет.
Поэтому переиспользовать `clientRescheduleAllowed` нельзя — набор правил другой.

**Ноль новых запросов к БД:** `Company` уже `Include`'ится в `GetClientBookings` (строка 617),
`minHours` там уже вычисляется (строка 646), `visitStartUtc` — тоже (строка 648). Поле — это одна
строка арифметики в уже существующем `Select`.

### §304.4. Фронт: константа `> 2` уходит совсем

`ClientBookingsPage.tsx:26-30` `canCancelBooking` **удаляется**. Кнопка «Отменить» рисуется по
`b.clientCancelAllowed`, ровно как «Перенести» уже рисуется по `b.clientRescheduleAllowed`
(строка 194). Локальной арифметики по времени на этом экране не остаётся вовсе — значит, и второй
константы быть не может. Импорт `differenceInHours` из `date-fns` уходит, если больше не используется.

**Поведение при отсутствии поля** (старый кеш, другой эндпоинт): `clientCancelAllowed === undefined`
→ кнопка **показывается**, отказ приходит с сервера и показывается человеческим текстом. Это
сознательный выбор в пользу «сервер авторитетен»: скрывать кнопку по догадке — значит снова завести
правило на фронте.

`frontend/src/utils/cancelError.ts` получает ветку `409` → возвращать серверную строку дословно
(`serverMsg || 'Отменить запись уже нельзя — свяжитесь с салоном.'`), по образцу
`clientRescheduleError.ts:19-20`.

### §304.5. Видимые последствия выката (ответ на Р-2, вторая половина)

- **Бэкофилла нет и не нужно**: правило вычисляется в момент вызова, состояние записей не меняется.
- **Кто реально теряет возможность**: клиенты компаний с `ClientRescheduleMinHours > 2` — раньше
  интерфейс показывал им кнопку в промежутке от 2 ч до N ч, и сервер её принимал. После выката —
  отказ. Для компаний со значением по умолчанию (2 ч) фронт вёл себя так же и раньше; меняется лишь
  то, что правило теперь **нельзя обойти прямым вызовом API** (и в этом вся суть истории).
- **Прошедшие визиты**: клиент больше не может «отменить» визит, который уже начался или прошёл
  (раньше мог прямым вызовом). Персонал — может, как и раньше.
- ⚠️ **К `legal-counsel` (SPEC §5 п. 2):** допустимо ли, чтобы окно отмены задавалось каждой компанией
  без верхней границы (сегодня `Max = 168` ч = неделя), и не противоречит ли это опубликованным
  правилам отмены. **Заготовка на случай отрицательного ответа:** константа
  `ClientRescheduleWindow.MaxEnforcedCancelHours` и `Math.Min(minHours, …)` в одной точке §304.1 —
  правка на пять строк, без миграции. По умолчанию **не вводится**; вводится только по письменному
  требованию юриста, и тогда это отдельный пункт приёмки.

## §305. Блок A: интерфейс перестаёт врать (US-17-01…US-17-05)

Целиком фронтовый блок. Сервер по нему не меняется ни одной строкой — значит, он стартует в первый
же день, параллельно бэкенду, без мока.

### §305.1. US-17-01 — сетка переноса вычитает окно (C15-6.2)

`RescheduleModal` получает **новый необязательный проп** `minHours?: number` (по умолчанию `0` —
персонал, поведение не меняется). `ClientBookingsPage` передаёт `booking.clientRescheduleMinHours ?? 0`
рядом с уже передаваемым `horizonDays`.

Фильтрация — **одна граница, применённая к обеим сеткам**, чтобы не появилось двух правил:

```ts
const earliestAllowed = new Date(Date.now() + minHours * 3600_000)
// дни: день показывается, если в нём есть хоть один момент позже earliestAllowed
// слоты: слот показывается, если new Date(`${selectedDate}T${slot.start}`) > earliestAllowed
```

Сегодняшняя фильтрация «слоты сегодня позже текущей минуты» (`timeToMinutes(s.start) > nowMinutes`,
строки 88 и 122) заменяется этой же границей — при `minHours = 0` результат тот же, что сегодня.
**Клиентские часы — не источник правды:** сервер всё равно перепроверит (`§257.4` цикла 15);
это исключительно «не предлагать то, на что придёт отказ».

Второй критерий US-17-01 (гонка/устаревшая вкладка → человеческий текст на `400`) уже выполнен
существующим `getClientRescheduleErrorMessage` (`case 400: return serverMsg`) — нужен **тест**, а не код.

### §305.2. US-17-02 — объяснение вместо пустоты (C15-6.1)

В `ClientBookingsPage`, там, где сегодня `{b.clientRescheduleAllowed && (<Button…>)}` (строка 194),
появляется `else`-ветка:

- `clientRescheduleAllowed === false` **и** `clientRescheduleMinHours != null` **и** статус
  `Pending`/`Confirmed` → текст: `Перенести можно не позже чем за {N} ч до визита`;
  при `N === 0` — `Перенести уже нельзя`.
- поля нет (старый кеш) → **экран ведёт себя ровно как сегодня** (ни кнопки, ни текста).

Текст — `<p>`, а не `<Button disabled>`: отключённая кнопка недоступна скринридеру как объяснение.
Приёмка: `grep -rn "clientRescheduleMinHours" frontend/src` находит чтение минимум в одном компоненте.

### §305.3. US-17-03 — подсказка перестаёт врать (C15-6.3)

**Решение архитектора (US-17-03 оставляет выбор): меняем ТЕКСТ, не поведение.**

аддитивность. Цена правки текста — ноль, цена правки поведения — новый контракт + риск молча сбросить
чужую настройку.

`CompanyManagePage.tsx:885` → `Пусто — оставить текущее значение. 0 — можно перенести и отменить вплоть
до начала визита. У новой компании по умолчанию 2 часа.` (Слово «и отменить» — обязательно: после §304

## §306. Блок C, часть 1: подстановка правовых величин (US-17-07, C15-1)

### §306.1. Чиним ФРОНТ, сканер не трогаем

Прямое указание SPEC и `CURRENT_STATE` C15-1: сканер обязан видеть **больше**, чем подставляльщик,
иначе он перестанет ловить опечатки в именах. Значит `RuntimeValueScanner.cs` остаётся как есть,
а `legalRuntimeValues.ts` ослабляется до той же формы.

```ts
// было: /<span data-legal-value="([a-zA-Z]+)"><\/span>/g
const VALUE_PATTERN = /<span\b[^>]*?\bdata-legal-value\s*=\s*"([^"]*)"[^>]*>\s*<\/span>/g

function conditionalPattern(attr: 'data-legal-when' | 'data-legal-unless'): RegExp {
  return new RegExp(`<span\\b[^>]*?\\b${attr}\\s*=\\s*"([^"]*)"[^>]*>([\\s\\S]*?)</span>`, 'g')
}
```

Что этим разрешается: любое число пробелов/переносов строк, произвольные другие атрибуты до и после
(`class`, `id`, `data-testid`), пробельное содержимое внутри «пустого» `value`-спана.
Что сохраняется без изменений: порядок разрешения (`value` → `when` → `unless`, см. doc-comment
файла), экранирование значения (`escapeHtml`), правило «неизвестное имя оставляем как есть»
(`if (!(name in values)) return match`) — фронт не ломается, имя ловит сборка.

Что **не** покрывается и должно быть записано в коде комментарием: одинарные кавычки
(`data-legal-value='x'`) — их не видит и сканер (`"([^"]*)"`), так что расхождения не возникает;
символ `>` внутри значения атрибута — теоретически возможен, практически в правовых текстах не
встречается, и `[^>]*` его не переживёт. Оба случая ловятся тестом-корпусом (§306.2), а не надеждой.

### §306.2. Тест, который поймал бы расхождение (обязательная часть истории)

Сегодня расхождение не ловит **ни один** тест — и не поймает, если тесты писать отдельно на каждой

## §307. Блок C, часть 2: два уведомления по снятому с продажи тарифу (US-17-08, US-17-09, C15-7)

«Снятый с продажи тариф» в модели данных — это `SubscriptionPlanConfig.IsActive = true` **и**
`IsPublic = false` (§255.2/§255.3 цикла 15). Новых полей не требуется.

### §307.1. US-17-08 — предупреждение ДО смены тарифа

Самостоятельной смены тарифа в кабинете нет: путь один — заявка (`POST /api/billing/subscription/request`)
плюс ручная операция суперадмина. Значит предупреждение обязано быть **в ответе на заявку** и **на
экране заявки**.

`SubscriptionRequestDto` получает **одно необязательное поле** `IrreversibilityNotice (string?)`,
по умолчанию `null` (позиционная запись — поле добавляется **в конец** со значением по умолчанию,
чтобы не ломать существующие вызовы, ровно как `LastRejectedRequest` в §7 цикла 7).

Когда поле непусто:

```
текущая подписка активна (AccountSubscription.PlanConfigId != null)
  И  текущий PlanConfig.IsPublic == false        // тариф снят с продажи
  И  заявка просит СМЕНУ тарифа (RequestedPlanId != null && RequestedPlanId != текущий PlanConfigId)
```

Во всех остальных случаях — `null` (в том числе: заявка только на опции; тариф публичный; подписки нет).

Где считается: `OwnerSubscriptionService.BuildAsync` уже держит `sub` (строка 29) и вызывает
`BuildPendingRequestDto` (строка 94). Сигнатура последнего получает **необязательный** параметр
`bool currentPlanWithdrawn = false`, чтобы второй вызывающий (`AdminBillingController.cs:407`,
админский экран) продолжал компилироваться и вёл себя как сегодня. Текст собирает **сервер** —
фронт печатает как есть (конвенция §41 п. 8 цикла 7).

**Текст — от `legal-counsel`** (см. §317). Заготовка-заглушка в коде не допускается: пока текста нет,
задача не считается закрытой.

**Второе место — отметка на будущее.** Рядом с кодом, собирающим уведомление, обязателен комментарий:
`// §307.1 — второе обязательное место этого предупреждения (п. 6.13.15 03-terms-owner.html) — экран
самостоятельной смены тарифа в кабинете. Его сегодня НЕТ; когда появится, текст берётся отсюда же.`
Это дословное требование второго критерия US-17-08.

**Фронт:** `frontend/src/pages/BillingPage.tsx` — если `pendingRequest.irreversibilityNotice` непусто,
показать его заметным блоком (тот же стиль, что у `warning`) **и в ответе на отправку заявки**, и при
последующих открытиях экрана (поле приходит в `GET /api/billing/subscription` внутри `pendingRequest`).
Типы фронта здесь — генерируемые (`frontend/src/api/billing.ts:2` → `types/api-cycle7.generated.ts`),
поэтому поле добавляется **и** в `contracts/cycle7/openapi.yaml` (`SubscriptionRequestDto`), после чего
`npm run types:api` перегенерирует файл. Диff генерации обязан быть ровно одним необязательным полем —
это и есть проверка, что контракт цикла 7 не поехал.

### §307.2. US-17-09 — упоминание в напоминании об окончании оплаченного периода (ответ на Р-6 SPEC)

**Механизм в продукте есть, новую функцию делать не нужно.** «Напоминание об окончании оплаченного
периода» — это `OwnerSubscriptionDto.Warning` вида `Kind = "Expiring"`, которое собирает
`OwnerSubscriptionService.BuildWarning` (строки 202–233) по условию
`BillingCalculator.IsExpiringSoon(sub.PaidUntil, sub.PlanConfig.NotifyDaysBefore, now)` (строки 55–56).
Это экранное предупреждение в кабинете владельца, а не исходящее сообщение: исходящей рассылки об
истечении подписки в продукте нет вовсе (проверено: среди
`ServiceBooking.API/Services/Scheduling/Tasks/*` задачи с таким смыслом нет). **Поэтому US-17-09 —
правка одной серверной строки, а не новый сценарий, и объём цикла не растёт.**

Правка: в ветке `if (isExpiringSoon …)` текст дополняется предупреждением о необратимости **тогда и
только тогда**, когда `sub?.PlanConfig?.IsPublic == false`. Формулировку даёт `legal-counsel`.

**Регрессия, обязательная к тесту:** при публичном тарифе строка предупреждения **не меняется ни на
символ** (сегодня: `Подписка истекает через {N} дн. — продлите её, чтобы не потерять возможности
тарифа.`). Это проверяется точным сравнением строк, а не `Contains`.

Ветка `Kind = "Expired"` **не трогается**: требование п. 6.8.5 — про напоминание **до** окончания,
а не про уже истёкшую подписку. (Если юрист скажет иначе — правка на две строки в том же методе.)

## §308. Блок D, часть 1: снапшот миграции и защита от повторения (US-17-11, C15-3/C15-4)

### §308.1. Правка `Designer.cs` — почему это безопасно (ответ на Р-5 SPEC)

`…Designer.cs` — это **снимок модели на момент миграции**, который EF Core использует только
как точку отсчёта при генерации СЛЕДУЮЩЕЙ миграции. В БД он не попадает никогда: таблица
`__EFMigrationsHistory` хранит только `MigrationId` и версию EF, а применяется `Up()`. Правка
Designer'а уже применённой миграции:

- **не меняет состояние ни одной БД** (dev, staging, прод) — ни одного DDL не выполняется;
- **не делает миграцию «непримененной»** — `MigrationId` и `Up()`/`Down()` не трогаются;
- **не требует деплоя** — это разработческий артефакт.

Что именно чинить: в `ServiceBooking.Infrastructure/Migrations/20260924074741_ResetUnverifiedPhoneNumberConfirmedMirror.Designer.cs`
в сущности `Company` вернуть пять свойств `AddressLatitude`, `AddressLongitude`, `AddressPrecision`,
`AddressVerifiedAt`, `AddressVerifiedInputKey` — **скопировав их дословно** (типы, `IsRequired`,
`HasMaxLength`, `HasColumnType`, порядок) из `20260924065320_AddCompanyAddressVerification.Designer.cs`.
`AppDbContextModelSnapshot.cs` **не трогать вовсе** — он корректен.

**Приёмочная проверка, она же доказательство безопасности:**

```bash
dotnet tool restore
dotnet dotnet-ef migrations add __DriftProbe --project ServiceBooking.Infrastructure \
  --startup-project ServiceBooking.API --output-dir Migrations/__probe
# Up() обязан быть ПУСТЫМ
dotnet dotnet-ef migrations remove --project ServiceBooking.Infrastructure --startup-project ServiceBooking.API
```

Непустой `Up()` означает, что снапшот и модель разошлись, — тогда чинится снапшот, а не пишется
миграция. Файлы пробы в коммит не попадают.

### §308.2. Защита от повторения — две проверки в CI

Обе добавляются в job `backend` файла `.github/workflows/ci.yml`, **после** шага `Build`:

1. **`Migrations snapshot drift` (авторитетная).** Шаги из §308.1 в неинтерактивном виде: если
   сгенерированная проба содержит непустой `Up()` — job красный. Ловит любое расхождение
   `AppDbContextModelSnapshot` ↔ модель, в том числе «миграцию сгенерировали чужим `dotnet-ef`».
   Подключения к БД шаг не требует (`migrations add` работает по design-time модели).
2. **`Designer snapshots are monotonic` (дешёвая, ловит ровно C15-4).** Скрипт
   `deploy/ci/check-migration-snapshots.sh`: миграции сортируются по имени (это хронология); для
   каждой соседней пары множество `b.Property<…>("Имя")` внутри каждой сущности в Designer'е N+1
   обязано **включать** множество из Designer'а N, **кроме** имён, для которых в `*.cs` миграции N+1
   есть `DropColumn(name: "Имя"`. Последний Designer сверяется с `AppDbContextModelSnapshot.cs`.
   Нарушение — красный CI с именем файла и пропавшей колонки. Это единственная проверка, которая
   поймала бы C15-4 **в тот день**, когда он возник.

**Требование про инструмент (C15-3)** записывается там, где его увидят, — тремя строками в
`README.md` (раздел для разработчика) и `DEPLOY.md`: миграции генерируются **только**
`dotnet tool restore && dotnet dotnet-ef …`; глобальный `dotnet-ef` новее 8.0.11 портит `Up()`.
Плюс комментарий в `.config/dotnet-tools.json` невозможен (json без комментариев) — поэтому ссылка
на §308 ставится в шаге CI.

## §309. Блок D, часть 2: зависимости с точкой останова (US-17-10, C15-2)

Работа ведётся **строго по шагам, с фиксацией результата после каждого** (решение заказчика §0-bis:
«решение принимать по факту первого прогона, не авансом»):

```
Ш1. npm audit --json > /tmp/audit-before.json      # факт, а не цифра из документа
Ш2. npm audit fix                                  # только совместимые обновления
Ш3. npm run lint && npx tsc --noEmit && npm run test:run && npm run build
    ЕСЛИ high == 0 -> ГОТОВО, пункт закрыт, идти в Ш6
Ш4. Для каждого оставшегося high посмотреть, что предлагает `npm audit fix --force`:
    - мажорная версия пакета, НО API пакета в нашем коде не используется напрямую
      (или используется в 1–2 местах, где правка не меняет поведение)  -> можно
    - требуется правка маршрутизации (react-router) или вызовов API (axios interceptors,
      формы ответов об ошибках)                                        -> СТОП
Ш5. СТОП означает: пакет НЕ поднимается; в CURRENT_STATE.md §9 заводится пункт C17-N
    («high остаётся, причина, что именно придётся переписать»), и работа по нему
    выносится в отдельный цикл. Это не провал истории, а её предусмотренный исход.
Ш6. Оставшиеся moderate/low перечислить в §9 с причиной.
```

**Красные флаги, при которых срабатывает СТОП немедленно** (их не надо проверять экспериментом, это
известно): `react-router` v6 → v7 (меняются типы `RouteObject`, `data router`, поведение

Если текущая версия `axios` уже 1.x, подъём внутри мажора безопасен.

Регрессия, обязательная после любого поднятия версий: маршрутизация (переходы по всем ролям),
загрузка файлов (фото/логотип — `form-data`), обработка ошибок форм (те самые `*Error.ts`).

## §311. Блок D, часть 4: флейк Web Push (US-17-14, AV3) — задача изменилась

**Находка сверки (§302):** тест
`StaffPushDispatchTests.RealRunner_MasterRemovedFromCompany_HoldsDeliveryEvenThoughAlreadyQueued`
(`StaffPushTests.cs:303-330`) **уже не ждёт стенных часов**: он запускается с
`disableAutomaticTicking: true` и делает один детерминированный проход
`await factory.RunStaffPushDispatchPassAsync()` (`PushDispatchTestFactory.cs:91-96`, прямой вызов
`task.ExecuteAsync`). Константы `DispatchWaitSeconds` в файле больше нет. То есть **характер ожидания
уже исправлен циклом 14** — а `AV3` описывает состояние до этой правки.

Поэтому US-17-14 делается так:

1. **Сначала измерение, потом код.** Полный прогон `ServiceBooking.Tests` **трижды**, под параллельной
   нагрузкой ×3 (три одновременных прогона на машине), как требует критерий приёмки.
2. **Если зелено все три раза** — правка кода не нужна: пункт закрывается записью в §9
   («AV3 закрыт: характер ожидания исправлен в цикле 14 коммитом перевода PUSH-006…009 на
   `RunStaffPushDispatchPassAsync`; подтверждено тройным прогоном под нагрузкой, дата, ревизия»).
   Поднимать бюджеты **запрещено** — SPEC прямо это исключает.
3. **Если падает** — причина **не** в этом тесте, а в общем контуре (аренда тестовой БД, лимит
   соединений `SERVICEBOOKING_TEST_MAX_PARALLEL_THREADS`, фикстура класса). Тогда чинится найденная
   причина, и правка обязана менять **характер ожидания** (ждать сделанную работу), а не бюджет.

   `Подписка истекает через {N} дн. — продлите её, чтобы не потерять возможности тарифа.`
   Нужно решить: дополняем эту строку или заменяем целиком.
3. **Правило отмены (US-17-06):** допустимо ли настраиваемое окно отмены без верхней границы (сегодня
   до 168 ч), и не противоречит ли это клиентскому соглашению/оферте. Если нужна граница — назвать
   число (§304.5 содержит готовую правку).

**По Р6/US-17-15 юрист в этом цикле не вызывается** — решение заказчика §0-bis.

## §318. Долг, который цикл фиксирует заранее (в `CURRENT_STATE.md` §9, префикс `C17-`)

Записать **при закрытии цикла**, даже если всё зелёное:

- `C17-1` — сверка типов из контракта в CI охватывает только циклы 15 и 17; контракты 7/9/10/11/13/14
  остаются без автосверки (§310, причина — вероятность красного CI на старых расхождениях).
- `C17-2` — `PATCH /bookings/{id}/cancel` отвечает `403` постороннему, тогда как `reschedule` отвечает
  `404` (§304.2). Разнобой осознанный: выравнивание — ломающее изменение, отдельное решение.
- `C17-3` — клиент по-прежнему может «отменить» уже завершённую (`Completed`) запись, если она
  дальше окна: статусной проверки в `Cancel` нет и цикл её не добавлял (за пределами US-17-06).
- `C17-4` — `C15-8` (ручное назначение скрытого тарифа) остаётся без ответа заказчика; нужен **до
  публикации** правового комплекта.

  непогашенные `high` с указанием, что именно придётся переписать.
- `C17-6` — окно отмены и окно переноса управляются одним полем; если продукту понадобятся разные
  значения, это миграция + экран настроек.
- `C17-7` — e2e (Playwright) в проекте нет; US-17-01/02/06 проверены компонентными и функциональными
  тестами, сквозного браузерного сценария «клиент нажал — сервер отказал — текст на экране» нет.
