## 38. Общее для всех эндпоинтов цикла

### 38.1 Соглашения, действующие без изменений

Из §0.1 цикла 3: JSON, **camelCase**, перечисления — **строками** (`JsonStringEnumConverter`),
`DateOnly` → `"2026-10-01"`, `TimeOnly` → `"18:30:00"`, `DateTime` → ISO-8601 UTC.
Из §0.2: тело осознанной 4xx — **голая строка** (`text/plain`), а не `ProblemDetails`;
403 и 401 — **пустое тело** (кроме `POST /api/auth/login`, который и раньше слал строку).
`AddProblemDetails()` по-прежнему запрещён. Заголовок авторизации — `Authorization: Bearer <jwt>`.

### 38.2 Коды, которыми пользуется этот цикл

| Код | Когда | Тело |
|---|---|---|
| 400 | валидация: услуга не принадлежит компании, мастер не в компании, диапазон дат вне правил, >5 услуг, повтор услуги, мастер не умеет услугу; **новое:** не-российский телефон (§44), дата окончания подписки не указана (§42.1), дата записи за горизонтом компании (§41.2/§43.1), горизонт вне 1..365 (§41.4) | голая строка |
| 401 | неверный телефон или пароль | голая строка `Invalid credentials` |
| 402 | тариф не разрешает онлайн-запись | голая строка |
| 403 | не владелец / не персонал / салон выключил онлайн-запись | **пустое** |
| 404 | компании, услуги, участника, владельца нет | пусто или голая строка |
| 409 | слот занят; отключение признака «оказывает услуги» при наличии будущих записей без подтверждения | голая строка |
| **423** | **новый в цикле**: аккаунт временно заблокирован после серии неудачных попыток входа | голая строка |
| 429 | лимит `auth-login`, `booking-create`, **новый `availability`** | голая строка |
| 451 | требуется принять новую редакцию документов (глобальный фильтр; на `POST /api/auth/**` не встречается) | голая строка |

### 38.4 ⚠️ Изменения поведения при неизменной форме

1. **`GET /api/companies/{id}/masters`** перестаёт возвращать участников с выключенным признаком

2. **`GET /api/bookings/slots?manual=true`** на дату без расписания возвращает не сутки

3. **`PUT /api/admin/owners/{id}/subscription`**: отсутствующее в теле `isActive` теперь означает
   `true` (было — молча `false`), а `paidUntil` без времени суток означает **конец** этого дня

4. **⚑ Новое в редакции 2. `PUT /api/admin/owners/{id}/subscription`**: при заданном `planConfigId`
   поле `paidUntil` стало **обязательным** — его отсутствие даёт **400**, а не «бессрочную»
   подписку (§42.1). Ответ Q2.
5. **⚑ Новое в редакции 2. Четыре эндпоинта, создающих новую запись с телефоном, отвергают
   не-российский номер** кодом 400 (§44.2). Раньше принимался любой номер длиной 10–15 цифр.
   Ответ Q4. Эндпоинты, где телефон — **ключ к уже существующим данным** (вход, поиск, заметка о
   клиенте), намеренно остаются как были (§44.3).
6. **⚑ Новое в редакции 2. `POST /api/bookings` отвергает дату дальше горизонта компании**
   кодом 400 — для клиентов и гостей, но не для персонала (§43.1). Ответ Q5.

## 39. `POST /api/auth/login` — различимые причины отказа (US-60)

### 39.1 Запрос — без изменений

```json
{ "phone": "+7 (999) 000-00-00", "password": "secret123" }
```
Телефон принимается **в любом виде**: `+7…`, `8…`, слитно, со скобками и дефисами. Сервер приводит
его к канонической форме (`PhoneNormalizer`) — клиент **не обязан** этого делать, но после US-61
поле всё равно отправляет канонические цифры.

> ⚑ **Редакция 2, важно для US-61.** На логине страновая проверка (§44) **не применяется**:
> вход обязан пускать аккаунты, зарегистрированные до цикла, в том числе с не-российскими
> номерами. Неподходящий номер просто не найдётся и даст обычный 401 — отдельного 400 здесь нет
> намеренно, чтобы не подсказывать перебирающему, какой номер «выглядит правильно».

### 39.2 Успех — без изменений

`200` + `AuthResponseDto`:
```json
{ "token": "eyJ…", "userId": "…", "phone": "79990000000", "email": null,
  "firstName": "Иван", "lastName": "Иванов", "roles": ["Client"] }
```

### 39.3 Отказы — стало четыре различимых кода вместо одного

> ⚑ **Редакция 2, контекст.** Заказчик подтвердил: со стенда приходит **401**. Но 401 сегодня
> отдают **три разных исхода** (`ARCHITECTURE_CYCLE6.md` §42.1): аккаунт не найден, пароль неверен
> и **аккаунт заблокирован Identity** (`CheckPasswordSignInAsync` зовётся с `lockoutOnFailure: true`,
> а `IsLockedOut` отдельно не проверяется). Строка таблицы про 423 — не «задел на будущее», а
> починка живой, наблюдаемой прямо сейчас неразличимости.

| Код | Причина | Тело | Что показывает фронт |
|---|---|---|---|
| 401 | номер не найден **или** пароль неверен | `Invalid credentials` | «Неверный телефон или пароль» |
| **423** | аккаунт заблокирован Identity после 5 неудачных попыток (15 минут) — **сегодня неотличим от 401** | `Account temporarily locked` | «Вход временно заблокирован из-за нескольких неудачных попыток. Попробуйте через 15 минут» |
| 403 | вход в аккаунт не разрешён (`SignInResult.IsNotAllowed`; сейчас недостижимо, закрываем на будущее) | пусто | «Вход в этот аккаунт недоступен. Обратитесь в поддержку» |
| 429 | лимит `auth-login` — 10 попыток в минуту с одного IP | голая строка от `OnRejected` | тело ответа; запасной текст — «Слишком много попыток входа, попробуйте через несколько минут» |
| 5xx | внутренняя ошибка | — | «Сервис временно недоступен. Попробуйте ещё раз через минуту» |
| ответа нет (сеть/CORS) | — | — | «Не удалось связаться с сервером. Проверьте интернет и попробуйте ещё раз» |

**Гарантия против перебора:** ответы на «номера нет» и «пароль неверен» обязаны быть **побайтово
одинаковыми** (тот же код, то же тело, никакой разницы во времени ответа сверх естественной). Это
проверяется функциональным тестом. Различается **только** блокировка (423).

### 39.4 Что происходит сразу после входа

`POST /api/auth/**` находится в allow-list правового фильтра, поэтому **451 на самом логине
невозможен** — подтверждено и кодом (`Services/Legal/LegalConsentFilter.cs:91`), и ответом
заказчика (401). Если версии принятых документов в токене разошлись с текущим манифестом, 451
придёт на первом же защищённом запросе, и фронт обязан показать **экран принятия документов**
(`ConsentGate`, поведение цикла 3), а не ошибку входа и не молчаливый отказ. Пользователя при 451
**не разлогинивать** — это по-прежнему запрещено.

### 39.5 Обязательство фронтенда

`LoginPage` больше не подменяет любую ошибку строкой «Неверный телефон или пароль»
(`frontend/src/pages/LoginPage.tsx:55–57`). Весь разбор — в `utils/authError.ts`, по коду статуса;
тексты — из таблицы §39.3. Ветка «ответа нет» (`error.response === undefined`) обязана быть
отдельной: сегодня она неотличима от неверного пароля и даёт ложный диагноз.

### 39.6 `POST /api/auth/register` — форма отказа 400 и требования к паролю — **новое в редакции 3**

Это та часть US-60, ради которой история вообще появилась: именно здесь заказчик застрял, а не на
входе. Регистрация отклонялась политикой паролей, а пользователь видел «Проверьте введённые данные».

**Требования к паролю** (политика ASP.NET Core Identity, `Program.cs`) — **не менее 8 символов,
хотя бы одна строчная буква, хотя бы одна заглавная, хотя бы одна цифра**; неалфавитный символ
не требуется. Ответ заказчика на Q6 — политику **не менять**, а показать требования человеку.

⚠️ **Схема описывает политику, а не наоборот.** В первой реализации цикла схема говорила
`minLength: 8` и больше ничего; контрактная проверка нашла расхождение, и оно было «исправлено»
ослаблением политики (коммит `1615e8f`, откачен коммитом `95a2b14`). Это прямо противоречило
решению заказчика. Правило на будущее: при расхождении схемы и поведения правится **схема**, если
заказчик явно не решил иначе.

**Формы тела ответа 400 — их две, и клиент обязан различать:**

| Причина | Тело | Content-Type |
|---|---|---|
| Не принято согласие | строка `Consent to the Terms of Service and the Privacy Policy is required.` | `text/plain` |
| Телефон не российский | строка `Введите номер телефона в формате +7 (900) 000-00-00` | `text/plain` |
| Пароль/логин отвергнуты Identity | **массив** объектов `{ "code": "...", "description": "..." }` | `application/json` |

Коды Identity, которые обязаны иметь человеческий русский перевод на клиенте:
`PasswordTooShort`, `PasswordRequiresLower`, `PasswordRequiresUpper`, `PasswordRequiresDigit`,
`PasswordRequiresUniqueChars`, `DuplicateUserName` (последний особенно важен: это «этот телефон уже
зарегистрирован», а сегодня он неотличим от «проверьте данные»).

**Обязательство фронтенда:** `utils/authError.ts` разбирает тело-массив (сейчас оно молча
отбрасывается проверкой `typeof data === 'string'`, и весь массив превращается в пустую строку);
при нескольких ошибках показываются **все**, а не первая; форма регистрации выводит требования к
паролю **рядом с полем и до отправки**, а не только в тексте отказа.

## 40. Признак «оказывает услуги» (US-62) и список специалистов (US-64)

### 40.1 `GET /api/companies/{id}/masters?serviceId={guid}` — ⚠️ изменился состав

Доступ: публично. Форма ответа **не меняется**:
```json
[ { "userId": "…", "firstName": "Анна", "lastName": "П.", "avatarUrl": null, "bio": "Колорист" } ]
```
Новое правило состава: участник попадает в ответ, если
`(Role == Master || Role == CompanyOwner) && Company.IsActive && ProvidesServices == true`,
и — при переданном `serviceId` — умеет эту услугу (существующее правило с существующим запасным
вариантом: если для услуги нет **ни одной** записи в `MasterServices`, её умеют все).

**Это единственный источник истины о списке специалистов** — для клиентской записи, для записи
персоналом и для виджета. Отсюда правило US-64 целиком фронтовое:

| Длина массива | Поведение клиентской записи и записи персоналом |
|---|---|
| 0 | «Сейчас записаться нельзя» (не пустой список, не сломанный шаг) |
| 1 | шаг выбора мастера **не показывается**, мастер подставлен, его имя видно в сводке подтверждения |
| ≥2 | как сейчас |

Индикатор прогресса строится по фактическому числу шагов, а не по константе из четырёх.

### 40.2 `GET /api/companies/{id}/members` — `MemberDto` + одно поле

Доступ: владелец компании или SuperAdmin. Добавляется:
```jsonc
{ /* …существующие поля… */ "providesServices": true }
```
Поле есть у **любого** участника; смысл оно имеет для ролей `Master` и `CompanyOwner`.
По умолчанию — `true` (в том числе у всех существующих участников после миграции).

### 40.3 `PUT /api/companies/{id}/members/{memberId}/provides-services` — **новый**

Доступ: **владелец этой компании** (в том числе для себя и для второго владельца) или SuperAdmin.
Мастер себе признак не меняет → 403.

Запрос:
```json
{ "providesServices": false, "confirm": false }
```

| Код | Когда | Тело |
|---|---|---|
| 204 | применено | пусто |
| 409 | `providesServices == false`, `confirm != true` и у участника есть **будущие** записи (`Date >= сегодня`, `Status != Cancelled`) в этой компании | голая строка: «У специалиста 3 будущие записи. Они останутся в силе и в расписании, но клиенты перестанут видеть его при записи. Повторите с подтверждением.» — число подставляет сервер |
| 403 | не владелец этой компании / мастер меняет себе | пусто |
| 404 | компании или участника нет, либо участник не из этой компании | пусто |

Повтор того же запроса с `"confirm": true` выполняет действие (204). Включение признака
(`providesServices: true`) подтверждения **не требует** никогда.

**Гарантии:** признак меняет **только** состав ответа §40.1. Он не убирает человека из кабинета,
расписания, отчётов и базы клиентов, не отменяет и не скрывает уже созданные записи и не меняет
никаких прав.

## 41. Время: слоты, доступность дней и горизонт записи (US-65, US-66, US-67)

### 41.1 `GET /api/bookings/slots` — ⚠️ поведение и два новых параметра

```
GET /api/bookings/slots?companyId={guid}&masterId={string}
                       &serviceId={guid}            — legacy, одна услуга
                       &serviceIds={guid}&serviceIds={guid}   — US-67, 1..5 услуг
                       &date={date}
                       [&manual=true][&extendedHours=true]
```

Ответ — без изменений: `[ { "start": "10:00:00", "end": "11:30:00" } ]`.

Правила:

- `serviceId` **или** `serviceIds` — обязателен хотя бы один способ. Если переданы оба, `serviceId`
  обязан совпадать с `serviceIds[0]`, иначе 400. Длительность слота = **сумма** длительностей.
- `manual` уважается **только** для персонала этой компании (проверка независимая, как сейчас);
  для всех остальных флаги молча игнорируются.
- `extendedHours` уважается **только** вместе с `manual`.

| `manual` | `extendedHours` | вызывающий | дата без строки расписания даёт |
|---|---|---|---|
| нет | — | любой | **пустой список** (поведение не меняется) |
| да | нет | персонал | ⚠️ **09:00–21:00** (было 00:00–24:00) |
| да | да | персонал | 00:00–24:00 |

Коды: 400 «услуга не принадлежит компании» / «мастер не работает в компании» / «услуг больше пяти» /
«повтор услуги» / «мастер не оказывает услугу X»; 404 «услуга не найдена».
**Горизонт записи этот эндпоинт не проверяет** — он про один конкретный день, а границу дней
задаёт §41.2 и §43.1.

**Клиентская запись этим изменением не затронута** — она ходит без `manual`, и это проверяется
отдельным тестом.

### 41.2 `GET /api/bookings/availability` — **новый** (US-65)

Состояние **всех дней диапазона одним запросом**. Доступ: публично (анонимно), политика
лимитирования `availability` — 60 запросов в минуту с IP, превышение → 429.

```
GET /api/bookings/availability?companyId={guid}&masterId={string}
                              &serviceIds={guid}[&serviceIds=…]   (или &serviceId={guid})
                              &from={date}&to={date}[&manual=true]
```

Ответ `200`:
```json
{
  "from": "2026-10-01",
  "to": "2026-10-31",
  "totalDurationMinutes": 90,
  "stepMinutes": 30,
  "horizonDays": 90,
  "horizonLastDate": "2026-12-20",
  "days": [
    { "date": "2026-10-01", "status": "Available",   "lastFreeSlotStart": "18:30:00" },
    { "date": "2026-10-02", "status": "DayOff",      "lastFreeSlotStart": null },
    { "date": "2026-10-03", "status": "FullyBooked", "lastFreeSlotStart": null }
  ]
}
```

| Поле | Смысл |
|---|---|
| `days` | **каждая** дата диапазона ровно один раз, по возрастанию |
| `status` | `Available` — есть хотя бы один свободный слот под суммарную длительность; `FullyBooked` — рабочий день, свободных слотов нет; `DayOff` — нет рабочего расписания на дату |
| `lastFreeSlotStart` | начало **последнего** свободного слота дня или `null`. Нужен клиенту, чтобы пометить сегодняшний день как «время уже вышло» по своим локальным часам |
| `totalDurationMinutes` | сумма длительностей запрошенных услуг — эхо, чтобы клиент убедился, что считали то же самое |
| **`horizonDays`** | ⚑ редакция 2: горизонт записи **этой компании** в днях (`Company.bookingHorizonDays`, §41.4) |
| **`horizonLastDate`** | ⚑ редакция 2: последняя дата, на которую клиент может записаться = сегодня (UTC) + `horizonDays`. Календарь по ней отключает переход на следующий месяц — второго запроса для этого не нужно |

Ограничения запроса (нарушение → 400 с голой строкой):

- `to >= from`;
- диапазон **не длиннее 31 дня**;
- ⚑ **изменено в редакции 2:** `to` не дальше **`today + horizonDays`** (было: жёстко `today + 90`).
  Текст ошибки: «Записаться можно не дальше чем на N дней вперёд», N подставляет сервер;
- `from` не раньше `today - 1`;
- услуг 1..5, без повторов; те же проверки принадлежности, что в §41.1.

`manual=true` уважается только для персонала компании и означает то же, что в §41.1 (дни без
расписания считаются по окну 09:00–21:00, а не выпадают в `DayOff`). **Горизонт при `manual=true`
не применяется** — у персонала запись вне горизонта законна.

**Чего в ответе нет и не будет:** чужих записей, имён и телефонов клиентов, времени чужих визитов,
количества записей. Раскрывается ровно «можно / нельзя / выходной».

**Сервер не помечает прошедшие дни.** Это делает браузер по локальной дате: зон в расписании нет
(долг проекта), и вводить их этот цикл не будет. Приоритет отрисовки на клиенте:
`прошедший > DayOff > FullyBooked > Available`.

### 41.3 Четыре состояния дня в интерфейсе (US-65, фронтовая часть контракта)

| Состояние | Источник | Кликается | Подпись |
|---|---|---|---|
| рабочий со свободным временем | `Available` | да | — |
| выходной | `DayOff` | **нет** | «выходной» |
| занято | `FullyBooked` | нет | **«Занято»**, подсказка «на этот день свободного времени не осталось» |
| прошедший | локальная дата браузера | нет | приглушён |

Формулировка **«Занято»** — ответ заказчика от 2026-09-22 (`SPEC.md` §0.1). Редакции 1–2 этого
документа предлагали «всё занято» с запасным вариантом «нет мест»; заказчик выбрал короткое
«Занято», и это перекрывает прежнее предложение. Хранится одной константой `DAY_FULL_LABEL`. Некликабельность передаётся цветом **и** подписью **и** `aria-disabled` — цвета одного
недостаточно. Переход на месяц за `horizonLastDate` — кнопка `disabled` с пояснением «Записаться
можно не дальше чем на N дней вперёд».

### 41.4 ⚑ Горизонт записи в настройках компании (US-65, Q5) — **новое в редакции 2**

Заказчик: «вынести в настройки компании, по умолчанию 90 дней».

**`CompanyDto` — одно новое поле** (отдаётся везде, где отдаётся компания, включая публичный
`GET /api/companies/{slug}`):

```jsonc
{ /* …существующие поля… */ "bookingHorizonDays": 90 }
```

**`PUT /api/companies/{id}` — одно новое необязательное поле в `UpdateCompanyDto`:**

```jsonc
{ "bookingHorizonDays": 60 }
```

| Значение | Смысл |
|---|---|
| поле отсутствует или `null` | **не трогать** текущее значение (общая конвенция `UpdateCompanyDto`) |
| `0` | **сбросить к значению по умолчанию — 90**. Ноль никогда не означает «записаться нельзя» |
| 1..365 | новое значение горизонта |
| < 0 или > 365 | **400**, голая строка «Горизонт записи — от 1 до 365 дней»; значение в базе не меняется |

Доступ — тот же, что у остальных полей этого эндпоинта: владелец компании или SuperAdmin,
иначе 403. Ответ при успехе — `200` + обновлённый `CompanyDto` (форма ответа не меняется).

**Где горизонт применяется:** `GET /api/bookings/availability` (§41.2) и `POST /api/bookings`
(§43.1). Больше нигде: слоты одного дня, перенос записи персоналом и ручная запись персоналом
горизонтом **не ограничены**.

**Интерфейс владельца:** поле на вкладке «Настройки» компании, подпись «На сколько дней вперёд
клиент может записаться», подсказка «Пусто или 0 — 90 дней по умолчанию». Пустое поле фронт
отправляет как `0`, а не как пустую строку.

## 42. Тариф (US-63)

### 42.1 `PUT /api/admin/owners/{ownerUserId}/subscription` — ⚠️ три уточнения смысла

Доступ: SuperAdmin. Форма тела прежняя:
```json
{ "planConfigId": "…", "paidUntil": "2026-12-31", "isActive": true, "comment": "оплата за декабрь" }
```

| Поле | Новое правило |
|---|---|
| `isActive` | стало необязательным: **отсутствует или `null` → `true`**. Раньше отсутствие поля молча давало `false` и роняло владельца во Free |
| `paidUntil` | ⚑ **изменено в редакции 2 (ответ Q2): при заданном `planConfigId` поле ОБЯЗАТЕЛЬНО.** Отсутствует или `null` → **400**, голая строка «Укажите дату окончания подписки»; подписка при этом не создаётся и не изменяется, запись в журнал не добавляется. Дата **без времени суток** (`2026-12-31`) означает **конец** этого дня (`23:59:59.999Z`), то есть «оплачено по 31 декабря включительно». Явно переданное время суток сохраняется как есть. *Было в редакции 1: `null` — бессрочно.* |
| `planConfigId` | `null` — снять тариф (Free); в этом случае `paidUntil` **не требуется** и игнорируется. Неизвестный id → 404, неактивный план → 400 (как сейчас) |

Ответ: `204`. Ошибки: 404 «Owner not found» / «Plan not found», 400 «Plan is not active» /
**«Укажите дату окончания подписки»**.

> **Существующие подписки с пустой датой.** На стенде такие строки есть. Они чинятся **миграцией
> данных** (`BackfillSubscriptionPaidUntil`: `PaidUntil = сейчас + 1 год` для всех строк с `NULL`,
> `ARCHITECTURE_CYCLE6.md` §43.5). После выката цикла состояние «подписка без даты» не существует
> ни в базе, ни в контракте, поэтому отдельного признака в §42.2 для него нет.

### 42.2 `GET /api/admin/owners/{ownerUserId}/subscription` — **новый** (диагностика)

Доступ: SuperAdmin. Отвечает на вопрос «тариф назначен — почему не работает», одним запросом.

```json
{
  "ownerUserId": "…",
  "ownerName": "Иван Иванов",
  "planConfigId": "…",
  "planName": "Стандарт",
  "paidUntil": "2026-12-31T23:59:59.999Z",
  "isActive": true,
  "planIsActive": true,
  "status": "Active",
  "statusText": "Тариф «Стандарт» действует до 31 декабря 2026",
  "effective": {
    "allowOnlineBooking": true, "allowMailing": false, "allowAnalytics": true,
    "allowPublicListing": true, "allowOnlinePayment": false,
    "maxEmployees": 5, "maxCompanies": 2
  },
  "companies": [
    { "companyId": "…", "name": "Салон на Ленина",
      "allowSelfBooking": true, "onlineBookingEnabled": true, "blockingReason": "None" }
  ]
}
```

- `status` ∈ `NoSubscription | Active | Expired | Deactivated | PlanRetired`;
  `statusText` — **русский текст от сервера** (включая «Истёк 3 октября 2026» для `Expired`).
- `blockingReason` ∈ `None | NoSubscription | SubscriptionInactive | SubscriptionExpired |
  PlanRetired | PlanDisallowsOnlineBooking | SelfBookingDisabledByOwner` — почему именно эта
  компания не принимает онлайн-записи. Различает «тариф не даёт» (402 при записи) и «владелец сам
  выключил» (403 при записи) — это разные проблемы с одинаковым симптомом.
- `paidUntil` в ответе `null` только при `status == NoSubscription` (подписки нет вовсе).
- 404 — владельца нет.

### 42.3 Тексты отказов при записи

Формы ответов `POST /api/bookings` не меняются; меняется то, что видит человек:

| Код | Когда | Текст пользователю |
|---|---|---|
| 402 | тариф компании не разрешает онлайн-запись | «Онлайн-запись недоступна: тариф компании её не включает» |
| 403 | `Company.AllowSelfBooking == false` | «Салон сейчас не принимает онлайн-записи» |

### 42.4 Что суперадмин обязан видеть в форме

⚑ **Изменено в редакции 2.** Было: подпись под полем даты «Пусто — бессрочно, пока подписка
активна». Стало:

- поле «Оплачено до» — **обязательное**, когда выбран любой план: `required`, кнопка «Сохранить»
  заблокирована при пустом значении, текст ошибки под полем «Укажите дату окончания подписки»;
- при выборе «Free (без тарифа)» поле даты **скрывается** — снятие тарифа даты не требует;
- панель фактического состояния из §42.2 рядом с формой (текст — с сервера);
- предупреждение при выборе плана с `allowOnlineBooking == false`: «В этом тарифе онлайн-запись
  выключена — клиенты не смогут записаться сами».

Серверный 400 показывается пользователю как есть: `frontend/src/utils/planError.ts` при 400 уже
отдаёт тело ответа сервера, правок в маппере не требуется.

## 43. Несколько услуг за визит (US-67)

Режется первой. Пока история не сделана, `serviceIds` просто не присылается, и всё работает как
сегодня — ни один другой раздел контракта от этого не меняется.

### 43.1 `POST /api/bookings` — одно новое поле и одна новая граница

```jsonc
{
  "companyId": "…",
  "serviceId": "…",                    // обязателен, = serviceIds[0]
  "serviceIds": ["…", "…"],            // необязателен; 1..5, без повторов
  "masterId": "…",
  "date": "2026-10-05",
  "startTime": "10:00:00",
  "notes": null,
  "guestName": null, "guestPhone": null, "guestEmail": null,
  "captchaToken": null
}
```

Правила (нарушение → 400 с голой строкой):
`serviceIds` длиной 1..5; без повторов; все услуги принадлежат `companyId` и активны;
`serviceId == serviceIds[0]`; **мастер умеет все** выбранные услуги. Всё остальное — восемь
существующих гейтов (`AllowSelfBooking`, капча, тариф, предоплата, конфликт слота под advisory-lock,
снимки цены и комиссии) — **не меняется**.

⚑ **Новое в редакции 2 (ответ Q5): горизонт записи.** Для **клиента и гостя** дата визита обязана
укладываться в `today + Company.bookingHorizonDays` (§41.4); нарушение → **400**, голая строка
«Записаться можно не дальше чем на N дней вперёд». Для **персонала** (ручная запись сотрудником)
граница **не применяется** — салон может записать клиента на любую дату. Код именно 400, а не 409:
409 на этом эндпоинте означает «слот занят / время в прошлом», и путать эти случаи нельзя.

⚑ **Новое в редакции 2 (ответ Q4): `guestPhone`** проходит страновую проверку (§44): не-российский
номер → **400** «Введите номер телефона в формате +7 (900) 000-00-00». Проверка одна и та же для
гостевой самозаписи и для ручной записи гостя персоналом — обе идут через этот эндпоинт.

Длительность визита = сумма; цена визита = сумма цен на момент записи; последующее изменение прайса
уже созданный визит не переписывает.

### 43.2 `BookingDto` — два новых поля, старые сохраняют смысл

```jsonc
{
  /* …все существующие поля… */
  "serviceId": "…",           // первая услуга визита — как и раньше
  "serviceName": "Стрижка",   // её название — как и раньше
  "price": 4500,              // ИТОГ визита (сумма услуг) — как и раньше для одной услуги
  "totalDurationMinutes": 90, // новое
  "services": [               // новое; всегда непустой, даже у записей, созданных до цикла
    { "serviceId": "…", "name": "Стрижка",    "durationMinutes": 60, "price": 2000 },
    { "serviceId": "…", "name": "Окрашивание","durationMinutes": 30, "price": 2500 }
  ]
}
```

Гарантии: `Σ services[].price == price`, `Σ services[].durationMinutes == totalDurationMinutes`,
`services[0].serviceId == serviceId`. Записи, созданные до цикла, отдают массив из одного элемента —
клиент не обязан различать «до» и «после».

### 43.3 Где это видно

Визит показывается **одной строкой** со списком услуг, суммарной длительностью и ценой: у клиента,
у мастера, у владельца, в админке. Отзыв — по-прежнему один на визит. Тексты уведомлений
подставляют услуги перечислением через запятую (без пустых мест и без `undefined`). Персонал при
ручной записи выбирает несколько услуг так же, как клиент. Виджет `/embed/:slug` **остаётся на одной
услуге за визит** — зафиксировано явно.

### 43.4 Перенос записи

`PATCH /api/bookings/{id}/reschedule` — форма не меняется (`{ "date", "startTime" }`); сервер берёт
длительность из **суммы услуг визита**, а не из одной услуги. Горизонт записи здесь не проверяется:
эндпоинт доступен только персоналу.

## 44. ⚑ Телефон (US-61): только российский формат — и это правило сервера

> **Раздел переписан в редакции 2.** Было: «API не меняется ни в одной точке, маска — исключительно
> представление». Ответ заказчика по Q4 — **иностранные номера пока нельзя**, и запрет обязан
> действовать на сервере: иначе он обходится любым клиентом API.

### 44.1 Правило

Номер приводится к канонической форме (`PhoneNormalizer.Normalize`: только цифры; `8XXXXXXXXXX` →
`7XXXXXXXXXX`; десятизначный, начинающийся на `9`, → `79XXXXXXXXX`) и обязан после этого выглядеть
как **`7` + 10 цифр**. Всё остальное отвергается.

- В базе по-прежнему лежит **каноническая форма** — формат хранения не меняется.
- Ограничение временное («пока нельзя»), поэтому на сервере оно живёт в одном предикате
  (`PhoneNormalizer.IsRussian`, `ARCHITECTURE_CYCLE6.md` §48.1), а на фронте — в одной функции
  (`utils/phone.ts: isRussianPhone`). Снятие запрета = правка по одному месту на каждой стороне.
- Проверка применяется **только там, где создаётся новая запись с телефоном** (§44.2). Там, где
  телефон — ключ к уже существующим данным, её нет (§44.3): иначе запрет ломал бы работу с
  номерами, зарегистрированными до цикла.

### 44.2 Четыре эндпоинта, у которых появляется новый 400

| Эндпоинт | Поле | Код и тело при не-российском номере |
|---|---|---|
| `POST /api/auth/register` | `phone` | **400**, «Введите номер телефона в формате +7 (900) 000-00-00» (раньше: «Phone number must contain 10 to 15 digits.» только при длине вне 10–15) |
| `POST /api/profile/change-phone` | `newPhone` | то же |
| `POST /api/companies/{id}/members` (добавление сотрудника) | `phone` | то же |
| `POST /api/bookings` | `guestPhone` | то же — и для гостевой самозаписи, и для ручной записи гостя персоналом |

Форма запросов и успешных ответов у всех четырёх **не меняется** — добавляется только новая
причина 400. В машиночитаемой схеме подробно описан `POST /api/auth/register` (он анонимный, и
готовый инструмент может его проверить); у остальных трёх форма не менялась, поэтому они описаны
здесь словами.

### 44.3 Где проверки намеренно НЕТ

| Эндпоинт / место | Почему |
|---|---|
| `POST /api/auth/login` | вход обязан пускать аккаунты, зарегистрированные до цикла (§44.4); плюс валидация на логине подсказывала бы перебирающему, что номер «выглядит правильно» |
| `POST /api/masters/clients/notes` (`guestPhone`) | это **не** создание гостя, а заметка о клиенте: телефон здесь ключ, по которому заметка привязывается к уже существующей истории визитов. Новый иностранный номер сюда попасть не может — его отсекает `POST /api/bookings` |
| Поиск по телефону в админке и в базе клиентов мастера | ищут по обрывку номера и по номерам старого формата — запрет сломал бы работу с существующими данными |
| Сид суперадмина (`SuperAdmin:Phone`) | инфраструктурное значение; неудачная проверка уронила бы старт приложения |
| Определение номера канала GREEN-API | это номер салона, полученный от внешнего сервиса, а не пользовательский ввод |

### 44.4 Существующие не-российские номера продолжают работать

На стенде такие аккаунты возможны (прежние правила допускали 10–15 цифр). Контракт гарантирует:

| Сценарий | Поведение после цикла |
|---|---|
| вход таким номером | **200**, как раньше |
| показ номера в любом интерфейсе | как раньше (`formatPhone` отдаёт `+<цифры>` для не-`7XXXXXXXXXX`) |
| поиск по такому номеру, заметка о таком госте | работает |
| его записи, отзывы, уведомления | работают |
| смена номера на другой иностранный | **400** |
| регистрация нового иностранного номера | **400** |

Миграции, чистки и блокировки таких данных цикл **не делает**.

### 44.5 Фронтовая часть

- Маска ввода — жёсткая: поле показывает `+7 (___) ___-__-__`, ведущие `8`/`7`/`+7` сводятся к `+7`,
  другой код страны не принимается; при вставке чужого номера под полем появляется «Пока принимаем
  только российские номера, в формате +7 (900) 000-00-00».
- Отправлять на сервер по-прежнему можно как канон, так и человеческий формат — сервер нормализует.
- Единственная функция форматирования на фронте — `frontend/src/utils/phone.ts` (дополняется,
  не дублируется). **Поля поиска и поле телефона в заметке о клиенте маской не ограничиваются** —
  они работают с уже существующими данными (§44.3).
- В логи телефон не попадает в новых местах — маскирование остаётся обязательным.

## 45. TS-типы, которые фронтенд обязан обновить

Типы копируются вручную (`frontend/src/types/index.ts`) — генерации из OpenAPI в этом цикле нет,
поэтому список явный:

```ts
export type DayAvailabilityStatus = 'Available' | 'FullyBooked' | 'DayOff'

export interface DayAvailability {
  date: string
  status: DayAvailabilityStatus
  lastFreeSlotStart: string | null
}

export interface AvailabilityResponse {
  from: string
  to: string
  totalDurationMinutes: number
  stepMinutes: number
  horizonDays: number        // редакция 2 (Q5)
  horizonLastDate: string    // редакция 2 (Q5)
  days: DayAvailability[]
}

export interface BookingServiceLine {
  serviceId: string
  name: string
  durationMinutes: number
  price: number
}
// Booking       += services: BookingServiceLine[]; totalDurationMinutes: number
// Member        += providesServices: boolean
// Company       += bookingHorizonDays: number                 // редакция 2 (Q5)
// UpdateCompany += bookingHorizonDays?: number | null         // редакция 2 (Q5); 0 = сбросить к 90

export type SubscriptionStatus =
  | 'NoSubscription' | 'Active' | 'Expired' | 'Deactivated' | 'PlanRetired'
export type PlanNotAppliedReason =
  | 'None' | 'NoSubscription' | 'SubscriptionInactive' | 'SubscriptionExpired'
```

Расхождение с сервером ловится инструментом, а не глазами:
`npx openapi-typescript openapi-cycle6.yaml -o /tmp/api-cycle6.d.ts` + `npx tsc --noEmit`
(`ARCHITECTURE_CYCLE6.md` §53.2).
