## 1. Контекст: кто пользователь и какую проблему решает цикл

Продукт (SaaS онлайн-записи) уже работает: публичный каталог, страница компании, запись гостем и
клиентом, кабинеты мастера/владельца, админка, тарифы. Этот цикл **не добавляет пользовательской
функциональности** (за исключением п. Q3), а снимает накопившийся долг.

| Роль | Проблема, которую закрывает этот цикл |
|---|---|
| **Разработчик/архитектор команды** | В solution лежит проект-пустышка и две неиспользуемые страницы на 379 строк, которые выглядят рабочими; единственная проверка изменений — 230 функциональных тестов, требующих живой PostgreSQL и минуты времени, и `tsc` для фронта. Быстрой обратной связи нет |
| **QA** | Нет ни одного теста фронта; поведение сложных модалок и мапперов ошибок проверяется руками |
| **Владелец компании** | Расписание его мастеров может прочитать любой залогиненный пользователь; мастер технически может изменить прайс компании |
| **Клиент** | В «Моих визитах» не видит цены визита и не может вернуться к компании; вкладка «Предстоящие» показывает всё подряд |
| **Суперадмин** | «Удалённый» тариф продолжает работать у подписчиков — мягкое удаление не даёт заявленного эффекта |

**MVP цикла** = четыре направления из запроса пользователя: мёртвый код, юнит-тесты, приоритетные
узкие места, роль `Master` в услугах. Всё остальное из §5/§9 CURRENT_STATE — осознанно отложено (§7).

## 4. E2/E3 — Юнит-тесты

### 4.1 Зачем (проблема)
Сейчас единственная автоматическая проверка бэкенда — 230 функциональных тестов, которым нужна живая
PostgreSQL и ~1 минута; фронтенд не покрыт ничем, кроме `tsc`. Ошибка в чистой логике (сетка слотов,
разрешение тарифа, маппер ошибок) обнаруживается либо через HTTP-тест, либо руками.

### US-02
**Как разработчик, я хочу запускать быстрые юнит-тесты без базы данных, чтобы получать обратную связь
по чистой логике за секунды, а не за минуту.**

**Ограничения (не выбор технологии — это зона архитектора, здесь требования):**
- Юнит-тесты бэкенда должны выполняться **на машине без запущенной PostgreSQL** и без
  `WebApplicationFactory`. Отдельный тестовый проект или отдельная коллекция — на усмотрение архитектора,
  но команда запуска должна быть одна и документированная.
- Тестовый стек бэкенда должен совпадать с уже используемым в `ServiceBooking.Tests` (xUnit +
  FluentAssertions, см. CURRENT_STATE §7) — новых фреймворков не заводим.
- Фронтенд: раннер должен работать с существующей конфигурацией Vite/TS (`frontend/tsconfig.json`,
  `strict`, `noUnusedLocals`) **без второго сборочного конфига** и запускаться как `npm test`
  (и `npm run test:run` для однократного прогона в DoD). *Предположение: это Vitest + Testing Library +
  jsdom как единственный вариант, не требующий отдельного пайплайна (низкий риск — заменяемо).*
  Финальный выбор — за архитектором.
- **Юнит-тесты не заменяют существующие функциональные.** `ServiceBooking.Tests` остаётся как есть.

### 5.1 `GET /api/workinghours` без проверки принадлежности (CURRENT_STATE §5.3.6, §9 P1-3)

#### US-04
**Как владелец компании, я хочу, чтобы расписание моих мастеров не мог прочитать посторонний
залогиненный пользователь, чтобы график работы сотрудников не утекал конкурентам.**

**Критерии приёмки:**
1. `GET /api/workinghours?masterId=X&companyId=Y` возвращает 403, если вызывающий не является:
   мастером `X`, владельцем компании `Y` (`CompanyMember.Role == CompanyOwner`) или `SuperAdmin`
   (то есть переиспользуется существующий предикат `CanManage`, `WorkingHoursController.cs:98`).
2. Мастер получает 200 для **своего** `masterId` — это сценарий вкладки «Расписание» в кабинете:
   `frontend/src/pages/CabinetPage.tsx:146` передаёт `selfMasterId = user?.id` для не-владельцев.
3. Владелец получает 200 для **любого мастера своей компании** — сценарий
   `frontend/src/pages/owner/ScheduleTab.tsx` (владелец листает мастеров).
4. Анонимный запрос — 401 (как сейчас).
5. Публичная запись **не сломана**: гость не вызывает этот эндпоинт, слоты приходят из
   `GET /api/bookings/slots` (публичный). Регрессия проверяется существующими BK-тестами.
6. Новые тесты `WH-011..WH-014` (посторонний → 403; чужой мастер той же компании → 403; свой → 200;
   владелец чужого мастера → 200) + запись в `TEST_CATALOG.md`.

### 5.5 E5 — Роль `Master` в услугах (§5.3.4, §9 P1-2) — **Q1 решён: изменение услуг только у владельца**

**Факт (подтверждён чтением):** `ServiceBooking.API/Controllers/ServicesController.cs:82-92` —
`CanManageCompany` пропускает `cm.Role == UserRole.CompanyOwner || cm.Role == UserRole.Master`.
Этот предикат используется в `Create` (строка 31), `Update` (строка 56) и `Delete` (строка 75).
Во всех остальных контроллерах аналогичная проверка ограничена `CompanyOwner` + `SuperAdmin`:

(`CompaniesController.cs:105`).

#### Разбор вариантов

| Вариант | Что даёт | Против |
|---|---|---|
| **A. Полный запрет мастеру на запись (рекомендуем)** | Услуга — это **прайс компании**: `Service.Price` попадает в `Booking.Price` снимком (`BookingsController.cs:119`), а `Booking.Price` — основа отчёта по мастерам и его комиссии (`ReportsController`, CURRENT_STATE §4.9). Мастер, меняющий цену услуги, меняет собственную выручку и выручку компании. Плюс: единая модель прав со всеми остальными контроллерами | Отбирает существующую техническую возможность (см. Q1) |
| **B. Чтение да, изменение нет** | Формально это и есть вариант A: `GET /api/services` (`ServicesController.cs:16-25`) **уже анонимный**, роль на него не влияет — мастеру ничего дополнительно разрешать не нужно | Как отдельный вариант не существует — сводится к A |
| **C. Мастер правит только «свои» услуги (по `MasterService`)** | Выглядит гибко: мастер уточняет длительность своей процедуры | Ломается о модель данных: `Service` принадлежит **компании**, а `MasterService` — это связка «умеет» (`ServiceBooking.Core/Entities/MasterService.cs`). Одну и ту же услугу могут выполнять несколько мастеров — правка одним меняет цену и длительность **для всех**, включая публичную витрину. Плюс потребуется новая ветка прав, которой нет ни в одном контроллере, и новый UI, которого нет |

**Рекомендация: вариант A.** Обоснование: (1) корректность денег — цена услуги влияет на выручку и
комиссию; (2) консистентность — это единственное место в кодовой базе с расширенной трактовкой
`CanManageCompany`, и CURRENT_STATE прямо называет это скорее непреднамеренным; (3) стоимость правки —
одна строка предиката.

**Влияние на UI и риск для существующих пользователей — низкий:**
- CRUD услуг живёт только в `ServicesTab` внутри `frontend/src/pages/owner/CompanyManagePage.tsx:25-65`;
- эта страница открывается роутом `/owner/company/:id`, защищённым
  `ProtectedRoute roles={['CompanyOwner','SuperAdmin']}` (`frontend/src/App.tsx:64-68`);
- ссылка на неё есть только в списке **собственных** компаний (`CabinetPage.tsx:79`,
  данные из `companiesApi.getMy`);
- в кабинете мастера вкладки «Услуги» нет вовсе (`CabinetPage.tsx` — расписание, клиенты, визиты).

То есть **через интерфейс мастер сегодня не может изменить услугу**, и запрет не ломает ни одного
UI-сценария. Остаточный риск — прямые вызовы API (маловероятно, но недоказуемо со стороны кода): его
закрывает подтверждение Q1 у заказчика.

### 5.9 E7 — CI на GitHub Actions (решение Q5)

#### US-11
**Как владелец репозитория, я хочу, чтобы при каждом push и pull request прогонялись сборка и все
тесты, чтобы сломанный код не доезжал до `master` незамеченным.**

**Критерии приёмки:**
1. В `.github/workflows/` есть workflow, срабатывающий на `push` в `master` и на `pull_request`.
2. Джоб бэкенда: `dotnet build ServiceBooking.sln` (0 ошибок), затем юнит-тесты (E2) и

3. Функциональные тесты требуют реальной PostgreSQL, а строка подключения захардкожена с **пустым

   `postgres:16` с `POSTGRES_HOST_AUTH_METHOD=trust`, **либо** строка подключения выносится в
   переменную окружения с сохранением текущего значения по умолчанию. Второй вариант предпочтителен,
   но не должен ломать локальный запуск разработчика.
4. Джоб фронтенда: `npm ci`, `npx tsc --noEmit`, `npm run test:run` (E3), `npm run build`.
5. Workflow **красный**, если падает хоть один шаг; проверяется намеренно сломанным тестом в черновом PR.
6. Время полного прогона — не больше 10 минут (ориентир: функциональный набор ~1 мин локально).
7. Секреты в workflow не хардкодятся; тестовая БД — эфемерный контейнер, к боевой базе CI не ходит.
8. В `README.md` описано, что проверяет CI и как воспроизвести те же шаги локально.

**Вне скоупа US-11:** автодеплой из CI, публикация образов в registry, branch protection rules
(включаются в настройках GitHub руками, кодом не описываются).

## 6. Нефункциональные требования

1. **Производительность тестов.** Юнит-набор бэкенда — < 10 с, фронтенда — < 30 с, без БД и без сети.
   Функциональный набор не должен вырасти дольше **1,5 мин** (сейчас ~1 мин).
2. **Отсутствие регрессий.** `dotnet test ServiceBooking.Tests` — 0 упавших. Число тестов не меньше 230
   (ожидаемо больше: новые WH-, BK-, ADM-, SVC-кейсы). Единственные тесты, меняющие смысл, —
   SVC-003 и SVC-007 (§5.5).
3. **Сборка.** `dotnet build ServiceBooking.sln` — 0 ошибок, 0 предупреждений (цель E1).
   `npm run build` во `frontend/` проходит, `npx tsc --noEmit` чист.
4. **Безопасность.** Изменения только сужают права, не расширяют. Ни один эндпоинт по итогам цикла не
   должен отдавать данные компании тому, кто не является её участником, владельцем или суперадмином.
   Сообщения об ошибках не раскрывают существование чужих объектов сверх того, что уже раскрыто
   (например, 403 вместо 404 там, где так уже сделано).
5. **Обратная совместимость API.** Поля из DTO **не удаляются** и не добавляются: контракт
   `BookingDto` в этом цикле не меняется (Q3). Коды ответов меняются только там, где это явный предмет истории
   (403 в услугах, 404 в бронировании, 409/400 в планах). Все изменения кодов перечисляются в PR
   и в `API_DOCUMENTATION.md`.
6. **Совместимость с деплоем.** Удаление Blazor-проекта не должно влиять на `ServiceBooking.API/Dockerfile`,
   `docker-compose.yml`, `docker-compose.prod.yml`, `deploy/*`. Проверяется сборкой образа.
7. **Конвенции.** Новый код следует §6 CURRENT_STATE: primary constructors, `record`-DTO, ручной маппинг,
   402 для тарифных гейтов, приватные предикаты прав, комментарии «почему» на английском; фронт —
   именованные экспорты, слой `src/api/*`, react-query, Tailwind-утилиты. Новых библиотек, кроме
   тестового раннера фронта, не добавляем.
8. **Доступность.** Изменений в разметке в этом цикле практически нет: US-06 только удаляет
   неисполняемые ветки. Если правка всё же затронет видимую разметку, действует минимум —
   интерактивные элементы `<button>`/`Button`, а не `div` с `onClick`.
9. **Документация как часть работы.** `TEST_CATALOG.md` и `API_DOCUMENTATION.md` обновляются в тех же
   PR, что и код (проект уже держит их в актуальном состоянии — коммит `263c661`).

## 10. Открытые вопросы архитектору

Не решения, а точки, которые должен закрыть architect до кодирования:

1. **Форма юнит-тестируемости.** Как сделать `SlotService`/`SubscriptionResolver` тестируемыми без БД:
   выделять чистые функции, вводить абстракцию над данными или использовать in-memory провайдер EF.
   Ограничение из спеки: юнит-тест не должен требовать запущенной PostgreSQL, внешнее поведение
   API не меняется.
2. **Расположение юнит-тестов бэкенда:** отдельный проект в solution или отдельная коллекция в
   `ServiceBooking.Tests` (там сейчас `[CollectionBehavior(DisableTestParallelization = true)]` и
   общий `TestDatabaseFixture`). Требование — одна документированная команда запуска.
3. **Механика глобальной обработки исключений** и точный контракт тела ошибки для каждого кода —
   с учётом R3 и того, что фронтенд разбирает `response.data` как строку.
4. **Где живёт проверка «компания существует»** в `POST /api/bookings`, чтобы 404 не разошёлся с
   тарифным гейтом 402 по порядку (US-05, критерий 2).
5. **Форма правила «предстоящие»** для `GET /api/bookings/client?status=upcoming`: фильтр на стороне
   БД по дате+времени с учётом отсутствия таймзон (§7) — какое «сейчас» считаем правильным.
6. **Единый предикат прав.** В цикле правки точечные, но `ServicesController.CanManageCompany` и
   `WorkingHoursController.CanManage` затрагиваются оба — стоит ли уже сейчас вынести общий хелпер
   или это отдельная задача (§9 P2-11).
7. **Порог покрытия как gate.** Нужно ли настраивать провал сборки при падении покрытия ниже 80 % по
   перечисленным файлам, если CI в цикл не входит (Q5).
