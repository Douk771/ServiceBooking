## §270. Что цикл 16 делает с API — в одной таблице

Цикл разбирает долг. Поэтому **новых эндпоинтов ноль**, и ровно один маршрут меняет тело ответа.

| Маршрут | Что с ним в цикле 16 | Ломающее? |
|---|---|---|

## §271. Конвенции, действующие без изменений

1. JSON — `camelCase`; enum — строками (PascalCase, имена членов C#); `DateTime` — ISO-8601 UTC;
   `DateOnly` — `YYYY-MM-DD`; `TimeOnly` — `HH:mm:ss`.
2. Тела осознанных ошибок **400 / 409 / 429** — **голая строка** (`text/plain`) по-русски.
3. **401 и 403 — пустое тело.** `ProblemDetails` не используется (кроме необработанных 500).
4. 🔴 **404 и 409 без явного тела — ПУСТОЕ тело, и это правило всего API, всех маршрутов всех циклов**
   (`Program.cs:170`, `SuppressMapClientErrors = true`). Это AV8. Внешняя документация (TD-12) обязана
   сказать это как общее правило, а не как особенность цикла 13.
5. **451** — «требуется принять новую редакцию документов» (`LegalConsentFilter`).
   `GET /api/profile/export` — в allow-list гейта и **остаётся** в нём.
6. Единственное намеренное исключение из «4xx — строка»: массив ошибок Identity (`application/json`) у
   `POST /api/auth/register`.
7. Именованные политики лимитов не меняются: `data-export` 3/сутки, `phone-change` 5/час,
   `subject-request`, `uploads`, `auth-register` 5/час на IP.

## §272. 🔴 Правило, которое контракт обязан удержать: ответ не должен быть оракулом

Гейт TD-03 **не имеет права** сообщать, существуют ли на номере гостевые данные.

| Запрещено | Разрешено |
|---|---|
| `409 «На этом номере есть записи, подтвердите номер»` в выгрузке | секция `guestDataGate.applied = true` |
| `guestDataGate.hiddenCount: 7` | отсутствие любых счётчиков скрытого |
| показывать врезку в UI, потому что «данные не нашлись» | показывать врезку, потому что `profile.phoneVerified === false` |
| разные тексты для «данные есть»/«данных нет» | один и тот же текст всегда |

Проверяется тестом: ответы `GET /api/profile/export` для двух неподтверждённых аккаунтов — одного с
гостевыми данными на номере, другого без — совпадают по составу секций и по значению `guestDataGate`
(различаются только собственными данными аккаунта).

Тот же запрет действует на `POST /api/subject-requests`: ответ байт в байт одинаков независимо от того,
известен ли номер системе (§50.1 цикла 5) — «удобных» подсказок не добавлять.

## §273. `GET /api/profile/export` — единственное изменение формы за цикл

**Авторизация:** Bearer. **Лимит:** `data-export`, 3/сутки. **451:** не применяется (allow-list).
**Заголовок:** `Content-Disposition: attachment; filename="servicebooking-export-YYYY-MM-DD.json"`.

### §273.1. Новая секция (аддитивная)

```jsonc
{
  "generatedAtUtc": "2026-09-25T10:00:00Z",
  "profile":  { /* ... без изменений ... */ },
  "consent":  [ /* ... */ ],
  "memberships": [ /* ... */ ],
  "bookings": [ /* ... */ ],
  "reviews":  [ /* ... */ ],
  "notesAboutMe": [ /* ... */ ],
  "photosAboutMe": [ /* ... */ ],
  "operatorsNote": "Оператором заметок, фотографий ...",
  "operators": [ /* ... */ ],
  "notifications": [ /* ... */ ],
  "optOut": { /* ... */ },
  "healthNotes": [ /* ... */ ],
  "phoneVerification": { "phoneVerified": false, "method": null, "verifiedAtUtc": null },

  // ── НОВОЕ В ЦИКЛЕ 16 ────────────────────────────────────────────────────────
  "guestDataGate": {
    "applied": true,
    "reason": "PhoneNotVerified",
    "explanation": "<текст legal-counsel; до его появления — нейтральный fallback>",
    "subjectRequestPath": "/subject-request"
  }
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `applied` | `boolean` (обязательное) | `true` — ветка сопоставления по телефону не применялась. `false` — выгрузка полная, как до цикла |
| `reason` | `"PhoneNotVerified" \| null` | машиночитаемая причина; `null` при `applied: false`. Перечисление append-only |
| `explanation` | `string \| null` | готовый русский текст **собирает сервер**; фронт формулировок не сочиняет (та же конвенция, что у `PhoneVerificationSessionStatus.message`) |
| `subjectRequestPath` | `string \| null` | путь штатного пути реализации прав — `/subject-request` |

🔴 Полей вида `hiddenCount`, `hasHiddenData`, `guestPhoneMatched` в секции **нет и не должно появиться**
(§272).

### §273.2. Что именно пропадает из выгрузки при `applied: true`

Не отдаются строки, найденные **только по строке телефона**:
`bookings` (гостевые), `notesAboutMe` (гостевые), `photosAboutMe` (гостевые), `healthNotes` (гостевые),
производные от них `operators` и `whatIsStoredByCompany`, `optOut`, а также `phoneVerification`,
привязанное к номеру, которым аккаунт не доказал владения.

Отдаётся всё, что привязано к `ClientId`/`RecipientUserId`: собственные профиль, согласия, членства,
записи, отзывы, уведомления.

### §273.3. Что при `applied: false`

**Поведение дословно прежнее.** Это главный предмет регрессии: весь существующий набор `PROF-`/`PHV-`
на подтверждённом аккаунте обязан остаться зелёным без правок.

### §273.4. Коды ответа

| Код | Тело | Когда |
|---|---|---|
| `200` | JSON-файл выгрузки | всегда при живом аккаунте (в том числе при закрытом гейте — **не 403 и не 409**) |
| `401` | пустое | нет токена |
| `404` | пустое | аккаунт не найден |
| `429` | `text/plain` | превышен `data-export` |

⚠️ Закрытый гейт **не** даёт 4xx. Отдать 403/409 значило бы сказать «на этом номере что-то есть» — §272.

## §274. `POST /api/profile/delete-account`

**POST, не DELETE** (существующая конвенция: нужно тело с текущим паролем).
Тело запроса — без изменений: `{ "currentPassword": "..." }`.

| Код | Тело | Когда |
|---|---|---|
| `204` | пустое | удалено |
| `400` | `text/plain` «Неверный текущий пароль» | пароль не подошёл |
| `401` | пустое | нет токена |
| `404` | пустое | аккаунт не найден |
| `409` | `text/plain` «За вами числится компания…» | гейт владельца компании (без изменений) |

**Что меняется (поведение, не форма).** При неподтверждённом номере **ни одна** сущность, сопоставленная
только по `GuestPhone`, не попадает ни в `RemoveRange`, ни в анонимизацию. Собственные данные аккаунта
удаляются как раньше: заметки и заметки о здоровье по `ClientId`, свои push-подписки, свои записи и
уведомления, отзывы, членства, надгробие аккаунта.

🔴 **Ответ по-прежнему `204` и не сообщает, что что-то осталось нетронутым** (§272). Пользователь узнаёт о
правиле **до** нажатия кнопки — из врезки на экране удаления (§276), а не из ответа сервера.

**Цикл 16 дополнительно (TD-05):** в той же транзакции имя клиента в журнале изменений записи заменяется
надгробием — см. §275.

## §275. `GET /api/bookings/{id}/history` — надгробие вместо имени удалённого клиента

**Форма ответа не меняется.** Меняются значения.

```jsonc
{
  "bookingId": "…",
  "precedesJournal": false,
  "events": [
    {
      "id": "…",
      "kind": "Rescheduled",
      "occurredAtUtc": "2026-09-20T09:15:00Z",
      "actor": {
        "kind": "Client",
        "name": "Удалённый пользователь",   // было: реальное имя клиента
        "role": "Client",
        "label": "Удалённый пользователь"   // собирает сервер
      },
      "reschedule": { "previousDate": "…", "previousStartTime": "…", "newDate": "…", "newStartTime": "…" },
      "cancellationReason": null
    }
  ]
}
```

Правила:
- надгробие — **та же строка**, что уже используется продуктом при удалении аккаунта:
  `"Удалённый пользователь"`;
- применяется к `actor.kind ∈ { Client, Guest }`, когда за актёром стоит удалённый аккаунт;
- 🔴 **ФИО сотрудников (`Staff`, `SuperAdmin`, `System`) не затрагиваются** — другой субъект и другой срок
  хранения (D1/TD-18);
- `kind`, `occurredAtUtc`, `role`, состав событий — без изменений, журнал остаётся append-only.

Доступ не меняется: персонал компании (`Master`/`CompanyOwner`) или `SuperAdmin`; всем остальным,
**включая клиента этой записи**, — `404` с пустым телом (существующее решение, не «баг»).

## §276. Что должен показать фронтенд (контракт UI, не HTTP)

### §276.1. Источник признака

**Единственный** источник условия показа врезки — `profile.phoneVerified === false`
(`GET /api/profile`, существующее поле цикла 14). Никогда — «выгрузка вернулась пустой» (§272).

### §276.2. Где

| Экран | Что показать |
|---|---|
| `/profile` рядом с кнопкой «Скачать мои данные» | врезка `GuestDataGateNotice`: почему часть данных не попадёт в файл и что делать |
| `/profile/delete-account` (`DeleteAccountPage`) | та же врезка **до** подтверждения удаления: часть данных не будет удалена этим действием |
| после успешной выгрузки, если `guestDataGate.applied === true` | тот же текст, взятый из `explanation` ответа |

### §276.3. Текст

- Берётся из `uiTexts` правового комплекта (`legal.json`, ключ `guestDataGateNotice`, хук `useLegalText`)
  либо из поля `explanation` ответа выгрузки. **Фронтенд формулировок не сочиняет.**
- До появления текста `legal-counsel` работает нейтральный fallback сервера — экран не должен быть пустым.
- Обязательно содержит: (а) почему; (б) что сделать, чтобы получить доступ (подтвердить номер);
  (в) что делать, если MAX нет — ссылку на `/subject-request` и срок ответа.

### §276.4. Доступность (НФТ §7.7)

Врезка — обычный текстовый блок, связанный с кнопкой выгрузки/удаления через `aria-describedby`;
читается скринридером так же, как существующие сообщения об ошибках, и называет следующий шаг.
Новых экранов цикл не добавляет.

## §277. Компенсирующий путь: `POST /api/subject-requests` (существующий, не меняется)

Анонимный. Описан здесь потому, что для пользователя без MAX он становится **единственным** путём
реализации прав, а значит его форма — часть контракта цикла 16.

**Запрос**
```jsonc
{
  "kind": "Access | Deletion | Rectification | …",   // SubjectRequestKind, строкой
  "phone": "+7 (900) 000-00-01",
  "contactValue": "…",        // ≤ 200 символов, обязателен
  "message": "…",             // ≤ 4000 символов, обязателен
  "captchaToken": "…"         // обязателен, когда капча включена
}
```

**Ответ `202 Accepted`**
```json
{ "reference": "SR-K7M2QX", "responseDueByWorkingDays": 10 }
```
(поля и формат `reference` — как в реальном коде цикла 5: `SubjectRequestAcceptedDto` и `SubjectRequestReference.Generate()`, никогда не менявшемся в цикле 16; здесь была расхождение — контракт цикла 16 транскрибировал их неверно.)

| Код | Тело | Когда |
|---|---|---|
| `202` | JSON выше | принято |
| `400` | `text/plain` | тип/телефон/контакт/текст/капча |
| `429` | `text/plain` | политика `subject-request` |
| `503` | `text/plain` | не удалось durable-записать обращение |

🔴 **Ответ одинаков независимо от того, известен ли номер системе.** Ни один ответ, ни одна длина, ни
один заголовок не должны зависеть от наличия аккаунта или прошлых обращений.

## §278. `GET /api/admin/scheduled-tasks` — форма прежняя, значения честнее

Только `SuperAdmin`. Форма `ScheduledTaskStatusDto` **не меняется**:

```jsonc
[
  {
    "name": "data-retention",
    "enabled": true,
    "periodMinutes": 1440,
    "lastStartedAtUtc": "2026-09-25T03:00:00Z",
    "lastFinishedAtUtc": "2026-09-25T03:00:07Z",
    "lastDurationMs": 7123,
    "lastSucceeded": false,
    "lastSummary": "retention[dry] ok=13 skipped=2 failed=1 | … | failed: booking-event",
    "lastError": "InvalidOperationException: …",
    "isOverdue": false
  }
]
```

Что меняется по существу (TD-04):
- падение **одного** правила больше не отменяет остальные;
- `lastSummary` **сохраняется и при ошибке** (сегодня затирается в `null` — именно поэтому дефект
  N9-6 было не видно);
- сводка явно перечисляет три ведра: **ok / skipped (не настроено) / failed (с именем правила)**;
- `lastSucceeded = false` + непустой `lastError`, когда хотя бы одно правило упало — «тихого успеха»
  больше нет.

`RETENTION_DRY_RUN=true` по умолчанию не меняется. В сводке — только числа и имена правил, **никаких ПДн**.

## §279. `POST /api/companies/{id}/mail` — валидация входа (TD-09)

Маршрут: `POST /api/companies/{id:guid}/mail`, роль — владелец компании или SuperAdmin.

**Было:** `record SendMailDto(string Subject, string Message)` без единого атрибута — пустая или
гигантская строка доходила до хранилища.

**Стало:** `subject` и `message` обязательны и ограничены по длине; нарушение → `400` **голой строкой**
по-русски (конвенция §271.2; `InvalidModelStateResponseFactory` уже приводит ошибки модели к этой форме —
`ProblemDetails` здесь не появляется).

Успешный ответ не меняется: `200 { "recipientCount": <int>, "message": "Рассылка поставлена в очередь" }`.
`402` при тарифном запрете — без изменений.

⚠️ Само поведение функции «Рассылка» (§9.27: выглядит готовой, но писем не шлёт) цикл 16 **не чинит** —
это продуктовое решение заказчика, вынесенное открытым вопросом.

## §283. Как QA проверяет контракт автоматически

1. **Форма интерфейса:** `schemathesis run contracts/cycle16/openapi.yaml --base-url … --checks all`.
2. **Спека валидна:** `npx @redocly/cli lint --config contracts/redocly.yaml …` (четыре спеки, объём —
   `ARCHITECTURE_CYCLE16.md` §248.3).
3. **Фронт не разошёлся со спеками:** регенерация всех шести `src/types/*.generated.ts` +
   `git diff --exit-code -- src/types` (шаг CI, §248.2).
4. **Проверка «от обратного» обязательна:** намеренно внесённое расхождение делает CI красным; результат
   с номером прогона — в отчёт (§248.4). Без этого шаг считается непроверенным.
5. **Оракул:** тест на совпадение ответов выгрузки для двух неподтверждённых аккаунтов (§272).
6. **Регрессия:** весь существующий набор на **подтверждённом** аккаунте — зелёный без правок (§273.3).
